1.1 三种创建线程的方式

先看最基础的东西。Java 创建线程有三种方式，但真正要理解的是它们的设计差异——为什么官方推荐 Runnable 而不是继承 Thread。

_01_HelloThread.java46 行 · JDK 25 实测通过
package course.ch01;

/**
 * ch01_01 三种创建线程的方式 —— 最小可运行示例
 *
 * 运行：java src/main/java/course/ch01/_01_HelloThread.java
 */
public class _01_HelloThread {

    public static void main(String[] args) throws Exception {
        // 方式一：继承 Thread（不推荐，Java 单继承限制）
        Thread t1 = new Thread("worker-1") {
            @Override
            public void run() {
                System.out.println("[" + Thread.currentThread().getName() + "] 继承 Thread 的方式");
            }
        };

        // 方式二：实现 Runnable（推荐，任务与线程解耦）
        Thread t2 = new Thread(
                () -> System.out.println("[" + Thread.currentThread().getName() + "] 实现 Runnable 的方式"),
                "worker-2");

        // 方式三：Callable + FutureTask（有返回值、可抛异常）
        java.util.concurrent.FutureTask<String> t3 =
                new java.util.concurrent.FutureTask<>(() -> "Callable 的返回值");
        Thread t3Thread = new Thread(t3, "worker-3");

        t1.start();
        t2.start();
        t3Thread.start();

        System.out.println("[" + Thread.currentThread().getName() + "] 拿到：" + t3.get());

        // 对比：直接调用 run() 只是普通方法调用，不会开新线程
        Thread t4 = new Thread(() -> System.out.println(
                "[" + Thread.currentThread().getName() + "] 这是直接在 main 线程里同步执行的"));
        t4.run();          // 注意这里是 run() 不是 start()

        // 常用 API
        System.out.println("当前线程 = " + Thread.currentThread().getName());
        System.out.println("CPU 核心数 = " + Runtime.getRuntime().availableProcessors());
        System.out.println("isDaemon = " + Thread.currentThread().isDaemon());
    }
}

[worker-2] 实现 Runnable 的方式
[main] 拿到：Callable 的返回值

1.2 线程的六种状态与流转

线程状态是理解后续一切并发机制的基础。Java 定义了 6 种状态，下面这个程序会逐个把它们打印出来，比看图和背表格有效得多。

_02_ThreadState.java88 行 · JDK 25 实测通过
package course.ch01;

/**
 * ch01_02 线程的 6 种状态流转（实测）
 *
 * 运行：java src/main/java/course/ch01/_02_ThreadState.java
 */
public class _02_ThreadState {

    public static void main(String[] args) throws Exception {
        // 1) NEW：创建了但没 start
        Thread t = new Thread(() -> {
            try {
                Thread.sleep(300);     // TIMED_WAITING
            } catch (InterruptedException e) {
                Thread.currentThread().interrupt();
            }
        }, "demo");
        System.out.println("1. 刚 new 出来        : " + t.getState());

        // 2) RUNNABLE
        t.start();
        Thread.sleep(50);
        System.out.println("2. start 之后         : " + t.getState());

        // 3) TIMED_WAITING（sleep / wait(超时) / join(超时) / parkNanos）
        Thread.sleep(100);
        System.out.println("3. 在 sleep 中        : " + t.getState());

        // 4) WAITING（wait() / join() / park()）
        Object lock = new Object();
        Thread waiter = new Thread(() -> {
            synchronized (lock) {
                try {
                    lock.wait();          // 释放锁并进入 WAITING
                } catch (InterruptedException e) {
                    Thread.currentThread().interrupt();
                }
            }
        }, "waiter");
        waiter.start();
        Thread.sleep(100);
        System.out.println("4. 在 wait 中         : " + waiter.getState());

        synchronized (lock) {
            lock.notifyAll();             // 唤醒 → BLOCKED / RUNNABLE
        }
        waiter.join();                    // 主线程 WAITING

        System.out.println("5. 阻塞在 sync 上     : " + blockedStateDemo());

        t.join();
        System.out.println("6. 执行完毕           : " + t.getState());
        System.out.println("   已终止线程再 start : ");
        try {
            t.start();                    // 只能 start 一次
        } catch (IllegalThreadStateException e) {
            System.out.println("   → 抛 IllegalThreadStateException：" + e.getClass().getSimpleName());
        }
    }

    /** 构造一个 BLOCKED 状态的线程并返回其状态 */
    private static String blockedStateDemo() throws InterruptedException {
        Object lock = new Object();
        Thread holder = new Thread(() -> {
            synchronized (lock) {
                try {
                    Thread.sleep(500);
                } catch (InterruptedException e) {
                    Thread.currentThread().interrupt();
                }
            }
        });
        holder.start();
        Thread.sleep(50);

        Thread blocked = new Thread(() -> {
            synchronized (lock) { /* 抢不到锁，停在 BLOCKED */ }
        }, "blocked");
        blocked.start();
        Thread.sleep(100);
        String s = blocked.getState().toString();
        blocked.join();
        holder.join();
        return s;
    }
}

3. 在 sleep 中        : TIMED_WAITING

Q面试加分点：BLOCKED 和 WAITING 的区别
很多人答不清这两个。关键差异是「是否释放了锁」和「在等什么」：BLOCKED 是还没拿到锁，在锁的入口队列排队；WAITING 是已经拿到了锁，主动调用 wait() 释放锁后进入条件队列等待通知。
另外注意 sleep() 不释放锁，而 wait() 会释放锁——这也是高频考点。

1.3 亲手复现第一个并发 Bug

现在来看并发编程的本质问题。下面这段代码，不加锁的结果每次运行都不一样，而且一定是「丢数据」。请务必亲手跑一遍。

_03_RaceCondition.java52 行 · JDK 25 实测通过
package course.ch01;

/**
 * ch01_03 第一个并发 Bug：竞态条件（Race Condition）
 *
 * 反复运行，你会看到不同的结果 —— 这就是并发的“不确定性”。
 * 运行：java src/main/java/course/ch01/_03_RaceCondition.java
 */
public class _03_RaceCondition {

    static int unsafeCount = 0;
    static final Object LOCK = new Object();
    static int safeCount = 0;

    public static void main(String[] args) throws Exception {
        int threads = 10;
        int times = 100_000;

        Thread[] ts = new Thread[threads];
        for (int i = 0; i < threads; i++) {
            ts[i] = new Thread(() -> {
                for (int j = 0; j < times; j++) {
                    unsafeCount++;                 // 非原子操作：读-改-写
                    synchronized (LOCK) {
                        safeCount++;               // 加锁后正确
                    }
                }
            });
            ts[i].start();
        }
        for (Thread t : ts) t.join();

        int expected = threads * times;
        System.out.println("期望值      : " + expected);
        System.out.println("非同步结果  : " + unsafeCount + "   丢失 = " + (expected - unsafeCount));
        System.out.println("同步结果    : " + safeCount + "   丢失 = " + (expected - safeCount));

        // 用字节码视角解释：i++ 实际是三条指令
        System.out.println("""

                ------------------- 原因分析 -------------------
                unsafeCount++ 在字节码层面是 3 步：
                  iload  -> 把值从主内存/工作内存读入操作数栈
                  iinc   -> 在栈上 +1
                  istore -> 写回
                两个线程可能都读到 100，各自 +1 后都写回 101 —— 一次自增凭空消失。
                这就是“读-改-写”非原子性导致的丢失更新（Lost Update）。
                -------------------------------------------------
                """);
    }
}
运行输出（实测）
期望值      : 1000000
非同步结果  : 995836   丢失 = 4164
同步结果    : 1000000   丢失 = 0

为什么 count++ 会丢数据？因为它在字节码层面根本不是一步操作：

count++ 的真实执行过程：
  +---------------------------------------------------+
  |  iload  count    <- 1. 从内存把值读到操作数栈      |
  |  iinc   count,1  <- 2. 在栈上把值 +1              |
  |  istore count    <- 3. 把结果写回内存             |
  +---------------------------------------------------+

两个线程同时执行时可能发生：
  时刻 T1  线程A 读到 count = 100
  时刻 T2  线程B 读到 count = 100     <- 读到同一个值！
  时刻 T3  线程A 计算 100+1 = 101，写回
  时刻 T4  线程B 计算 100+1 = 101，写回  <- 覆盖了 A 的结果

结果：两次自增，count 只增加了 1。这就是「丢失更新」(Lost Update)。
!并发的三大问题（贯穿整个教程）
① 原子性：一个或多个操作要么全部执行且不被中断，要么全不执行。count++ 不满足原子性。
② 可见性：一个线程修改了共享变量，其他线程能否立即看到。这是第 2 章 volatile 要解决的问题。
③ 有序性：程序执行的顺序是否与代码顺序一致。编译器和 CPU 为了性能会做重排序，这是第 11 章的主题。
后面每一章，你都可以归类到这三个问题中的某一个。

2.1 先看一个真实的可见性问题

下面这段代码，理论上 main 线程把 stop 改成 true 后，worker 线程应该立刻退出循环。但实际情况是——它可能永远不退出。

_01_VisibilityProblem.java38 行 · JDK 25 实测通过
package course.ch02;

/**
 * ch02_01 可见性问题：没有 volatile 时，线程可能永远读不到别的线程的修改
 *
 * 运行：java src/main/java/course/ch02/_01_VisibilityProblem.java
 *   → 会打印「卡住了」或超时退出（JIT 把 stop 提升为循环不变量）
 */
public class _01_VisibilityProblem {

    static /* volatile */ boolean stop = false;
    static int counter = 0;

    public static void main(String[] args) throws Exception {
        Thread worker = new Thread(() -> {
            while (!stop) {          // 编译器可能优化成 while(true)
                counter++;
            }
            System.out.println("worker 正常退出，counter = " + counter);
        }, "worker");
        worker.start();

        Thread.sleep(1000);
        stop = true;                 // main 线程改了，worker 未必看得到
        System.out.println("main 已把 stop 置为 true");

        worker.join(2000);
        if (worker.isAlive()) {
            System.out.println(">>> 卡住了！worker 至今没看到 stop=true（可见性问题）");
            System.out.println(">>> 把上面 stop 字段的 volatile 打开，再试一次");
            worker.interrupt();
            System.exit(0);
        } else {
            System.out.println(">>> 本次侥幸通过（可能因为 JIT 没做优化 / 打印触发了内存屏障）");
        }
    }
}
运行输出（实测）
main 已把 stop 置为 true
>>> 卡住了！worker 至今没看到 stop=true（可见性问题）
>>> 把上面 stop 字段的 volatile 打开，再试一次

把代码里 static boolean stop 改成 static volatile boolean stop，重新运行，worker 就会立刻退出。这就是 volatile 最直观的价值。

i为什么会有可见性问题？
现代 CPU 为了弥补内存与 CPU 之间的速度差，每个核心都有自己的缓存（L1/L2/L3）。线程 A 修改了变量，可能只是写进了自己的缓存，没有刷到主内存；线程 B 读的又是自己缓存里的旧值。更糟的是，JIT 编译器发现 stop 在循环里从未被本线程修改，会直接把它优化成 while(true)——这叫循环不变量提升。

2.2 volatile 的正确用法与经典误用

很多人以为 volatile 能解决一切并发问题。看下面这个实验：

_02_VolatileWrongVsRight.java46 行 · JDK 25 实测通过
package course.ch02;

/**
 * ch02_02 volatile 正确用法 vs 经典误用
 *
 * 结论一：volatile 保证可见性 + 有序性，但不保证原子性 —— 不能用来做复合运算的计数。
 * 结论二：volatile boolean 做「状态标志位」是最经典、也最正确的用法。
 *
 * 运行：java src/main/java/course/ch02/_02_VolatileWrongVsRight.java
 */
public class _02_VolatileWrongVsRight {

    static volatile int wrongCount = 0;         // 误用：volatile 修饰的计数器
    static volatile boolean shutdown = false;   // 正用：状态标志位

    public static void main(String[] args) throws Exception {
        // ---------- 误用演示 ----------
        Thread[] ts = new Thread[10];
        for (int i = 0; i < ts.length; i++) {
            ts[i] = new Thread(() -> {
                for (int j = 0; j < 100_000; j++) wrongCount++;
            });
            ts[i].start();
        }
        for (Thread t : ts) t.join();
        int expected = 10 * 100_000;
        System.out.println("volatile 计数器：期望 " + expected + "，实际 " + wrongCount
                + "，丢失 " + (expected - wrongCount));
        System.out.println("→ volatile 只能保证『每次都读到最新值』，无法让 ++ 整体原子\n");

        // ---------- 正用演示 ----------
        Thread daemon = new Thread(() -> {
            long n = 0;
            while (!shutdown) {         // 能可靠地看到 main 的修改
                n++;
            }
            System.out.println("优雅停止，共循环 " + n + " 次");
        }, "daemon");
        daemon.start();
        Thread.sleep(200);
        shutdown = true;                // 立即可见
        daemon.join();
        System.out.println("→ volatile boolean 做开关：正确且零成本");
    }
}

注意看：用 volatile 修饰的计数器，丢失了 67 万次自增！而用 volatile 做状态开关却完美工作。原因在于：

场景volatile 是否够用原因
状态标志位（boolean flag）够用只有一个线程写、多个线程读，写操作本身原子
计数器（count++）不够++ 是「读-改-写」三步复合操作
单次赋值（引用替换）够用引用赋值是一条指令，天然原子
check-then-act（先判断后行动）不够判断和行动之间存在竞态窗口
✓volatile 的三个正确使用场景（背下来）
① 状态标志位：一个线程写、多个线程读的开关，例如优雅停机标志。
② 一次性安全发布：配合双重检查锁，防止其他线程看到半初始化对象。
③ 独立观察：定期「发布」观察结果供其他线程读取，例如配置热更新。
除这三种之外，一律优先考虑 Atomic* 类或加锁。

2.3 双重检查锁（DCL）—— volatile 最重要的实战应用

这是并发领域最著名的「看起来没问题但有致命 Bug」的代码。面试出现频率极高，而且大多数候选人都只知道「要加 volatile」，讲不清为什么。

package course.ch02;

/**
 * ch02_03 双重检查锁（DCL）单例的演进史
 *
 * 这是面试高频题，也是「volatile 保证有序性」最经典的实战场景。
 * 运行：java src/main/java/course/ch02/_03_DclSingleton.java
 */
public class _03_DclSingleton {

    // ============ 版本一：有 BUG 的 DCL ============
    static class BrokenDcl {
        private static BrokenDcl instance;      // 缺少 volatile

        private BrokenDcl() {}

        public static BrokenDcl getInstance() {
            if (instance == null) {                     // 第一次检查
                synchronized (BrokenDcl.class) {
                    if (instance == null) {             // 第二次检查
                        instance = new BrokenDcl();     // 问题就在这里！
                    }
                }
            }
            return instance;
        }
    }

    // ============ 版本二：正确的 DCL ============
    static class CorrectDcl {
        private static volatile CorrectDcl instance;   // 关键：volatile

        private CorrectDcl() {}

        public static CorrectDcl getInstance() {
            if (instance == null) {
                synchronized (CorrectDcl.class) {
                    if (instance == null) {
                        instance = new CorrectDcl();
                    }
                }
            }
            return instance;
        }
    }

    // ============ 版本三：静态内部类（推荐，无锁且优雅）============
    static class HolderSingleton {
        private HolderSingleton() {}

        private static class Holder {
            private static final HolderSingleton INSTANCE = new HolderSingleton();
        }

        public static HolderSingleton getInstance() {
            return Holder.INSTANCE;      // 由 JVM 类加载机制保证线程安全
        }
    }

    // ============ 版本四：枚举（《Effective Java》作者推荐，防反射/反序列化）============
    enum EnumSingleton {
        INSTANCE;
        public void doSomething() { System.out.println("枚举单例做业务"); }
    }

    public static void main(String[] args) throws Exception {
        System.out.println("""
            =========== 为什么无 volatile 的 DCL 是错的？===========
            new BrokenDcl() 在字节码层面是 3 步：
              ① memory = allocate();        // 分配内存
              ② ctorInstance(memory);       // 初始化对象（调用构造器）
              ③ instance = memory;          // 把引用指向内存地址
            其中 ② 和 ③ 可能被编译器/CPU 重排序为 ①→③→②。
            此时线程 B 在第一次检查处看到 instance != null（已经指向内存地址），
            就直接 return 了一个『构造器还没执行完的半成品对象』——
            使用它的字段就会读到默认值 0 / null。这叫『逸出』(Escape)。

            加上 volatile 后，②和③之间会插入 StoreStore 内存屏障，
            禁止这种重排序，问题消失。
            ======================================================
            """);

        System.out.println("正确 DCL 单例 = " + CorrectDcl.getInstance());
        System.out.println("静态内部类   = " + HolderSingleton.getInstance());
        EnumSingleton.INSTANCE.doSomething();

        // 并发验证：100 个线程同时拿，必须是同一个对象
        java.util.concurrent.CountDownLatch latch = new java.util.concurrent.CountDownLatch(1);
        java.util.Set<Integer> ids = java.util.concurrent.ConcurrentHashMap.newKeySet();
        Thread[] ts = new Thread[100];
        for (int i = 0; i < ts.length; i++) {
            ts[i] = new Thread(() -> {
                try { latch.await(); } catch (InterruptedException e) { Thread.currentThread().interrupt(); }
                ids.add(System.identityHashCode(CorrectDcl.getInstance()));
            });
            ts[i].start();
        }
        latch.countDown();
        for (Thread t : ts) t.join();
        System.out.println("100 个线程拿到的不同实例数量 = " + ids.size() + "（正确应为 1）");
    }
}

核心问题在于 new BrokenDcl() 这个动作，在字节码层面是三步：

new BrokenDcl() 的三步分解：
  +--------------------------------------------------+
  |  1 memory = allocate()     分配对象内存空间       |
  |  2 ctorInstance(memory)    调用构造器初始化       |
  |  3 instance = memory       把引用指向内存地址     |
  +--------------------------------------------------+

JIT 编译器和 CPU 允许 2 和 3 重排序，变成 1 -> 3 -> 2：

  线程 A                                   线程 B
  --------------------------------------------------------
  instance = new BrokenDcl()
    1 分配内存
    3 instance = memory     <- 引用已非 null，但对象还没初始化！
                                        if (instance == null) 判断为 false

Q面试标准答法（务必背下来）

/**
 * ch03_01 synchronized 的三种用法 + 锁对象到底是谁
 *
 * 运行：java src/main/java/course/ch03/_01_SynchronizedBasics.java

public class _01_SynchronizedBasics {

    private final Object lock = new Object();
    private int count = 0;

    // 1) 修饰实例方法 → 锁是 this（当前实例）
    public synchronized void syncMethod() { count++; }

    // 2) 修饰静态方法 → 锁是 Class 对象（全局唯一）
    public static synchronized void staticSyncMethod() { /* ... */ }

    // 3) 修饰代码块 → 锁是你指定的任意对象
    public void blockSync() {
        synchronized (lock) {
            count++;
        }
    }

    public static void main(String[] args) throws Exception {
        _01_SynchronizedBasics demo = new _01_SynchronizedBasics();
        int threads = 20, times = 50_000;

        CountC1 c1 = new CountC1();
        runParallel(() -> c1.incMethod(), threads, times);
        System.out.println("场景1 锁 this（同一实例）      : " + c1.n + " 期望 " + (threads * times));

        CountC2 c2a = new CountC2(), c2b = new CountC2();
        runParallel(() -> c2a.incMethod(), threads / 2, times);
        runParallel(() -> c2b.incMethod(), threads / 2, times);

        System.out.println("""
            public synchronized void m() { ... }
            等价于
            public void m() { synchronized (this) { ... } }

            public static synchronized void m() { ... }
            等价于
            public void m() { synchronized (Xxx.class) { ... } }
            """);

        // 验证：synchronized 是可重入的
        System.out.println("=========== 可重入性验证 ===========");
        Reentrant demo2 = new Reentrant();
        demo2.outer();

        Thread[] ts = new Thread[threads];
        for (int i = 0; i < threads; i++) {
            ts[i] = new Thread(() -> { for (int j = 0; j < times; j++) r.run(); });
            ts[i].start();
        }
        for (Thread t : ts) t.join();
    }

    static class CountC1 { int n = 0; synchronized void incMethod() { n++; } }
    static class CountC2 { int n = 0; synchronized void incMethod() { n++; } }
    static class CountC3 { static int n = 0; static synchronized void incStatic() { n++; } }

    static class Reentrant {
        synchronized void outer() {
            System.out.println("outer 拿到锁");
            inner();                              // 同一把锁再拿一次，不会死锁
        }
        synchronized void inner() {
            System.out.println("inner 再次拿到同一把锁（重入成功）");
        }
    }

package course.ch03;

import java.util.LinkedList;
import java.util.Queue;
import java.util.concurrent.CountDownLatch;

/**
 * ch03_04 wait / notify / notifyAll —— 手写生产者消费者
 *
 * 三个必须背下来的铁律：
 *   ① wait() 必须在 synchronized 块里调用，否则抛 IllegalMonitorStateException
 *   ② 必须用 while 而不是 if 判断条件（防「虚假唤醒」Spurious Wakeup）
 *   ③ 优先用 notifyAll() 而不是 notify()（notify 可能唤醒错对象导致信号丢失）
 *
 * 运行：java src/main/java/course/ch03/_04_WaitNotify.java
 */
public class _04_WaitNotify {

    static final int CAPACITY = 3;
    static final Queue<Integer> queue = new LinkedList<>();
    static volatile boolean finished = false;

    public static void main(String[] args) throws Exception {
        int producers = 2, consumers = 2, itemsPerProducer = 10;
        CountDownLatch done = new CountDownLatch(producers);
        long start = System.currentTimeMillis();

        for (int i = 0; i < producers; i++) {
            final int pid = i;
            new Thread(() -> {
                for (int j = 0; j < itemsPerProducer; j++) {
                    produce(pid * 100 + j);
                }
                done.countDown();
            }, "producer-" + i).start();
        }

        for (int i = 0; i < consumers; i++) {
            new Thread(() -> {
                while (!finished || !queue.isEmpty()) {
                    Integer v = consume();
                    if (v != null) {
                        // 模拟处理耗时
                        try { Thread.sleep(5); } catch (InterruptedException e) { Thread.currentThread().interrupt(); }
                    }
                }
            }, "consumer-" + i).start();
        }

        done.await();
        finished = true;
        Thread.sleep(500);
        System.out.println("\n全部完成，耗时 " + (System.currentTimeMillis() - start) + " ms");

        // 演示 ①：不在同步块里 wait → 抛异常
        try {
            new Object().wait();
        } catch (IllegalMonitorStateException e) {
            System.out.println("演示① 未持有锁就 wait → " + e.getClass().getSimpleName() + ": " + e.getMessage());
        }
    }

    static void produce(int value) {
        synchronized (queue) {
            while (queue.size() == CAPACITY) {          // 铁律②：用 while
                try {
                    System.out.println(Thread.currentThread().getName() + " 队列满，等待...");
                    queue.wait();
                } catch (InterruptedException e) {
                    Thread.currentThread().interrupt();
                    return;
                }
            }
            queue.offer(value);
            System.out.println(Thread.currentThread().getName() + " 生产 " + value + " 队列=" + queue);
            queue.notifyAll();                          // 铁律③：notifyAll
        }
    }

    static Integer consume() {
        synchronized (queue) {
            while (queue.isEmpty()) {
                if (finished) return null;
                try {
                    queue.wait(100);
                } catch (InterruptedException e) {
                    Thread.currentThread().interrupt();
                    return null;
                }
                if (queue.isEmpty() && finished) return null;
            }
            Integer v = queue.poll();
            queue.notifyAll();
            return v;
        }
    }
}

!wait/notify 的三条铁律
铁律一：wait() 必须在 synchronized 块内调用，否则抛 IllegalMonitorStateException。原理是 wait 需要先释放锁，你没锁可释放自然报错。
铁律二：必须用 while 而不是 if 判断条件。因为存在「虚假唤醒」(Spurious Wakeup)——线程可能在没被通知的情况下自己醒来。用 if 的话醒来后不重新检查条件就继续执行，会导致队列越界等严重错误。
铁律三：优先用 notifyAll() 而非 notify()。notify 只唤醒一个线程，如果唤醒的是「不该醒的那个」（比如生产者唤醒了另一个生产者），信号就丢失了，可能导致所有线程都卡住。

package course.ch04;

import java.util.concurrent.locks.AbstractQueuedSynchronizer;

/**
 * ch04_01 手写一个 AQS 同步器 —— 这是理解 AQS 最快的路径
 *
 * 目标：实现一个「同一时刻最多允许 N 个线程通过」的共享锁（信号量语义）。
 * 通过这个例子你会彻底搞懂：
 *   - state 的语义由子类自己定义
 *   - tryAcquireShared / tryReleaseShared 的返回值含义
 *   - 为什么 AQS 把「排队」这件事帮你做好了
 *
 * 运行：java src/main/java/course/ch04/_01_MySharedLock.java
 */
public class _01_MySharedLock {

    /** 允许 N 个线程同时进入的共享锁 */
    static class MySharedLock {
        private final Sync sync;

        MySharedLock(int permits) {
            this.sync = new Sync(permits);
        }

        private static class Sync extends AbstractQueuedSynchronizer {
            Sync(int permits) {
                setState(permits);          // state 表示「剩余可用许可数」
            }

            /** 共享模式获取：返回值 >=0 表示成功，负数表示失败 */
            @Override
            protected int tryAcquireShared(int acquires) {
                for (;;) {
                    int available = getState();
                    int remaining = available - acquires;
                    if (remaining < 0) {
                        return remaining;                     // 许可不够，去排队
                    }
                    if (compareAndSetState(available, remaining)) {
                        return remaining;                     // CAS 成功，拿到许可
                    }
                    // CAS 失败 → for(;;) 自旋重试
                }
            }

            /** 共享模式释放：返回 true 表示可能唤醒后继节点 */
            @Override
            protected boolean tryReleaseShared(int releases) {
                for (;;) {
                    int current = getState();
                    int next = current + releases;
                    if (next < current) throw new Error("Maximum permit count exceeded");
                    if (compareAndSetState(current, next)) {
                        return true;
                    }
                }
            }

            /** 给外面的 lock() / unlock() 用的门面 */
            void acquireShared1() { acquireShared(1); }
            void releaseShared1() { releaseShared(1); }
            int available() { return getState(); }
        }

        public void lock()   { sync.acquireShared1(); }
        public void unlock() { sync.releaseShared1(); }
        public int available() { return sync.available(); }
    }

    static final MySharedLock LOCK = new MySharedLock(3);   // 最多 3 个并发

    public static void main(String[] args) throws Exception {
        System.out.println("初始许可数 = " + LOCK.available() + "，启动 10 个线程抢 3 个许可\n");
        Thread[] ts = new Thread[10];
        for (int i = 0; i < ts.length; i++) {
            final int id = i;
            ts[i] = new Thread(() -> {
                LOCK.lock();
                try {
                    System.out.printf("线程%-2d 拿到许可，剩余=%d，当前并发中...%n",
                            id, LOCK.available());
                    Thread.sleep(300);
                } catch (InterruptedException e) {
                    Thread.currentThread().interrupt();
                } finally {
                    LOCK.unlock();
                    System.out.printf("线程%-2d 释放许可，剩余=%d%n", id, LOCK.available());
                }
            }, "t" + i);
        }
        for (Thread t : ts) t.start();
        for (Thread t : ts) t.join();

        System.out.println("""
            ================== AQS 设计精髓 ==================
            AQS 把「同步器」拆成两半：
              ① 通用骨架（AQS 自己实现，你复用）：
                 - volatile int state + CLH 双向队列
                 - 获取失败的线程如何入队、阻塞（LockSupport.park）
                 - 释放时如何唤醒后继（unparkSuccessor）
              ② 业务规则（子类必须实现，你定制）：
                 - tryAcquire / tryRelease        （独占模式）
                 - tryAcquireShared / tryReleaseShared（共享模式）
                 - isHeldExclusively               （是否被独占）

            模板方法模式：AQS 定义流程，你只填空。
            所有返回值语义（务必记牢）：
              tryAcquire          : true=成功, false=失败
              tryRelease          : true=完全释放, false=还没释放干净
              tryAcquireShared    : >=0 成功（返回剩余量）, <0 失败
              tryReleaseShared    : true=可以唤醒后继
            ==================================================
            """);
    }
}

package course.ch04;

import java.util.concurrent.locks.AbstractQueuedSynchronizer;

/**
 * ch04_02 手写一把不可重入的独占锁 —— 理解独占模式
 *
 * 运行：java src/main/java/course/ch04/_02_MyExclusiveLock.java
 */
public class _02_MyExclusiveLock {

    /** 最简独占锁：state=0 空闲，state=1 已占用 */
    static class MyLock {
        private static class Sync extends AbstractQueuedSynchronizer {
            @Override
            protected boolean tryAcquire(int arg) {
                if (compareAndSetState(0, 1)) {          // 0→1 CAS 成功就拿到锁
                    setExclusiveOwnerThread(Thread.currentThread());
                    return true;
                }
                return false;
            }

            @Override
            protected boolean tryRelease(int arg) {
                if (getState() == 0) throw new IllegalMonitorStateException();
                setExclusiveOwnerThread(null);
                setState(0);                              // 释放：不需要 CAS，因为只有持有者能释放
                return true;
            }

            @Override
            protected boolean isHeldExclusively() {
                return getState() == 1;
            }
        }

        private final Sync sync = new Sync();

        public void lock()   { sync.acquire(1); }
        public boolean tryLock() { return sync.tryAcquire(1); }
        public void unlock() { sync.release(1); }
    }

    static int unsafe = 0;
    static int safe = 0;
    static final MyLock LOCK = new MyLock();

    public static void main(String[] args) throws Exception {
        int n = 10, times = 100_000;
        Thread[] ts = new Thread[n];
        for (int i = 0; i < n; i++) {
            ts[i] = new Thread(() -> {
                for (int j = 0; j < times; j++) {
                    unsafe++;                   // 不加锁
                    LOCK.lock();                // 用我们手写的锁
                    try {
                        safe++;
                    } finally {
                        LOCK.unlock();
                    }
                }
            });
            ts[i].start();
        }
        for (Thread t : ts) t.join();

        System.out.println("期望     : " + (n * times));
        System.out.println("不用锁   : " + unsafe + "   丢失 = " + (n * times - unsafe));
        System.out.println("手写AQS锁: " + safe + "   丢失 = " + (n * times - safe));

        // 演示不可重入的后果
        System.out.println("\n===== 不可重入的坑 =====");
        Thread t = new Thread(() -> {
            LOCK.lock();
            System.out.println("外层拿到锁");
            System.out.println("尝试再次 lock（不可重入）...");
            boolean acquired = LOCK.tryLock();
            System.out.println("第二次 tryLock 结果 = " + acquired + "  → 同一线程也拿不到，会死锁！");
            LOCK.unlock();
        });

        t.start();

        if (t.isAlive()) {

        }

被问到 AQS 时按这个顺序答，条理清晰且显得有深度：

① 是什么：AbstractQueuedSynchronizer，一个用于构建锁和同步器的框架，ReentrantLock、Semaphore、CountDownLatch 都基于它。
② 三大要素：volatile int state（同步状态）+ CLH 变体双向队列（排队）+ 模板方法（扩展点）。
③ state 的语义由子类定义：ReentrantLock 里是重入次数，Semaphore 里是剩余许可数，CountDownLatch 里是剩余计数，ReentrantReadWriteLock 里高 16 位是读锁数、低 16 位是写锁数。
④ 工作流程：acquire → tryAcquire 成功返回，失败则 addWaiter 入队 → acquireQueued 自旋并 park；释放时 release → tryRelease → unparkSuccessor 唤醒后继。
⑤ 主动延伸：为什么用双向队列？因为节点取消时需要访问前驱把自己摘掉，单向队列做不到。这是体现你读过源码的细节。

    /** 公平 vs 非公平：公平锁按 FIFO 排队，吞吐略低但更可控 */
    static void fairVsUnfair() throws Exception {
        for (boolean fair : new boolean[]{false, true}) {
            Lock lock = new ReentrantLock(fair);
            StringBuilder order = new StringBuilder();
            Thread[] ts = new Thread[5];
            for (int i = 0; i < ts.length; i++) {
                final int id = i;

                        order.append(id);
                        Thread.sleep(10);

                        lock.unlock();
                    }
                });

            }

    static void tryLockTimeout() throws Exception {
        Lock lockA = new ReentrantLock();
        Lock lockB = new ReentrantLock();
        AtomicInteger success = new AtomicInteger();

        // 线程1：先 A 后 B
        Thread t1 = new Thread(() -> transfer(lockA, lockB, "线程1", success));
        // 线程2：先 B 后 A（经典死锁顺序）
        Thread t2 = new Thread(() -> transfer(lockB, lockA, "线程2", success));
        t1.start(); t2.start();
        t1.join(5000); t2.join(5000);
        System.out.println("  两个线程都成功结束了（靠 tryLock 超时打破了死锁）");
    }

    static void transfer(Lock first, Lock second, String name, AtomicInteger success) {
        try {
            if (first.tryLock(100, TimeUnit.MILLISECONDS)) {
                try {
                    Thread.sleep(50);
                    if (second.tryLock(100, TimeUnit.MILLISECONDS)) {
                        try {
                            success.incrementAndGet();
                            System.out.println("  " + name + " 同时拿到两把锁，成功");
                        } finally {
                            second.unlock();
                        }
                    } else {

            Thread.currentThread().interrupt();
        }

    static void lockInterruptibly() throws Exception {
        Lock lock = new ReentrantLock();
        lock.lock();
        Thread waiter = new Thread(() -> {
            try {
                System.out.println("  子线程尝试可中断地获取锁...");
                lock.lockInterruptibly();       // 会一直等，但能被中断

                System.out.println("  等待中被 interrupt 成功打断（这是 synchronized 做不到的）");
            }
        });
        waiter.start();
        Thread.sleep(300);
        waiter.interrupt();
        waiter.join();

package course.ch05;

import java.util.LinkedList;
import java.util.Queue;
import java.util.concurrent.locks.Condition;
import java.util.concurrent.locks.ReentrantLock;

/**
 * ch05_02 用 Condition 手写有界阻塞队列 —— 对比 wait/notify 的优雅之处
 *
 * 关键点：一把锁可以有多个条件队列，实现「生产者只唤醒消费者、消费者只唤醒生产者」，
 *         避免 wait/notify 那种「notifyAll 唤醒一大片却只有一半能用」的惊群问题。
 *
 * 运行：java src/main/java/course/ch05/_02_ConditionQueue.java
 */
public class _02_ConditionQueue {

    /** 完全模拟 ArrayBlockingQueue 的实现思路 */
    static class BoundedQueue<E> {
        private final Object[] items;
        private int putIndex, takeIndex, count;
        private final ReentrantLock lock = new ReentrantLock();
        private final Condition notFull  = lock.newCondition();   // 生产者在此等待
        private final Condition notEmpty = lock.newCondition();   // 消费者在此等待

        BoundedQueue(int capacity) { items = new Object[capacity]; }

        public void put(E e) throws InterruptedException {
            lock.lockInterruptibly();
            try {
                while (count == items.length) {
                    notFull.await();                     // 队列满，生产者挂起
                }
                items[putIndex] = e;
                if (++putIndex == items.length) putIndex = 0;   // 环形数组
                count++;
                notEmpty.signal();                       // 只叫醒一个消费者（精准通知）
            } finally {
                lock.unlock();
            }
        }

        @SuppressWarnings("unchecked")
        public E take() throws InterruptedException {
            lock.lockInterruptibly();
            try {
                while (count == 0) {
                    notEmpty.await();                    // 队列空，消费者挂起
                }
                E e = (E) items[takeIndex];
                items[takeIndex] = null;                 // help GC
                if (++takeIndex == items.length) takeIndex = 0;
                count--;
                notFull.signal();                        // 只叫醒一个生产者
                return e;
            } finally {
                lock.unlock();
            }
        }

        public int size() {
            lock.lock();
            try { return count; } finally { lock.unlock(); }
        }
    }

    public static void main(String[] args) throws Exception {
        BoundedQueue<Integer> q = new BoundedQueue<>(5);
        long start = System.currentTimeMillis();
        int total = 200;

        Thread producer = new Thread(() -> {
            try {
                for (int i = 1; i <= total; i++) {
                    q.put(i);
                    if (i % 50 == 0) System.out.println("已生产 " + i + " 个");
                }
            } catch (InterruptedException e) { Thread.currentThread().interrupt(); }
        }, "producer");

        Thread[] consumers = new Thread[3];
        java.util.concurrent.atomic.AtomicInteger consumed = new java.util.concurrent.atomic.AtomicInteger();
        for (int i = 0; i < consumers.length; i++) {
            consumers[i] = new Thread(() -> {
                try {
                    while (true) {
                        Integer v = q.take();
                        if (v == 0) {         // 毒丸，用来优雅停止
                            q.put(0);         // 转交给下一个消费者
                            break;
                        }
                        consumed.incrementAndGet();
                    }
                } catch (InterruptedException e) { Thread.currentThread().interrupt(); }
            }, "consumer-" + i);
        }

        for (Thread c : consumers) c.start();
        producer.start();
        producer.join();
        Thread.sleep(200);
        q.put(0);        // 投毒丸
        for (Thread c : consumers) c.join(2000);

        System.out.println("消费总数 = " + consumed.get() + "，期望 " + total
                + "，耗时 " + (System.currentTimeMillis() - start) + " ms");

        System.out.println("""
            
            ============ Condition vs wait/notify ============
            1) 一个 Lock 可 newCondition() 出多个条件队列：
               - notFull  → 队列满时生产者等待
               - notEmpty → 队列空时消费者等待
               各自独立，signal 精准唤醒目标角色，避免无效唤醒。

            2) 三种等待方法：
               await()          : 等价 wait()
               awaitUninterruptibly() : 不可中断
               awaitNanos(n) / await(time, unit) : 超时等待，返回剩余时间
               awaitUntil(deadline) : 等到绝对时间

            3) 底层实现：每个 Condition 内部维护一个单向等待队列（firstWaiter/lastWaiter），
               节点复用的是 AQS 的 Node，状态为 Node.CONDITION。
               signal 时把节点从条件队列转移到 AQS 的同步队列，等待被唤醒后重新抢锁。

            4) 注意：Condition 必须在 lock() 和 unlock() 之间使用，
               否则抛 IllegalMonitorStateException。
            ==================================================
            """);
    }

Q为什么 ReentrantReadWriteLock 的读锁不支持 Condition？
这个问题很能考察对 Condition 本质的理解。readLock().newCondition() 会直接抛 UnsupportedOperationException。
原因是：Condition 的 await() 语义是「释放当前线程持有的全部锁，然后等待」。但读锁是可共享的——多个线程可以同时持有读锁。如果某个线程 await 时释放了读锁，它无法界定「要释放到哪个程度」，也无法保证唤醒后能重新获得相同数量的读锁。所以 JDK 直接选择不支持，避免语义歧义。

/**

public class _01_ReadWriteLock {

    /** 场景：读多写少的缓存 */
    static class RwCache<K, V> {
        private final Map<K, V> map = new HashMap<>();
        private final ReentrantReadWriteLock rw = new ReentrantReadWriteLock();

        public V get(K k) {
            rw.readLock().lock();                // 读锁：多个读线程可并发
            try {
                System.out.println("  [" + Thread.currentThread().getName() + "] 获得读锁，当前读锁数="
                        + rw.getReadLockCount());
                sleep(100);
                return map.get(k);
            } finally {
                rw.readLock().unlock();
            }
        }

        public void put(K k, V v) {
            rw.writeLock().lock();               // 写锁：独占
            try {
                System.out.println("  [" + Thread.currentThread().getName() + "] 获得写锁（独占）");
                sleep(100);
                map.put(k, v);
            } finally {
                rw.writeLock().unlock();
            }
        }
    }

    /** StampedLock：乐观读，读性能最强 */
    static class StampedCache {
        private double x, y;
        private final StampedLock sl = new StampedLock();

        void move(double dx, double dy) {
            long stamp = sl.writeLock();         // 悲观写锁，返回版本号
            try { x += dx; y += dy; } finally { sl.unlockWrite(stamp); }
        }

        double distanceFromOrigin() {
            long stamp = sl.tryOptimisticRead();  // 乐观读：不加锁，只取版本号
            double cx = x, cy = y;                // 把字段拷到局部变量（可能读到不一致快照）
            if (!sl.validate(stamp)) {            // 校验：期间有没有被写过？
                stamp = sl.readLock();            // 有被写 → 退化成悲观读锁重来
                try { cx = x; cy = y; } finally { sl.unlockRead(stamp); }
            }
            return Math.sqrt(cx * cx + cy * cy);
        }
    }

        System.out.println("===== 1) ReentrantReadWriteLock：读读共享 =====");

        for (int i = 0; i < 3; i++) {
            new Thread(() -> { cache.get("k"); latch.countDown(); }, "reader-" + i).start();

        latch.await();

        writer.join(); reader.join();

        System.out.println("\n===== 3) StampedLock 乐观读 =====");
        StampedCache sc = new StampedCache();
        sc.move(3, 4);
        System.out.println("  乐观读得到距离 = " + sc.distanceFromOrigin() + "（期望 5.0）");
        Thread t = new Thread(() -> { for (int i = 0; i < 100; i++) sc.move(0.001, 0.001); });

            | 锁                       | 特性                                     | 适用场景          |
            |--------------------------|------------------------------------------|-------------------|
            | ReentrantReadWriteLock   | 可重入、支持公平/非公平、锁降级支持      | 通用读多写少      |

            ① 读锁不支持条件队列：readLock().newCondition() 直接抛 UnsupportedOperationException

package course.ch07;

import java.util.concurrent.*;

/**
 * ch08_02 手写一个极简线程池 —— 理解 ThreadPoolExecutor 内部到底在做什么
 *
 * 运行：java src/main/java/course/ch07/_02_MyThreadPool.java
 */
public class _02_MyThreadPool {

    /** 极简线程池：固定线程数 + 有界队列 + 拒绝策略 */
    static class SimplePool implements AutoCloseable {
        private final BlockingQueue<Runnable> queue;
        private final Worker[] workers;
        private volatile boolean running = true;
        private final RejectPolicy rejectPolicy;

        enum RejectPolicy { ABORT, CALLER_RUNS, DISCARD }

        SimplePool(int poolSize, int queueCapacity, RejectPolicy policy) {
            this.queue = new ArrayBlockingQueue<>(queueCapacity);
            this.rejectPolicy = policy;
            this.workers = new Worker[poolSize];
            for (int i = 0; i < poolSize; i++) {
                workers[i] = new Worker("simple-pool-" + i);
                workers[i].start();          // 核心线程：启动即阻塞在 take() 上（预热）
            }
        }

        public void execute(Runnable task) {
            if (!running) throw new IllegalStateException("pool is shut down");
            if (queue.offer(task)) return;    // 入队成功，走正常路径

            // 队列满 → 走拒绝策略
            switch (rejectPolicy) {
                case ABORT -> throw new RejectedExecutionException("队列已满，任务被拒绝");
                case CALLER_RUNS -> {
                    System.out.println("  [拒绝] 队列满，" + Thread.currentThread().getName() + " 自己执行");
                    task.run();
                }
                case DISCARD -> System.out.println("  [拒绝] 静默丢弃");
            }
        }

        /** 工作线程：经典的「取任务-执行」死循环 */
        private class Worker extends Thread {
            Worker(String name) { super(name); setDaemon(true); }

            @Override
            public void run() {
                while (running) {
                    try {
                        Runnable task = queue.poll(100, TimeUnit.MILLISECONDS);  // 阻塞获取
                        if (task != null) {
                            task.run();          // 真正执行任务
                        }
                    } catch (InterruptedException e) {
                        Thread.currentThread().interrupt();
                        return;
                    } catch (Throwable t) {
                        // 关键：任务异常不能让工作线程死掉
                        System.err.println("任务执行异常: " + t);
                    }
                }
            }
        }

        public int queueSize() { return queue.size(); }

        @Override
        public void close() {
            running = false;
            for (Worker w : workers) w.interrupt();
        }
    }

                    try { Thread.sleep(200); } catch (InterruptedException e) { Thread.currentThread().interrupt(); }
                });
            }
            Thread.sleep(2000);
        }

        System.out.println("\n===== 对比 JDK 原生 ThreadPoolExecutor 的源码骨架 =====");
        System.out.println("""

① 为什么用 ctl 一个字段同时表达「状态」和「线程数」？
因为要保证「判断状态」和「读取线程数」的原子性。如果分成两个字段，在两次读取之间状态可能已经变了，需要额外加锁。合并成一个 AtomicInteger 后，一次 CAS 就能同时更新两者。高 3 位是 RUNNING/SHUTDOWN/STOP/TIDYING/TERMINATED，低 29 位是线程数（上限约 5 亿）。

② 为什么新建的 worker 先执行 firstTask 而不是先去 take()？
这是「快速路径」优化。如果新线程创建后先去队列取任务，而此时队列是空的，就会白白多一次上下文切换的往返。

③ 为什么任务抛异常后工作线程不会死？
runWorker() 内部有 try/finally 包裹，异常通过 afterExecute 钩子传递，然后 while 循环继续 getTask() 取下一个任务。

    static void shutdownVsShutdownNow() throws Exception {
        ThreadPoolExecutor pool = new ThreadPoolExecutor(
                1, 1, 0, TimeUnit.SECONDS, new LinkedBlockingQueue<>());
        for (int i = 0; i < 5; i++) {
            final int id = i;
            pool.execute(() -> {
                try { Thread.sleep(500); } catch (InterruptedException e) {
                    System.out.println("  任务" + id + " 被中断");
                    Thread.currentThread().interrupt();
                }
            });
        }
        Thread.sleep(100);
        System.out.println("  提交 5 个任务后，队列长度 = " + pool.getQueue().size());

        // shutdown()：不接受新任务，但把队列里的跑完
        pool.shutdown();
        System.out.println("  调用 shutdown() 后 isShutdown=" + pool.isShutdown()
                + "，队列还在跑，剩余 = " + pool.getQueue().size());

        System.out.println("  等待完成 = " + done + "，isTerminated=" + pool.isTerminated());

        ThreadPoolExecutor pool2 = new ThreadPoolExecutor(
                1, 1, 0, TimeUnit.SECONDS, new LinkedBlockingQueue<>());
        for (int i = 0; i < 5; i++) pool2.execute(() -> {
            try { Thread.sleep(1000); } catch (InterruptedException e) { Thread.currentThread().interrupt(); }

                + "（立即中断线程 + 清空队列）");
        pool2.awaitTermination(3, TimeUnit.SECONDS);
    }

    static void gracefulShutdown() throws Exception {
        ThreadPoolExecutor pool = new ThreadPoolExecutor(
                2, 4, 60, TimeUnit.SECONDS,
                new ArrayBlockingQueue<>(100),
                r -> { Thread t = new Thread(r, "biz-pool-" + System.nanoTime() % 1000); return t; },
                new ThreadPoolExecutor.CallerRunsPolicy());

            try { Thread.sleep(200); } catch (InterruptedException e) { Thread.currentThread().interrupt(); }
        });

        pool.shutdown();                                    // ① 拒绝新任务

            Thread.currentThread().interrupt();
        }
        System.out.println("  已完成 10 个任务，线程池优雅关闭成功");

8.2 线程池参数到底设多少？

理论公式（面试可以背）：

  CPU 密集型（计算为主，几乎不阻塞）
     线程数 = N + 1        （N = CPU 核心数）
     为什么 +1？为了在偶发的缺页中断或其他暂停时，仍能有一线程顶上。

  IO 密集型（大量等待网络/磁盘）
     线程数 = N x (1 + 等待时间 / 计算时间)
     例：CT=50ms 计算, WT=450ms 等待, N=8
         -> 8 x (1 + 9) = 80 个线程

但生产实践更推荐「压测 + 动态调整」：
  +---------------------------------------------------------+
  | 1 按公式给一个初值                                       |
  | 2 用 JMeter/wrk 做压力测试，观察 QPS 和响应时间曲线      |
  | 3 找到 QPS 不再上升、但响应时间开始飙升的拐点            |
  | 4 取拐点值的 80% 作为配置                                |
  | 5 接入配置中心（Nacos/Apollo），支持运行时热更新         |
  |   setCorePoolSize() / setMaximumPoolSize() 都支持动态改  |
  +---------------------------------------------------------+
  为什么不能只靠公式？
  因为公式里的「等待时间/计算时间」在真实业务中很难准确测量，
  而且流量模式会变化（大促 vs 平时）。

import java.util.List;
import java.util.concurrent.*;

 * 运行：java src/main/java/course/ch08/_02_CompletableFutureBasic.java

public class _02_CompletableFutureBasic {

    static final ExecutorService POOL = Executors.newFixedThreadPool(8, r -> {
        Thread t = new Thread(r, "cf-pool");
        t.setDaemon(true);
        return t;
    });

    public static void main(String[] args) throws Exception {
        System.out.println("===== 1) 四种创建方式 =====");
        // ① 已完成的
        CompletableFuture<String> f1 = CompletableFuture.completedFuture("立即完成");
        // ② 无返回值的异步任务
        CompletableFuture<Void> f2 = CompletableFuture.runAsync(
                () -> System.out.println("    runAsync 在 " + Thread.currentThread().getName()), POOL);
        // ③ 有返回值的异步任务
        CompletableFuture<String> f3 = CompletableFuture.supplyAsync(() -> "supplyAsync 结果", POOL);
        // ④ 手动完成（用于回调式 API 桥接）
        CompletableFuture<String> f4 = new CompletableFuture<>();
        new Thread(() -> f4.complete("手动完成")).start();

        System.out.println("    " + f1.get() + " / " + f3.get() + " / " + f4.get());
        f2.get();

        System.out.println("\n===== 2) 串行链式：thenApply / thenAccept / thenRun =====");
        String chainResult = CompletableFuture
                .supplyAsync(() -> 10, POOL)
                .thenApply(v -> {                       // 有入参有返回：转换
                    System.out.println("    thenApply 在 " + Thread.currentThread().getName());
                    return v * 2;
                })
                .thenApply(v -> v + 5)
                .thenApply(v -> "最终结果=" + v)
                .get();
        System.out.println("    " + chainResult);
        System.out.println("    注意：thenApply 在「上一个任务的执行线程」上运行（同线程续跑）");

        System.out.println("\n===== 3) 带 Async 后缀：切换到别的线程 =====");
        CompletableFuture.supplyAsync(() -> "A", POOL)
                .thenApplyAsync(v -> {
                    System.out.println("    thenApplyAsync 在 " + Thread.currentThread().getName());
                    return v + "B";
                }, POOL)
                .thenAcceptAsync(v -> System.out.println("    thenAcceptAsync 拿到 " + v), POOL)
                .get();

        System.out.println("\n===== 4) 异常处理三件套 =====");
        // handle：无论成功失败都执行，可转换结果
        String h = CompletableFuture.<String>supplyAsync(() -> {
            throw new RuntimeException("模拟失败");
        }, POOL).handle((v, e) -> e != null ? "handle 兜底: " + e.getMessage() : v).get();
        System.out.println("    handle      → " + h);

        // exceptionally：只在异常时兜底
        String ex = CompletableFuture.<String>supplyAsync(() -> {
            throw new RuntimeException("boom");
        }, POOL).exceptionally(e -> "exceptionally 兜底: " + e.getCause().getMessage()).get();
        System.out.println("    exceptionally → " + ex);

        // whenComplete：观察结果但不改变它
        String wc = CompletableFuture.supplyAsync(() -> "正常值", POOL)
                .whenComplete((v, e) -> System.out.println("    whenComplete 观察到: v=" + v + ", e=" + e))
                .get();
        System.out.println("    whenComplete → 返回值不变: " + wc);

        System.out.println("\n===== 5) 组合：thenCompose（扁平化）vs thenCombine（合并）=====");
        // thenCompose：第二个任务依赖第一个的结果（串行）
        String compose = CompletableFuture.supplyAsync(() -> "用户ID=100", POOL)
                .thenCompose(uid -> CompletableFuture.supplyAsync(() -> "根据[" + uid + "]查到订单", POOL))
                .get();
        System.out.println("    thenCompose → " + compose);

        // thenCombine：两个独立任务并行，都完成后合并
        long t0 = System.currentTimeMillis();
        CompletableFuture<String> ca = CompletableFuture.supplyAsync(() -> { sleep(300); return "A"; }, POOL);
        CompletableFuture<String> cb = CompletableFuture.supplyAsync(() -> { sleep(300); return "B"; }, POOL);
        String combined = ca.thenCombine(cb, (a, b) -> a + "+" + b).get();
        System.out.println("    thenCombine → " + combined
                + "，耗时 " + (System.currentTimeMillis() - t0) + "ms（并行，非 600ms）");

        System.out.println("\n===== 6) 多任务编排：allOf / anyOf =====");
        long t1 = System.currentTimeMillis();
        List<CompletableFuture<String>> tasks = Arrays.asList("服务1", "服务2", "服务3").stream()
                .map(name -> CompletableFuture.supplyAsync(() -> {
                    sleep(200);
                    return name + "结果";
                }, POOL))
                .collect(Collectors.toList());

        CompletableFuture.allOf(tasks.toArray(new CompletableFuture[0])).join();
        List<String> results = tasks.stream().map(CompletableFuture::join).collect(Collectors.toList());
        System.out.println("    allOf 全部完成 → " + results
                + "，耗时 " + (System.currentTimeMillis() - t1) + "ms");

        Object any = CompletableFuture.anyOf(
                CompletableFuture.supplyAsync(() -> { sleep(500); return "慢"; }, POOL),
                CompletableFuture.supplyAsync(() -> { sleep(100); return "快"; }, POOL)
        ).get();
        System.out.println("    anyOf 第一个完成 → " + any);

        System.out.println("""
            
            ============ 方法速查表 ============
            | 方法             | 入参→出参      | 用途                        |
            |------------------|---------------|-----------------------------|
            | thenApply        | T→U           | 转换结果（串行）            |
            | thenAccept       | T→void        | 消费结果                    |
            | thenRun          | void→void     | 不关心结果，跑下一步        |
            | thenCompose      | T→CF<U>       | 依赖前一结果返回新 CF（扁平化）|
            | thenCombine      | (T,U)→V       | 两个独立 CF 结果合并        |
            | allOf            | CF[]→CF<Void> | 全部完成                    |
            | anyOf            | CF[]→CF<Object>| 任一完成                   |
            | handle           | (T,E)→U       | 成功/失败都处理，可改变结果 |
            | exceptionally    | E→T           | 只处理异常，兜底返回        |
            | whenComplete     | (T,E)→void    | 只观察不改变结果            |

            ---------- 三个必知要点 ----------
            ① 没有 Async 后缀的方法：如果任务已完成，用调用者线程执行；
               如果未完成，用「完成那个任务的线程」执行。→ 可能阻塞调用者，
               也可能在任意线程跑，容易踩坑。生产建议显式用带 Async 的版本并传线程池。

               parallelStream 也用它 → 共用会互相影响，必须传自己的池。
            ③ allOf 返回 CompletableFuture<Void>，拿不到各个结果，
               需要自己 join 每个子任务（本项目演示了标准写法）。
            ====================================
            """);

        POOL.shutdown();
    }

handle(T,E) → U成功/失败都处理，可改变结果
exceptionallyE → T只处理异常，兜底返回
whenComplete(T,E) → void只观察不改变结果
!CompletableFuture 的三个致命坑
① 默认线程池是 ForkJoinPool.commonPool()，线程数只有 CPU-1，而且被 parallelStream 等共用。一个慢任务就能拖垮全站。所有异步方法必须显式传入自己的线程池。

② 在 thenApply 里做阻塞操作（如 RPC 调用），会占住线程池的线程。应该用 thenApplyAsync 并传入独立的线程池。

③ 忘记加超时。没有超时的异步调用就是一颗定时炸弹，下游卡住会一直占着线程。每个下游调用都要加 orTimeout()。

  |  Node[] table                                            |
  |  +----++----++--------------++----++----+              |

  * 扩容支持多线程协同迁移（helpTransfer）
Q为什么 JDK8 放弃分段锁？
两个核心原因：

① 分段锁的并发度上限被固定死了。默认 16 段意味着最多 16 个线程并发写，而且段数在初始化后无法修改。桶级锁没有这个限制。
② JDK8 的 synchronized 已经做了大量优化（锁消除、锁粗化、轻量级锁自旋），在低竞争场景下性能已接近 CAS。所以用 synchronized 锁桶头节点，既简化了实现（不用维护 Segment 继承体系），又获得了更细的锁粒度。

追问：为什么 key 和 value 都不能为 null？
因为并发场景下需要「一次查找」就区分「key 不存在」和「key 存在但值为 null」。HashMap 可以用 containsKey 做二次确认，但 CHM 为了性能不做二次查找，所以干脆禁止 null。

            很多人以为：ThreadLocal 是一个 Map，key 是线程，value 是值。
            实际上完全相反！

                Thread 对象里有一个字段：
                    ThreadLocal.ThreadLocalMap threadLocals;

                ThreadLocalMap 的 Entry：
                    static class Entry extends WeakReference<ThreadLocal<?>> {
                        Object value;                          // 强引用
                        Entry(ThreadLocal<?> k, Object v) {
                            super(k);                          // key 是弱引用！
                            value = v;
                        }
                    }

            → 所以数据是存在「线程」身上的，ThreadLocal 只是访问它的「钥匙」。
            → 这也是为什么每个线程天然隔离，不需要任何同步。

            ============== 内存泄漏问题（面试必问）==============
            引用链：Thread → ThreadLocalMap → Entry → value（强引用）
                                     ↑
                                  key（弱引用）→ ThreadLocal 对象

            当 ThreadLocal 对象被置为 null（外部无强引用）：
              ① key 是弱引用 → GC 时 key 被回收，变成 null
              ② 但 value 是强引用，且被 Thread 引用着 → value 无法回收
              ③ 如果线程长期存活（线程池！），value 就一直堆着 → 内存泄漏

            ---------- 为什么用弱引用？（这是设计的精妙处）----------
            用强引用的话，ThreadLocal 对象即使外部不用了，也会因为被 Map 引用而
            永远无法回收 → 泄漏更严重（连 ThreadLocal 对象本身都漏了）。
            用弱引用，至少 ThreadLocal 对象能回收，泄漏范围缩小到 value。

            ---------- 三重防御 ----------
            ① ThreadLocal 的 set/get/remove 会顺带清理 key=null 的 Entry（expungeStaleEntry）
            ② 强烈建议：显式声明为 private static final（保证外部一直有强引用，
               避免 key 被提前回收导致 Entry 变成「真·僵尸」）
            ③ 最关键：用完必须 remove()，尤其是在线程池里！
            ====================================================
            """);

        System.out.println("===== 3) 不 remove 的后果演示（线程池场景）=====");
        ExecutorService pool = Executors.newFixedThreadPool(1);
        // 第一次任务：设置了值，故意不清理
        pool.submit(() -> {
            LEAK.set(new byte[10 * 1024 * 1024]);    // 10MB
            System.out.println("  任务1 在 " + Thread.currentThread().getName()
                    + " 上放了 10MB，未清理");
        }).get();
        // 第二次任务：同一个线程，居然能读到上次的残留（也可能被 GC 掉，取决于时机）
        pool.submit(() -> {
            System.out.println("  任务2 在 " + Thread.currentThread().getName()
                    + " 上读到残留 = " + (LEAK.get() != null ? "有！脏数据！" : "null"));
            LEAK.remove();     // 正确姿势
        }).get();
        pool.shutdown();
        pool.awaitTermination(2, TimeUnit.SECONDS);
        System.out.println("  → 线程复用导致上下文串味，这就是「脏数据」事故的根源");

        System.out.println("\n===== 4) 正确姿势：try-finally 模板 =====");
        System.out.println("""
            private static final ThreadLocal<Ctx> CTX = new ThreadLocal<>();

            public void doBusiness() {
                CTX.set(new Ctx(...));          // 或 ThreadLocal.withInitial(...)
                try {
                    // ... 业务逻辑，期间可以随意 CTX.get()
                } finally {
                    CTX.remove();               // 必须！finally 保证异常也清理
                }
            }

            或者用 JDK8 的 withInitial 简化：
            private static final ThreadLocal<SimpleDateFormat> SDF =
                ThreadLocal.withInitial(() -> new SimpleDateFormat("yyyy-MM-dd"));
            → 但 SDF 依然建议在 finally 里 remove（线程池场景）
            """);

        System.out.println("===== 5) 典型应用场景 =====");
        System.out.println("""
            ① 用户上下文 / 租户隔离：把 userId、tenantId、traceId 透传到各层
               （Spring 的 RequestContextHolder 就是这么实现的）
            ② 事务上下文：Spring 的 TransactionSynchronizationManager 用
               ThreadLocal 存 Connection / TransactionStatus
            ③ 非线程安全工具的复用：SimpleDateFormat、Random
               → 但更好的方案是 DateTimeFormatter（本身线程安全）
            ④ 链路追踪：MDC（SLF4J 的 Mapped Diagnostic Context）底层就是 ThreadLocal
            ⑤ 数据库多数据源路由、分库分表的路由键

            ---------- 跨线程传递问题（重要！）----------
            ThreadLocal 不能被子线程继承，new Thread 后 CTX.get() 是 null。
            解决方案：
            ① InheritableThreadLocal：子线程创建时复制父线程的值
               缺点：线程池里线程是复用的，创建时机不对，值会不对
            ② 阿里开源的 TransmittableThreadLocal (TTL)：
               配合 TtlExecutors.getTtlExecutorService(pool) 包装线程池，
               能在「提交任务时」把当前线程的上下文快照传递过去
               这是线程池场景下唯一正确的方案
            -------------------------------------------
            """);

        // 演示 InheritableThreadLocal
        System.out.println("===== 6) InheritableThreadLocal 演示 =====");
        InheritableThreadLocal<String> itl = new InheritableThreadLocal<>();
        itl.set("父线程的值");
        new Thread(() -> System.out.println("  子线程读到: " + itl.get())).start();
        Thread.sleep(200);
        System.out.println("  （对比普通 ThreadLocal 在子线程中会是 null）");
    }

这是互联网公司最典型的 CompletableFuture 应用场景。打开一个商品详情页，需要调用 6 个下游服务，串行调用要 900ms，并行只需要最慢那个的时间。

_02_CfRealWorld.java165 行 · JDK 25 实测通过
package course.ch10;

import java.util.Arrays;
import java.util.List;
import java.util.concurrent.*;
import java.util.function.Supplier;

/**
 * ch10_02 CompletableFuture 实战：商品详情页聚合（互联网大厂高频场景）
 *
 * 场景：打开一个商品详情页，需要并行调用 6 个下游服务：
 *   商品基本信息、库存、价格、优惠券、评价、推荐
 * 串行 = 各服务耗时之和；并行 = 最慢那个的耗时。
 *
 * 运行：java src/main/java/course/ch10/_02_CfRealWorld.java
 */
public class _02_CfRealWorld {

    static final ExecutorService BIZ_POOL = new ThreadPoolExecutor(
            16, 32, 60, TimeUnit.SECONDS,
            new ArrayBlockingQueue<>(200),
            r -> { Thread t = new Thread(r, "detail-pool"); t.setDaemon(true); return t; },
            new ThreadPoolExecutor.CallerRunsPolicy());

    // ---------- 模拟的 RPC 客户端 ----------
    static String getProductInfo(String sku)      { return rpc("商品信息[" + sku + "]", 120); }
    static Integer getStock(String sku)           { return Integer.parseInt(rpc("88", 80)); }
    static Long getPrice(String sku)              { return Long.parseLong(rpc("19900", 100)); }
    static List<String> getCoupons(String sku, Long price) {
        return Arrays.asList(rpc("满199减20|满99减10", 150).split("\\|"));
    }
    static String getReviews(String sku)          { return rpc("好评率98%", 200); }
    static String getRecommend(String sku)        { return rpc("推荐：同款A/同款B", 250); }

    static String rpc(String result, long costMs) {
        sleep(costMs);
        return result;
    }

    public static void main(String[] args) throws Exception {
        String sku = "SKU-10086";

        // ============ 方式一：完全串行 ============
        System.out.println("===== 方式一：串行调用 =====");
        long s1 = System.currentTimeMillis();
        String info1 = getProductInfo(sku);
        Integer stock1 = getStock(sku);
        Long price1 = getPrice(sku);
        List<String> coupons1 = getCoupons(sku, price1);
        String reviews1 = getReviews(sku);
        String rec1 = getRecommend(sku);
        long serialMs = System.currentTimeMillis() - s1;
        System.out.println("  总耗时 = " + serialMs + "ms");

        // ============ 方式二：CompletableFuture 并行编排 ============
        System.out.println("\n===== 方式二：CompletableFuture 并行编排 =====");
        long s2 = System.currentTimeMillis();

        // 阶段1：无依赖的 4 个服务，全部并行发起
        CompletableFuture<String> infoF    = CompletableFuture.supplyAsync(() -> getProductInfo(sku), BIZ_POOL);
        CompletableFuture<Integer> stockF  = CompletableFuture.supplyAsync(() -> getStock(sku), BIZ_POOL);
        CompletableFuture<Long> priceF     = CompletableFuture.supplyAsync(() -> getPrice(sku), BIZ_POOL);
        CompletableFuture<String> reviewF  = CompletableFuture.supplyAsync(() -> getReviews(sku), BIZ_POOL);

        // 阶段2：优惠券依赖价格 → 用 thenCompose 串联
        CompletableFuture<List<String>> couponF = priceF.thenComposeAsync(
                p -> CompletableFuture.supplyAsync(() -> getCoupons(sku, p), BIZ_POOL), BIZ_POOL);

        // 推荐服务不阻塞主流程 → 给它加超时兜底
        CompletableFuture<String> recF = CompletableFuture
                .supplyAsync(() -> getRecommend(sku), BIZ_POOL)
                .orTimeout(300, TimeUnit.MILLISECONDS)
                .exceptionally(e -> "推荐服务降级：默认推荐");

        // 等待所有结果
        CompletableFuture.allOf(infoF, stockF, priceF, reviewF, couponF, recF).join();
        long parallelMs = System.currentTimeMillis() - s2;

        System.out.println("  商品 = " + infoF.join());
        System.out.println("  库存 = " + stockF.join());
        System.out.println("  价格 = " + priceF.join() + " 分");
        System.out.println("  优惠 = " + couponF.join());
        System.out.println("  评价 = " + reviewF.join());
        System.out.println("  推荐 = " + recF.join());
        System.out.printf("  总耗时 = %dms（串行 %dms，提速 %.1f 倍）%n",
                parallelMs, serialMs, (double) serialMs / parallelMs);

        // ============ 方式三：AnyOf 竞速 + 超时降级 ============
        System.out.println("\n===== 方式三：多数据源竞速（谁快用谁）=====");
        String fastest = (String) CompletableFuture.anyOf(
                CompletableFuture.supplyAsync(() -> rpc("主库数据", 300), BIZ_POOL),
                CompletableFuture.supplyAsync(() -> rpc("缓存数据", 20), BIZ_POOL),
                CompletableFuture.supplyAsync(() -> rpc("从库数据", 150), BIZ_POOL)
        ).get();
        System.out.println("  取到最快返回的 = " + fastest);

        // ============ 方式四：超时 + 降级 + 兜底（生产级模板）============
        System.out.println("\n===== 方式四：生产级「超时降级」模板 =====");
        String result = withFallback("核心服务", 100,
                () -> rpc("真实数据", 400),            // 实际耗时 400ms
                "兜底默认值");                          // 超时后的降级值
        System.out.println("  结果 = " + result);

        String result2 = withFallback("核心服务", 500,
                () -> rpc("真实数据", 100),
                "兜底默认值");
        System.out.println("  结果 = " + result2);

        System.out.println("""
            
            ============== 生产级 CompletableFuture 使用规范 ==============
            【必须做】
            ① 永远传入自定义线程池，不要用默认的 ForkJoinPool.commonPool()
               原因：commonPool 的线程数是 CPU-1，被 parallelStream / 其他业务共用，
                     一个慢任务会拖垮全站。这是最容易被忽视的生产事故。

            ② 每个下游调用都加超时：orTimeout(ms) 或 completeOnTimeout(value, ms)
               没有超时的 RPC 调用 = 埋了一颗定时炸弹。

            ③ 线程池隔离：不同下游用不同池
               否则「推荐服务慢」会把「价格服务」的线程全部占满 → 级联雪崩。

            ④ 一定要处理异常：exceptionally / handle
               否则异常会被静默吞掉，接口返回 null，排查困难。

            【常见坑】
            × 在 thenApply 里做阻塞操作（如 RPC）→ 会占住线程池线程
              → 应该用 thenApplyAsync 并传入独立线程池
            × 忘了 join/get → 主线程提前返回，异步任务白跑
            × allOf 之后忘记处理各个子任务的异常 → join 会抛 CompletionException
              → 建议用 allOf 后逐个 handle 兜底，而不是直接 join
            × 嵌套 CompletableFuture 不扁平化（用 thenApply 返回 CF<CF<T>>）
              → 应该用 thenCompose
            ===============================================================
            """);

        BIZ_POOL.shutdown();
    }

    /** 超时降级通用模板 */
    static String withFallback(String name, long timeoutMs,
                                Supplier<String> business, String fallback) {
        try {
            return CompletableFuture.supplyAsync(business, BIZ_POOL)
                    .orTimeout(timeoutMs, TimeUnit.MILLISECONDS)
                    .exceptionally(e -> {
                        System.out.println("    [" + name + "] 超时/异常，触发降级：" + shortMsg(e));
                        return fallback;
                    })
                    .get();
        } catch (Exception e) {
            return fallback;
        }
    }

    static String shortMsg(Throwable e) {
        Throwable c = e.getCause() != null ? e.getCause() : e;
        return c.getClass().getSimpleName();
    }

    static void sleep(long ms) {
        try { Thread.sleep(ms); } catch (InterruptedException e) { Thread.currentThread().interrupt(); }
    }
}

package course.ch11;

/**
 * ch11_01 happens-before 八大规则 + 指令重排序实测
 *
 * 运行：java src/main/java/course/ch11/_01_HappensBefore.java
 */
public class _01_HappensBefore {

    static int a = 0, b = 0, x = 0, y = 0;
    static volatile boolean flagA = false, flagB = false;

    public static void main(String[] args) throws Exception {
        System.out.println("===== 1) 重排序实测：不留神就出现的 (0,0) 结果 =====");
        System.out.println("  （x86 是强内存模型 + JIT 需要预热，这个实验需要跑很多轮才有机会复现）");
        int zeroCount = 0, total = 2_000_000;
        // 用 CountDownLatch 让两个线程尽可能同时起跑，增加重排复现概率
        for (int i = 0; i < total; i++) {
            a = b = x = y = 0;
            java.util.concurrent.CountDownLatch start = new java.util.concurrent.CountDownLatch(1);
            Thread t1 = new Thread(() -> {
                try { start.await(); } catch (InterruptedException e) { Thread.currentThread().interrupt(); }
                a = 1;              // ①
                x = b;              // ②  这两行可能被重排
            });
            Thread t2 = new Thread(() -> {
                try { start.await(); } catch (InterruptedException e) { Thread.currentThread().interrupt(); }
                b = 1;              // ③
                y = a;              // ④
            });
            t1.start(); t2.start();
            start.countDown();
            t1.join(); t2.join();
            if (x == 0 && y == 0) zeroCount++;
        }
        System.out.println("  出现 (x=0, y=0) 的次数 = " + zeroCount + " / " + total);
        System.out.println("""
              → 按顺序一致性推导，(x,y) 只可能是 (1,0)、(0,1)、(1,1)，绝不该出现 (0,0)。
                如果上面数字 > 0，说明 ①② 或 ③④ 之间发生了重排序（StoreLoad 重排）。
                在 x86 上复现率很低（TSO 强内存模型），在 ARM 上会明显得多 ——
                这正是为什么「我本机跑没问题」的并发 bug 到了 ARM 服务器就炸。
                可以加 -XX:-UseCompressedOops 之类参数、或改用 volatile 验证差异。
              """);
        System.out.println("  对比：给 a/b 都加上 volatile 后（禁止重排序），(0,0) 将彻底消失。");

        System.out.println("===== 2) happens-before 八大规则（背下来）=====");
        System.out.println("""
            | # | 规则名称                | 说明                                                    |
            |---|-------------------------|---------------------------------------------------------|
            | 1 | 程序顺序规则            | 同一线程内，前面的操作 hb 后面的操作                     |
            | 2 | 监视器锁规则            | 对同一把锁的 unlock hb 后续的 lock                       |
            | 3 | volatile 变量规则       | 对 volatile 变量的写 hb 后续的读                         |
            | 4 | 线程启动规则            | Thread.start() hb 该线程内的所有操作                     |
            | 5 | 线程终止规则            | 线程内所有操作 hb 其他线程检测到该线程终止（join 返回） |
            | 6 | 线程中断规则            | interrupt() hb 被中断线程检测到中断                      |
            | 7 | 对象终结规则            | 构造器结束 hb finalize() 开始                            |
            | 8 | 传递性                  | A hb B，B hb C  ⟹  A hb C                               |

            ---------- 怎么用这条规则解题？ ----------
            题目：下面代码 i 的值是多少？
                int i = 0;
                new Thread(() -> { i = 5; }).start();   // 线程A
                System.out.println(i);                  // 主线程

            分析：主线程打印时，线程A 可能还没执行（无 hb 关系），i 可能是 0 也可能是 5。
            修正：加 join() → 规则5生效，保证 i = 5。
                 或用 volatile / AtomicInteger。

            ---------- 关键理解 ----------
            happens-before 不是「代码执行顺序」，而是「内存可见性保证」：
            如果 A hb B，则 A 的所有内存写入对 B 都可见，且 A 不会被重排到 B 之后。

            ---------- as-if-serial 语义 ----------
            单线程内，不管怎么重排序，都不能改变程序的执行结果。
            但多线程之间没有这个保证 —— 这就是并发 bug 的根源。
            ============================================================
            """);

为什么 (x=0, y=0) 是不可能的（如果没有重排序）？

  线程1                      线程2
  a = 1;         1          b = 1;         3
  x = b;         2          y = a;         4

  按顺序执行的所有可能：
    T1先跑完 -> a=1, x=b(此时b可能0或1), b=1, y=a=1
      -> 可能是 (x=0, y=1) 或 (x=1, y=1)
    T2先跑完 -> b=1, y=a(此时a可能0或1), a=1, x=b=1

1程序顺序规则同一线程内，前面的操作 hb 后面的操作
2监视器锁规则对同一把锁的 unlock hb 后续的 lock
3volatile 变量规则对 volatile 的写 hb 后续的读
4线程启动规则Thread.start() hb 该线程内的所有操作
5线程终止规则线程内所有操作 hb 其他线程检测到它终止（join 返回）
6线程中断规则interrupt() hb 被中断线程检测到中断
7对象终结规则构造器结束 hb finalize() 开始
8传递性A hb B，B hb C 则 A hb C
Qhappens-before 的本质（一句话说透）
happens-before 不是「代码执行顺序」，而是「内存可见性保证」。
如果 A hb B，那么：① A 的所有内存写入对 B 都可见；② A 不会被重排序到 B 之后。
它是对程序员的一种承诺：只要你满足 hb 关系，就不用关心底层到底有没有重排序、缓存有没有同步——JVM 保证你能看到正确的结果。

而单线程内的重排序自由，是由 as-if-serial 语义保证的：不管怎么重排序，单线程的执行结果不能变。但多线程之间没有这个保证——这就是并发 bug 的根源。

11.2 伪共享：一个不起眼的性能杀手

上面第 5 个实验的结果很震撼：只是给变量加了些「填充字段」，性能就提升了 4.3 倍。这就是伪共享（False Sharing）的威力。

CPU 缓存行是 64 字节。假设两个变量落在同一个缓存行里：

  内存（缓存行 = 64 字节）
  +----------------------------------------------------------+
  |  volatile long value1  |  volatile long value2  | 其他数据 |
  +----------------------------------------------------------+
        ^ 线程1 只改这个           ^ 线程2 只改这个

  逻辑上：两个线程操作完全无关的变量，不需要任何同步
  实际上：CPU 的缓存一致性协议以「缓存行」为最小单位

  线程1 修改 value1
      -> 该缓存行被标记为失效（Invalid）
      -> 线程2 的缓存中这行也失效了
      -> 线程2 必须重新从主内存加载整行
      -> 线程2 改 value2  -> 线程1 的缓存行又失效
      -> 来回拉锯，性能暴跌

解决方案：填充（Padding）让变量独占一个缓存行

  +----------------------------------------------------------+
  | p1,p2,p3,p4,p5,p6,p7 (7x8=56字节填充) | value | 填充     |
  +----------------------------------------------------------+
        ^ 填充字段，让 value 独占缓存行
  或者用 JDK8+ 的注解：@sun.misc.Contended

JDK 中的应用：
  * LongAdder 的 Cell 数组
  * Disruptor 的 Sequence
  * ConcurrentHashMap 的 CounterCell
  -> 这就是为什么这些类要写得那么「啰嗦」，每个字段周围都有一堆填充

    static final ReentrantLock RA = new ReentrantLock();
    static final ReentrantLock RB = new ReentrantLock();

    static void preventByTryLock() throws Exception {
        Thread t1 = new Thread(() -> transfer(RA, RB, "线程1"));
        Thread t2 = new Thread(() -> transfer(RB, RA, "线程2"));
        t1.start(); t2.start();
        t1.join(3000); t2.join(3000);
        System.out.println("  两个线程都能结束（tryLock 超时后释放已持有的锁，打破循环等待）");
    }

    static void transfer(ReentrantLock first, ReentrantLock second, String name) {
        boolean gotFirst = false, gotSecond = false;
        try {
            gotFirst = first.tryLock(200, TimeUnit.MILLISECONDS);
            if (gotFirst) {
                Thread.sleep(100);      // 模拟业务耗时，制造竞争窗口
                gotSecond = second.tryLock(200, TimeUnit.MILLISECONDS);
                if (gotSecond) {
                    System.out.println("  " + name + " 成功拿到两把锁");
                } else {
                    System.out.println("  " + name + " 拿不到第二把锁，主动放弃（避免死锁）");
                }
            }
        } catch (InterruptedException e) {
            Thread.currentThread().interrupt();
        } finally {
            if (gotSecond) second.unlock();
            if (gotFirst) first.unlock();
        }
    }

    static void sleep(long ms) {
        try { Thread.sleep(ms); } catch (InterruptedException e) { Thread.currentThread().interrupt(); }
    }

package course.ch13;

import java.util.concurrent.ArrayBlockingQueue;
import java.util.concurrent.BlockingQueue;
import java.util.concurrent.CountDownLatch;
import java.util.concurrent.atomic.AtomicLong;

/**
 * ch13_01 无锁队列原理：从阻塞队列到 RingBuffer（Disruptor 核心思想）
 *
 * 运行：java src/main/java/course/ch13/_01_RingBuffer.java
 */
public class _01_RingBuffer {

    /**
     * 单生产者单消费者（SPSC）无锁环形队列
     * 核心思想：用两个序号 + volatile 代替锁，生产者和消费者完全独立推进
     */
    static class SpscRingBuffer<T> {
        private final Object[] buffer;
        private final int mask;                  // 容量必须是 2 的幂，mask = capacity - 1
        private volatile long head = 0;          // 消费者序号（下一个要读的位置）
        private volatile long tail = 0;          // 生产者序号（下一个要写的位置）

        SpscRingBuffer(int capacity) {
            if (Integer.bitCount(capacity) != 1) throw new IllegalArgumentException("必须 2 的幂");
            this.buffer = new Object[capacity];
            this.mask = capacity - 1;
        }

        /** 生产者：不需要锁，只需要保证不与消费者读同一格 */
        public boolean publish(T item) {
            long currentTail = tail;
            if (currentTail - head >= buffer.length) {
                return false;                    // 队列满
            }
            buffer[(int) (currentTail & mask)] = item;
            tail = currentTail + 1;              // volatile 写，立刻对消费者可见
            return true;
        }

        /** 消费者 */
        @SuppressWarnings("unchecked")
        public T consume() {
            long currentHead = head;
            if (currentHead >= tail) {
                return null;                     // 队列空
            }
            T item = (T) buffer[(int) (currentHead & mask)];
            head = currentHead + 1;
            return item;
        }

        public long size() { return tail - head; }
    }

    public static void main(String[] args) throws Exception {
        System.out.println("===== 1) 无锁环形队列功能验证 =====");
        SpscRingBuffer<Integer> rb = new SpscRingBuffer<>(16);
        for (int i = 0; i < 10; i++) rb.publish(i);
        System.out.println("  放入 10 个后 size = " + rb.size());
        StringBuilder sb = new StringBuilder();
        Integer v;
        while ((v = rb.consume()) != null) sb.append(v).append(" ");
        System.out.println("  依次取出: " + sb);
        System.out.println("  取出后 size = " + rb.size());

        System.out.println("\n===== 2) 性能对比：无锁 RingBuffer vs 阻塞队列 =====");
        int items = 10_000_000;
        long t1 = testBlockingQueue(items);
        long t2 = testRingBuffer(items);
        System.out.printf("  ArrayBlockingQueue : %5d ms%n", t1);
        System.out.printf("  无锁 RingBuffer    : %5d ms  (快 %.1f 倍)%n", t2, (double) t1 / t2);

        System.out.println("""
            
            ============== 为什么 RingBuffer 这么快？==============
            1) 数组预先分配，永不 GC（无对象创建 = 无 GC 停顿）
            2) 序号单调递增，用位运算 & (capacity-1) 代替取模 %
            3) 生产者只用 volatile long tail，消费者只用 volatile long head
               → 没有锁竞争，没有 CAS 失败重试
            4) 内存顺序友好：消费者和生产者访问不同的缓存行（配合缓存行填充效果更好）

            ---------- 与 BlockingQueue 的本质区别 ----------
            ArrayBlockingQueue：
              put/take 都要先 lock()，队列满/空时线程 park 挂起（涉及内核态切换）
              → 每次操作有锁开销 + 可能的上下文切换开销

            无锁 RingBuffer：
              用「序号差值」判断满/空，无需挂起线程
              生产者只管推，消费者只管取，各自独立推进
              → 但要自己处理「队列满怎么办」和「没有数据怎么办」（自旋或降级）

            ---------- Disruptor 的三大杀手锏 ----------
            ① RingBuffer + 序号栅栏（SequenceBarrier）
               支持多消费者、消费者组、依赖链（如 handlerA → handlerB）
            ② 消除伪共享
               每个 Sequence 都做了缓存行填充（64 字节对齐）
            ③ 批量处理（Batch EventProcessor）
               一次取一批，摊薄序号 CAS 的成本
            → 官方基准测试：比 ArrayBlockingQueue 快一个数量级
            ======================================================
            """);
    }

    static long testBlockingQueue(int items) throws Exception {
        BlockingQueue<Integer> q = new ArrayBlockingQueue<>(1024);
        CountDownLatch done = new CountDownLatch(1);
        AtomicLong sum = new AtomicLong();
        Thread consumer = new Thread(() -> {
            try {
                for (int i = 0; i < items; i++) {
                    sum.addAndGet(q.take());
                }
            } catch (InterruptedException e) { Thread.currentThread().interrupt(); }
            done.countDown();
        });
        consumer.start();
        long s = System.nanoTime();
        for (int i = 0; i < items; i++) q.put(i);
        done.await();
        return (System.nanoTime() - s) / 1_000_000;
    }

    static long testRingBuffer(int items) throws Exception {
        SpscRingBuffer<Integer> rb = new SpscRingBuffer<>(1024);
        CountDownLatch done = new CountDownLatch(1);
        AtomicLong sum = new AtomicLong();
        Thread consumer = new Thread(() -> {
            long got = 0;
            while (got < items) {
                Integer v = rb.consume();
                if (v != null) {
                    sum.addAndGet(v);
                    got++;
                }
            }
            done.countDown();
        });
        consumer.start();
        long s = System.nanoTime();
        for (int i = 0; i < items; i++) {
            while (!rb.publish(i)) {
                Thread.onSpinWait();      // 队列满则自旋等待
            }
        }
        done.await();
        return (System.nanoTime() - s) / 1_000_000;
    }
}

  [OK] 极高吞吐、极低延迟的场景（金融、游戏、日志采集）
  [OK] 逻辑简单，容易证明正确性

package course.ch14;

import java.util.Arrays;
import java.util.Random;
import java.util.concurrent.*;
import java.util.stream.IntStream;

/**
 * ch14_01 ForkJoinPool：分治 + 工作窃取
 *
 * 运行：java src/main/java/course/ch14/_01_ForkJoin.java
 */
public class _01_ForkJoin {

    public static void main(String[] args) throws Exception {
        System.out.println("CPU 核心数 = " + Runtime.getRuntime().availableProcessors());

        System.out.println("\n===== 1) 手写 RecursiveTask：并行归并排序 =====");
        int[] arr = new Random(42).ints(20_000_000, 0, 100_000).toArray();
        int[] copy = arr.clone();

        long s1 = System.currentTimeMillis();
        Arrays.sort(copy);
        long serialMs = System.currentTimeMillis() - s1;

        long s2 = System.currentTimeMillis();
        ForkJoinPool pool = new ForkJoinPool();
        MergeSortTask task = new MergeSortTask(arr, 0, arr.length, 10_000);
        pool.invoke(task);
        long parallelMs = System.currentTimeMillis() - s2;

        System.out.printf("  Arrays.sort（单线程）: %5d ms%n", serialMs);
        System.out.printf("  ForkJoin 并行归并    : %5d ms%n", parallelMs);

        System.out.println("\n===== 2) ForkJoinPool 任务提交方式 =====");
        ForkJoinPool fjp = new ForkJoinPool(4);
        // execute / submit / invoke 三种
        System.out.println("  invoke(task)      → 提交并阻塞等待结果（最常用）");
        System.out.println("  submit(task)      → 提交并返回 ForkJoinTask，不阻塞");
        System.out.println("  execute(task)     → 提交无返回值任务");
        System.out.println("  pool.invokeAll(c) → 批量提交 Collection<Callable>");

        // 并行流底层就是 ForkJoinPool.commonPool
        long s3 = System.currentTimeMillis();
        long sum = IntStream.rangeClosed(1, 50_000_000)
                .asLongStream()
                .parallel()
                .sum();
        System.out.printf("%n  并行流求和 = %d，耗时 %d ms%n", sum, System.currentTimeMillis() - s3);
        System.out.println("  → parallelStream 默认使用 ForkJoinPool.commonPool()");
        System.out.println("    commonPool 线程数 = CPU 核数 - 1，被全 JVM 共享");
        System.out.println("""
                【生产注意】可以自定义池提交：
                    try (ForkJoinPool custom = new ForkJoinPool(32)) {
                        long r = custom.submit(() ->
                            list.parallelStream().map(...).collect(...)).get();
                    }
                """);
        fjp.shutdown();
        pool.shutdown();

        System.out.println("""
            
            ============== ForkJoinPool 核心机制 ==============
            【1】分治（Divide and Conquer）
               把大任务 fork() 拆成小任务，递归到足够小就 compute() 直接算，
               然后 join() 合并结果。阈值（threshold）很关键：
                 太大 → 拆得不够，并行度低
                 太小 → 任务太碎，调度开销超过收益

            【2】工作窃取（Work-Stealing）—— 它的灵魂
               每个工作线程有自己的一条双端队列（Deque）：
                 - 自己的任务从队头取（LIFO，符合栈式递归的局部性）
                 - 空闲时从别人的队尾「偷」任务（FIFO，偷大任务粒度）
               优点：负载自动均衡，不会出现「一个线程忙死，其他闲着」

               为什么自己用 LIFO，偷别人用 FIFO？
                 因为递归拆分的任务里，越靠后拆出来的越「大」，
                 偷大的能一次偷到更多工作量，减少窃取次数（降低竞争）。

            【3】与 ThreadPoolExecutor 的区别
               ThreadPoolExecutor：共享一条任务队列，所有线程抢同一个队列头
                                   → 队列头是热点，需要加锁/CAS
               ForkJoinPool      ：每个线程一条队列，减少竞争，支持窃取

            【4】适用场景
               CPU 密集型的分治计算：排序、归并、树遍历、大数组聚合
               不适合：IO 密集（线程会被阻塞，无法窃取走阻塞）
                       任务粒度极细（调度开销大于收益）

            【5】ForkJoinTask 三个子类
               RecursiveAction ：无返回值
               RecursiveTask<V>：有返回值（本项目演示）
               CountedCompleter ：JDK8+，更灵活，CompletableFuture 底层用到
            ====================================================
            """);
    }

    /** 并行归并排序 */
    static class MergeSortTask extends RecursiveTask<int[]> {
        private final int[] arr;
        private final int lo, hi;
        private final int threshold;

        MergeSortTask(int[] arr, int lo, int hi, int threshold) {
            this.arr = arr; this.lo = lo; this.hi = hi; this.threshold = threshold;
        }

        @Override
        protected int[] compute() {
            if (hi - lo <= threshold) {
                // 足够小，直接串行排序（避免任务过碎）
                int[] sub = Arrays.copyOfRange(arr, lo, hi);
                Arrays.sort(sub);
                return sub;
            }
            int mid = (lo + hi) >>> 1;
            MergeSortTask left = new MergeSortTask(arr, lo, mid, threshold);
            MergeSortTask right = new MergeSortTask(arr, mid, hi, threshold);

            left.fork();                       // 异步提交左半部分
            int[] rightResult = right.compute(); // 当前线程算右半部分（不浪费）
            int[] leftResult = left.join();     // 等左半部分

            return merge(leftResult, rightResult);
        }

        private int[] merge(int[] a, int[] b) {
            int[] r = new int[a.length + b.length];
            int i = 0, j = 0, k = 0;
            while (i < a.length && j < b.length) r[k++] = a[i] <= b[j] ? a[i++] : b[j++];
            while (i < a.length) r[k++] = a[i++];
            while (j < b.length) r[k++] = b[j++];
            return r;
        }
    }

工作窃取（Work-Stealing）—— ForkJoinPool 的灵魂：

  每个工作线程有自己的一条双端队列（Deque）：

    线程1 的队列                    线程2 的队列
  +------------------+          +------------------+
  |  队尾 [任务J][任务K] |          |  队尾 [空]        |
  |                  |          |                  |
  |  队头 [任务A][任务B] |          |  队头 [空]        |
  +------------------+          +------------------+
        ^                              ^
     自己从队头取                   空闲了！
     （LIFO，栈式）                     |
                                       |  从别人队尾「偷」
                                       +--------------> 偷任务J

  为什么自己用 LIFO，偷别人用 FIFO？
    递归拆分的任务里，越靠后拆出来的任务粒度越「大」（子任务还没被细分）。
    偷大的 -> 一次偷到更多工作量 -> 减少窃取的次数 -> 降低竞争。

  为什么比 ThreadPoolExecutor 快？
    ThreadPoolExecutor：所有线程抢同一条队列的头部
                        -> 队列头是热点，需要加锁/CAS，竞争激烈
    ForkJoinPool：每个线程一条队列，互不干扰
                  -> 只在「偷」的时候才有跨线程操作

  | CountedCompleter    | 更灵活，CompletableFuture 底层用到  |
  +---------------------+------------------------------------+

package course.ch16;

import java.util.*;
import java.util.concurrent.*;
import java.util.concurrent.atomic.*;
import java.util.concurrent.locks.ReentrantLock;

/**
 * ch16 综合实战：三个大厂级场景
 *
 * 场景一：高并发秒杀扣减库存（超卖防控）
 * 场景二：分布式限流器（令牌桶）
 * 场景三：多级缓存 + 缓存击穿防护
 *
 * 运行：java src/main/java/course/ch16/_01_SeckillStock.java
 */
public class _01_SeckillStock {

    // ============================================================
    // 场景一：秒杀库存扣减 —— 四种方案的演进
    // ============================================================
    static class StockService {
        private int stock = 100;                               // 方案1：裸 int
        private volatile int vStock = 100;                      // 方案2：volatile（无效）
        private int sStock = 100;                               // 方案3：synchronized
        private final AtomicInteger aStock = new AtomicInteger(100);  // 方案4：CAS
        private int lStock = 100;                               // 方案5：Lock
        private final ReentrantLock lock = new ReentrantLock();

        // 方案1：非线程安全
        public boolean deduct1() {
            if (stock > 0) { stock--; return true; }
            return false;
        }

        // 方案2：volatile 无效（check-then-act 不是原子操作）
        public boolean deduct2() {
            if (vStock > 0) { vStock--; return true; }
            return false;
        }

        // 方案3：synchronized（有效但性能一般）
        public synchronized boolean deduct3() {
            if (sStock > 0) { sStock--; return true; }
            return false;
        }

        // 方案4：CAS 无锁自旋 —— 秒杀场景首选（注意加失败重试上限防活锁）
        public boolean deduct4() {
            for (int retry = 0; retry < 100; retry++) {
                int cur = aStock.get();
                if (cur <= 0) return false;
                if (aStock.compareAndSet(cur, cur - 1)) return true;
            }
            return false;
        }

        // 方案5：Lock
        public boolean deduct5() {
            lock.lock();
            try {
                if (lStock > 0) { lStock--; return true; }
                return false;
            } finally { lock.unlock(); }
        }

        public int getRemaining(int scheme) {
            return switch (scheme) {
                case 1 -> stock; case 2 -> vStock; case 3 -> sStock;
                case 4 -> aStock.get(); case 5 -> lStock; default -> -1;
            };
        }
    }

    public static void main(String[] args) throws Exception {
        System.out.println("========== 场景一：秒杀库存扣减（库存 100，200 个线程抢）==========");
        int threads = 200, initialStock = 100;

        for (int scheme = 1; scheme <= 5; scheme++) {
            final int s = scheme;
            AtomicInteger success = new AtomicInteger();
            CountDownLatch start = new CountDownLatch(1);
            CountDownLatch end = new CountDownLatch(threads);
            // 每次用全新实例，并且用「同一个实例被多轮并发」放大竞态
            StockService svc = new StockService();

            for (int i = 0; i < threads; i++) {
                new Thread(() -> {
                    try {
                        start.await();
                        // 每个线程多尝试几轮，显著放大非原子操作的竞态窗口
                        for (int k = 0; k < 200; k++) {
                            boolean ok = switch (s) {
                                case 1 -> svc.deduct1();
                                case 2 -> svc.deduct2();
                                case 3 -> svc.deduct3();
                                case 4 -> svc.deduct4();
                                default -> svc.deduct5();
                            };
                            if (ok) success.incrementAndGet();
                        }
                    } catch (InterruptedException e) { Thread.currentThread().interrupt(); }
                    finally { end.countDown(); }
                }).start();
            }
            start.countDown();
            end.await();

            int remaining = svc.getRemaining(s);
            int soldCount = initialStock - remaining;
            boolean correct = (remaining >= 0) && (soldCount == initialStock)
                              && (success.get() == initialStock);
            String status = correct ? "[正确]" : "[超卖/错误]";

    static class TokenBucketRateLimiter {
        private final long capacity;          // 桶容量
        private final long ratePerSec;        // 每秒补充令牌数
        private double tokens;                // 当前令牌数
        private long lastRefillNanos;
        private final ReentrantLock lock = new ReentrantLock();

        TokenBucketRateLimiter(long capacity, long ratePerSec) {
            this.capacity = capacity;
            this.ratePerSec = ratePerSec;
            this.tokens = capacity;
            this.lastRefillNanos = System.nanoTime();
        }

        public boolean tryAcquire() {
            lock.lock();
            try {
                refill();
                if (tokens >= 1) {
                    tokens -= 1;
                    return true;
                }
                return false;
            } finally { lock.unlock(); }
        }

        private void refill() {
            long now = System.nanoTime();
            long elapsed = now - lastRefillNanos;
            if (elapsed <= 0) return;
            double add = elapsed / 1_000_000_000.0 * ratePerSec;
            if (add > 0) {
                tokens = Math.min(capacity, tokens + add);
                lastRefillNanos = now;
            }
        }
    }

    static void rateLimiterDemo() throws Exception {
        TokenBucketRateLimiter limiter = new TokenBucketRateLimiter(10, 50);  // 容量10，50 QPS
        AtomicInteger passed = new AtomicInteger(), rejected = new AtomicInteger();

        // 模拟 1 秒内 300 个请求
        long start = System.currentTimeMillis();
        Thread[] ts = new Thread[300];
        for (int i = 0; i < ts.length; i++) {
            ts[i] = new Thread(() -> {
                if (limiter.tryAcquire()) passed.incrementAndGet();
                else rejected.incrementAndGet();
            });
            ts[i].start();
        }
        for (Thread t : ts) t.join();
        long cost = System.currentTimeMillis() - start;

    static class CacheWithSingleFlight {
        private final ConcurrentHashMap<String, String> cache = new ConcurrentHashMap<>();
        private final ConcurrentHashMap<String, CompletableFuture<String>> inflight = new ConcurrentHashMap<>();
        private final AtomicInteger dbCalls = new AtomicInteger();

        /** 关键：同一个 key 的并发请求只查一次 DB */
        public String get(String key) throws Exception {
            String cached = cache.get(key);
            if (cached != null) return cached;

            // computeIfAbsent 保证只有一个线程创建 Future
            CompletableFuture<String> future = inflight.computeIfAbsent(key, k -> {
                CompletableFuture<String> f = new CompletableFuture<>();
                // 异步去加载
                CompletableFuture.runAsync(() -> {
                    try {
                        String value = loadFromDb(k);        // 模拟查库
                        cache.put(k, value);
                        f.complete(value);
                    } catch (Exception e) {
                        f.completeExceptionally(e);
                    } finally {
                        inflight.remove(k);
                    }
                });
                return f;
            });
            return future.get(3, TimeUnit.SECONDS);
        }

        /** 模拟慢查询 */
        private String loadFromDb(String key) {
            dbCalls.incrementAndGet();
            try { Thread.sleep(300); } catch (InterruptedException e) { Thread.currentThread().interrupt(); }
            return "DB值[" + key + "]";
        }

        public int dbCallCount() { return dbCalls.get(); }
    }

    static void cacheBreakdownDemo() throws Exception {

        System.out.println("""

                 原因：热点数据 TTL 到期
                 解决：① 互斥锁重建（本项目演示的单飞模式）

                 解决：① TTL 加随机值（如 30min + random(0,5min)）
                       ② 多级缓存（本地 Caffeine + Redis）
                       ③ Redis 高可用（哨兵/集群）

            【Q1】说说 Java 内存模型（JMM）？
            ▸ 考察意图：是否理解「规范」和「实现」的区别。
            ▸ 标准答案：
              JMM 是一个抽象规范，不是物理内存结构。它规定了：
              ① 所有变量存主内存，每个线程有自己的工作内存（抽象概念，
                 实际对应 CPU 寄存器 + 缓存 + 编译器优化）
              ② 线程对变量的操作必须在工作内存中进行，不能直接读写主内存
              ③ 定义了 8 种原子操作：lock/unlock/read/load/use/assign/store/write
              ④ 核心目的：屏蔽不同硬件和操作系统的内存访问差异，
                 让 Java 程序在各种平台上有一致的并发语义
            ▸ 加分点：主动提「JMM 解决的是可见性、有序性、原子性三个问题」，
              并说明原子性只保证基本类型的读写（long/double 在 32 位 JVM 上可能不原子，
              但 volatile 修饰的 long/double 是原子的）。
            ▸ 追问链：JMM 和 CPU 缓存一致性协议（MESI）什么关系？
                      → JMM 是规范，MESI 是硬件实现的一种方式，JMM 不绑定具体协议。

            【Q2】volatile 的作用是什么？原理是什么？
            ▸ 标准答案：
              ① 保证可见性：写操作立即刷新到主内存，读操作从主内存读最新值
              ② 保证有序性：禁止指令重排序（通过内存屏障）
              ③ 不保证原子性：i++ 这类复合操作仍然不安全
              原理：
              - 汇编层面，volatile 写会加 lock 前缀指令
              - x86 上这条 lock 指令实际是 MFENCE 的效果，会：
                a) 将当前处理器缓存行写回内存
                b) 使其他 CPU 缓存的该内存地址失效（缓存一致性协议）
              - 同时在编译器和 CPU 层面插入内存屏障禁止重排序
            ▸ 加分点：能说出「四种内存屏障」和「volatile 写前插 StoreStore、
              写后插 StoreLoad」。
            ▸ 追问链：单例的双重检查锁为什么要加 volatile？
                      → 因为 new 对象的「初始化」和「赋值引用」可能重排序，
                        导致其他线程拿到未初始化完成的对象。

            【Q3】happens-before 规则有哪些？
            ▸ 标准答案：程序顺序、监视器锁、volatile 变量、线程启动、
              线程终止、线程中断、对象终结、传递性（8 条）。
            ▸ 加分点：强调 happens-before 是「可见性保证」而非「执行顺序」，
              并且它是对程序员的一种承诺：只要满足 hb 关系，
              你就可以放心地认为前面的写入对后面可见。

            【Q4】synchronized 的实现原理？锁升级过程？
            ▸ 标准答案（按层次答）：
              【Java 层】修饰方法时 ACC_SYNCHRONIZED 标志；
                        修饰代码块时 monitorenter/monitorexit 指令
              【JVM 层】基于 ObjectMonitor（C++ 实现），
                       核心字段：_owner、_EntryList、_WaitSet、_count
              【锁升级】无锁 → 偏向锁 → 轻量级锁 → 重量级锁
                - 偏向锁：Mark Word 记录线程 ID，同一线程进入无需 CAS
                - 轻量级锁：CAS 把 Mark Word 指向线程栈的 Lock Record，

                - 重量级锁：自旋失败/竞争激烈，Mark Word 指向 ObjectMonitor，

               所以现在面试更应关注轻量级锁和重量级锁。」
            ▸ 追问链：为什么锁升级不可逆？→ 撤销成本高，且锁定竞争程度通常是持续的。

            【Q6】讲一下 AQS 的原理？
            ▸ 标准答案（结构化回答）：
              【是什么】AbstractQueuedSynchronizer，一个抽象同步器框架
              【核心三要素】
                ① volatile int state：同步状态，语义由子类定义
                   - ReentrantLock：state = 重入次数
                   - Semaphore：state = 剩余许可数
                   - CountDownLatch：state = 剩余计数
                   - ReentrantReadWriteLock：高16位读锁数 + 低16位写锁数
                ② CLH 变体的双向队列：存放获取失败的线程节点（Node）
                ③ 模板方法：tryAcquire/tryRelease/tryAcquireShared/tryReleaseShared
              【工作流程（以独占锁为例）】
                acquire() → tryAcquire() 成功则返回
                          → 失败则 addWaiter() 入队
                          → acquireQueued() 在队列中自旋 + park
                释放时 release() → tryRelease() → unparkSuccessor() 唤醒后继
              【Node 的关键字段】
                waitStatus：CANCELLED(1)/SIGNAL(-1)/CONDITION(-2)/PROPAGATE(-3)
                prev/next/thread：队列节点信息
            ▸ 加分点：主动说明「为什么用双向队列」
              → 因为节点取消时需要能把自己从队列中摘掉，
                需要访问前驱节点，所以必须双向。

            【Q7】ReentrantLock 的公平锁和非公平锁区别？为什么默认非公平？
            ▸ 标准答案：
              公平锁：tryAcquire 里先 hasQueuedPredecessors() 检查是否有前驱，
                     有则直接失败去排队 → 严格 FIFO
              非公平锁：直接 CAS 抢，抢到就执行 → 允许插队
              默认非公平的原因：公平锁每次都要唤醒队头线程（上下文切换开销），
                              而非公平锁给了「刚释放锁的线程立刻重入」的机会，
                              吞吐量更高。实测差距可达数倍。
            ▸ 加分点：非公平锁不会导致饥饿，因为队头线程仍会被唤醒，
                        只是可能在唤醒的过程中被刚到的线程抢走一次。

            【Q8】线程池的核心参数和执行流程？
            ▸ 标准答案：背七大参数 + 四步流程（见 ch07_01）。
            ▸ 加分点（这是拉开差距的地方）：

              ② 指出「无界队列导致 maximumPoolSize 失效」这个经典坑
              ③ 主动说阿里规范：禁用 Executors，手写 ThreadPoolExecutor

            【Q9】线程池大小怎么设置？
            ▸ 标准答案：
              CPU 密集：N + 1
              IO 密集：2N（或根据阻塞系数）
              精确公式：线程数 = N × (1 + 等待时间/计算时间)
            ▸ 加分点（超越八股）：
              「但生产环境更推荐『压测 + 动态调整』：
               先按公式给初值，再通过压测找最优值，
               最后接入配置中心实现运行时热更新（setCorePoolSize）。
               因为公式里的等待时间、计算时间很难准确测量，
               而且业务流量会变化。」

            【Q10】线程池里的任务抛异常了会怎样？
            ▸ 标准答案：
              - execute() 提交：异常会打印到控制台，触发 UncaughtExceptionHandler，
                工作线程会被替换重建
              - submit() 提交：异常被封装进 Future，只有 get() 时才抛 ExecutionException，
                不 get 就静默吞掉（最坑）
            ▸ 加分点：给出三种兜底方案
              ① 任务内部 try-catch
              ② 重写 afterExecute()
              ③ 用 submit 后统一收集 Future 并检查

            【Q11】ConcurrentHashMap 如何保证线程安全？JDK7 和 JDK8 的区别？
            ▸ 标准答案：
              JDK7：Segment 分段锁（继承 ReentrantLock），默认 16 段，
                    并发度固定不可变；数组+链表
              JDK8：取消 Segment，改为「CAS + synchronized 锁单个桶头节点」；
                    数组+链表+红黑树（链表 ≥8 且容量 ≥64 时树化）；
                    size() 用 baseCount + CounterCell[] 分段计数；
                    扩容支持多线程协同（helpTransfer）
            ▸ 加分点：解释为什么放弃分段锁 ——
              段数固定意味着并发度上限固定，且段间负载不均；
              桶级锁粒度更细，且 synchronized 在 JDK8 后做了大量优化，
              在低竞争场景下性能接近 CAS。
            ▸ 追问链：为什么 key 和 value 不能为 null？
                      → 无法区分「key 不存在」和「key 存在但值为 null」，
                        这在并发场景下会造成歧义（HashMap 允许因为可以用
                        containsKey 判断，但 CHM 为了性能不做双重查找）。

            【Q12】ThreadLocal 会内存泄漏吗？怎么避免？
            ▸ 标准答案：
              会。引用链是 Thread → ThreadLocalMap → Entry → value（强引用）。
              Entry 的 key 是 ThreadLocal 的弱引用，ThreadLocal 被回收后
              key 变成 null，但 value 仍被 Thread 强引用，
              线程池场景下线程长期存活 → value 无法回收 → 泄漏。
              避免：① 用 private static final 声明
                   ② 用完在 finally 里 remove()
            ▸ 加分点：解释「为什么用弱引用」
              → 用强引用会更糟（连 ThreadLocal 对象都无法回收）；
                弱引用至少把泄漏范围缩小到 value，
                且 set/get/remove 会顺带清理 key=null 的 Entry。
            ▸ 追问链：怎么跨线程传递上下文？
                      → InheritableThreadLocal（线程池下失效）或
                        TransmittableThreadLocal（TTL，正确方案）。

import org.openjdk.jmh.annotations.*;
import org.openjdk.jmh.runner.Runner;
import org.openjdk.jmh.runner.options.Options;
import org.openjdk.jmh.runner.options.OptionsBuilder;

import java.util.concurrent.TimeUnit;
import java.util.concurrent.atomic.AtomicLong;
import java.util.concurrent.atomic.LongAdder;

/**
 * ch18_01 JMH 基准测试 —— 并发性能优化的唯一可靠手段
 *
 * 为什么不能手写 System.nanoTime() 测性能？
 *   ① JIT 预热不充分：前几万次执行是解释模式，比稳态慢几十倍
 *   ② 死代码消除：JIT 发现结果没被使用，直接把整个循环删掉
 *   ③ 常量折叠：编译期就能算出的结果直接替换成常量
 *   ④ 循环展开、分支预测、CPU 频率调节都会干扰结果
 *   JMH 通过预热轮次、Blackhole、@Fork 等机制系统性地解决这些问题。
 *
 * 运行（Maven 工程）：
 *   mvn clean package
 *   java -jar target/jmh-benchmarks.jar
 *   或只跑某个类：
 *   java -jar target/jmh-benchmarks.jar ".*AdderBenchmark.*"
 */
@BenchmarkMode({Mode.Throughput, Mode.AverageTime})
@OutputTimeUnit(TimeUnit.NANOSECONDS)
@Warmup(iterations = 3, time = 1, timeUnit = TimeUnit.SECONDS)
@Measurement(iterations = 5, time = 1, timeUnit = TimeUnit.SECONDS)
@Fork(1)
@State(Scope.Benchmark)
public class _01_JmhBenchmark {

    // ============================================================
    // 实验一：AtomicLong vs LongAdder 高并发累加
    // ============================================================
    @Benchmark
    @Threads(16)
    public long atomicLong(AtomicState s) {
        return s.atomicLong.incrementAndGet();
    }

    @Benchmark
    @Threads(16)
    public long longAdder(AdderState s) {
        s.longAdder.increment();
        return s.longAdder.sum();
    }

    // ============================================================
    // 实验二：不同锁策略的计数器
    // ============================================================
    @Benchmark
    @Threads(16)
    public long synchronizedCounter(SyncState s) {
        synchronized (s.lock) { s.value++; }
        return s.value;
    }

    @Benchmark
    @Threads(16)
    public long lockCounter(LockState s) {
        s.lock.lock();
        try { s.value++; } finally { s.lock.unlock(); }
        return s.value;
    }

    // ============================================================
    // 实验三：伪共享的影响
    // ============================================================
    @Benchmark
    @Threads(4)
    public void falseSharing(FalseSharingState s) {
        for (int i = 0; i < 100; i++) {
            s.unpadded[s.threadIndex()].value++;
        }
    }

    @Benchmark
    @Threads(4)
    public void padding(PaddedState s) {
        for (int i = 0; i < 100; i++) {
            s.padded[s.threadIndex()].value++;
        }
    }

    @State(Scope.Benchmark)
    public static class AtomicState {
        final AtomicLong atomicLong = new AtomicLong();
    }

    @State(Scope.Benchmark)
    public static class AdderState {
        final LongAdder longAdder = new LongAdder();
    }

    @State(Scope.Benchmark)
    public static class SyncState {
        final Object lock = new Object();
        long value;
    }

    @State(Scope.Benchmark)
    public static class LockState {
        final java.util.concurrent.locks.ReentrantLock lock =
                new java.util.concurrent.locks.ReentrantLock();
        long value;
    }

    @State(Scope.Benchmark)
    public static class FalseSharingState {
        final Shared[] unpadded = new Shared[8];
        {
            for (int i = 0; i < unpadded.length; i++) unpadded[i] = new Shared();
        }
        int threadIndex() {
            return (int) (Thread.currentThread().threadId() % unpadded.length);
        }
    }

    @State(Scope.Benchmark)
    public static class PaddedState {
        final PaddedCell[] padded = new PaddedCell[8];
        {
            for (int i = 0; i < padded.length; i++) padded[i] = new PaddedCell();
        }
        int threadIndex() {
            return (int) (Thread.currentThread().threadId() % padded.length);
        }
    }

    public static class Shared { volatile long value; }

    /** 缓存行填充：64 字节 = 8 个 long */
    public static class PaddedCell {
        volatile long p1, p2, p3, p4, p5, p6, p7;
        volatile long value;
    }

为什么不能手写 System.nanoTime() 测性能？

  1 JIT 预热不充分
     前几万次执行走解释器，比 JIT 编译后的机器码慢几十倍。
     不预热就测，你测的是「解释执行速度」而不是「生产速度」。

  2 死代码消除（Dead Code Elimination）
     如果计算结果没被使用，JIT 会把整个循环直接删掉。
     你测出的「零耗时」其实是代码被优化没了。

  3 常量折叠（Constant Folding）
     编译期能算出来的结果，直接替换成常量。

  4 循环展开优化
     空循环体会被 JIT 直接优化掉。

  5 CPU 频率调节 / 线程调度干扰
     单次测量噪声太大，必须多次迭代取统计值。

JMH 通过预热轮次、Blackhole、@Fork 独立进程等机制，系统性地解决了这些问题。

  java -jar target/jmh-benchmarks.jar
  # 或只跑某个类
  java -jar target/jmh-benchmarks.jar ".*JmhBenchmark.*"
注解作用
@Benchmark标记被测方法

@Warmup预热轮次（不计入结果）

@Param参数化测试

18.2 并发性能优化的完整方法论

第 0 步：先测量，不要猜！
        没有 profiling 的优化都是玄学。
        工具：JMH（微基准）/ async-profiler（火焰图）/
             arthas（线上诊断）/ JFR（JVM 内置，零开销）

第 1 步：找瓶颈 —— 是 CPU 打满？锁竞争？还是 GC？
        +- CPU 打满 -> top -H -p <pid> 找热点线程 -> jstack 看栈
        +- 锁竞争   -> arthas 的 monitor 命令看锁等待
        +- GC 频繁  -> jstat -gcutil <pid> 1s

第 2 步：按「性价比」排序优化手段（这个顺序很重要）：
        +----------------------------------------------------+
        | 1 消除共享（最重要）                                |
        |   -> 线程本地化、无状态设计、不可变对象             |
        |   -> 这是唯一能「根治」并发问题的方法               |
        +----------------------------------------------------+
        | 2 减少临界区                                        |
        |   -> 缩小锁范围（只锁必要的代码）                   |
        |   -> 读写分离（读多写少用读写锁/COW）               |
        +----------------------------------------------------+
        | 3 降低锁竞争                                        |
        |   -> 分段锁、CAS、无锁数据结构                      |
        |   -> 缓存行填充（消除伪共享）                       |
        +----------------------------------------------------+
        | 4 减少内存分配                                      |
        |   -> 对象池、预分配、避免装箱、避免日志字符串拼接   |
        +----------------------------------------------------+
        | 5 最后才考虑：换锁类型 / 调 JVM 参数                |
        +----------------------------------------------------+

第 3 步：每次只改一个变量，改完重新测量，确认真的有提升。

第 4 步：警惕「过早优化」——
        先保证正确，再保证可读，最后才优化。
        Knuth 的原话是「过早优化是万恶之源」，
        但完整的表述是「在 97% 的情况下不成熟的优化是万恶之源，
        但我们不应放过那关键的 3%」——前提是你先通过测量找到了那 3%。

一个真实的优化案例（面试可以讲）：
  现象：订单查询接口 P99 从 50ms 涨到 800ms
  定位：
    1 arthas 的 trace 命令发现 80% 时间在获取本地缓存锁
    2 代码用 synchronized 修饰了整个方法，包括了序列化操作
  优化：
    1 缩小锁范围，只锁真正的共享结构修改
    2 改用 ConcurrentHashMap（原先用 HashMap + synchronized）
    3 热点数据加 Caffeine 本地缓存
  结果：P99 降到 60ms，QPS 从 2000 提升到 8000
