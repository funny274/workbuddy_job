01为什么需要泛型：一个 Object 容器的血案

1.1 没有泛型的年代

Java 5 之前，集合框架只能存 Object。任何类型都能塞进去，取出来必须自己强转：

// JDK 1.4 风格：List 内部就是 Object[]
List list = new ArrayList();
list.add("hello");
list.add(Integer.valueOf(123));   // 手写装箱
list.add(new Date());

String s = (String) list.get(1);  // 编译通过，运行时炸
// java.lang.ClassCastException: java.lang.Integer cannot be cast to java.lang.String

这段代码暴露了三个致命问题：

类型不安全

编译器完全不知道你往里放什么、取什么。错误从「编译期」推迟到了「生产环境的某个凌晨」。

强制转换噪音

每个 get() 都要加一个强转。代码里塞满了 (String)、(User)，读起来全是噪音。

无自文档性

看到一个 List 参数，你得翻遍调用方才能猜出里面装的是用户还是订单。

1.2 泛型的三大收益

List<String> list = new ArrayList<>();
list.add("hello");
list.add(123);          // ❌ 编译错误：不兼容的类型。错误被提前了！

String s = list.get(0); // ✅ 不需要强转，编译器已经知道是 String
收益一句话解释工程价值
类型安全把类型错误的发现时间从运行时提前到编译期缺陷成本：编译期 1 倍 vs 生产环境 100 倍
消除强转编译器自动插入正确的类型转换代码可读性显著提升，减少 ClassCastException
泛型算法一套算法适配多种类型，且保持类型信息Collections.sort、Stream、框架的通用能力

1.3 关键设计决策：为什么 Java 选择了「擦除」

这是理解后续所有「别扭之处」的钥匙，必须讲清楚。

2004 年 Java 5 引入泛型时，Sun 面临一个硬约束：世界上已经存在海量的 Java 代码和已编译的 class 文件，不能因为引入泛型就把它们全部作废。这个约束在 JSR 14 里被称为 迁移兼容性（Migration Compatibility）。

两条技术路线

路线 A：具化泛型（Reified Generics）——像 C# 那样，运行时真的存在 List<String> 和 List<Integer> 两个不同的类型，各有自己的 Class 对象。类型信息保留到运行时。

路线 B：类型擦除（Type Erasure）——泛型只是编译期的「类型检查 + 自动插桩」。编译完成后，List<String> 就是 List，和老的 class 文件二进制兼容。

Java 选了 B。代价是运行时拿不到泛型实参；收益是新老代码可以无缝混用——这正是 Java 生态能平滑演进二十年的原因之一。

所以你后面遇到的所有限制——不能 new T()、不能 instanceof List<String>、不能重载——都不是设计者疏忽，而是为兼容性付出的、经过权衡的代价。面试时能说出这一层，档次立刻不同。

02泛型基础语法全解

2.1 泛型类

把类型当作参数传给类。注意 T 只是一个占位符，它没有任何运行时实体：

public class Box<T> {
    private T value;                 // 字段类型可以是 T

    public Box(T value) { this.value = value; }

    public void set(T value) { this.value = value; }
    public T get() { return value; }

    public static void main(String[] args) {
        Box<String> b1 = new Box<>("hello");   // T 被实参化为 String
        Box<Integer> b2 = new Box<>(42);        // T 被实参化为 Integer
        String s = b1.get();                     // 无需强转
        Integer i = b2.get();
        System.out.println(b1.getClass() == b2.getClass());  // true！
    }
}
注意最后一行

b1.getClass() == b2.getClass() 输出 true。这是类型擦除最直接的证据：运行时 Box<String> 和 Box<Integer> 都是 同一个类 Box，只有一份字节码。

多个类型参数：

public class Pair<K, V> {
    private final K key;
    private final V value;
    public Pair(K key, V value) { this.key = key; this.value = value; }
    public K getKey() { return key; }
    public V getValue() { return value; }
}

Pair<String, Integer> p = new Pair<>("age", 30);

2.2 泛型接口

泛型接口是大厂框架里最常见的抽象手段。Repository<T, ID> 就是典型：

public interface Repository<T, ID> {
    T findById(ID id);
    List<T> findAll();
    void save(T entity);
    void deleteById(ID id);
}

// 使用时把类型参数「钉死」
public class UserRepository implements Repository<User, Long> {
    @Override public User findById(Long id) { return null; /* ... */ }
    @Override public List<User> findAll() { return List.of(); }
    @Override public void save(User entity) { }
    @Override public void deleteById(Long id) { }
}

两种实现风格，理解它们的差别很重要：

实现方式写法含义典型场景
固定实参class UserRepo implements Repository<User, Long>实现类就是某个具体类型业务 DAO
传递参数class BaseRepo<T, ID> implements Repository<T, ID>实现类保持泛型MyBatis-Plus 的 BaseMapper<T>

2.3 泛型方法（最容易搞混的部分）

泛型方法的类型参数声明在返回类型之前，位置极其关键：

// 类型参数 <T> 在修饰符之后、返回类型之前
public static <T> T firstOrNull(List<T> list) {
    return (list == null || list.isEmpty()) ? null : list.get(0);
}

// 多个类型参数的泛型方法
public static <K, V> Map<V, K> invert(Map<K, V> source) {
    Map<V, K> result = new HashMap<>();
    source.forEach((k, v) -> result.put(v, k));
    return result;
}
三个高频错误写法 
// ❌ 错误 1：<T> 写在返回类型之后 —— 这不是泛型方法
public static T first(List<T> list) { ... }

// ❌ 错误 2：静态方法直接用类的类型参数
public class Box<T> {
    public static T create() { ... }   // 编译错误！
    // 原因：静态成员属于类本身，不随实例的类型参数变化
}

// ✅ 正确：静态方法自己声明类型参数
public class Box<T> {
    public static <E> Box<E> create(E value) { return new Box<>(value); }
}

泛型方法与所在类是否为泛型类完全无关。这是面试常考点。一个普通类里也可以有泛型方法；一个泛型类里的方法也未必是泛型方法。判断标准只有一个：该方法自己有没有声明 <T>。

public class Utils {
    // 普通类中的泛型方法：类型参数 T 只在这个方法里生效
    public static <T extends Comparable<T>> T max(List<T> list) {
        T m = list.get(0);
        for (T t : list) if (t.compareTo(m) > 0) m = t;
        return m;
    }
}

2.6 原始类型（Raw Type）：一个必须理解的「逃生口」

不使用任何类型参数的泛型类型，叫原始类型：

List rawList = new ArrayList();      // Raw Type
List<String> typed = new ArrayList<>();  // Parameterized Type
Raw Type ≠ List<Object>

这是一个极其常见的误解。它们的区别在于：List<Object> 参与泛型检查，List（raw）会关闭所有泛型检查。

List<String> typed = new ArrayList<>();

List raw = typed;            // 赋值给 raw type：仅产生警告
raw.add(123);                // ⚠️ 编译通过（只警告），但污染了集合

String s = typed.get(0);     // 💥 ClassCastException 在别的代码里爆发

这就是所谓的堆污染（Heap Pollution），第 9 章会详述。Raw type 的可怕之处在于：它把编译期的类型安全网撕开了一个口子，而且错误会传染到看起来完全无辜的代码里。

什么时候必须用 raw type？只有三处：

  1. class 字面量：List.class（不能写 List<String>.class）
  2. instanceof 检查：obj instanceof List（不能写 instanceof List<String>）
  3. 与遗留（Java 5 之前）代码互操作

2.7 显式类型见证（Explicit Type Argument）

当编译器推断不出类型时，可以手工指定：

// 历史写法（Java 8 之前很常见）
List<String> empty = Collections.<String>emptyList();

// 注意语法：<String> 在方法名之前，紧跟在点号之后
// Java 8 起有了目标类型推断，多数情况可以省：
List<String> empty2 = Collections.emptyList();

真正需要手工见证的，是编译器拿不到类型线索的场景——也就是表达式没有「目标类型」可供反推的时候：

// 语法：<具体类型> 写在方法名之前
List<String> a = Collections.<String>emptyList();
Map<String, Integer> b = Collections.<String, Integer>emptyMap();   // 多个类型参数

// 目标类型推断（Java 8+）覆盖了绝大多数情况 —— 从左侧变量或方法形参反推
List<String> c = Collections.emptyList();     // ✅ 从 c 的声明推断 T = String
process(Collections.emptyList());              // ✅ 从 process(List<String>) 的形参推断

// 一旦失去了赋值目标或形参上下文，推断只能退化为 Object
System.out.println(Collections.emptyList());   // T = Object（这里恰好无所谓）
Object any = Collections.emptyList();          // T = Object

// 此时若确实需要特定类型，显式见证就是唯一的兜底手段
List<String> d = Collections.<String>emptyList();
顺带澄清一个常被混淆的点

list.toArray() 返回 Object[] 不是「类型推断失败」——它的签名本来就是这样。Object[] toArray() 和 <T> T[] toArray(T[] a) 是两个不同的重载，后者要求你传一个数组进去充当「类型载体」。这个惯用法（以及为什么是 new T[0] 而不是 new T[size]）在第 9 章会专门讲。

小结：本章需要形成肌肉记忆的四条
  • 泛型方法的 <T> 在返回类型之前，静态方法必须自己声明
  • Box<String>.class == Box<Integer>.class —— 擦除的体现
  • Raw Type 会关闭泛型检查，是堆污染的入口
  • 菱形 <> 是首选，显式类型见证是兜底手段

03类型擦除：Java 泛型的全部秘密

一句话定义

类型擦除（Type Erasure）：Java 编译器在把源码编译成字节码时，会丢弃所有泛型类型实参，把类型变量替换成它的边界（无界则替换为 Object），并在必要的地方插入强制类型转换。运行时，泛型「不存在」。

3.1 擦除的四条规则

#源码中的类型擦除后说明
1List<String>、Box<T>List、Box泛型实参被抹掉，只剩原始类型
2T（无界类型变量）Object没有边界就退化为 Object
3T extends NumberNumber擦除到最左侧边界
4T extends Comparable<T> & SerializableComparable多边界时只保留第一个（可以是类或接口）

规则 4 有个重要推论，而且它直接呼应了第 1 章的主题——边界的顺序会影响擦除结果，而擦除结果决定了方法签名的二进制形态。

JDK 里最著名的一个「多此一举」：Collections.max

翻 JDK 源码会发现 Collections.max 的签名长得很奇怪：

public static <T extends Object & Comparable<? super T>> T max(Collection<? extends T> coll)

第一个边界 Object 看起来完全多余——Comparable 本来就继承自 Object，写它干什么？答案是：为了二进制兼容。

  • JDK 1.4 时代，max 的签名是 public static Object max(Collection)
  • 泛型化时如果只写 <T extends Comparable<? super T>>，擦除结果是 Comparable，返回类型描述符就从 Ljava/lang/Object; 变成了 Ljava/lang/Comparable;
  • 描述符一变，所有已经编译好的调用方字节码都会在链接阶段找不到方法，直接抛 NoSuchMethodError
  • 加上 Object & 让擦除回退成 Object，二十年前编译的老字节码依然能正常链接

一个看似多余的写法，背后是整个 Java 生态的兼容包袱。这是「擦除决定一切」最精妙的注脚，也是 Joshua Bloch 在《Effective Java》里专门讨论这个签名的原因。

3.2 字节码实证：亲眼看到擦除

光看规则不够，我们反编译看真相。准备两个文件：

    public T get() { return value; }

// Main.java
public class Main {
    public static void main(String[] args) {
        Box<String> box = new Box<>();
        box.set("hello");
        String s = box.get();

3.3 由擦除导致的七大限制

这七条是大厂面试的绝对高频区，建议逐条背下「限制 + 原因 + 规避方案」三件套。

限制 1：不能实例化类型变量 —— new T() 非法

public class Factory<T> {
    public T create() {
        return new T();   // ❌ 编译错误：类型参数 T 不能被直接实例化
        // 原因：擦除后这行代码变成 new Object()，编译器不知道要 new 什么
    }
}

规避方案 A：传入 Class<T>（类型令牌）

public class Factory<T> {
    private final Class<T> type;
    public Factory(Class<T> type) { this.type = type; }

    public T create() throws Exception {
        return type.getDeclaredConstructor().newInstance();
    }
}

Factory<User> f = new Factory<>(User.class);
User u = f.create();

规避方案 B：传入工厂函数（更现代，推荐）

public class Factory<T> {
    private final Supplier<T> supplier;
    public Factory(Supplier<T> supplier) { this.supplier = supplier; }
    public T create() { return supplier.get(); }
}

Factory<User> f = new Factory<>(User::new);
Factory<List<String>> fl = new Factory<>(ArrayList::new);
方案 B 优于方案 A 的三个理由
  • 没有受检异常（Class.newInstance() 会抛 InstantiationException / IllegalAccessException）
  • 支持无默认构造器的类（可以传 () -> new User("default")）
  • 支持带类型参数的构造（ArrayList<String>::new 这种方案 A 做不到，因为 ArrayList<String>.class 不合法）

限制 2：不能创建泛型数组 —— new T[] / new List<String>[10] 非法

List<String>[] arr = new List<String>[10];  // ❌ 编译错误：泛型数组创建
T[] tArr = new T[10];                        // ❌ 编译错误
为什么禁止？因为数组是「运行时类型检查」的

数组在运行时知道自己的元素类型（String[].class 真的存在）。而擦除后 List<String>[] 会变成 List[]，此时下面这段代码就会出问题：

// 假设允许（实际上不允许）
List<String>[] lsa = new List<String>[10];
Object[] oa = lsa;                    // 数组协变，合法
List<Integer> li = new ArrayList<>();
oa[0] = li;                           // 💥 编译期无法拦截（擦除后都是 List）
String s = lsa[0].get(0);             // 💥 ClassCastException

所以编译器干脆在编译期就禁止你创建泛型数组，从源头堵死这个漏洞。

规避方案：用集合代替数组，或用通配符数组 + 强转

// 方案 A：用 List 代替数组（首选）
List<List<String>> lists = new ArrayList<>();

// 方案 B：确实需要数组时，用通配符 + 受控强转
@SuppressWarnings("unchecked")
List<String>[] arr = (List<String>[]) new List<?>[10];

// 方案 C：泛型方法里的数组（借助反射）
@SuppressWarnings("unchecked")
public static <T> T[] newArray(Class<T> type, int size) {
    return (T[]) java.lang.reflect.Array.newInstance(type, size);
}

限制 3：不能在 instanceof 中使用泛型实参

if (obj instanceof List<String>) { }   // ❌ 编译错误
if (obj instanceof List<?>) { }         // ✅ 通配符可以（无意义但合法）
if (obj instanceof List) { }            // ✅ Raw type 可以，但仍有警告

原因同样是擦除：运行时的 obj.getClass() 拿不到 <String>，这个判断无法执行。

限制 4：不能重载「擦除后签名相同」的方法

public class Holder {
    public void print(List<String> list) { }   // ❌
    public void print(List<Integer> list) { }  // ❌
    // 编译错误：name clash: print(List<Integer>) and print(List<String>)
    //          have the same erasure
}
一个容易踩的变体：泛型方法重载 
public class Holder {
    public <T> void print(List<T> list) { }
    public void print(List<Integer> list) { }   // ❌ 同样冲突
}

因为 <T> void print(List<T>) 擦除后就是 void print(List)，与 print(List<Integer>) 的擦除签名一致。

限制 5：类级别的类型参数不能用于静态成员

public class Box<T> {
    private static T instance;                        // ❌ 编译错误
    public static T getInstance() { return null; }    // ❌ 编译错误
}

原因：静态成员属于类，不属于某个实例。Box<String> 和 Box<Integer> 共享同一份静态区，那 instance 到底该是什么类型？无解，所以禁止。

同时也解释了为什么 Collection<E> 里没有静态的泛型方法，而 Collections（独立的工具类）里有。

限制 6：不能是基本类型

List<int> list = new ArrayList<int>();   // ❌ 编译错误
List<Integer> list2 = new ArrayList<>(); // ✅ 必须用包装类
这条限制的代价比想象中大

因为擦除后是 Object，而 Object 装不下 int，所以只能用包装类：每次存取都要装箱/拆箱。在高频场景（比如每秒百万次的大数据量循环）下，这个开销是真实存在的：

// 写入时装箱：1000 万个 int 变成 1000 万个 Integer 对象
List<Integer> list = new ArrayList<>();
for (int i = 0; i < 10_000_000; i++) {
    list.add(i);              // 隐式装箱：Integer.valueOf(i)
}

// 读取时拆箱：每次 get 都要调一次 intValue()
long sum = 0;
for (int i = 0; i < 10_000_000; i++) {
    sum += list.get(i);       // 隐式拆箱：Integer.intValue()
}

// 对照：换成原始类型数组，装箱拆箱开销全部消失
int[] arr = new int[10_000_000];

这是一道很好的面试延伸题：泛型不支持基本类型 → 用包装类 → 装箱开销 → 引出「为什么会有 IntStream、ToIntFunction、mapToInt」。这正是 JDK 8 引入原始类型特化流（primitive stream specialization）的动机之一。

限制 7：不能捕获或抛出类型变量的异常

public <T extends Exception> void run() {
    try {
        // ...
    } catch (T e) { }        // ❌ 编译错误：不能捕获类型变量
}

public class MyException<T> extends Throwable { }  // ❌ 泛型类不能继承 Throwable

泛型方法可以声明 throws T，但用处极其有限（调用方无法通过 catch 精确捕获）。实践中基本不用。

3.5 常见误解澄清（面试爱挖这些坑）

❌ 误解：运行时泛型信息全丢了

事实：类、方法、字段的声明处的泛型签名，以 Signature 属性的形式保留在 class 文件里（不是为了运行时使用，而是为了编译器在编译下游代码时能校验）。所以 getGenericReturnType() 能拿到 List<String>。丢失的只是对象实例上的实参。第 10 章细讲。

❌ 误解：List 就是 List<Object>

事实：两者编译产物相同，但语义完全不同。List<Object> 参与泛型检查（只能加 Object 及其子类，但读出来都是 Object）；List 关闭所有检查（可以加任何东西，读出即炸）。

❌ 误解：泛型有运行时性能损耗

事实：泛型本身零运行时开销（就是 Object + checkcast）。真正的开销来自装箱/拆箱和checkcast 的类型检查。前者的锅是「不支持基本类型」，不是泛型的锅。

❌ 误解：擦除是「为了省字节码空间」

事实：压缩体积只是副产品。真正的第一动机是二进制向后兼容——让 Java 5 编译的泛型代码能和 Java 1.4 的已编译代码无缝互调。

04桥接方法与字节码实证

这一章讲一个90% 的 Java 开发者不知道，但面试官一问就露底的知识点。它也是理解 AOP 代理、反射调用、MyBatis 方法解析等一系列生产问题的前提。

4.1 问题的起源：擦除破坏了「重写」

先看一段看起来很正常的代码：

public class Node<T> {
    private T data;
    public void setData(T data) { this.data = data; }
}

public class MyNode extends Node<Integer> {
    @Override
    public void setData(Integer data) {     // 意图：重写父类方法
        System.out.println("MyNode.setData: " + data);
    }
}

问题来了。擦除之后：

  • Node.setData 的签名是 setData(Object)
  • MyNode.setData 的签名是 setData(Integer)

参数类型不同，这是重载（overload），不是重写（override）！ 如果照这个逻辑运行，多态就失效了：

Node<Integer> node = new MyNode();
node.setData(42);   // 期望调用 MyNode.setData，实际会调用 Node.setData —— 输出丢失

但现实中这段代码运行正常，输出确实是 MyNode.setData: 42。为什么？

4.2 答案：编译器偷偷生成了一个桥接方法

桥接方法（Bridge Method）：编译器会在子类中自动合成一个与父类擦除后签名一致的方法，内部把调用转发给真正的实现。它是 synthetic 的（合成），在源码中不可见。

反编译 javap -c -p MyNode：

public class MyNode extends Node<java.lang.Integer> {
  public MyNode();
    Code:
       0: aload_0
       1: invokespecial #1    // Method Node."<init>":()V
       4: return

  public void setData(java.lang.Integer);       // 你写的那个
    Code:
       0: getstatic     #7    // Field java/lang/System.out:Ljava/io/PrintStream;
       3: invokedynamic #13   // makeConcatWithConstants
       8: invokevirtual #17   // PrintStream.println
      11: return

  public void setData(java.lang.Object);        // ★ 编译器合成的桥接方法
    Code:
       0: aload_0
       1: aload_1
       2: checkcast     #23   // class java/lang/Integer   ← 强转
       5: invokevirtual #25   // Method setData:(Ljava/lang/Integer;)V  ← 转发给真实现
       8: return
}
桥接方法做了什么

setData(Object) 是编译器凭空造出来的，它有且仅有两个动作：

  1. checkcast Integer —— 把 Object 转回 Integer
  2. invokevirtual setData(Integer) —— 转发给真正的实现

这样，通过父类引用 Node<Integer> 调用 setData(Object) 时，虚方法表会命中这个桥接方法，桥接方法再转给你的实现。多态被「修好」了。

4.3 桥接方法的触发条件

场景是否生成桥接方法说明
子类重写泛型父类的泛型方法，且实参不同是最常见，如上例
实现泛型接口的泛型方法是Comparable<T>、Comparator<T> 的实现类都是
协变返回类型是子类返回更具体的类型时
方法签名完全相同否无需桥接
非泛型类的重写否擦除前后一致

一个高频实例——实现 Comparable：

public class Person implements Comparable<Person> {
    private int age;
    @Override
    public int compareTo(Person o) { return Integer.compare(this.age, o.age); }
}

编译后 Person 里会有两个 compareTo：

public int compareTo(Person);            // 你写的
public int compareTo(java.lang.Object);  // 桥接方法：checkcast Person 后转发

4.4 桥接方法在生产环境引发的三个真实问题

坑问题 1：反射遍历方法时出现「重复方法」
for (Method m : MyNode.class.getDeclaredMethods()) {
    System.out.println(m.getName() + " | synthetic=" + m.isSynthetic()
        + " | bridge=" + m.isBridge());
}
// 输出：
// setData | synthetic=false | bridge=false
// setData | synthetic=true  | bridge=true    ← 凭空多出来的一个

后果：如果你用反射做「方法名 + 参数类型」的映射（比如自研的 RPC 框架、简易版 Spring MVC 参数绑定），桥接方法可能导致映射到错误的方法，或者出现「同一个方法被处理两次」。

正确的过滤写法：

for (Method m : MyNode.class.getDeclaredMethods()) {
    // 关键：过滤掉桥接方法和合成方法
    if (m.isBridge() || m.isSynthetic()) continue;
    // 或者：过滤掉参数类型是 Object 的「重载伪影」
    // ...
}
坑问题 2：Spring AOP 代理中桥接方法导致切面失效或重复执行

Spring AOP 基于 JDK 动态代理时，是通过接口方法匹配切点的。当代理对象调用泛型方法时，可能走到桥接方法上，而桥接方法的注解/参数信息与你源码里的方法不一致，导致：

  • 切点表达式 execution(* com.x.Service.save(..)) 匹配不上（因为桥接方法所在类是合成类）
  • 自定义注解被读不到（注解写在真方法上，桥接方法上没有）
  • 通知执行两次（真方法一次、桥接转发一次）

排查思路：在切面里打印 MethodSignature.getMethod().isBridge()；或改用 CGLIB 代理（通过子类继承，行为不同但仍需注意）。

坑问题 3：MyBatis / JPA 泛型方法解析

MyBatis-Plus 的 BaseMapper<T> 需要通过反射知道 T 到底是什么（才能拼出表名）。它的做法是解析 Mapper 接口的泛型父接口签名：

// 简化版原理：从子接口往上找，直到找到带泛型实参的声明
private Class<?> resolveEntityType(Class<?> mapperInterface) {
    for (Type type : mapperInterface.getGenericInterfaces()) {
        if (type instanceof ParameterizedType pt) {
            Type arg = pt.getActualTypeArguments()[0];
            if (arg instanceof Class<?> c) return c;
        }
    }
    return null;
}

如果中间隔了多层泛型继承，getActualTypeArguments() 可能返回 TypeVariable 而不是 Class，此时需要递归向上解析边界——这正是 ResolvableType 这类工具存在的价值（第 12 章）。

动手验证练习（强烈建议做一遍）
  1. 写下 Node<T> 和 MyNode 两个类，编译
  2. 执行 javap -c -p -v MyNode，找 ACC_BRIDGE 和 ACC_SYNTHETIC 标志位
  3. 把子类方法的参数改成 Object（与父类擦除后的签名一致），桥接方法会消失——此时它已经是真正的重写，不需要转发
  4. 写一个 implements Comparable<Person>，观察 compareTo(Object) 的出现

亲手做过一次，这个知识点就永久归你了。

05型变：不变、协变、逆变与 PECS

这是泛型里最容易在面试中翻车的一章。List<Object> = new ArrayList<String>() 为什么不行？? extends 和 ? super 怎么选？搞清这一章，你对 Java 类型系统的理解会超过大多数 8 年经验的人。

5.1 先看一个反直觉的事实：数组是协变的，泛型不是

// 数组：协变（covariant）—— 编译通过！
Object[] objArr = new String[10];
objArr[0] = 42;      // 💥 编译通过，但运行时 ArrayStoreException

// 泛型：不变（invariant）—— 编译就拦住了
List<Object> objList = new ArrayList<String>();  // ❌ 编译错误
// 报错：不兼容的类型: ArrayList<String> 无法转换为 List<Object>
为什么数组允许协变，而泛型不允许？

数组协变是 Java 早期设计的一个「历史遗留缺陷」。它破坏类型安全（上面的 ArrayStoreException 就是代价），但 Java 1.0 为了支持 Object[] 接收任意数组、方便写通用排序/打印工具，就这么定了。

这个缺陷的代价是：每次数组写入都要在运行时做类型检查（这就是 ArrayStoreException 的由来）——性能损失是真实的。

Java 5 设计泛型时，设计者吸取了这个教训：与其在运行时检查，不如在编译期禁止。所以泛型选择了不变——更安全，零运行时开销。这也是为什么「泛型数组创建」被禁止（第 3 章限制 2）。

核心洞察：泛型的不变不是「麻烦」，而是用编译期的严格换来了运行时的安全。

5.2 为什么 List<String> 不能当成 List<Object>

假设允许，会发生什么：

// 假设这行合法（实际不合法）
List<Object> objs = new ArrayList<String>();
objs.add(42);                 // Object 的列表，加个 Integer 看起来天经地义
String s = (String) objs.get(0);   // 💥 而这个 String 列表里现在躺着 Integer

类型安全被彻底破坏。这就是不变性的必要性。

5.3 通配符：在不变的基础上找回灵活性

不能协变，但很多场景确实需要「接受一堆不同类型的 List」。Java 的答案是通配符（Wildcard）。

上界通配符 ? extends T —— 协变，只能读

// 接受 List<Integer>、List<Double>、List<Number>……
public static double sum(List<? extends Number> list) {
    double total = 0;
    for (Number n : list) {      // ✅ 读出来一定是 Number（或其子类）
        total += n.doubleValue();
    }
    return total;
}

sum(List.of(1, 2, 3));           // List<Integer>  ✅
sum(List.of(1.5, 2.5));          // List<Double>   ✅
sum(List.of(1L, 2L, 3L));        // List<Long>     ✅
关键：? extends 只能读，不能写 
List<? extends Number> list = new ArrayList<Integer>();
Number n = list.get(0);   // ✅ 读：一定是 Number

list.add(1);              // ❌ 编译错误
list.add(1.5);            // ❌ 编译错误
list.add(null);           // ✅ 只有 null 可以（null 是所有引用类型的成员）

// 为什么不能 add？编译器知道 list 可能是 List<Double>、List<Long>...
// 无论加什么类型，都可能是错的。所以干脆全部禁止。

下界通配符 ? super T —— 逆变，只能写

// 接受 List<Integer>、List<Number>、List<Object>
public static void fill(List<? super Integer> list) {
    list.add(1);           // ✅ 写：无论底层是 Integer/Number/Object 的列表，加 Integer 都合法
    list.add(2);

    // Integer x = list.get(0);  // ❌ 读不了！只能读成 Object
    Object o = list.get(0);      // ✅ 只能当成 Object
}

List<Integer> ints = new ArrayList<>();
List<Number> nums = new ArrayList<>();
List<Object> objs = new ArrayList<>();

fill(ints);   // ✅
fill(nums);   // ✅
fill(objs);   // ✅

无界通配符 ?

public static int size(List<?> list) {   // 只想知道长度，不关心元素类型
    return list.size();
}
List<?> 和 List<Object> 的区别（高频考点）
操作List<?>List<Object>
接收 List<String>✅ 可以❌ 不可以
get()返回 Object返回 Object
add(任意对象)❌ 只能 add(null)✅ 可以 add 任何东西
语义「某种未知类型的列表」「元素类型明确是 Object 的列表」

一句话记忆：List<?> 是只读视图，List<Object> 是明确的万能容器。方法参数如果只想读，用 List<?>；确实要往里塞各种类型，才用 List<Object>。

5.4 PECS 原则：一劳永逸的选择口诀

PECS —— Producer Extends, Consumer Super

来自 Joshua Bloch《Effective Java》Item 31，是泛型通配符的唯一实用准则：

  • 参数是生产者（你从它里面读数据）→ 用 ? extends T
  • 参数是消费者（你往它里面写数据）→ 用 ? super T
  • 既是生产者又是消费者 → 别用通配符，老老实实用 <T>

直觉记忆法：extends 向上是「只出」（产出），super 向下是「只进」（消耗）。出 extends，进 super。

看 JDK 源码怎么用这个原则：

// java.util.Collections
// 1. copy：从 src 读（生产者），往 dest 写（消费者）
public static <T> void copy(List<? super T> dest,    // Consumer → super
                           List<? extends T> src) {  // Producer → extends
    // ...
}

// 2. max：从 coll 读，需要比较 → 生产者
public static <T extends Object & Comparable<? super T>> T max(Collection<? extends T> coll) {
    // ...
}

// 3. java.util.stream.Stream
// forEach：消耗元素 → Consumer<? super T>
void forEach(Consumer<? super T> action);

// map：从 stream 读（生产者），产出 R
<R> Stream<R> map(Function<? super T, ? extends R> mapper);
为什么 Stream.map 的参数是 Function<? super T, ? extends R>

拆开看非常清楚：

  • ? super T：这个函数消费 T 类型的元素，所以参数位置用 super
  • ? extends R：这个函数产出 R 类型的结果，所以返回位置用 extends

一个 Function 的入参是「消费者」，返回是「生产者」。记住这个模型，JDK 里所有函数式接口的通配符你都能自己推导出来，不用背。

5.5 型变对照图

5.6 通配符捕获（Wildcard Capture）：一个巧妙的小坑

看这段代码，直觉上应该能编译，实际上不行：

// 看似合理的写法
public static void swap(List<?> list, int i, int j) {
    Object tmp = list.get(i);
    list.set(i, list.get(j));    // ❌ 编译错误
    list.set(j, tmp);            // ❌ 编译错误
}
编译器报错：capture of ? 类型不匹配

原因：List<?> 中每个 ? 是一个未知但固定的类型（叫 capture），编译器无法证明 list.get(j) 拿到的元素与 list.set(i, ...) 期望的元素是同一类型。虽然它们显然来自同一个 list，但编译器的类型系统不这么推理。

解决方案：让泛型方法「捕获」这个类型

// 公开 API 保持通配符，内部用泛型方法捕获
public static void swap(List<?> list, int i, int j) {
    swapHelper(list, i, j);      // 调用时，? 被捕获为某个具体的 E
}

private static <E> void swapHelper(List<E> list, int i, int j) {
    E tmp = list.get(i);         // 现在 E 是明确的类型，编译通过
    list.set(i, list.get(j));
    list.set(j, tmp);
}

这就是 JDK 里 Collections.swap 的实际实现方式。能说出「通配符捕获」并给出这个解法，是很强的加分项。

06通配符 vs 类型参数：何时用哪个

这是一个「写 API 时才会遇到，但一遇到就纠结」的问题。<T> 和 ? 看起来都能表达「某种类型」，但适用场景截然不同。

6.1 判断准则：类型参数只出现一次 → 用通配符

《Effective Java》Item 31 的核心结论

如果类型参数在方法签名中只出现一次，就把它替换成通配符。

理由：类型参数的作用是在多个位置之间建立类型约束。如果它只出现一次，那这个「约束」根本不存在——它只是被用了一次而已，而通配符能表达得更简洁、且能给调用方更多灵活性。

// ❌ 不好：T 只出现了一次
public static <T> void printAll(List<T> list) {
    for (T t : list) System.out.println(t);
}

// ✅ 更好：用通配符
public static void printAll(List<?> list) {
    for (Object t : list) System.out.println(t);
}

好处在哪里？因为 <T> 版本里，调用方必须提供一个具体类型；而 List<?> 版本可以接受任何列表。API 的约束更弱，意味着适用面更广。

6.2 什么时候必须用 <T>：约束需要跨位置传递

// T 出现 3 次：参数、参数、返回值 —— 必须建立它们之间的关系
public static <T> T pickOne(List<T> from, List<T> to) {
    T item = from.get(0);
    to.add(item);       // 语义要求：放进 to 的东西，必须是从 from 里取的
    return item;
}

// 用通配符无法表达这个约束：
// public static Object pickOne(List<?> from, List<?> to) —— 丢失了类型关联
判断条件用 <T>用 ?
类型在多个参数/返回值间建立关联是否
类型只在一个位置出现否是
需要往容器里写数据（消费者）是? super T 也可
需要从容器里读数据（生产者）是? extends T 也可
需要 new T() / 调用 T 的方法必须做不到

6.3 常见的重构对比

// ------- ❌ 类型参数版（T 只用一次） -------
public static <T> void addAll(List<T> dest, Iterable<T> src) { ... }

// ------- ✅ 通配符版（更灵活） -------
public static <T> void addAll(List<? super T> dest, Iterable<? extends T> src) {
    // T 仍然需要，因为它连接了 dest 和 src
    // 但两侧都用通配符放宽了接受的类型范围
}

这段就是 Collections.addAll 的真实形态。注意它同时用了 <T> 和通配符——类型参数负责「建立关系」，通配符负责「放宽边界」。两者不是二选一，而是配合使用。

实用重构检查清单
  1. 看看方法签名里的类型参数，数一下出现次数
  2. 只出现一次 → 先尝试换成 ?，能编译通过就用通配符
  3. 出现多次 → 保留 <T>，但检查每个位置是否能用 ? extends/? super 放宽
  4. 替换后跑一遍单测——如果调用方反而需要更多强转，说明改错了方向

07边界与递归类型参数（F-bounded）

7.1 上界（Upper Bound）

// 限定 T 必须是 Number 及其子类
public static <T extends Number> double sum(List<T> list) {
    double total = 0;
    for (T t : list) {
        total += t.doubleValue();   // ✅ 因为 T 是 Number，可以调用 Number 的方法
    }
    return total;
}

上界的真正价值：它不只是「限制」，更是授权——因为 T extends Number，编译器才允许你在方法体里把 T 当作 Number 使用。没有边界，T 就是 Object，什么方法都调不了。

7.2 多边界（Intersection Type）

// 语法：T extends 类 & 接口1 & 接口2
public static <T extends Number & Comparable<T> & Serializable> T max(List<T> list) {
    T m = list.get(0);
    for (T t : list) {
        if (t.compareTo(m) > 0) m = t;   // 需要 Comparable
    }
    return m;                             // 需要 Serializable 才能序列化返回
}
多边界的硬性规则
  • 如果有类类型，类必须放在第一项：<T extends Number & Serializable> ✅；<T extends Serializable & Number> ❌
  • 擦除时只保留第一个边界（所以顺序影响字节码里 T 的实际类型）
  • 除了第一个，其余都必须是接口

7.3 递归类型参数（F-bounded Polymorphism）

这是泛型里最「烧脑」也最优雅的用法。定义是：类型参数受自身约束，写作 T extends Xxx<T>。

案例 1：JDK 里的 Enum

public abstract class Enum<E extends Enum<E>> implements Comparable<E>, Serializable {
    public final int compareTo(E o) { ... }
    // ...
}
为什么要这么写？拆解一下

目标是：让 Status.ACTIVE.compareTo(Status.INACTIVE) 里的参数必须是同一个枚举类型，而不能是别的枚举。

  • 如果写成 Enum implements Comparable<Enum> → compareTo 接受任何 Enum，任意两个枚举都能比，类型不安全
  • 写成 Enum<E> implements Comparable<E> → E 是谁？不知道
  • 写成 Enum<E extends Enum<E>> → 「E 是一个枚举，且这个枚举的同类就是 E 自己」，约束闭环了

于是 class Status extends Enum<Status>，compareTo 的参数就被钉死为 Status。

案例 2：Comparable / Comparator 的正确姿势

// ❌ 错误：一个 Student 竟然能和 Teacher 比较
public class Student implements Comparable {
    public int compareTo(Object o) { ... }
}

// ❌ 半对：编译能过，但语义没约束住
public class Student implements Comparable<Object> { ... }

// ✅ 正确：只能和 Student 比
public class Student implements Comparable<Student> {
    @Override
    public int compareTo(Student o) { return Integer.compare(this.id, o.id); }
}

案例 3：自限定泛型 Builder（大厂里很常见）

这是 F-bounded 最有工程价值的应用场景——链路式 API 中的继承：

// 基础 Builder
public abstract class BaseBuilder<T, B extends BaseBuilder<T, B>> {
    protected String id;
    protected long createTime;

    @SuppressWarnings("unchecked")
    protected B self() { return (B) this; }   // ★ 关键：把自己转成子类型返回

    public B id(String id) { this.id = id; return self(); }
    public B createTime(long t) { this.createTime = t; return self(); }

    public abstract T build();
}

// 子类 Builder
public class UserBuilder extends BaseBuilder<User, UserBuilder> {
    private String name;

    public UserBuilder name(String name) { this.name = name; return this; }

    @Override
    public User build() {
        User u = new User();
        u.setId(id); u.setName(name); u.setCreateTime(createTime);
        return u;
    }
}

// 使用：所有方法都能链式调用，且顺序随便换
User user = new UserBuilder()
        .id("U001")
        .name("张三")
        .createTime(System.currentTimeMillis())
        .build();
没有 F-bounded 会怎样？ 
// 如果 BaseBuilder 只写 <T>，那么 id() 只能返回 BaseBuilder<T>
// 链式调用到这里就断了：
new UserBuilder().id("U001").name("张三");
//                 ^^^^^^^^^^^^ 返回 BaseBuilder，没有 name() 方法！

F-bounded 的核心作用：让父类的方法返回「子类自己的类型」，从而保住链式调用的类型流。 这一招在 Spring Security 的配置 DSL、各类 RPC 客户端 Builder、领域模型构造器里极为常见。

案例 4：类型安全的「自我比较」与树结构

// 保证树的节点只能包含与自己同类型的子节点
public abstract class TreeNode<T extends TreeNode<T>> {
    protected List<T> children = new ArrayList<>();

    public void addChild(T child) { children.add(child); }   // 类型安全

    public abstract T self();
}

public class DeptNode extends TreeNode<DeptNode> {
    @Override public DeptNode self() { return this; }
}

DeptNode root = new DeptNode();
root.addChild(new DeptNode());     // ✅
// root.addChild(new UserNode());  // ❌ 编译错误，做到「同类型」约束

7.4 小结：F-bounded 的识别特征

看到 <T extends SomeClass<T>> 这种「自己约束自己」的写法，就是 F-bounded。它的三大用途：

  1. 类型安全的比较（Enum、Comparable）—— 保证只和同类比
  2. 链式 Builder 的继承 —— 保证父类方法返回子类型
  3. 同构容器 —— 保证容器只装同类元素

细节 2：var 与泛型（一个真实争议）

为什么很多大厂规范禁用或限制 var？ 
// var 在泛型场景下会「藏起」关键类型信息
var list = new ArrayList<>();          // 💀 推断为 ArrayList<Object>！
list.add("a");
list.add(123);                          // 编译通过，类型安全丢了

// 对比：显式写法会立刻报错
List<String> list2 = new ArrayList<>();  // 正确推断为 ArrayList<String>
list2.add(123);                          // ❌ 编译错误，符合预期

这是 var 最危险的用法：在「右侧无法提供类型信息」时用 var，会让泛型实参退化为 Object，悄悄破坏类型安全。正确做法是 var list = new ArrayList<String>();（右侧显式给出）。

面试可复用表述：「var 是局部变量类型推断，它不改变类型系统。风险在于当右侧类型信息不足时（如 new ArrayList<>()）会推断成 ArrayList<Object>，反而丢掉了泛型的类型安全。所以规范里通常要求 var 右侧必须显式带上泛型实参。」

8.4 Record 与泛型：新语法，老规则（Java 16+）

Record 是 Java 16 正式引入的不可变数据载体。它和泛型组合得非常自然——但要注意：擦除规则没有任何改变。

// Record 完全可以泛型化
public record Page<T>(List<T> records, long total, int pageNum, int pageSize) {

    // 紧凑构造器：泛型参数同样可以做校验和防御性拷贝
    public Page {
        if (pageNum < 1) throw new IllegalArgumentException("页码必须从 1 开始");
        records = (records == null) ? List.of() : List.copyOf(records);
    }

    public boolean isEmpty() { return records.isEmpty(); }

    // 泛型方法照样可以定义 —— 而且写法比传统类更干净
    public <R> Page<R> map(Function<? super T, ? extends R> mapper) {
        return new Page<>(records.stream().map(mapper).toList(),
                          total, pageNum, pageSize);
    }
}

// 使用：不可变载体 + 泛型转换，类型安全且零样板代码
Page<User> userPage = new Page<>(users, 100, 1, 20);
Page<UserVO> voPage = userPage.map(UserConverter::toVO);
Record 不会「带来」运行时类型信息

一个常见误解是：record 是"更具体的类型"，所以能拿到泛型实参。这是错的——record 编译后就是普通类，同样受擦除约束。

Page<User> p = new Page<>(users, 100, 1, 20);

// ❌ 拿不到 User —— 实例上没有任何泛型信息
// p.getClass() 就是 Page.class，和 Page<Order> 的实例是同一个类

// ✅ 要拿类型，仍然只能靠「声明处」的信息 —— record 的组件也是一种声明
TypeVariable<?>[] tv = Page.class.getTypeParameters();      // [T]

// ✅ 反序列化同样躲不开 TypeReference
Page<User> page = objectMapper.readValue(json,
        new TypeReference<Page<User>>() {});

一个实用的工程观察：record + 泛型是写「不可变传输对象」的现代组合，map 这类转换方法比传统 DTO 干净得多。但不要因为语法新就以为它绕过了擦除——所有泛型的限制在这里一条都不少，这是 Java 类型系统的地基，语言语法层的新特性不会改变它。

09泛型数组、可变参数与堆污染

9.1 堆污染（Heap Pollution）的本质

定义

堆污染：一个参数化类型的变量，指向了一个不是该参数化类型的对象，导致运行时出现意料之外的类型错误。

它不是「内存泄漏」那种污染，而是类型系统被欺骗——编译器以为容器里是 String，实际躺着 Integer。

三种产生堆污染的途径：

途径 1：Raw Type 混用（最常见）

List<String> safe = new ArrayList<>();
List raw = safe;              // ⚠️ 警告：unchecked
raw.add(42);                  // ⚠️ 警告但编译通过
String s = safe.get(0);       // 💥 ClassCastException
// 注意：异常在 safe 上抛出，但凶手是 raw —— 错误「传染」了

途径 2：未检查的强转

@SuppressWarnings("unchecked")
List<String> list = (List<String>) (List<?>) someListOfIntegers;  // 💣
String s = list.get(0);   // 💥

途径 3：泛型可变参数（最隐蔽，也是 @SafeVarargs 存在的原因）

// 泛型可变参数会隐式创建一个泛型数组
public static <T> void dangerous(List<T>... lists) {   // ⚠️ 警告：Possible heap pollution
    Object[] objects = lists;          // 编译器允许这个赋值
    objects[0] = Arrays.asList(42);    // 💣 往里面塞了错误类型
}

List<String> a = new ArrayList<>();
dangerous(a);                          // 调用后 a 可能被污染
为什么可变参数会创建泛型数组？

可变参数本质是数组。当 T 是泛型时，编译器需要创建 T[]——而第 3 章说过，泛型数组创建是被禁止的。JDK 在这里做了一个妥协：允许它（并给出 unchecked 警告），但要求你承诺不往数组里写东西。

这个承诺的正式表达方式就是 @SafeVarargs。

9.2 三个注解的正确用法（高频考点）

注解作用范围语义风险
@SuppressWarnings("unchecked")类 / 方法 / 字段 / 局部变量「我知道有未检查警告，别报」不校验，压过头会掩盖真 bug
@SafeVarargsJava 7：static 方法、final 实例方法、构造器
Java 9+：额外支持 private 实例方法		「我保证不污染可变参数数组」编译器信任你，写错了它会替你背锅
为什么实例方法必须是 final如果允许被重写，子类就能破坏「不污染数组」这个承诺，所以编译器强制要求 final（或 private——private 方法本身不可重写）。这是硬性约束，不是风格建议。
 
// 正确的 @SafeVarargs 用法：只读，不写数组
@SafeVarargs
public static <T> List<T> listOf(T... items) {
    return new ArrayList<>(Arrays.asList(items));   // 只读 items，安全
    // 绝不能：items[0] = something;  ← 这会破坏承诺
}
反面教材：JDK 里真实踩过的坑

Arrays.asList 在早期设计上直接包装了传入的数组（而非拷贝），如果配合泛型可变参数使用，就可能把外部数组暴露给调用方造成污染。这也是为什么 List.of(...)（Java 9）返回的是不可变拷贝——从设计上堵死了这条路。

启示：接受可变参数时如果需要保存，先拷贝再存，不要直接持有调用方传入的数组引用。

9.3 实战建议：怎么写出「零警告」的泛型代码

  3. 每处 @SuppressWarnings 都写注释说明「为什么这里是安全的」——这是团队代码规范的加分项

9.4 泛型数组的正确姿势：toArray(new T[0])

虽然「创建泛型数组」被禁止，但「把集合转成数组」是日常高频操作。Collection 为此提供了两个重载，理解它们的差别能解释一个被问了十几年的经典问题。

public interface Collection<E> {
    Object[] toArray();                  // 重载 1：无参版，只能返回 Object[]
    <T> T[] toArray(T[] a);              // 重载 2：泛型方法，你传一个数组充当"类型载体"
}

重载 2 之所以要传数组进去，本质上是绕开擦除的一种变通——运行时拿不到 E，只能由调用方把一个真实类型的实例带进来，让方法能通过 a.getClass() 知道该创建什么数组。

List<String> list = List.of("a", "b", "c");

// ❌ 只能得到 Object[]，没法直接当 String[] 用
Object[] arr1 = list.toArray();

// ⚠️ 能跑，但在泛型场景下有隐患：数组实例被交给了集合，可能被写坏
String[] arr2 = list.toArray(new String[list.size()]);

// ✅ 社区公认的惯用法
String[] arr3 = list.toArray(new String[0]);
为什么是 new String[0] 而不是 new String[size]？

早期答案偏重「可读性好、不用重复算长度」，但现代 JVM 上的真实原因是 JIT 优化效果不同。看 JDK 里 ArrayList.toArray(T[] a) 的实现：

public <T> T[] toArray(T[] a) {
    if (a.length < size) {
        // 传入的数组太小 → 按 a 的运行时类型新建一个
        return (T[]) Arrays.copyOf(elementData, size, a.getClass());
    }
    System.arraycopy(elementData, 0, a, 0, size);
    if (a.length > size) a[size] = null;      // 补齐 null 终止符
    return a;
}

两个分支都要拷贝数据，差别在于：

  • 传 new T[size] 走下面的 System.arraycopy 分支，需要在堆上分配一个运行时大小的数组，JIT 可优化的空间小
  • 传 new T[0] 走上面的 Arrays.copyOf 分支——而 Arrays.copyOf 是被 JIT 内联的 intrinsic；同时 new T[0] 是编译期常量大小的分配，更容易被逃逸分析消除

JVM 性能专家 Aleksey Shipilëv 在 2016 年的基准测试（Arrays of Wisdom of the Ancients）中给出了这个结论，此后成为社区共识。这条结论对 ArrayList、HashSet、以及集合 Stream.toArray() 同样适用。

面试可复用表述

「toArray(new T[0]) 这个看似浪费的写法是有性能依据的。集合的 toArray() 无参版本无法知道元素类型，只能返回 Object[]；而传一个长度 0 的数组，会让 JVM 走常量长度的分配路径，Arrays.copyOf 又是 intrinsic，实测比传精确长度的数组更快。这个设计本身就是擦除的产物——如果 Java 有具化泛型，toArray() 根本不需要这个参数。」

9.5 补充：什么时候该放弃泛型

最后一个容易被忽略的判断——泛型不是越多越好。下面这些信号说明你可能用过头了：

信号问题更合适的做法
方法体里出现 instanceof 分支判断类型说明你在用泛型模拟「编译期特化」——而 Java 做不到改用多态（策略模式）/ 函数式接口
类型参数超过 3 个调用方必须显式写全，可读性急剧下降抽成配置对象 / 减少抽象层次
到处 @SuppressWarnings("unchecked")类型安全网已经被你自己拆掉了重新设计 API，让类型信息显式传入
为了「通用」写了个 <T>，实际只用了 1~2 种类型过度抽象，增加理解成本却没有收益直接写具体的重载
泛型只用来「省一个强转」收益太小，白增复杂度保留显式强转更清晰

核心原则：泛型的价值在于「同一套逻辑需要适配多个类型，且类型关系需要被编译器保证」。如果这两个条件只满足一个，泛型多半是过度设计。这条判断力，往往比会写泛型更体现工程成熟度。

10反射与运行时泛型信息

本章要破除的核心误解

「类型擦除后，运行时拿不到泛型信息」——这句话只对了一半。

准确的说法是：对象实例上的泛型实参丢失了，但类型声明处的泛型签名被保留在 class 文件里。

  • new ArrayList<String>() 这个对象——运行时不知道自己是 String 列表 ❌
  • class Foo { List<String> names; } 这个字段声明——运行时能读到 List<String> ✅

这个差异是所有框架泛型能力的技术基础。

10.1 为什么声明处的信息能保留？

因为 Signature 属性。编译器会把泛型签名以 UTF-8 字符串的形式写进 class 文件的 attribute 区域：

// javap -v Foo 输出的片段
public class com.example.Foo {
  java.util.List<java.lang.String> names;
    descriptor: Ljava/util/List;
    Signature: #15   // Ljava/util/List<Ljava/lang/String;>;   ← 泛型签名在这里
}
保留 Signature 的官方理由

Java 虚拟机规范明确写着：保留泛型签名的目的是「为了支持反射和其他工具（如编译器）使用」。也就是说，官方从设计之初就为框架留了这个口子——只是不同的 JVM 语言（如 Scala、Kotlin）对它的依赖程度不同。

10.3 万能取类型：从子类反推父类泛型实参

这是最重要的一段代码，它是 TypeReference、TypeToken、泛型 DAO 的技术核心。

/**
 * 从子类/匿名子类反推出父类（或接口）上的泛型实参
 */
public static Type resolveTypeArgument(Class<?> childClass, Class<?> targetClass) {
    // 沿着继承链向上找
    Class<?> current = childClass;
    while (current != null && current != Object.class) {
        Type superType = current.getGenericSuperclass();       // 父类的泛型信息

        if (superType instanceof ParameterizedType pt) {
            if (pt.getRawType() == targetClass) {
                return pt.getActualTypeArguments()[0];          // ★ 拿到了 T 的实参
            }
        }
        current = current.getSuperclass();
    }
    return null;
}

看它怎么工作：

public abstract class AbstractDao<T> { }

public class UserDao extends AbstractDao<User> { }      // ★ 实参在这里

// 运行结果
Type t = resolveTypeArgument(UserDao.class, AbstractDao.class);
System.out.println(t);   // class com.example.User   —— 找到了！

// 但如果中间隔了一层：
public abstract class BaseDao<T> extends AbstractDao<T> { }
public class OrderDao extends BaseDao<Order> { }

// 需要递归解析：BaseDao<T> 拿到的实参是 TypeVariable T 而不是 Class
// 必须继续往 BaseDao 的边界找 —— 这就是 ResolvableType 要做的事

实战：手写一个 TypeReference（Jackson 的简化版）

public abstract class TypeReference<T> {
    private final Type type;

    protected TypeReference() {
        // ★ 关键：getClass() 拿到的是匿名子类（如 TypeReference<List<User>> 的匿名子类）
        //   它的 getGenericSuperclass() 保留了 List<User> 的完整信息
        Type superClass = getClass().getGenericSuperclass();
        if (superClass instanceof ParameterizedType pt) {
            this.type = pt.getActualTypeArguments()[0];
        } else {
            throw new IllegalStateException("缺少泛型实参，请使用匿名子类语法");
        }
    }

    public Type getType() { return type; }
}

// 使用：注意必须带 {} 创建匿名子类，否则 getGenericSuperclass() 只是原始类型
TypeReference<List<User>> ref = new TypeReference<List<User>>() {};
System.out.println(ref.getType());   // java.util.List<com.example.User>  ✅ 信息完整保留
为什么必须写 {}？

这是新手最容易犯的错。看两个版本的差别：

// ❌ 直接实例化抽象类？不行（编译错误），所以必须用匿名子类
// TypeReference<List<User>> r = new TypeReference<List<User>>();

// ✅ 匿名子类：编译期生成一个 TypeReference$1.class，
//    它的 getGenericSuperclass() 是 ParameterizedType（信息完整）
TypeReference<List<User>> r = new TypeReference<List<User>>() {};

// 💀 危险：如果基于已有实例去取，拿不到信息
class MyRef extends TypeReference<List<User>> { }
new MyRef().getGenericSuperclass();  // ✅ 可以，因为父类签名保留了

原理：泛型信息保留在「类的声明」上。只有通过 extends / 匿名子类的方式，才能在字节码层面把 List<User> 写进某个类的 Signature 属性。直接 new 出来的对象没有任何声明位置可以承载这个信息。

实战：getClass() 的泛型语义小陷阱

// 编译器对 getClass() 有特殊规则：返回 Class<? extends X>
// 所以下面这行编译不过：
// Class<List<String>> c = list.getClass();   // ❌ 泛型信息根本不存在

11Java 泛型 vs C++ 模板：一次彻底的对比

如果你有 C++ 背景，这一章会非常有价值——它能让你把两套心智模型彻底分开，避免「用 C++ 模板的直觉去理解 Java 泛型」而处处碰壁。

11.1 本质区别：一个是运行时机制，一个是编译期展开

C++ 模板：编译期代码生成器

模板是语法层面的宏展开。vector<int> 和 vector<double> 会生成两份完全独立的机器码。类型信息在编译期全部可用，编译后就不存在了（没有运行时的模板概念）。

Java 泛型：编译期类型检查器

泛型是类型系统的约束。只有一份字节码，泛型实参在编译后被抹掉。运行时看不到 T，但类型检查在编译期是严格的。

11.3 三个「思维转换」要点

转换 1：不要期待 Java 有「编译期 if」

C++ 里可以用 if constexpr 或 SFINAE 做到「根据类型选择不同分支」。Java 里做不到——因为擦除后只有一个版本的方法体，你无法「按 T 分支」。

// Java 里想要这种效果，只能靠「运行时判断 + 强转」
public <T> void handle(T value) {
    if (value instanceof String) { ... }        // 运行时判断，不是编译期特化
    else if (value instanceof Integer) { ... }
    // 这本质上是「伪泛型」——真正的泛型算法不该这么写
}

正确的 Java 思路：用多态 + 函数式接口代替编译期分支。

转换 2：Java 泛型的性能优势在别处

C++ 模板的一个卖点是「零开销抽象」（无装箱、无虚调用）。Java 泛型的卖点是「零代码膨胀 + 类型安全」。

所以别指望用 Java 泛型写出「比手写类型更快的数值代码」——那需要 Project Valhalla 的值类型（仍未正式落地）。如果你的场景是「千万级 int 数组求和」，正确的 Java 工具是 IntStream / int[]，而不是 List<Integer>。

11.4 CRTP vs F-bounded：一个精妙的对照

如果你写过 C++ 的 CRTP（奇异递归模板模式），你会发现 Java 的 F-bounded 泛型几乎是它的翻版：

// C++ CRTP
template <typename T>
class Base {
public:
    void interface() {
        static_cast<T*>(this)->implementation();   // 静态派发到子类
    }
};

class Derived : public Base<Derived> {
public:
    void implementation() { /* ... */ }
};
// Java F-bounded（对应写法）
public abstract class Base<T extends Base<T>> {
    public void interfaceMethod() {
        self().implementation();       // 静态类型就能调到子类方法
    }
    protected abstract T self();       // 相当于 static_cast<T*>(this)
}

public class Derived extends Base<Derived> {
    public void implementation() { /* ... */ }
}
能说出这个对照，是很强的加分项

面试可以这样表述：「Java 的 F-bounded 泛型在形态上与 C++ 的 CRTP 高度相似，都用于在继承体系下保住子类型信息——C++ 靠 static_cast 把 this 转成子类，Java 靠 self() 加一次受控强转。区别在于 C++ 的 CRTP 是编译期静态派发，无虚函数开销；而 Java 因为擦除，self() 里的强转是运行时 checkcast，且最终还是走虚方法派发。」

12大厂框架中的泛型全景

前面十一章是「原理」，这一章是「落地」。下面每一个都是你在大厂代码库里天天见到的泛型用法，理解它们背后的机制，才能在看源码时不迷糊、在出问题时能定位。

12.1 集合与 Stream：泛型设计的教科书

public interface Collection<E> extends Iterable<E> { ... }
public interface List<E> extends Collection<E> { ... }
public interface Map<K, V> { Set<Map.Entry<K, V>> entrySet(); ... }

// 泛型方法 + 通配符 + 函数式接口的组合
public interface Stream<T> {
    Stream<T> filter(Predicate<? super T> predicate);          // 消费 T
    <R> Stream<R> map(Function<? super T, ? extends R> mapper); // 消费 T，产出 R
    void forEach(Consumer<? super T> action);                    // 消费 T
    <R> R collect(Collector<? super T, A, R> collector);         // 复杂的通配符嵌套
}
为什么 Stream 的每个方法都带通配符？

以 filter 为例，写成 Predicate<T> 也能工作，但会限制调用方。用 Predicate<? super T> 后，一个 Predicate<Object> 也可以传入 Stream<String>——因为它能处理任何对象，自然也能处理 String。这就是 PECS 原则在 API 设计上的体现：放宽参数类型，让 API 更好用。

Stream<String> stream = list.stream();

Predicate<String> p1 = s -> s.length() > 3;
Predicate<Object> p2 = o -> o != null;     // 更通用的谓词

stream.filter(p1);   // ✅
stream.filter(p2);   // ✅ 因为声明是 Predicate<? super String>
// 如果声明是 Predicate<T>，这一行就编译不过了

12.2 Spring 全家桶

12.2.1 ResolvableType：Spring 的泛型解析引擎

// 场景 1：从 Repository 接口反推实体类型
public interface UserRepository extends JpaRepository<User, Long> { }

ResolvableType t = ResolvableType.forClass(UserRepository.class);
Class<?> domainType = t.as(JpaRepository.class).getGeneric(0).resolve();  // User
Class<?> idType     = t.as(JpaRepository.class).getGeneric(1).resolve();  // Long

// 场景 2：解析字段/方法上的嵌套泛型
class MyService {
    private Map<String, List<Order>> cache;
}
ResolvableType fieldType = ResolvableType.forField(
        MyService.class.getDeclaredField("cache"));
ResolvableType valueType = fieldType.getGeneric(1);        // List<Order>
Class<?> orderClass = valueType.getGeneric(0).resolve();    // Order

// 场景 3：判断泛型是否兼容（常用于事件监听器匹配）
ResolvableType eventType = ResolvableType.forClass(OrderCreatedEvent.class);
boolean match = listenerType.as(ApplicationListener.class)
        .getGeneric(0).isAssignableFrom(eventType);
ResolvableType 解决的三个原生痛点
  1. 多层继承：A → B<T> → C extends B<User>，原生 API 拿到的是 TypeVariable，ResolvableType 会自动沿继承链解析到 User
  2. 嵌套泛型：Map<String, List<Order>> 可以逐层 getGeneric(i) 下钻
  3. 类型变量替换：会带着「上下文」去解析 T，而不是孤立地看待它
另一把常被忽略的工具：GenericTypeResolver

Spring 还提供了 org.springframework.core.GenericTypeResolver，专门用于从类或方法上反推泛型实参。它比 ResolvableType 更轻、更直接：

// 反推单个泛型实参
Class<?> entityType = GenericTypeResolver.resolveTypeArgument(
        UserRepository.class, JpaRepository.class);        // User

// 反推全部泛型实参
Class<?>[] args = GenericTypeResolver.resolveTypeArguments(
        UserRepository.class, JpaRepository.class);        // [User.class, Long.class]

// 拿到「类型变量 → 类型实参」的完整映射表
Map<TypeVariable, Type> map =
        GenericTypeResolver.getTypeVariableMap(UserRepository.class);
// {T=class User, ID=class Long}

选择建议：只是简单反推一个泛型实参时，GenericTypeResolver 一行搞定、语义自解释；涉及多层继承、嵌套泛型、需要逐层下钻时，用 ResolvableType。两者互补——ResolvableType 更现代、能力更全，而 GenericTypeResolver 在「我明确知道要取哪一个实参」的场景下更简洁。

工程细节：TypeReference 应该声明为 static final 常量 
// ❌ 每次调用都 new 一个匿名类实例：每次都要付一遍反射解析泛型的代价
public List<User> list() {
    return objectMapper.readValue(json, new TypeReference<List<User>>() {});
}

// ✅ 提为静态常量：类型只解析一次，并复用同一个 Type 实例
private static final TypeReference<List<User>> USER_LIST_TYPE =
        new TypeReference<List<User>>() {};

public List<User> list() {
    return objectMapper.readValue(json, USER_LIST_TYPE);
}

原因有两层：其一，TypeReference 的构造器里要调 getClass().getGenericSuperclass()，这是一次反射调用；其二，Jackson 内部对 Type 维护了缓存，复用同一个 Type 实例命中缓存的概率更高。在 QPS 较高的接口上，这个差别是可测量的。

为什么 List<User> users = (List<User>) JSON.parseArray(json) 会炸？

因为反序列化时框架不知道要创建什么类型的元素，只能退化成 JSONObject 或 LinkedHashMap。变量声明上的 <User> 在擦除后不存在，框架看不到。所以必须把类型信息作为参数显式传进去。

13.1 统一响应封装 Result<T>

public class Result<T> implements Serializable {
    private static final long serialVersionUID = 1L;

    private int code;
    private String message;
    private T data;                 // ★ 业务数据，类型由调用方决定
    private long timestamp;

    public Result() { this.timestamp = System.currentTimeMillis(); }

    public static <T> Result<T> success(T data) {
        Result<T> r = new Result<>();
        r.code = 0; r.message = "success"; r.data = data;
        return r;
    }

    public static <T> Result<T> success() { return success(null); }

    public static <T> Result<T> fail(int code, String message) {
        Result<T> r = new Result<>();
        r.code = code; r.message = message;
        return r;
    }

    /** 用于把 Result<A> 转换成 Result<B>（保留状态码） */
    public <R> Result<R> map(Function<? super T, ? extends R> mapper) {
        Result<R> r = new Result<>();
        r.code = this.code; r.message = this.message; r.timestamp = this.timestamp;
        r.data = this.data == null ? null : mapper.apply(this.data);
        return r;
    }

    // getter / setter ...
}

// 使用
@GetMapping("/users/{id}")
public Result<User> getUser(@PathVariable Long id) {
    return Result.success(userService.findById(id));
}

@GetMapping("/users")
public Result<PageResult<User>> list(@RequestParam int page) {
    return Result.success(userService.page(page));       // ★ 嵌套泛型
}
设计要点
  • success / fail 是静态泛型工厂方法，类型由调用方推断
  • map 方法用了 Function<? super T, ? extends R>，是 PECS 的标准用法
  • 注意：Result<Void> 和 Result<Object> 的选择——无返回数据时用 Result<Void>，语义更清晰

13.2 泛型分页对象 Page<T>

public class PageResult<T> {
    private List<T> records;      // 当前页数据
    private long total;           // 总记录数
    private int pageNum;
    private int pageSize;
    private int pages;            // 总页数

    public static <T> PageResult<T> of(List<T> records, long total, int pageNum, int pageSize) {
        PageResult<T> p = new PageResult<>();
        p.records = records; p.total = total;
        p.pageNum = pageNum; p.pageSize = pageSize;
        p.pages = pageSize <= 0 ? 0 : (int) ((total + pageSize - 1) / pageSize);
        return p;
    }

    /** 把一页 A 转成一页 B —— 极其常用的套路 */
    public <R> PageResult<R> convert(Function<? super T, ? extends R> mapper) {
        List<R> converted = this.records.stream()
                .map(mapper)
                .collect(Collectors.toList());
        return PageResult.of(converted, total, pageNum, pageSize);
    }

    public boolean isEmpty() { return records == null || records.isEmpty(); }
    // getter / setter ...
}

13.3 泛型 DAO 基类

public abstract class BaseDao<T, ID> {
    private final Class<T> entityClass;

    @SuppressWarnings("unchecked")
    protected BaseDao() {
        // ★ 构造期从子类反推泛型实参（前提：子类必须是具体类型）
        Type superType = getClass().getGenericSuperclass();
        if (!(superType instanceof ParameterizedType pt)) {
            throw new IllegalStateException(
                getClass().getName() + " 必须以 BaseDao<Entity, Id> 的形式继承");
        }
        this.entityClass = (Class<T>) pt.getActualTypeArguments()[0];
    }

    public Class<T> getEntityClass() { return entityClass; }
    public String getTableName() {
        return CaseFormat.UPPER_CAMEL.to(CaseFormat.LOWER_UNDERSCORE, entityClass.getSimpleName());
    }

    public abstract T selectById(ID id);
    public abstract int insert(T entity);
    public abstract int update(T entity);
    public abstract int deleteById(ID id);
}

// 子类只声明泛型，不用重复写反射代码
public class UserDao extends BaseDao<User, Long> {
    @Override public User selectById(Long id) { ... }
    // ...
}
这个模式的硬性前提

如果你写 public class GenericDao<T> extends BaseDao<T, Long>（保持泛型），那么构造器里解析出来的是 TypeVariable 而不是 Class，强转会失败。子类必须「落地」为具体类型，或者改用 ResolvableType 做递归解析。

13.4 策略工厂：Map<Key, Handler<I, O>>

// 泛型处理器接口
public interface OrderHandler<I extends OrderCommand, O> {
    /** 支持处理的命令类型 */
    Class<I> supportType();
    /** 处理 */
    O handle(I command);
}

// 工厂：自动注册所有 Handler，按类型分发（Spring 自动注入 List）
@Component
public class OrderHandlerFactory {

    private final Map<Class<?>, OrderHandler<?, ?>> handlerMap = new ConcurrentHashMap<>();

    public OrderHandlerFactory(List<OrderHandler<?, ?>> handlers) {
        for (OrderHandler<?, ?> h : handlers) {
            handlerMap.put(h.supportType(), h);
        }
    }

    @SuppressWarnings("unchecked")
    public <I extends OrderCommand, O> O dispatch(I command) {
        OrderHandler<I, O> handler = (OrderHandler<I, O>) handlerMap.get(command.getClass());
        if (handler == null) {
            throw new IllegalArgumentException("未找到处理器: " + command.getClass());
        }
        return handler.handle(command);     // ★ 类型安全由调用方保证
    }
}

public interface CacheService {

    <T> List<T> getList(String key, Class<T> elementType);

}

// 带自动加载的封装（防止缓存穿透的常见写法）
public class LoadingCache<K, V> {
    private final CacheService cache;
    private final Function<K, V> loader;
    private final Class<V> valueType;
    private final Duration ttl;

    public LoadingCache(CacheService cache, Class<V> valueType,
                        Function<K, V> loader, Duration ttl) {
        this.cache = cache; this.valueType = valueType;
        this.loader = loader; this.ttl = ttl;
    }

    public V get(K key) {
        String cacheKey = valueType.getSimpleName() + ":" + key;
        V cached = cache.get(cacheKey, valueType);
        if (cached != null) return cached;

        V loaded = loader.apply(key);            // 缓存未命中，回源
        if (loaded != null) cache.put(cacheKey, loaded, ttl);
        return loaded;
    }
}

13.6 泛型 + 单例注册表

// 类型安全的单例注册表（避免到处写 ClassCastException）
public final class SingletonRegistry {
    private static final Map<Class<?>, Object> REGISTRY = new ConcurrentHashMap<>();

    private SingletonRegistry() { }

    public static <T> void register(Class<T> type, T instance) {
        REGISTRY.put(type, instance);
    }

    public static <T> T get(Class<T> type) {           // ★ 返回类型自动正确
        Object obj = REGISTRY.get(type);
        if (obj == null) throw new IllegalStateException("未注册: " + type);
        return type.cast(obj);                          // ★ 用 Class.cast 而非强转
    }
}

// 使用：不需要强转，编译期就保证了类型
SingletonRegistry.register(UserService.class, new UserServiceImpl());
UserService svc = SingletonRegistry.get(UserService.class);   // ✅ 类型安全
Class.cast() 优于 (T) 强转

type.cast(obj) 的好处：不需要 @SuppressWarnings("unchecked")（因为编译器知道 Class<T>.cast 返回 T），而且会抛出语义更准确的 ClassCastException。这是写泛型工具类时的一个「洁癖级」技巧。

13.7 泛型事件总线（简化版）

public class EventBus {
    private final Map<Class<?>, List<Consumer<?>>> subscribers = new ConcurrentHashMap<>();

    // 订阅：类型安全
    public <E> void subscribe(Class<E> eventType, Consumer<E> listener) {
        subscribers.computeIfAbsent(eventType, k -> new CopyOnWriteArrayList<>())
                   .add(listener);
    }

    @SuppressWarnings("unchecked")
    public <E> void publish(E event) {
        List<Consumer<?>> list = subscribers.get(event.getClass());
        if (list == null) return;
        for (Consumer<?> c : list) {
            ((Consumer<E>) c).accept(event);       // 受控强转：注册时已保证类型匹配
        }
    }
}

// 使用
EventBus bus = new EventBus();
bus.subscribe(OrderCreatedEvent.class, e -> System.out.println(e.getOrderId()));
bus.publish(new OrderCreatedEvent("ORD-001"));

15.1 初级：基础概念（10 题）

初级Q1. 什么是泛型？它解决了什么问题？
答题要点

泛型是 Java 5 引入的参数化类型机制，把类型本身作为参数传递给类/接口/方法。解决三个问题：编译期类型安全、消除强制类型转换、支持泛型算法。

可复用表述

「泛型的本质是把类型从运行时提前到编译期校验。Java 5 之前集合只能存 Object，取出来必须强转，类型错误要到运行时才暴露。泛型让编译器在编译期就能拦下 list.add(123) 这种错误，同时在取出时自动插入正确的类型转换——所以它既提升了安全性，也提升了可读性。代价是引入了类型擦除，带来了一系列限制。」

可能的追问

→ 那泛型有性能开销吗？（答：泛型本身零开销，字节码就是 Object + checkcast；真正的开销是包装类的装箱/拆箱）

初级Q2. 泛型类、泛型接口、泛型方法分别怎么写？
答题要点
  • 泛型类：class Box<T> { T value; }
  • 泛型接口：interface Repo<T, ID> { T find(ID id); }
  • 泛型方法：类型参数声明在返回类型之前，public static <T> T first(List<T> list)
关键区分点（这是加分项）

泛型方法与所在类是否泛型无关。判断标准只有一个：方法自己有没有声明 <T>。普通类里可以有泛型方法；泛型类里的方法也未必是泛型方法。

可能的追问

→ 静态方法能用泛型类的类型参数吗？（不能，静态区不随实例的类型参数变化，必须自己声明 <E>）

初级Q3. 什么是类型擦除？
答题要点

编译器在生成字节码时丢弃泛型实参，把类型变量替换为其边界（无界则替换为 Object）。所以 List<String> 和 List<Integer> 在运行时是同一个类。

可复用表述

「类型擦除是 Java 泛型的实现方式。擦除规则是：无界类型变量擦除到 Object，有界类型变量擦除到最左侧边界，多边界只保留第一个。可以验证：new ArrayList<String>().getClass() == new ArrayList<Integer>().getClass() 返回 true；用 javap -c 反编译可以看到字段描述符是 Ljava/lang/Object; 而不是 T，并且在调用点有一条编译器插入的 checkcast。选择擦除是为了迁移兼容性——保证 Java 5 的代码能和 1.4 时代的已编译 class 文件互相调用。」

可能的追问

→ 为什么不用 C# 那种具化泛型？（具化需要改 JVM 指令集和 class 文件格式，无法二进制兼容；C# 是全新平台没有历史包袱）

初级Q4. List<String> 和 List<Integer> 是同一个类吗？
答题要点

运行时是同一个类（ArrayList），字节码只有一份。但编译期是两个不同的类型，不能互相赋值，编译器对它们的检查是分开的。

可复用表述

「这是类型擦除最直接的体现：编译期是两个类型，运行时是一个类型。可以这样验证——list1.getClass() == list2.getClass() 为 true；但 List<String> a = new ArrayList<Integer>() 编译不过。这个'双重身份'正是 Java 泛型所有'别扭之处'的根源：所有限制都来自'运行时不知道 T 是什么'。」

初级Q5. 什么是原始类型（Raw Type）？和 List<Object> 有什么区别？
答题要点

Raw type 是不带任何类型参数的泛型类型（List）。它们的编译产物相同，语义完全不同：List<Object> 参与泛型检查；List 会关闭所有泛型检查，只给警告。

可复用表述

「Raw type 是 Java 为兼容遗留代码留的逃生口。危险在于它会把类型安全网撕开一个口子，而且错误会传染——List raw = typedList; raw.add(123); 之后，typedList 这个看起来完全无辜的变量在下游就会抛 CCE。所以现代代码里 raw type 只该出现在三处：class 字面量（List.class）、instanceof 检查、以及和 Java 5 之前的代码互操作。」

可能的追问

→ 那 List<?> 和 List<Object> 呢？（List<?> 能接收 List<String> 但不能 add；List<Object> 相反，详见 Q8）

初级Q6. 为什么不能写 new T() 和 new T[10]？

初级Q9. 泛型能不能用于基本类型？为什么？
答题要点

不能。List<int> 非法，必须用 List<Integer>。因为擦除后类型是 Object，而 Object 装不下 int，只能用引用类型。

进阶延伸（能把这道题答出深度）

「这个限制的代价是装箱/拆箱开销。在数据量大的场景下这是真实成本——比如千万级循环里 sum += list.get(i) 会隐式调用 Integer.intValue()。这也解释了为什么 JDK 8 要引入原始类型特化的流：IntStream、LongStream、mapToInt、ToIntFunction 这一整套 API 的存在，本质就是为了绕开'泛型不支持基本类型'带来的装箱开销。Project Valhalla 想引入的值类型（value types）就是为了从根本上解决这个问题，但至今仍未正式落地。」

初级Q10. 泛型有运行时开销吗？
答题要点

泛型本身没有。字节码层面就是 Object 加一次 checkcast，没有任何额外对象或方法调用。真正的开销来自两处：包装类的装箱/拆箱（因为不支持基本类型）、以及 checkcast 的类型检查（JIT 通常能优化掉）。

可复用表述

「泛型是零运行时开销的抽象——这一点和 C++ 模板类似，但原因不同：C++ 是靠编译期展开消除抽象，Java 是靠类型擦除。需要注意的是，checkcast 本身是有成本的，但因为类型检查能被 JIT 的逃逸分析和类型推导优化掉，实测中几乎可以忽略。真正的性能问题在装箱——如果一个热路径上大量使用泛型集合装数值，应该改用原始类型数组或特化流。」

15.2 中级：机制与源码（10 题）

中级Q11. 什么是桥接方法？为什么需要它？
答题要点

擦除会让子类的「重写」变成「重载」（Node.setData(Object) vs MyNode.setData(Integer)），多态会失效。编译器通过合成一个与父类擦除后签名一致的桥接方法，把调用转发给真实现，从而修复多态。

可复用表述

「桥接方法是编译器合成的、带 ACC_BRIDGE 和 ACC_SYNTHETIC 标志的方法。它只做两件事：checkcast 转成真实类型，然后 invokevirtual 转发给真实现。可以用 javap -c -p 验证：实现 Comparable<Person> 的类里会有两个 compareTo，一个是 compareTo(Person)，一个是合成的 compareTo(Object)。」

可能的追问（这里往往藏着真问题）

→ 桥接方法在实际项目中会造成什么问题？

答案要点：三类。①反射：getDeclaredMethods() 会多出一个方法，用「方法名+参数类型」做映射的框架会混乱，需要 isBridge() 过滤；②AOP：切点可能匹配到桥接方法，导致注解读不到或通知执行两次；③框架解析：MyBatis、Spring Data 之类靠泛型反推实体的框架，需要正确处理桥接与 TypeVariable。

中级Q12. 泛型为什么是不变的？数组为什么是协变的？
答题要点

泛型不变是为了类型安全：如果 List<String> 能赋给 List<Object>，就能往里塞 Integer，破坏 String 列表的约定。数组协变是 Java 1.0 的历史遗留，代价是运行时必须做 ArrayStoreException 检查。

可复用表述

「这是 Java 类型系统里一对很有意思的反差。数组协变是早期设计的缺陷——为了让 Object[] 能接收任意数组以便写通用工具，Java 1.0 就允许了协变，代价是每次数组写入都要在运行时做类型检查。Java 5 设计泛型时吸取了教训，选择了编译期禁止而非运行时检查：与其运行时付代价，不如编译期拦住。所以泛型不变不是'麻烦'，而是用编译期的严格换来运行时的安全和零开销。需要灵活性时，用通配符引入受控型变。」

可能的追问

→ Object[] arr = new String[10]; arr[0] = 42; 会怎样？（编译通过，运行时 ArrayStoreException——这就是数组协变的代价）

中级Q13. 什么是通配符捕获？怎么解决？
答题要点

List<?> 中的 ? 是一个「未知但固定」的类型（capture）。编译器无法证明 list.get(j) 的元素与 list.set(i, ...) 期望的是同一类型，所以交换元素的代码编译不过。

解决方案（必须给出代码）
public static void swap(List<?> list, int i, int j) {
    swapHelper(list, i, j);          // 调用时 ? 被捕获为具体类型 E
}
private static <E> void swapHelper(List<E> list, int i, int j) {
    E tmp = list.get(i);
    list.set(i, list.get(j));
    list.set(j, tmp);
}
加分点

「这也是 JDK Collections.swap 的真实实现方式——公开 API 保持通配符的可读性，内部用泛型方法把类型'捕获'出来。这个模式叫 wildcard capture。」

中级Q14. 什么是堆污染？怎么避免？
答题要点

堆污染指一个参数化类型的变量指向了不是该类型的对象，导致运行时类型错误。三个来源：raw type 混用、未检查的强转、泛型可变参数。

可复用表述

「堆污染的本质是类型系统被欺骗。最隐蔽的来源是泛型可变参数——因为可变参数本质是数组，而泛型数组是被禁止创建的，JDK 在这里做了妥协：允许创建但给出 unchecked 警告，并要求你承诺不往数组里写东西。这个承诺的正式表达就是 @SafeVarargs。」

防御手段
  • 编译开启 -Xlint:all -Werror，把警告当错误
  • @SuppressWarnings 的作用域缩到最小，且必须写注释说明为什么安全
  • 接受可变参数后先拷贝再保存，不要直接持有调用方传入的数组引用
  • 能不用泛型数组就不用，优先 List

中级Q16. 泛型接口怎么在框架里做通用能力？举个你用过或见过的例子。

MyBatis-Plus 的 BaseMapper<T>、Spring Data 的 JpaRepository<T, ID>、自定义的 BaseDao<T, ID>。核心机制是：框架通过反射解析泛型父类/父接口，反推出具体的实体类型，从而自动生成 SQL、表名映射或 CRUD 实现。

中级Q17. 为什么 objectMapper.readValue(json, List.class) 会出问题？
答题要点

因为 List.class 只告诉 Jackson「这是个 List」，没有告诉它元素是什么类型。Jackson 只能退化成 LinkedHashMap。变量声明上的 <User> 在擦除后不存在，框架根本看不到。

解决方案
List<User> users = objectMapper.readValue(json,
        new TypeReference<List<User>>() {});   // 匿名子类保留泛型信息
原理（这是关键，要能讲透）

「TypeReference 的原理是利用匿名子类的 Signature 属性。虽然泛型被擦除了，但类声明处的泛型签名会以 Signature 属性形式保留在 class 文件里（这是 JVM 规范明确要求保留的，目的就是给反射和工具使用）。所以 new TypeReference<List<User>>(){} 创建的这个匿名子类，它的 getGenericSuperclass() 返回一个 ParameterizedType，里面完整保留了 List<User>。注意必须带 {}——不加花括号就没有子类，也就没有地方承载这个签名。」

可能的追问

→ 那对象实例上的泛型信息丢了吗？（丢了。保留的只是声明处的签名，不是实例的）

中级Q18. 泛型方法中的类型参数只出现一次，该优化成什么？
答题要点

换成通配符。这是《Effective Java》Item 31 的结论：类型参数的作用是在多个位置之间建立类型约束，只出现一次说明没有约束，用通配符更简洁且对调用方更宽松。

代码对比
// ❌ T 只用了一次
public static <T> void printAll(List<T> list) { ... }

// ✅ 换通配符，接受面更广
public static void printAll(List<?> list) { ... }
加分点

「但要注意不是二选一。像 Collections.addAll(List<? super T> dest, Iterable<? extends T> src) 就同时用了 <T> 和通配符——类型参数负责'建立关系'，通配符负责'放宽边界'，两者配合使用。」

中级Q19. ? extends 和泛型方法 <T extends> 看起来都能限定上界，怎么选？
答题要点

关键区别在方法体内部能不能引用这个类型。

  • List<? extends Number>：方法体里无法命名这个类型，只能当成 Number 用，不能声明同类型的新变量
  • <T extends Number> void f(List<T>)：T 是一个可命名的类型，可以声明 T tmp、返回 T、在多个参数间建立关联
可复用表述

「判断标准是你需不需要在方法体里'提到'这个类型。如果只需要读出来当上界用，通配符足够；如果要声明变量、返回它、或者让多个参数共享同一个类型，就必须用类型参数。有一个细节：通配符捕获本质上是编译器在后台帮你生成了一个匿名的类型参数，所以有时你可以在通配符方法里'调用'一个泛型方法来间接获得命名能力——这就是 Collections.swap 的做法。」

15.3 高级：深度理解（8 题）

高级Q21. Java 为什么选择类型擦除而不是具化泛型？这个选择带来了哪些代价？
答题要点（分三层）

第一层 · 为什么：迁移兼容性（Migration Compatibility）。Java 5 发布时，世界上已有海量已编译的 class 文件和第三方库。具化泛型需要修改 JVM 指令集（checkcast 要支持带参数的类）、修改 class 文件格式、并让 List<String> 有自己的 Class 对象——这些都会导致老 class 文件无法加载、老代码无法调用新 API。C# 之所以能用具化泛型，是因为它 2005 年重新设计了整个平台，没有兼容包袱。

第二层 · 代价：①不能 new T()/new T[]、不能 instanceof、不能重载（七大限制）；②运行时拿不到实例的泛型实参，导致框架必须传 Class<T> 或 TypeReference；③不支持基本类型，引入装箱开销；④产生了桥接方法这种「编译器魔法」，给反射和 AOP 带来隐患。

第三层 · 如何权衡：这些代价换来的是整个 Java 生态的平滑演进。可以对比：Kotlin 同样运行在 JVM 上，也必须遵守擦除规则；而 C#、Scala（部分）走的是另一条路。没有绝对优劣，只有权衡。

加分表述

「有意思的是，Java 团队一直在想办法'补救'：@SafeVarargs、TypeReference 模式、MethodHandles 的泛型签名保留、以及正在推进的 Project Valhalla 值类型。本质上都是在擦除的框架下，尽量把类型信息找回来。」

高级Q22. 擦除之后，运行时还能拿到哪些泛型信息？
答题要点

「运行时拿不到泛型信息」这句话只对了一半。准确说：类/方法/字段的声明处签名被保留，对象实例上的实参丢失。

技术依据

保留的机制是 class 文件里的 Signature 属性——JVM 规范明确要求保留，目的是「支持反射和其他工具」。所以 getGenericSuperclass()、getGenericInterfaces()、Field.getGenericType()、Method.getGenericReturnType() 都能拿到完整的泛型签名。

Type 接口体系（能说出这个说明真读过了）
  • Class<T> —— 原始类型
  • ParameterizedType —— 参数化类型，getRawType() / getActualTypeArguments()
  • TypeVariable —— 类型变量 T，getBounds()
  • GenericArrayType —— 泛型数组 T[]
  • WildcardType —— 通配符 ? extends X
工程意义

「这个'半保留'的特性是整个 Java 框架生态泛型能力的技术基础。Jackson 的 TypeReference、Gson 的 TypeToken、Spring 的 ResolvableType、MyBatis-Plus 的 BaseMapper<T>、Spring Data 的 Repository 泛型解析——全部建立在这个机制上。」

高级Q23. TypeReference 的原理是什么？为什么必须写 {}？
答题要点（要能写出核心代码）
protected TypeReference() {
    // getClass() 返回的是运行时类 —— 即匿名子类 TypeReference$1
    Type superClass = getClass().getGenericSuperclass();
    // 显式继承的子类，其 Signature 属性保留了泛型实参
    this.type = ((ParameterizedType) superClass).getActualTypeArguments()[0];
}
为什么必须写 {}（这是本题的核心）

「泛型信息只保留在类声明处。直接 new TypeReference<List<User>>() 会创建 TypeReference 本身的实例——而 TypeReference 的定义里是 <T>，不是 List<User>，所以拿不到具体实参。加上 {} 后，编译器会生成一个新的匿名子类，在它的 Signature 属性里写入 TypeReference<List<User>>——信息这才有了承载位置。所以 {} 不是可选的语法糖，而是这个机制能工作的前提。」

进阶延伸

→ 但它不能解析字段或方法上的泛型。如果需要更强的能力（比如 Map<String, List<User>> 里再动态替换某个类型参数），Guava 的 TypeToken.where(...) 或 Spring 的 ResolvableType 才是完整方案。

高级Q24. ResolvableType 解决了什么原生反射做不到的事？
答题要点

原生反射 API 在处理「多层继承 + 嵌套泛型 + 类型变量」时会退化：拿到的是 TypeVariable 而不是具体的 Class，需要大量手写递归。

三个具体场景
// 场景 1：多层泛型继承
// A → B<T> extends A → C extends B<User>
// 原生：getGenericSuperclass() 得到 B<T>，T 是 TypeVariable，解析不下去
// ResolvableType：自动沿继承链把 T 替换为 User

// 场景 2：嵌套泛型逐层下钻
ResolvableType t = ResolvableType.forField(MyService.class.getDeclaredField("cache"));
// Map<String, List<Order>>
Class<?> orderType = t.getGeneric(1).getGeneric(0).resolve();   // Order

// 场景 3：依赖注入时的泛型匹配
boolean match = ResolvableType.forClass(UserValidator.class)
        .as(Validator.class).getGeneric(0).resolve() == User.class;
核心价值一句话

「ResolvableType 的本质是把泛型解析从'静态类型查看'变成了'带上下文的类型推演'。原生 API 回答的是'这个 Field 声明上写了什么'，而 ResolvableType 回答的是'在这个具体的类层次结构里，这个 T 最终是什么'。后者才是框架真正需要的能力。」

高级Q25. 什么是 F-bounded 泛型？举一个实际应用。
答题要点

F-bounded（递归类型参数）指类型参数受自身约束，写法 <T extends SomeClass<T>>。用途有三：类型安全的比较（Enum<E extends Enum<E>>）、链式 Builder 的继承、同构容器。

JDK 里的例子（要能解释为什么这么写）

Enum<E extends Enum<E>> implements Comparable<E>：目的是让 compareTo 的参数必须是同一个枚举类型。如果写成 Comparable<Enum>，任意两个枚举都能比较，类型不安全；写成 Comparable<E> 又不知道 E 是什么。只有「E 是一个枚举，且它的同类就是 E 自己」这个闭环约束，才能达到目的。

工程应用（能举例的加分）
public abstract class BaseBuilder<T, B extends BaseBuilder<T, B>> {
    @SuppressWarnings("unchecked")
    protected B self() { return (B) this; }
    public B id(String id) { this.id = id; return self(); }
}
public class UserBuilder extends BaseBuilder<User, UserBuilder> {
    public UserBuilder name(String n) { ...; return this; }
}
// 关键：没有 F-bounded，父类的 id() 只能返回 BaseBuilder，
// 链式调用到这里就断了 —— .id("x").name("张三") 编译不过
跨语言对照（如果你有 C++ 背景，这是王牌）

「Java 的 F-bounded 在形态上和 C++ 的 CRTP（奇异递归模板模式）几乎一样，都用于在继承体系下保住子类型信息。C++ 靠 static_cast<T*>(this)，Java 靠 self() 加一次受控强转。区别在于 C++ 的 CRTP 是编译期静态派发、无虚函数开销；而 Java 因为擦除，self() 里的强转是运行时 checkcast，最终仍走虚方法派发。」

高级Q26. 泛型擦除对 AOP / 动态代理有什么影响？
答题要点（按代理类型分）

JDK 动态代理：基于接口生代理。由于泛型方法擦除后签名变成 Object，且存在桥接方法，可能出现：①切点匹配到桥接方法而非真方法；②注解读不到（注解在真方法上）；③通知执行两次。

CGLIB 代理：通过继承生成子类并覆写方法。泛型场景下同样可能生成桥接方法，需要注意 final 方法无法代理、以及桥接方法的调用路径。

防御性写法
@Around("execution(* com.x.service.*.*(..))")
public Object around(ProceedingJoinPoint pjp) throws Throwable {
    MethodSignature sig = (MethodSignature) pjp.getSignature();
    Method m = sig.getMethod();
    if (m.isBridge() || m.isSynthetic()) {
        return pjp.proceed();          // 桥接方法直接放行，不重复处理
    }
    // 从目标对象重新取真方法（可能来自接口）
    Method real = AopUtils.getMostSpecificMethod(m, pjp.getTarget().getClass());
    // 在 real 上读注解
    MyAnno anno = real.getAnnotation(MyAnno.class);
    ...
}
加分点

「Spring 内部其实已经做了类似处理——AopUtils.getMostSpecificMethod 和 BridgeMethodResolver 就是专门用来把桥接方法还原成真方法的工具类。如果自己写切面，直接复用它们比自己处理更稳妥。」

高级Q27. 设计一个通用 API 时，你会怎么用泛型？（开放题）
答题框架（体现方法论，比答案本身更重要）
  1. 先问：类型信息需要在多处建立关联吗？ 是 → 用 <T>；否 → 用 ?
  2. 再问：参数是生产者还是消费者？ 读 → ? extends T；写 → ? super T；读写都要 → 保持 T（PECS）
  3. 需要运行时类型吗？ 需要 → 要求调用方传 Class<T> 或 TypeReference；不需要 → 不要增加调用方负担
  4. 需要实例化 T 吗？ 需要 → 用 Supplier<T> 而非 Class<T>（无受检异常、支持有参构造）
  5. 继承体系需要保住子类型吗？ 需要 → F-bounded（B extends Builder<T, B>）
可复用表述

「设计泛型 API 我遵循两个原则。第一是Joshua Bloch 的 PECS：先把每个参数分类成生产者或消费者，再决定用 extends 还是 super，这样 API 的接受面最广、类型约束最合理。第二是'不要向调用方索要它不需要提供的东西'——如果我的实现不需要 Class<T>，就绝不把它加进签名；但如果确实需要（比如要反射创建实例或反序列化），就必须显式要，否则一定会在运行时炸。我们项目的统一响应封装 Result<T>、分页对象 PageResult<T> 和通用 DAO 都是按这个思路设计的。」

高级Q28. 如果让你改造 Java 泛型，你会怎么做？
答题要点（考察技术视野，没有标准答案）

核心矛盾是：要保留二进制兼容，就不可能完全具化。业界的探索方向有三类：

  • Project Valhalla（值类型）：引入 value class 和特化泛型，让 List<int> 这类写法成为可能且零装箱开销。同时会引入「原始类型特化」的泛型（specialized generics），但为兼容，擦除的默认行为会保留——需要显式标注才做特化。
  • Kotlin 的 inline class + reified：inline fun <reified T> 通过内联把泛型实参「写死」到调用点，从而在函数内使用 T::class。这是一个非常巧妙的绕过方案——不改变类型系统，而是用内联机制在编译期注入类型信息。
  • Scala 3 的 erased / inline 机制：类似的思路，用内联换取类型信息保留。
可复用表述（这句很容易让面试官眼前一亮）

「如果让我改，我会倾向于沿着 Valhalla 的方向走：保留擦除作为默认行为以维持兼容，但增加一个显式的'特化泛型'语法——让需要零装箱开销或需要运行时类型信息的场景可以主动选择具化，代价是接受潜在的代码膨胀和二进制不兼容。这实际上就是'渐进式具化'的思路。Kotlin 的 reified 已经证明了这个方向是可行的——它不改变 JVM 的擦除规则，而是通过 inline 在编译期把类型信息注入到调用点，是一种非常务实的折中。」

15.4 两个高频延伸题

中级Q29. 为什么转数组推荐写 toArray(new T[0]) 而不是 toArray(new T[size])？
答题要点

集合的 toArray() 有两个重载：无参版只能返回 Object[]；<T> T[] toArray(T[] a) 需要调用方把一个真实类型的实例传进来充当「类型载体」——这就是擦除下的变通方案。

关键结论

传长度 0 的数组比传精确长度更快：new T[0] 会走 Arrays.copyOf（JIT intrinsic）分支，且是编译期常量大小的分配，更容易被逃逸分析消除；而 new T[size] 走 System.arraycopy 分支，需要分配一个运行时大小的数组。

可复用表述

见 9.4 节。点睛之句：「这个设计本身就是擦除的产物——如果 Java 有具化泛型，toArray() 根本不需要这个参数。」

高级Q30. 什么情况下不该用泛型？
答题要点

泛型的价值有两个前提，缺任何一个都该重新考虑：① 同一套逻辑需要适配多个类型；② 这些类型之间的关系需要被编译器保证。

五个「用过头」的信号
  • 方法体里出现 instanceof 分支判断类型 —— 你在用泛型模拟编译期特化，而 Java 做不到
  • 类型参数超过 3 个 —— 调用方必须写全，可读性急剧下降
  • 到处 @SuppressWarnings("unchecked") —— 类型安全网已经被自己拆掉了
  • 写了 <T> 但实际只用了 1~2 种类型 —— 纯粹的过度抽象
  • 只为了省一个强制转换 —— 收益小于理解成本
可复用表述

「我的判断标准是两个条件必须同时成立：既要适配多个类型，又要让类型关系被编译器保证。如果只是'能通用'但类型之间没有关联，那用 Object 或者干脆写几个重载反而更清楚。泛型的抽象成本是真实的——它会传导到每一个调用方，所以在团队代码里我倾向于只在收益明确的地方用泛型。」

16.4 一页纸总结（面试前 3 分钟看这个）

Java 泛型 · 核心八句话
  1. 擦除是一切的前提：编译期检查 + 自动插桩，运行时 List<String> 就是 List。选擦除是为了二进制兼容。
  2. 七大限制都源自擦除：不能 new T()/new T[]/instanceof/重载/静态成员/基本类型/catch T。
  3. 不变是为了安全：对比数组协变带来的 ArrayStoreException。灵活性用通配符补。
  4. PECS：Producer → ? extends（只读）；Consumer → ? super（只写）。出 extends，进 super。
  5. 桥接方法：编译器合成的转发方法，用来修复擦除破坏的多态。会给反射和 AOP 带来坑，要用 isBridge() 过滤。
  6. 声明处的泛型信息保留了（Signature 属性），这是 TypeReference / ResolvableType / 泛型 DAO 的技术基础；实例上的实参丢失。
  7. 实战三板斧：需要 new T 用 Supplier；需要反序列化用 TypeReference；需要解析继承体系用 ResolvableType。
  8. 多边界的顺序有实质影响：擦除只保留最左边界，而擦除结果决定了方法签名的二进制形态。JDK 的 Collections.max 写作 <T extends Object & Comparable<? super T>>，那个看似多余的 Object &，是为了让擦除回退成 Object，好让二十年前编译的老字节码继续链接得上。
