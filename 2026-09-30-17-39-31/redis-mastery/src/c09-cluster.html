Day3.2 · Cluster 集群：横向扩展的工程细节

一句话结论

Cluster 的核心是16384 个哈希槽 + Gossip 去中心化 + 分片级故障转移。面试深水区在三处：① 为什么是 16384 而不是 65536；② MOVED 和 ASK 的语义区别；③ 槽迁移过程中的正确性保证（以及 8.4 的原子槽迁移解决了什么）。

2. 哈希槽：16384 的由来与路由

✅ 为什么是 16384（2^14）而不是 65536（2^16）

这是 Redis 作者 antirez 亲自回答过的经典问题，四个理由：

  1. 心跳包大小：集群节点之间通过 Gossip 协议交换信息，每个节点都要用 bitmap 表示自己负责哪些槽。16384 个槽需要 16384/8 = 2KB 的 bitmap；65536 个槽则需要 8KB。心跳包每分钟都要发，8KB 的包会显著增加带宽消耗。
  2. 集群规模的实际约束：Redis 官方建议集群主节点数不超过 1000 个。16384 个槽在 1000 个节点时平均每节点 16 个槽，已经足够。如果真要 65536 个槽支持更多节点，说明规模已经超出 Redis Cluster 的适用范围（应该用其他方案）。
  3. 位图压缩考虑：当节点负责的槽是连续区间时，bitmap 可以用「节点 ID + 槽区间」来压缩表示。槽数少时压缩效果好、发送的字节少。
  4. 避免过大的集群配置传播开销：集群配置（nodes.conf 的等价物）在节点间传播，槽数越多、结构越复杂。

面试标准答法：「16384 是权衡结果——用 2KB 的 bitmap 表示槽分配，心跳包不至于太大；而且 16384 个槽在 1000 个节点规模下平均每节点 16 个槽，已经足够。如果用到 65536，心跳包要 8KB，带宽开销明显上升，而这些槽在实际集群规模下根本用不满。」

追问：为什么不用一致性哈希？
Redis Cluster 用的是固定槽数 + CRC16 取模，而不是一致性哈希。原因：固定槽数让槽的归属可以精确控制——扩容时可以精确指定「把 1000 个槽从 A 迁到 B」，而不是一致性哈希那种「虚拟节点随机分布」的模糊控制。运维可控性是 Redis Cluster 的选择理由。

########## 槽的计算与路由 ##########
# 槽位 = CRC16(key) mod 16384

# hash tag：用 {} 包裹的部分作为哈希输入，让多个 key 落同一槽
SET {user:1001}:profile "..."     # 槽 = CRC16("user:1001") mod 16384
SET {user:1001}:cart "..."        # 同一个槽！
SET {user:1001}:order "..."       # 同一个槽！

# 这样就能用 MULTI/Lua/MGET 操作这三个 key（同槽才允许）
MGET {user:1001}:profile {user:1001}:cart     # ✅ 可以
MGET user:1001:profile user:1002:cart        # ❌ CROSSSLOT 错误

# ⚠️ 但 hash tag 是双刃剑：
#    - 好处：同槽可用原子操作
#    - 风险：如果某用户的 key 特别多，会造成"数据倾斜 + 热点集中"
#    反例：不要用 {all} 作为 tag —— 那会把所有 key 塞进一个槽！

# 计算某个 key 的槽（客户端也可以算）
CLUSTER KEYSLOT user:1001

# 手动指定槽（运维用）
CLUSTER ADDSLOTS 0 1 2 3
CLUSTER DELSLOTS 0 1
CLUSTER SETSLOT 100 NODE <node-id>
CLUSTER SETSLOT 100 MIGRATING <target-node-id>    # 标记为迁出中
CLUSTER SETSLOT 100 IMPORTING <source-node-id>    # 标记为迁入中
CLUSTER SETSLOT 100 STABLE                        # 取消迁移状态

3. MOVED 与 ASK：重定向的两种语义

✅ MOVED vs ASK（这是最高频的深挖题）
维度MOVEDASK
触发场景槽的归属已经确定在别的节点（迁移已完成或本来就在那）槽正在迁移中，key 已经迁过去了但这个槽还没正式归属于目标节点
语义「这个槽永久由 X 节点负责」「这次你去 X 节点问一下，但这个槽还是我的」
格式-MOVED 3999 127.0.0.1:6381-ASK 3999 127.0.0.1:6381
客户端行为更新本地路由表（该槽永久指向新节点），然后重定向请求不更新路由表，只对这一次请求加 ASKING 命令后转发
是否改变拓扑是（客户端缓存更新）否（临时的一次性跳转）

为什么迁移中需要 ASK 而不是直接 MOVED？

槽迁移是一个槽一个槽进行的。假设槽 100 正在从 A 迁往 B。此时：

  1. 客户端请求 GET key1，key1 的槽是 100。
  2. 请求打到 A。A 检查槽 100：标记为 MIGRATING，且 key1 已经迁走了。
  3. A 回复 -ASK 100 B——不能回 MOVED，因为槽 100 还没正式归 B（其他 key 可能还在 A）。
  4. 客户端向 B 发送 ASKING + GET key1。B 的槽 100 是 IMPORTING 状态，只有收到 ASKING 才允许处理该槽的请求（否则会拒绝，因为它不认为槽是自己的）。

如果 A 找不到 key 且槽在 MIGRATING：（key 已迁走，但 A 还负责这个槽）→ 回 ASK。
如果 A 发现槽已经完全不属于自己 → 回 MOVED。

ASKING 命令的作用：告诉目标节点「本次请求请临时处理不属于你的槽」，且只对紧随其后的下一条命令有效。

########## 亲手观察 MOVED 与 ASK ##########

# 不用 -c 参数（不跟随重定向），直接连一个节点
redis-cli -p 7001
SET user:1001 x
# 如果 user:1001 的槽不在 7001 上，会返回：
# (error) MOVED 15568 127.0.0.1:7002

# 用 -c 参数（客户端自动跟随重定向）
redis-cli -c -p 7001
SET user:1001 x      # 会自动重定向到 7002 并成功

# 手工模拟迁移过程（在两台机器上）
# 1) 目标节点：标记为导入口
redis-cli -p 7002 CLUSTER SETSLOT 100 IMPORTING <7001-node-id>
# 2) 源节点：标记为迁出中
redis-cli -p 7001 CLUSTER SETSLOT 100 MIGRATING <7002-node-id>
# 3) 查看这个槽里有哪些 key
redis-cli -p 7001 CLUSTER GETKEYSINSLOT 100 10
# 4) 逐个迁移 key
redis-cli -p 7001 MIGRATE 127.0.0.1 7002 key1 0 5000
# 5) 槽空了之后，把槽归属正式转给 7002（需要所有节点同意）
redis-cli -p 7002 CLUSTER SETSLOT 100 NODE <7002-node-id>

4. Gossip 协议与集群通信

✅ Gossip 协议：去中心化的状态同步

为什么用 Gossip 而不用中心化（如 ZooKeeper）：① 无单点故障；② 部署简单（不需要额外组件）；③ 节点增减不需要协调中心；④ 网络分区时能自然分裂处理。

消息类型（5 种）：

消息作用
MEET节点加入集群时，通过 CLUSTER MEET 发送，让新节点认识其他节点
PING每秒随机选 5 个节点发送，携带自己和其他部分节点的状态
PONG对 PING/MEET 的响应，携带自身状态
FAIL某节点被判定为客观下线后，广播 FAIL 消息给所有节点
PUBLISH转发客户端在集群中发布的 Pub/Sub 消息（广播到所有节点）

通信机制：

  • 每个节点维护一个集群节点列表（含每个节点的状态、负责的槽、最后通信时间）。
  • 每秒随机选 5 个节点发 PING，如果对方最后响应时间超过 cluster-node-timeout 的一半，则立即也给它发 PING（加速故障发现）。
  • PING/PONG 携带的信息包括：节点 ID、当前 epoch、负责的槽 bitmap、若干其他节点的状态（这就是「Gossip 传染」的来源——通过互相传递第三方的状态，最终所有节点都知道全局状态）。
  • 每次选择要 PING 的节点是「随机 5 个」，且倾向于选择「最久没通信过的节点」。

消息大小限制：Gossip 消息里携带的节点状态数量有限（CLUSTER_SLOTS 相关的 bitmap 是 2KB，加上其他信息，单个消息通常几 KB）。这也是 16384 槽的另一个理由。

故障判定（两阶段，类似哨兵）：

  1. PFAIL（疑似下线）：单个节点发现某节点超过 cluster-node-timeout 没响应，标记为 PFAIL（只在自己这里标记）。
  2. FAIL（客观下线）：该节点通过 Gossip 收集其他节点的意见，如果超过半数的主节点也认为目标节点 PFAIL，就标记为 FAIL 并广播。注意：只统计「主节点」的意见。

5. 集群故障转移

✅ Cluster 的故障转移流程

当某个主节点被标记为 FAIL：

从节点发起选举

该主节点的从节点发现主节点 FAIL，且自己满足条件（cluster-replica-validity-factor：与主节点断连时间 ≤ node-timeout × factor；且自己的数据足够新），就发起选举。

延迟随机时间后请求投票

从节点等待 500ms + random(0~500ms) + rank × 1000ms 后，向所有主节点广播 FAILOVER_AUTH_REQUEST。rank 越小（数据越新）的从节点越早发起，越容易当选。

主节点投票

收到请求的主节点，如果在当前 epoch 内还没有投过票，且认为目标主节点确实 FAIL，就投赞成票。需要获得「过半主节点」的票数（N/2 + 1）才能当选。

晋升为主节点

得票过半的从节点：① 把 currentEpoch +1 并广播；② 接管原主节点的所有槽；③ 广播 PONG 让全集群更新路由表。

处理旧主节点

旧主节点恢复后，收到广播的新配置，会自动降级为从节点并同步数据（会先清空自己的数据）。

关键差异（与哨兵对比）：

  • 哨兵需要额外部署哨兵进程；Cluster 的选举由主节点自己完成（去中心化）。
  • Cluster 的故障转移是分片级的——只影响该分片的槽，其他分片继续服务。这是 Cluster 相对哨兵的重要优势。
  • Cluster 需要「超过半数主节点」存活才能完成故障转移。所以 3 主集群挂 2 个主节点就完了（不足半数）；生产推荐至少 3 主，最好是 5 主起。
⚠️ cluster-require-full-coverage 的致命配置

cluster-require-full-coverage yes（默认）的含义是：只要有任何一个槽不可用，整个集群就拒绝所有请求（CLUSTERDOWN）。

影响：如果某个主节点挂了且它的从节点也挂了（比如同时宕机），这 1/N 的槽不可用，整个集群（包括正常的分片）全部拒绝服务。

实际建议：

  • 如果业务可以接受「部分数据不可用但其他数据正常」 → 设为 no，这样只有受影响的槽返回错误，其他槽正常服务。
  • 如果设为 no，客户端必须能处理「部分 key 报 CLUSTERDOWN 错误」的情况。
  • 配合 cluster-allow-reads-when-down yes，在集群不可用时仍允许读（默认 no 时连读都拒绝）。

能说出这个配置的取舍，说明你考虑过「降级策略」——这是架构师视角。

6. 槽迁移与 8.4 的原子槽迁移

✅ 传统槽迁移的流程与问题

流程（redis-cli --cluster reshard 内部实现）：

  1. 目标节点把槽标记为 IMPORTING，源节点标记为 MIGRATING（通过 Gossip 同步状态）。
  2. 源节点用 CLUSTER GETKEYSINSLOT 分批获取槽内的 key。
  3. 对每批 key 执行 MIGRATE（原子地把 key 从源节点搬到目标节点）。
  4. 期间如果有客户端访问「已迁走的 key」→ 返回 ASK 重定向。
  5. 槽内 key 全部迁完后，通过 Gossip 把槽的归属正式转给目标节点。

问题：

  • 慢：迁移 100 万个 key 可能需要几十分钟（MIGRATE 是同步阻塞的，且每个 key 都有一轮 RTT）。
  • 迁移期间性能受影响：MIGRATE 会阻塞源节点和目标节点的主线程，同时大量 ASK 重定向会增加延迟。
  • 可能中断：如果迁移过程中网络抖动、客户端连接被打断，迁移可能失败或部分完成，需要人工介入。

8.4 的原子槽迁移（Atomic Slot Migration）：

  • 把「一个槽的迁移」作为一个原子操作：要么整个槽迁移成功，要么完全回滚，不会留下「一半在新、一半在旧」的中间状态。
  • 迁移期间使用「增量同步」机制保证数据一致——先做一次快照式的批量传输，然后持续同步增量，最后短暂停顿完成切换。
  • 收益：① 迁移速度大幅提升、迁移期间业务影响小；② 支持零停机扩缩容；③ 迁移失败可自动重试/回滚，降低运维风险。
  • 相关命令：CLUSTER MIGRATION（8.4+）。

8.2 的 CLUSTER SLOT-STATS 是配套能力：它按槽维度统计 CPU、网络、key 数量，让你能先找出「热槽」再决定迁移哪些槽——因为盲目迁移一个热槽只会把过载转移到另一个节点。

8.6 的 HOTKEYS 更进一步：在槽内定位到具体的热 key，因为一个槽内可能只有一两个 key 消耗了绝大部分资源，迁移槽解决不了根本问题，得改数据模型。

7. 客户端如何接入 Cluster

/**
 * Lettuce 接入 Cluster（Spring Boot 3.x）
 */
@Configuration
public class RedisClusterConfig {

    @Bean
    public LettuceConnectionFactory clusterFactory() {
        RedisClusterConfiguration config = new RedisClusterConfiguration(
            Arrays.asList(
                "10.0.0.11:7001", "10.0.0.12:7001", "10.0.0.13:7001"
                // 注意：不需要列出所有节点！客户端会通过 CLUSTER SLOTS 发现完整拓扑
            ));

        // 连接池（注意：集群下每个节点都会建池，总连接数 = 池大小 × 节点数）
        LettucePoolingClientConfiguration poolConfig = LettucePoolingClientConfiguration.builder()
            .poolConfig(new GenericObjectPoolConfig<StatefulConnection<byte[],byte[]>>() {{
                setMaxTotal(32);
                setMaxIdle(16);
                setMinIdle(4);
                setMaxWait(Duration.ofMillis(1000));
            }})
            .commandTimeout(Duration.ofSeconds(3))
            .build();

        // 关键：拓扑刷新策略
        LettuceClientConfiguration clientConfig = LettuceClientConfiguration.builder()
            .clientOptions(ClusterClientOptions.builder()
                .maxRedirects(3)                                   // MOVED/ASK 最大重定向次数
                .topologyRefreshOptions(ClusterTopologyRefreshOptions.builder()
                    // ① 定期刷新（兜底）
                    .enablePeriodicRefresh(Duration.ofSeconds(60))
                    // ② 自适应刷新（推荐）：遇到 MOVED 或连接失败时立即刷新
                    .enableAllAdaptiveRefreshTriggers()
                    .adaptiveRefreshTriggersTimeout(Duration.ofSeconds(30))
                    .build())
                .autoReconnect(true)
                .build())
            .clientOptions(ClientOptions.builder().build())
            .timeout(Duration.ofSeconds(3))
            .build();

        return new LettuceConnectionFactory(config, clientConfig);
    }
}
🚨 Cluster 客户端的四个致命坑
  1. 拓扑刷新没配好 → 故障转移后客户端一直报错：故障转移后槽归属变了，如果客户端不刷新路由表，会持续收到 MOVED 或连到旧节点。必须开启自适应刷新（enableAllAdaptiveRefreshTriggers）。
  2. 池大小 × 节点数 = 总连接数：3 主 3 从，每节点池 32 连接 → 如果客户端对主从都建池，就是 192 个连接/实例。50 个应用实例 = 9600 个连接。很容易打爆 Redis 的 maxclients。
  3. 跨槽操作直接失败：MGET k1 k2 如果 k1/k2 不同槽 → CROSSSLOT 错误。解法：用 hash tag 保证同槽，或在客户端拆成多次单 key 请求（性能差），或用 pipeline 分组发送。
  4. Lua 脚本跨槽不可用：脚本里涉及的 key 必须同槽。所以「用 Lua 做分布式锁」在集群下要确保锁 key 的所有操作在同一个 key 上（一般是同一个 key，没问题）；但「Lua 里操作多个不同业务的 key」会很麻烦。

面试深度问答

Redis Cluster 的原理？16384 个槽是怎么用的？基础

核心机制：

  1. 分片：整个键空间被划分为 16384 个哈希槽，每个主节点负责一部分槽。CLUSTER KEYSLOT key 计算槽位，公式是 CRC16(key) mod 16384。
  2. 路由：客户端请求任一节点，节点计算 key 的槽；如果槽不属于自己，返回 MOVED 重定向，客户端更新本地路由表并发到正确节点。
  3. 通信：节点间用 Gossip 协议交换状态（每秒随机 PING 5 个节点），最终达成全局一致。
  4. 高可用：每个主节点可挂 N 个从节点；主节点 FAIL 后，从节点通过 Raft-like 选举（需要过半主节点投票）晋升为主。
  5. 去中心化：没有中心节点，每个节点都保存完整的集群拓扑信息（槽 → 节点的映射）。

16384 的由来：见本节第 2 节（心跳包大小 / 集群规模 / 压缩考虑）。

hash tag：用 {} 包裹的部分作为哈希输入，让多个 key 落同一槽，从而支持多 key 原子操作。但要注意不能滥用，否则会造成数据倾斜。

MOVED 和 ASK 的区别？进阶

见本节第 3 节的对比表。核心一句话：

  • MOVED = 永久性重定向：槽的归属变了，客户端应该更新本地路由表。触发场景是「槽已经不属于当前节点」。
  • ASK = 临时性重定向：槽正在迁移中，当前节点仍认为槽是自己的（还有别的 key 在这个槽里），只是你要的这个 key 已经搬到新节点了。客户端不能更新路由表，只对本次请求加 ASKING 转发一次。

为什么需要 ASK：槽迁移是逐 key 进行的，期间槽会处于「一部分 key 在源节点、一部分在目标节点」的中间状态。如果这时回 MOVED，客户端会把整个槽都指向目标节点，但源节点上剩下的 key 就访问不到了。

ASKING 命令的作用：目标节点的槽处于 IMPORTING 状态时，默认会拒绝不属于自己的槽的请求（回 MOVED 让客户端去真正的归属节点）。ASKING 告诉它「这次请求请临时服务一下」，且只对下一条命令有效。

关键洞察：Cluster 的优点不只是「容量大」，还有「故障隔离」——一个分片挂了，只有它负责的槽不可用，其他槽继续服务（前提是 cluster-require-full-coverage no）。而哨兵架构下，主节点挂了就是全局不可写。

追问准备：为什么 Cluster 需要「过半主节点」而不是「过半节点」？
因为从节点不参与投票（它们的意见在 PFAIL 判定中也不计入）。只统计主节点能避免「从节点数量多的一方获得不当优势」，也让投票规模更稳定。

Cluster 模式下如何做多 key 操作和批量操作？高级

方案一：hash tag 强制同槽（首选）

SET {order:1001}:detail ...
SET {order:1001}:items ...
# 两个 key 同槽，可以 MGET / MULTI / Lua
MGET {order:1001}:detail {order:1001}:items   # ✅

注意：hash tag 会让这些 key 集中在同一个节点。如果某个 tag（比如某个大客户）的数据量特别大，会造成数据倾斜和热点集中。所以：用「业务实体 ID」做 tag 是合理的，用「业务类型」或「全局标签」做 tag 是灾难。

方案二：客户端分组 + Pipeline

把不同槽的 key 按槽分组，每组一个 pipeline 发到对应节点。Lettuce 的 ClusterConnectionProvider 会自动做类似的事（对 pipeline 中的命令按槽分组）。优点是透明，缺点是数据量小时网络 RTT 次数变多。

方案三：批量操作落离线任务

如果是「定期统计/清理」类的批量操作，不要在 Redis 里做——把 key 列表拿出来，用离线任务分片并发处理。

方案四：不用 Cluster

如果业务天然需要大量跨 key 原子操作（比如「一次事务涉及 10 个不同实体」），Cluster 会带来巨大改造成本。这时应该考虑：① 用哨兵架构（但容量受限）；② 把强一致操作下沉到数据库（DB 事务天然支持跨表）；③ 重新划分数据模型，让原子操作限定在单个实体范围内。

面试话术：「Cluster 下的多 key 操作本质上是个数据模型设计问题。如果发现某个功能大量需要跨槽原子操作，通常说明两件事之一：要么该业务不该放在 Cluster，要么数据模型需要按「聚合边界」重新划分——让「需要原子操作的一组数据」落在同一个实体 ID 下，用 hash tag 保证同槽。后者往往还能提升业务的内聚性。」

集群扩容时怎么保证不丢数据、不影响业务？专家

按「准备 → 执行 → 验证 → 回滚」四阶段回答，这是架构师级别的答复：

一、扩容前准备

  1. 容量评估：算清需要迁多少个槽（CLUSTER COUNTKEYSINSLOT / CLUSTER SLOT-STATS 评估每个槽的 key 数和资源消耗）。
  2. 识别热槽：用 8.2 的 CLUSTER SLOT-STATS ORDERBY CPU 找出 CPU/网络最重的槽。不要盲目迁移热槽——迁过去只是把过载转给新节点。热槽应该先用 8.6 的 HOTKEYS 定位到具体热 key，改数据模型解决。
  3. 选择时间窗口：低峰期执行。迁移过程中 MIGRATE 会阻塞主线程，同时产生大量 ASK 重定向。
  4. 备份：全集群 RDB/AOF 备份，并验证可恢复。
  5. 限速：redis-cli --cluster reshard 支持 --cluster-timeout 等参数控制；也可以用 CLUSTER MIGRATION 的批量控制（8.4）。关键是控制单位时间迁移的 key 数量，避免打满带宽和 CPU。

二、执行

  1. 加入新节点（--cluster add-node），新节点初始没有槽。
  2. 分批次迁移槽：每批 100-500 个槽，观察主从延迟、CPU、p99 延迟、ASK/MOVED 次数等指标。
  3. 每批之间暂停观察，确认没有异常再继续。不要一次迁完。
  4. 迁移完成后，为新节点补上从节点（提高可用性）。

三、验证

  • redis-cli --cluster check 确认槽分配均衡、无 fail 槽。
  • 抽样验证数据完整性（随机取 key 对比迁移前后、或抽样比对总 key 数）。
  • 压测确认吞吐和延迟符合预期。
  • 监控 24-48 小时，观察是否有 ASK/MOVED 异常增长。

四、回滚预案

  • 如果出现严重问题：把槽迁回原节点（反向 reshard）。所以迁移前要记录原始的槽分配方案。
  • 如果迁移中断在中间状态：用 CLUSTER SETSLOT ... STABLE 清理状态，或 --cluster fix 修复。
  • 8.4 的原子槽迁移让这个过程更安全——迁移失败可以自动回滚，不会留下中间状态。

补充：容量规划的经验值

  • 单实例内存不要超过 10-16GB（影响 fork 时间、全量同步时间、故障恢复时间）。
  • 槽数尽量均匀：16384 / 主节点数 尽量整除或接近；不均匀会导致数据倾斜。
  • 主节点数建议 3、5、7（奇数），保证多数票可达。
  • 预留 30% 容量用于峰值和 COW。
Cluster 有什么限制和坑？高级

列全（能列全说明你真用过）：

  1. 只有 db0：不能使用 SELECT 切换库。原来靠分库隔离业务的方案要改成 key 前缀隔离。
  2. 多 key 操作必须同槽：MGET/MSET/SINTERSTORE/RENAME 等，跨槽直接报 CROSSSLOT。
  3. Lua 脚本和事务不能跨槽。
  4. 哈希 tag 带来的数据倾斜风险：用错 tag 会把所有 key 塞进一个槽。
  5. 客户端复杂度：需要支持 MOVED/ASK 重定向、拓扑刷新、故障重试。
  6. 运维复杂度：槽迁移、节点扩缩容、监控、故障排查都比单机复杂得多。
  7. cluster-require-full-coverage 默认 yes：一个槽不可用整个集群拒绝服务。
  8. Pub/Sub 是广播的：普通 Pub/Sub 消息会广播到所有节点（7.0 引入 Sharded Pub/Sub，用 SSUBSCRIBE/SPUBLISH 让消息只在该分片内传递，大幅降低开销）。
  9. keys 数统计：DBSIZE 只返回当前节点的 key 数，要全集群统计需遍历所有主节点。
  10. 故障转移期间可能丢数据：异步复制，如果主节点在故障前写入的数据还没同步到从节点，切换后会丢。
  11. 节点重启后可能引发全量同步：如果从节点长时间离线，backlog 不够，全量同步会打满带宽。
  12. slot bitmap 的 Gossip 开销：节点数多时 Gossip 流量上升。

加分收尾：「这些限制的核心原因只有一个——Cluster 用『数据分布在多个节点』换来了扩展性，代价就是所有跨节点的原子性和操作变得昂贵或不可用。所以关键判断是：你的业务是否天然可分片。缓存、用户维度的数据天然可分；而强关联的复杂事务、报表类全局统计，就不适合放 Cluster。」
