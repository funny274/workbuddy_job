Day 5 · 第 3 节 预计 120 分钟 面试决胜环节

Day5.3 · 大厂场景题实战手册（12 个高频真题）

一句话结论

八股文决定你能不能进面试，场景题决定你能拿什么级别。10 年+ 岗位的场景题考察的不是「你会不会用某个命令」，而是「你能不能把业务需求翻译成合理的数据模型，并说清这样设计的代价和边界」。

本节给出 12 个高频场景，每个都按「需求分析 → 数据结构选型 → 核心实现 → 边界与代价 → 面试追问」五步展开。建议你先自己想想再往下看——这种「先想再对答案」的方式记忆最深。

✅ 场景题的通用答题框架（先建立方法论）

不管遇到什么场景题，都按这五步走：

第一步：澄清需求与约束（别急着答）

主动问清楚：数据规模（多少用户/多少 QPS/数据量多大）？一致性要求（能容忍多少延迟/不一致）？是否有持久化要求？读写比例？
这一步本身就是加分项——展示你不会盲目设计方案，而是先理解问题边界。

第二步：选数据结构 + 说清为什么

不是「我用 ZSet」，而是「用 ZSet，因为需要按分数排序 + 范围查询，这两个需求 ZSet 的跳表实现都是 O(logN)」。关键是「需求 → 结构特性」的对应关系。

第三步：给出核心实现（命令级或代码级）

写出关键的 Redis 命令或代码片段，证明你确实能落地。

第四步：主动说清边界与代价（关键）

这一步是区分「会用」和「能架构」的分水岭。主动说出：这个方案在什么规模下会出问题？有哪些一致性问题？故障了怎么办？面试官最想听的就是这个。

第五步：准备被追问的点

每个方案都有「深挖点」，提前准备好。比如做排行榜，面试官一定会追问「数据量到 1 亿怎么办」「分页怎么优化」「ZSet 底层是什么」。

场景 1：缓存与数据库一致（⭐ 最高频）

题目

「你们系统怎么保证缓存和数据库的一致性？如果并发更新出现脏数据怎么办？」

完整答法见 Day4.1，这里给出「面试速答版」：

  1. 先分级：「我会先区分一致性要求——强一致（用 DB 行锁，不用缓存）、最终一致（99% 场景，用 Cache Aside）、弱一致（定时刷新）。」
  2. 主流方案：「Cache Aside：先更新 DB，再删缓存。加『删除失败进 MQ 重试』兜底。」
  3. 为什么这样最优：「产生脏数据需要『读 DB 在 UPDATE 前 + 写缓存在 DEL 后』，即『读的整链路比写还慢』。而写 DB（加锁落盘）通常远慢于读 DB，所以概率极低。」
  4. 更强方案：「并发写更高的场景用延时双删 + 版本号比对；大型系统用 Canal 订阅 binlog（业务零侵入、binlog 不丢）。」
  5. 兜底三件套：「① 所有缓存设 TTL（最终自愈）；② 命中率监控；③ 关键业务对账任务。」
💡 追问准备

为什么删缓存而不是更新缓存？（三个理由：避免并发覆盖、避免无用功、避免复杂计算）／延时双删延迟多久？（200ms-1s，没有精确答案，更好的方案是版本号）／Canal 的延迟和代价？（几十到几百毫秒，需要 Canal + MQ）

场景 2：秒杀扣库存（⭐ 高频）

题目

「双 11 秒杀，1 万件商品，瞬间 100 万用户抢。怎么设计？怎么防超卖？」

第一步：澄清——「QPS 峰值多少？能不能接受少量超卖？库存的准确性要求到什么程度？」（通常：极高并发、绝对不允许超卖）

第二步：核心思路（分层削峰）

① 前端层：限流 + 防重复提交

按钮置灰、验证码、令牌桶限流（把 100 万请求砍到 10 万）。这是最有效的——把流量挡在最外层。

② Redis 层：预扣减（Lua 保证原子性）
-- 库存预扣减脚本（原子）
-- KEYS[1] = stock:sku1001, ARGV[1] = 购买数量
local stock = tonumber(redis.call('GET', KEYS[1]) or '-1')
local need = tonumber(ARGV[1])
if stock < need then
    return -1          -- 库存不足
end
redis.call('DECRBY', KEYS[1], need)
return stock - need

扣减成功 → 生成订单号 → 异步落库（发 MQ，由消费者写 DB）。

③ 热点库存分桶（解决热 key）

如果 1 万件都在一个 key，单分片会被打爆。拆成 100 个桶：stock:sku1001:0 ~ stock:sku1001:99，每桶 100 件，请求随机落到一个桶扣减。

int bucket = ThreadLocalRandom.current().nextInt(100);
String key = "stock:sku1001:" + bucket;
Long remain = eval(deductScript, key, num);
if (remain < 0) {
    // 本桶不足，可以尝试其他桶（提高成功率），或直接返回失败
}

代价：某个桶卖完了但其他桶还有 → 会「提前售罄」。缓解：桶数量多一些（如 100-1000），或者失败时轮询其他桶。

④ DB 层：兜底防超卖
-- 最终的防线：DB 层的条件更新（即使 Redis 出问题，也不会真的超卖）
UPDATE stock SET num = num - #{n} WHERE sku_id = #{id} AND num >= #{n};
-- 影响行数为 0 → 回滚，取消订单，并把库存还回 Redis

第四步：边界与代价（关键）

  • Redis 挂了怎么办：库存预扣减依赖 Redis。降级方案：① 直接走 DB 的 `UPDATE ... WHERE num >= n`（DB 有行锁，能保证不超卖，但 QPS 低）；② 限量放行（只放 DB 能承受的流量）。
  • Redis 扣减成功但订单创建失败：需要库存回补机制（订单超时未支付 → 定时任务把库存还回 Redis + DB）。要处理「重复回补」问题（幂等）。
  • 异步落库失败：MQ 要有重试 + 死信队列 + 人工兜底；同时 DB 层是最终防线（超卖可以被发现并纠正）。
  • 分桶带来的「提前售罄」：用户体验受损（明明还有货却说没货）。要权衡「桶的粒度」和「准确性」。
  • 库存的最终一致性：Redis 和 DB 可能不一致，需要对账任务定期校正。
💡 追问准备

为什么不用 Redis 事务／为什么用 Lua？（Lua 支持条件逻辑且原子）／为什么不用分布式锁？（100 万并发抢同一把锁，锁本身就是瓶颈）／库存放在 Redis 里，Redis 挂了会少卖吗？（会，所以要有降级和回补）／「1 万件 100 万人抢」真正有效的解法是什么？（大头是「限流 + 异步」，真正到 Redis 的请求应该是可控的，比如用「预约/抽签」把 100 万人先筛一遍）

场景 3：排行榜（⭐ 高频）

题目

「做一个直播平台的礼物排行榜（主播排行、日榜/周榜/月榜），怎么设计？」

第二步：数据结构 —— ZSet（按分数排序 + 范围查询，跳表实现都是 O(logN)）

########## 基础实现 ##########
# 用户送礼物 → 给主播加分
ZINCRBY rank:gift:daily:20260930 100 anchor:1001

# 取 Top 10（降序）
ZREVRANGE rank:gift:daily:20260930 0 9 WITHSCORES

# 查某个主播的排名（从高到低）
ZREVRANK rank:gift:daily:20260930 anchor:1001   # 返回 0-based 排名

# 查某个主播的分数
ZSCORE rank:gift:daily:20260930 anchor:1001

########## 周榜/月榜的实现方式 ##########
# 方式一：每个周期一个独立 key（推荐）
ZINCRBY rank:gift:week:2026W40 100 anchor:1001
ZINCRBY rank:gift:month:202609 100 anchor:1001

# 方式二：查询时用 ZUNIONSTORE 合并日榜（灵活但开销大）
ZUNIONSTORE rank:week:tmp 7 \
  rank:gift:daily:20260924 rank:gift:daily:20260925 \
  rank:gift:daily:20260926 rank:gift:daily:20260927 \
  rank:gift:daily:20260928 rank:gift:daily:20260929 \
  rank:gift:daily:20260930 \
  AGGREGATE SUM
# ⚠️ 复杂度是 O(N)，且临时 key 占内存，仅适合小规模或离线计算
# 生产推荐用「离线任务（如 Flink/Spark）算好周榜，写入 Redis」

第四步：边界与代价（这是重点）

问题解法代价
数据量太大（如 1 亿主播） ① 只保留 Top N：用 ZREMRANGEBYRANK 定期裁掉尾部
② 分片：按主播 ID 区间拆成多个 ZSet		 ① 排行榜之外的排名不准确
② 跨分片的全局排序需要额外聚合
深分页（查第 10000 名） ZSet 的 ZREVRANGE start stop 是 O(logN + M)（M 是返回数量），不是 O(N)，所以深分页其实是可接受的 ⚠️ 但「查某人的排名」ZREVRANK 是 O(logN)，没问题；如果是 MySQL 的 LIMIT 10000, 10 才是大问题
分数相同怎么排 ZSet 按「分数相同则按 member 字典序」排。
要自定义次序（如「同分先到先得」）→ 把时间戳编进分数		 分数变成复合结构，可读性下降
「同分先到先得」的分数设计 score = 礼物值 * 10^10 + (10^10 - 时间戳秒)
这样礼物值相同时，时间越早分数越高		 分数超出 double 精度会有问题（ZSet 分数是 double，53 位有效位）
历史榜单要保留多久 日榜设 7 天 TTL、周榜 30 天、月榜 90 天（按需） —
大主播的榜单调不动 — ZSet 的 ZINCRBY 是 O(logN)，1 亿 member 也就是 27 次比较，不是问题
⚠️ 一个真实的排行榜优化：不要「只保留 Top N 就完事」

「我们做过一个主播排行榜，一开始为了控制内存，用 ZREMRANGEBYRANK 只保留 Top 1000。结果产品要求『显示我自己的排名』——一个排在 5 万名的主播打开页面，发现显示不出自己的排名。

改进方案：① Redis 里保留完整的榜（按容量评估，100 万 member 的 ZSet 大约占 100-200MB，可以接受）；② 如果确实要控制内存，对「非 Top 用户」用单独的轻量结构记录分数（如 Hash），只在需要时计算排名。

教训：做数据模型设计时，一定要把「产品的完整需求」问清楚，而不是只按「技术最省资源」的方式做。」

场景 4：延时队列（⭐ 高频）

题目

「订单 30 分钟未支付要自动取消，怎么实现？（不能用定时任务扫全表那种低效方案）」

方案实现优点缺点
方案一：ZSet + 轮询
推荐		 把「执行时间戳」作为 score，订单号作为 member。定时任务每 N 秒查 ZRANGEBYSCORE key 0 now LIMIT 100，取出到期任务执行并删除 实现简单、可靠、支持任意延迟时间、可用 ZSet 天然排序 轮询有延迟（精度取决于轮询间隔）；需要处理「多实例并发轮询」（用分布式锁或 Lua 的原子取+删）
方案二：Stream + 消费者组（7.0+） 用 XADD 写入消息，用 XREADGROUP 消费、XACK 确认 原生 MQ 语义（消费者组、ACK、重试）；7.0 支持 XADD ... IDMP 幂等 Stream 本身不支持延时，需要消费端自己 sleep 或者用「延时 + 定时搬运」的组合
方案三：MQ 的延时消息（RocketMQ / RabbitMQ） 用 MQ 原生的延时能力（RocketMQ 支持 18 个延时级别） 最省事，可靠性最好 精度受限于 MQ 支持的延时级别（如 RocketMQ 只有固定几档）
方案四：时间轮（Netty / Kafka 内部） 内存中的时间轮结构 延迟精度高 ❌ 单机内存实现，重启丢失，不适合分布式可靠场景

方案一的完整实现（含关键的「原子取出」问题）

-- ⭐ 原子取出到期任务（解决多实例并发轮询的重复消费问题）
-- KEYS[1] = delay queue zset, ARGV[1] = 当前时间戳, ARGV[2] = 批量大小
local tasks = redis.call('ZRANGEBYSCORE', KEYS[1], 0, ARGV[1],
                          'LIMIT', 0, tonumber(ARGV[2]))
if #tasks > 0 then
    -- ⭐ 同一个脚本里"取出 + 删除"是原子的，多个实例不会拿到同一批任务
    redis.call('ZREM', KEYS[1], unpack(tasks))
end
return tasks
// 轮询调度（每 1 秒执行一次）
@Scheduled(fixedDelay = 1000)
public void pollDelayQueue() {
    long now = System.currentTimeMillis();
    // 原子取出最多 100 个到期任务
    List<String> tasks = (List<String>) redisTemplate.execute(
        new DefaultRedisScript<>(POLL_SCRIPT, List.class),
        Collections.singletonList("delay:queue:order"),
        String.valueOf(now), "100");

    if (tasks == null || tasks.isEmpty()) return;

    for (String orderNo : tasks) {
        try {
            orderService.cancelIfUnpaid(orderNo);   // ⚠️ 必须幂等（查状态再取消）
        } catch (Exception e) {
            // 失败 → 重新投递（但要加最大重试次数，防止死循环）
            retryOrDeadLetter(orderNo, e);
        }
    }
}

// 投递（下单时）
public void submitDelayTask(String orderNo, long delayMs) {
    long executeAt = System.currentTimeMillis() + delayMs;
    redisTemplate.opsForZSet().add("delay:queue:order", orderNo, executeAt);
}

第四步：边界与代价

  • 多实例重复消费：用 Lua 的「原子取+删」解决。但如果任务执行失败，任务已经从 ZSet 删了，怎么重试？ → 需要「重试队列」或「把失败任务放回 ZSet（加下一次执行时间）」。
  • 任务丢失风险：ZSet 是内存结构，如果不做持久化，Redis 重启后延时任务全丢。解法：① 开 AOF；② 更好的做法是「DB 存任务状态 + Redis 只做调度」——即使 Redis 丢了，可以用定时任务扫 DB（兜底）重建。
  • 轮询间隔的权衡：1 秒轮询 → 延迟最多 1 秒，但 QPS 也上去了（每秒一次查询）。如果是海量延时任务，要评估轮询的成本。
  • 精度要求高（如 100ms 精度）→ Redis 轮询不合适，要用时间轮或专门的调度系统。
  • 任务量极大（千万级）→ ZSet 内存占用高（每个 member 几十字节 + 跳表开销）。考虑分片（按时间分多个 ZSet）或用专门的延时消息 MQ。
💡 追问准备

为什么不用 keyspace notification（key 过期通知）？（不可靠：过期事件是「被动触发」的——只有在 key 被访问或定期删除时才触发，可能延迟很久甚至不触发；而且 Redis 不保证送达）／ZSet 的 score 用时间戳会有精度问题吗？（没有，毫秒时间戳约 10^12，double 有 53 位有效位能精确表示到 10^15）／怎么保证「取消订单」的幂等？（查订单状态，只有「待支付」才取消）

场景 5：分布式限流（⭐ 高频）

题目

「API 网关要对每个用户限流到 100 QPS，怎么实现？」

算法原理优点缺点
固定窗口计数器 INCR + EXPIRE，每 1 秒一个 key 最简单、内存最省 ❌ 临界问题：0.9 秒的 100 次 + 1.1 秒的 100 次 = 0.2 秒内 200 次
滑动窗口（ZSet） ZSet 存请求时间戳，用 ZREMRANGEBYSCORE 清理窗口外的 ✅ 精确 ❌ 每个请求都要存一个 member，内存开销大
滑动窗口（Redis 8 / RedisCell） 用近似算法（结合计数器和滑动） ✅ 内存开销小、精度可接受 需要 8.x 或额外模块
令牌桶 / 漏桶 <strong>允许一定程度的突发</strong>，用 Lua 实现「补充令牌 + 消费」 ✅ 符合真实流量特征（允许突发） 实现稍复杂 
-- ⭐ 固定窗口计数器（简单版，大多数场景够用）
-- KEYS[1] = 限流 key, ARGV[1] = 窗口秒数, ARGV[2] = 阈值
local current = redis.call('INCR', KEYS[1])
if current == 1 then
    -- ⭐ 只有第一次才设过期，避免每次刷新 TTL 导致窗口永不过期
    redis.call('EXPIRE', KEYS[1], ARGV[1])
end
if current > tonumber(ARGV[2]) then
    return 0
end
return 1
-- ⭐ 令牌桶（允许突发，更符合真实业务）
-- KEYS[1] = bucket key
-- ARGV[1] = 桶容量, ARGV[2] = 每秒补充速率, ARGV[3] = 当前时间(秒), ARGV[4] = 请求令牌数
local capacity   = tonumber(ARGV[1])
local rate       = tonumber(ARGV[2])
local now        = tonumber(ARGV[3])
local requested  = tonumber(ARGV[4])

-- 获取当前桶状态：tokens（令牌数）, lastTime（上次补充时间）
local bucket = redis.call('HMGET', KEYS[1], 'tokens', 'lastTime')
local tokens   = tonumber(bucket[1]) or capacity
local lastTime = tonumber(bucket[2]) or now

-- 按时间差补充令牌（不能超过容量）
local delta = math.max(0, now - lastTime)
tokens = math.min(capacity, tokens + delta * rate)

-- 判断是否够用
if tokens < requested then
    -- 令牌不足 → 写回状态，拒绝
    redis.call('HMSET', KEYS[1], 'tokens', tokens, 'lastTime', now)
    redis.call('EXPIRE', KEYS[1], math.ceil(capacity / rate) * 2)
    return 0
end

-- 扣减令牌并写回
tokens = tokens - requested
redis.call('HMSET', KEYS[1], 'tokens', tokens, 'lastTime', now)
redis.call('EXPIRE', KEYS[1], math.ceil(capacity / rate) * 2)
return 1
⚠️ 关于「滑动窗口 ZSet 版」
-- 滑动窗口（精确版，但内存开销大）
local now = tonumber(ARGV[1])
local window = tonumber(ARGV[2])       -- 窗口大小（毫秒）
local limit = tonumber(ARGV[3])
-- 清理窗口外的记录
redis.call('ZREMRANGEBYSCORE', KEYS[1], 0, now - window)
-- 统计当前窗口内的请求数
local count = redis.call('ZCARD', KEYS[1])
if count < limit then
    redis.call('ZADD', KEYS[1], now, now .. '-' .. math.random())
    redis.call('PEXPIRE', KEYS[1], window)
    return 1
end
return 0

为什么生产上慎用：假设限流 100 QPS，最坏情况下 ZSet 里有 100 个 member，每个 member 约 50-100 字节 → 单个用户约 10KB。如果有 10 万活跃用户同时被限流，就是 1GB 内存。而且每个请求都要 ZREMRANGEBYSCORE + ZCARD + ZADD 三条命令（用 Lua 合并成一条）。

实践建议：① 大多数场景用固定窗口 + 令牌桶就够了；② 需要精确滑动窗口时用 Redis 8 的原生支持或 RedisCell 模块（用近似算法，内存开销小得多）；③ 限流维度不要太多（用户 + IP + 接口三个维度，key 数量就是三倍）。

场景 6：UV / 日活统计（⭐ 高频）

题目

「统计每天的 UV（独立访客数），1 亿用户量级，怎么实现？」

方案演进（体现你的思考深度）

方案实现内存（1 亿用户）精度

########## Bitmap 方案（精确，要求 ID 是连续整数）##########

SETBIT uv:20260930 10086 1
SETBIT uv:20260930 20345 1

# 返回：5（约 0.81% 误差，即实际 100000 个用户可能报 99190 或 100810）

PFCOUNT uv:hll:week
# 统计这 7 天的累计去重 UV（不用一个一个 Set 去合并！）
✅ Bitmap vs HyperLogLog 的选型（面试必须说清楚）
维度BitmapHyperLogLog
内存与「最大 ID」成正比（1 亿位 = 12.5MB）固定 12KB
精度精确约 0.81% 标准误差
前置要求ID 必须是连续整数（或有可控范围）任意元素（字符串也行）
能否判断「某个用户是否存在」✅ 能（GETBIT）❌ 不能（只能估算总数）
能否做交集/留存分析✅ 能（BITOP AND/OR）⚠️ 只能合并（PFMERGE）求并集，不能求交集
适用ID 是数字、需要精确、需要做留存/漏斗分析只要一个总数（UV、PV 去重）

关键决策逻辑：

  1. 只需要「总数」且元素可能是字符串 → HyperLogLog。
  2. 需要「精确」或「判断个体是否存在」或「做交集分析」 → Bitmap（前提是 ID 是可控范围内的整数）。
  3. ID 是超大的稀疏数字（如 64 位 UUID 转数字） → Bitmap 会浪费大量空间。解法：① 用 HLL；② 或者维护一个「用户 ID → 连续序号」的映射（用 Redis 的 Hash 或 DB），把稀疏 ID 压缩成连续序号再用 Bitmap。
⚠️ Bitmap 的三个坑
  1. 偏移量必须是「能算出来的整数」：如果 userId 是 UUID（32 位十六进制），没法直接做 bit 偏移。需要先映射成序号。
  2. 位数组会「按最大偏移量分配」：如果只有 1 个用户但 ID 是 10 亿，那 Bitmap 就要占 125MB。所以要求 ID 密集或者能被映射压缩。（Redis 内部用 SDS 存储 bit 数组，如果高偏移位设置了，前面的低偏移位会全部补 0，用真实内存占位。）
  3. 时间维度的 key 数量：每天一个 key，一年 365 个。每个 12.5MB（如果是 1 亿用户）→ 一年约 4.5GB。要设置合理的 TTL（如 90 天），并评估总量。

场景 7：签到 / 打卡（⭐ 中频）

题目

「用户签到功能，要支持『本月签到记录』『连续签到天数』，怎么设计？」

########## 用 Bitmap 存一个月（每月一个 key）##########
# key 设计：sign:uid:1001:202609
# bit 偏移量 = 日期（1-31）

# 用户在 9 月 30 日签到（第 30 天）
SETBIT sign:uid:1001:202609 30 1

# 查看本月签到次数
BITCOUNT sign:uid:1001:202609
# 返回：签到天数

# 查某天是否签到
GETBIT sign:uid:1001:202609 30

# ⭐ 一次拿到整个月的签到明细（前端渲染日历）
# 在应用层把返回的 Bitmap（字节串）按位解析成日期数组
# 也可以 GET 拿到原始字节，然后 Java 里用 BitSet 解析

########## 统计「连续签到天数」的两种方案 ##########

# 方案 A：简单粗暴 —— 应用层解析 Bitmap 后从今天往前数
# （数据量小，一次 GET 拿一个月的数据，在内存里数，完全没问题）

# 方案 B：用 BITFIELD 做位段操作（更高级）
# 但连续天数本质上需要"扫描"，Bitmap 没提供"最长连续 1"的命令
# → 所以还是在应用层解析更实际
/**
 * 在应用层解析 Bitmap，计算连续签到天数
 */
public int getContinuousSignDays(Long userId) {
    String key = "sign:uid:" + userId + ":" + month();
    // 拿到整个 Bitmap 的字节数组
    byte[] bytes = redisTemplate.getConnectionFactory().getConnection()
        .stringCommands().get(key.getBytes());

    // 用 Java 的 BitSet 解析（注意 bit 顺序）
    BitSet bitSet = BitSet.valueOf(bytes);
    int today = LocalDate.now().getDayOfMonth();
    int continuous = 0;
    for (int day = today; day >= 1; day--) {
        // ⚠️ SETBIT 的 offset 是从 0 开始的，日期从 1 开始，所以要 -1
        if (bitSet.get(day - 1)) {
            continuous++;
        } else {
            break;
        }
    }
    // 如果跨月连续（如 8 月最后几天 + 9 月初），需要再查上个月的 key
    return continuous;
}

第四步：边界与代价

  • 跨月连续性：连续签到可能跨月（8/30、8/31、9/1）。要处理「本月全勤则继续查上月」的情况。
  • 内存：每个用户每月一个 key，最大 31 位（4 字节）。1 亿用户 × 4 字节 = 400MB（但 Redis 有对象开销，实际每 key 约 100-200 字节 → 1 亿用户约 10-20GB，需要用 Cluster 分片）。
  • 补签功能：SETBIT 允许把过去的某位置为 1，天然支持补签。但要记录「补签卡使用次数」等业务逻辑。
  • 更省的方案：如果只需要「连续天数」而不需要「日历明细」，可以用一个整数存连续天数（INCR），但要处理「断签」和「跨天」逻辑——复杂度反而更高，不如用 Bitmap。

SADD follow:1002 2002 2003 2005 2006

# ⭐ 共同关注（交集）—— Set 的核心价值

# 返回：2002, 2003

# 我关注的人也关注他（可能认识的人）
# 1) 我关注的人（follow:1001）
# 2) 这些人分别关注了谁（需要多次查询或用一个反向索引）
# 3) 汇总统计出现频率，排除已关注的 → 推荐

########## ⭐ 大规模场景：Set 求交集的性能问题 ##########
# SINTER 的复杂度是 O(N×M)（N 是最小集合大小，M 是集合数量）
# 如果两个千万粉丝的大 V 求共同粉丝……会阻塞 Redis！

# ✅ 解法一：把计算放到从节点 / 用 SINTERSTORE 异步算
SINTERSTORE tmp:common follow:1001 follow:1002
# → 但 SINTERSTORE 仍然在主线程执行，只是把结果存下来了

# ✅ 解法二：离线计算（推荐，生产做法）
# 用 Spark/Flink 离线算好「共同好友」「可能认识的人」
# 结果写入 Redis 供快速查询，或存入专门的推荐系统

# ✅ 解法三：限制集合大小
# 只对"小集合"求交集：先比较 SCARD，取最小的两个求交
# 但语义上要注意——求交集时结果受最小集合限制，所以可以先取最小的

########## 双向关注 vs 单向关注 ##########
# 单向关注（微博）：一个 Set 存"我关注的人"
SADD following:1001 2001 2002
SADD followers:2001 1001            # 同时维护"粉丝"集合（反向索引）
# 查询"我的粉丝"：SMEMBERS followers:1001
# 查询"互相关注"：SINTER following:1001 followers:1001

# 双向好友（微信）：用两个 Set 或者一个 Set（双向添加）

场景 9：附近的人（GEO）

题目

「实现『查找附近的商家』，5 公里内按距离排序，怎么设计？」

########## GEO 基本操作（底层是 ZSet，score 是 GeoHash 编码）##########

# 添加位置（经度、纬度、名称）
GEOADD shops 116.404 39.915 "天安门"
GEOADD shops 116.397 39.908 "王府井"
GEOADD shops 116.410 39.920 "东单"

# ⭐ 查找附近（核心命令）
# GEOSEARCH：推荐的命令（GEORADIUS 已废弃）
GEOSEARCH shops FROMLONLAT 116.400 39.910 BYRADIUS 5 km ASC COUNT 10 WITHDIST WITHCOORD
# FROMLONLAT  以某坐标为圆心
# BYRADIUS   按半径（也支持 BYBOX 按矩形）
# ASC        按距离升序（DESC 降序）
# COUNT 10   只取前 10 个
# WITHDIST   返回距离
# WITHCOORD  返回坐标

# 以「已存在的成员」为圆心查找
GEOSEARCH shops FROMMEMBER "天安门" BYRADIUS 3 km ASC WITHDIST

# 查两个位置的距离
GEODIST shops "天安门" "王府井" km
# 返回：约 0.85 km

# 获取成员的 GeoHash 编码
GEOHASH shops "天安门"

# 获取成员的经纬度
GEOPOS shops "天安门"
✅ GEO 的底层原理：GeoHash + ZSet

GeoHash 编码过程：

  1. 把经纬度范围（经度 -180~180，纬度 -90~90）不断二分，每分一次产生一位（经度位 / 纬度位交错）。
  2. 二分 N 次后得到一个 N 位的二进制串。
  3. 把这个二进制串做 base32 编码，得到 GeoHash 字符串。

关键特性：GeoHash 前缀相同的点，在地理上相邻（把二维的邻近性编码成了一维的前缀相似性）。

Redis 的实现：把 GeoHash 得到一个 52 位整数作为 ZSet 的 score，member 是元素名。所以 GEO 的所有操作都基于 ZSet——这正是为什么 Redis 能用 ZSet 实现 GEO 的原因。

范围查询的实现：Redis 计算出「覆盖目标区域所需的 GeoHash 前缀区间」，然后用 ZRANGEBYSCORE 在 ZSet 里按 score 范围取候选，最后精确计算每个候选到中心的距离并过滤排序。

为什么需要「最后精确计算」：GeoHash 是「把二维映射到一维」，存在边界问题——两个地理上很近的点，可能因为跨了 GeoHash 格子而前缀不同。所以 Redis 会取「相邻格子」的候选，再用真实的经纬度计算距离来精确过滤。

第四步：边界与代价

  • 数据量限制：一个 GEO key 就是一个 ZSet。如果一个 key 里存了全世界的商家（几千万），会变成大 key，且 GEOSEARCH 会在这个大 ZSet 上做范围查询。
    解法：按区域分片（shops:beijing、shops:shanghai），或者按「城市 + 业务类型」拆分。这是 GEO 在生产上最重要的优化。
  • 精度：GEO 的定位用的是「球面距离近似」（把地球当球体），实际误差在 0.5% 以内，对「附近的人」这种场景完全够用。
  • 动态更新位置：GEOADD 对已存在的 member 是更新位置（覆盖旧的）。对「骑手实时位置」这类场景，频繁 GEOADD 是可以的，但要注意写入量。
  • 替代方案：如果是超大规模的地理检索（如全世界的 POI），专业的空间索引方案（PostGIS / Elasticsearch 的 geo 查询 / 专门的 LBS 服务）可能更合适。Redis GEO 适合「中小规模 + 需要低延迟」的场景。

场景 10：分布式 ID / 发号器

题目

「需要生成全局唯一的订单号，趋势递增，怎么实现？」

方案实现优点缺点
数据库自增DB 的 AUTO_INCREMENT简单、绝对唯一❌ 并发能力受限；扩展性差
UUIDUUID.randomUUID()无中心、性能高❌ 无序（影响 DB 索引性能）、太长
雪花算法（Snowflake）时间戳 + 机器 ID + 序列号，64 位整数趋势递增、高性能、无中心⚠️ 依赖系统时钟（时钟回拨会重复）
Redis INCR原子自增绝对唯一、原子、实现简单⚠️ 依赖 Redis 可用性；纯递增会暴露业务量（可用时间戳+随机前缀混淆）
Redis + 号段模式每次取一批（如 1000 个）号段缓存在应用内存，用完再取性能极高、减少 Redis 压力应用重启会浪费一段 ID（可接受）
 
########## 简单版：Redis INCR ##########
SET seq:order 0
INCR seq:order          # 返回 1, 2, 3, ...

# 组合成业务 ID（日期 + 序号）
# INCR 得到 123，再拼成 order-20260930-000123
# ⚠️ 每天 0 点重置：用带日期的 key
INCR seq:order:20260930

########## 号段模式（推荐，性能最好）##########
# 每次 INCRBY 1000，拿到 1000 个可用 ID 的区间
INCRBY seq:order 1000
# 返回 1000 → 表示 [1, 1000] 这个区间归我
# 应用在内存里分配 1, 2, 3... 用完后再 INCRBY 1000
/**
 * 号段模式实现（美团 Leaf 的思路）
 */
public class SegmentIdGenerator {
    private final StringRedisTemplate redis;
    private final String key;
    private final long step;              // 每次取的号段大小

    private AtomicLong current;            // 当前分配的 ID
    private volatile long max;            // 当前号段的上限
    private final Object lock = new Object();

    public SegmentIdGenerator(StringRedisTemplate redis, String key, long step) {
        this.redis = redis;
        this.key = key;
        this.step = step;
        this.current = new AtomicLong(0);
        this.max = 0;
    }

    public long nextId() {
        long id = current.incrementAndGet();
        if (id <= max) {
            return id;
        }
        // 当前号段用完 → 取新号段
        synchronized (lock) {
            if (current.get() <= max) {     // 双重检查（可能别的线程已经取过了）
                return current.incrementAndGet();
            }
            long newMax = redis.opsForValue().increment(key, step);
            current.set(newMax - step + 1);
            max = newMax;
            return current.get();
        }
    }
}
⚠️ 号段模式的「双 Buffer」优化（美团 Leaf 的进阶）

问题：号段用完的那一刻，要同步去 Redis 取新号段——这个请求的延迟会叠加在业务上（虽然只有几毫秒，但在高并发下会形成「毛刺」）。

解法（双 Buffer）：提前异步加载下一个号段。当当前号段用到 10% 时，就异步去 Redis 取下一个号段放进内存。这样业务永远不会等待取号段。

// 简化逻辑
if (current.get() > max - step * 0.1) {    // 剩余不足 10% → 异步预取下一段
    if (nextSegmentReady.compareAndSet(false, true)) {
        asyncExecutor.submit(() -> {
            long newMax = redis.opsForValue().increment(key, step);
            nextSegment.set(new Segment(newMax - step + 1, newMax));
            nextSegmentReady.set(true);
        });
    }
}

代价：应用重启时会浪费「当前号段 + 预取号段」的 ID（可接受，ID 只要唯一递增就够了，不要求连续）。

第四步：边界与代价

  • Redis 挂了怎么办：号段模式在内存里有缓存，短期内（一个号段内）可以用。号段用完后无法取新号段 → 需要降级方案（如切换到雪花算法，或用 DB 兜底）。
  • ID 可读性 / 安全性：纯递增的 ID 会暴露业务量（竞争对手能通过 ID 推算出你的日订单量）。解法：① 前面加随机前缀；② 或者用「日期 + 随机数 + 序号」的组合。
  • 推荐方案：雪花算法（无中心、高性能）为主 + Redis 号段作为备选。雪花算法要处理时钟回拨（如果检测到时钟回拨，可以等待、或者用备用机器 ID 段）。

场景 11：消息队列 / Stream

题目

「用 Redis 做消息队列可以吗？怎么做？有什么限制？」

方案实现优点缺点
ListLPUSH 生产，BRPOP 消费简单、实现容易❌ 消息一旦被弹出就无法恢复（消费者崩溃丢消息）；不支持多消费者组
Pub/SubPUBLISH / SUBSCRIBE实时性好❌ 不持久化、无 ACK、消费者离线消息就丢 → 只能做实时通知，不能做可靠 MQ
Stream
推荐		XADD / XREADGROUP / XACK✅ 持久化、消费者组、ACK 重投、消息回溯⚠️ 需要手动 XTRIM 裁剪；功能不如专业 MQ（无延时、无事务消息）
 
########## Stream 完整用法 ##########

# 1. 生产消息（* = 自动生成 ID）
XADD orders * orderNo OR123 amount 99.9
# 返回消息 ID：1759161600000-0（毫秒时间戳-序号）

# ⭐ 限制队列长度（防止无限增长！）
XADD orders MAXLEN ~ 10000 * orderNo OR124 amount 199.9
# MAXLEN ~ 10000 表示"大约保留 10000 条"（~ 表示允许不完全精确，性能更好）

# 2. 创建消费者组（从最新消息开始消费）
XGROUP CREATE orders group1 $ MKSTREAM
# $ = 只消费新消息；0 = 从头开始消费所有历史消息

# 3. 消费（> 表示"还没投递给这个消费者的新消息"）
XREADGROUP GROUP group1 consumer1 COUNT 10 STREAMS orders >
# 返回消息：ID + 字段

# 4. 处理成功后 ACK
XACK orders group1 1759161600000-0

# ⭐ 5. 处理 pending（未 ACK）的消息（消费者崩溃后恢复）
XPENDING orders group1 - + 10
# 输出：消息 ID、消费者、空闲时间、投递次数

# 重新认领消息给其他消费者（处理"消费者崩溃留下的消息"）
XCLAIM orders group1 consumer2 60000 1759161600000-0
# 60000 = 最小空闲时间（ms），只认领空闲超过 60 秒的消息

# 或者用 XAUTOCLAIM（7.0+，更简洁）
XAUTOCLAIM orders group1 consumer2 60000 0 COUNT 10

# 6. 查看 Stream 信息
XINFO STREAM orders
XINFO GROUPS orders
XINFO CONSUMERS orders group1

# 7. 裁剪（定期清理旧消息）
XTRIM orders MAXLEN 10000
⚠️ 用 Redis 做 MQ 的关键限制（面试要说清）
  1. 必须手动裁剪（XTRIM / MAXLEN）：否则 Stream 会无限增长变成大 key。这是最常见的事故原因。
  2. 没有「延时消息」：Stream 不支持延时投递，需要自己用「ZSet + 延时搬运」实现。
  3. 没有事务消息 / 顺序消息的高级语义：相比 RocketMQ / Kafka，Stream 的功能较基础。
  4. 持久化依赖 RDB/AOF：如果持久化没配好，Redis 重启可能丢消息。而且主从切换也可能丢（异步复制）。
  5. 消费能力受限于单分片：Stream 是一个 key，所有消费者读的是同一个分片。虽然消费者组可以并行消费（不同消息分给不同消费者），但 Stream 本身的「生产」是单点的。
    解法：用多个 Stream（按业务分片，如 orders:shard0 ~ orders:shard9）。
  6. 不适合超大吞吐：Kafka 能做到百万 TPS，Redis Stream 更适合「中等吞吐 + 低延迟 + 已有 Redis 基础设施」的场景。
💡 选型话术（很实用）

「我的判断是：

  • 已经重度用 Redis，且 QPS 不高（如几千）→ 用 Stream。好处是不引入新组件，且能用 Redis 的生态（持久化、集群、监控）。
  • 需要高吞吐、严格顺序、延时消息、事务消息 → 用 RocketMQ / Kafka。这是专业工具做的事，Redis 替代不了。
  • 只是做实时通知/广播 → 用 Pub/Sub 或 Stream（Pub/Sub 不持久化，Stream 可以）。

我不建议用 List 或 Pub/Sub 做「可靠消息」——List 丢消息、Pub/Sub 不持久化，这两个坑我是踩过的。」

场景 12：分布式 Session / 验证码 / 防刷

题目组（这类「小场景」也要准备）
需求实现关键点

/**
 * ⭐ 验证码的完整实现（含防刷、防重放、防爆破）
 */
@Service
public class SmsCodeService {

    private static final String SEND_LIMIT = "sms:send:limit:";    // 发送频率限制
    private static final String CODE = "sms:code:";          // 验证码本身
    private static final String FAIL_COUNT = "sms:fail:";     // 验证失败次数

    private final StringRedisTemplate redis;
    // ⭐ 校验与删除必须原子，用 Lua
    private static final String VERIFY_SCRIPT =
        "local code = redis.call('GET', KEYS[1]) " +
        "if code == false then return -1 end " +          -- 不存在或已过期
        "if code ~= ARGV[1] then return 0 end " +            -- 验证码错误
        "redis.call('DEL', KEYS[1]) " +                      -- ⭐ 成功即删除（防重放）
        "return 1";

    /** 发送验证码 */
    public void send(String phone) {
        // ① 频率限制：60 秒内只能发一次
        Boolean allowed = redis.opsForValue()
            .setIfAbsent(SEND_LIMIT + phone, "1", Duration.ofSeconds(60));
        if (!Boolean.TRUE.equals(allowed)) {
            throw new BizException("发送过于频繁，请 60 秒后再试");
        }

        // ② 每日发送上限（可选，更强限制）
        Long dailyCount = redis.opsForValue().increment("sms:day:" + phone, 1);
        if (dailyCount != null && dailyCount == 1) {
            redis.expire("sms:day:" + phone, Duration.ofDays(1));
        }
        if (dailyCount != null && dailyCount > 10) {
            throw new BizException("今日发送次数已达上限");
        }

        // ③ 生成并存储验证码（5 分钟有效）
        String code = String.format("%06d", ThreadLocalRandom.current().nextInt(1000000));
        redis.opsForValue().set(CODE + phone, code, Duration.ofMinutes(5));

        // ④ 调用短信网关
        smsGateway.send(phone, code);
    }

    /** 校验验证码 */
    public boolean verify(String phone, String inputCode) {
        // ① 失败次数限制（防暴力破解）
        String failKey = FAIL_COUNT + phone;
        String failCount = redis.opsForValue().get(failKey);
        if (failCount != null && Integer.parseInt(failCount) >= 5) {
            throw new BizException("验证失败次数过多，请重新获取验证码");
        }

        // ② 原子校验 + 删除
        Long result = redis.execute(
            new DefaultRedisScript<>(VERIFY_SCRIPT, Long.class),
            Collections.singletonList(CODE + phone),
            inputCode);

        if (result != null && result == 1) {
            redis.delete(failKey);      // 成功则清空失败计数
            return true;
        }

        // ③ 记录失败次数（10 分钟内累计）
        Long fails = redis.opsForValue().increment(failKey);
        if (fails != null && fails == 1) {
            redis.expire(failKey, Duration.ofMinutes(10));
        }
        return false;
    }
}
💡 这类「小场景」的回答要点

不要因为是「小功能」就只答一句「用 SET 存」。要展示你考虑了边界：

  • TTL 一定要设（否则内存泄漏）——这是 Redis 使用最常见的坑。
  • 原子性（校验+删除用 Lua）。
  • 防刷/防爆破（频率限制、失败次数限制）。
  • 持久化要求（Session/Token 丢了用户要重新登录，能不能接受？）
  • DB 兜底（重要数据不能只存 Redis）。

🚨 场景题回答的四大禁忌
  1. 不问需求就设计：不知道数据规模、一致性要求就开始画架构。面试官会觉得你缺乏工程判断力。
  2. 只答「用什么」，不说「为什么」：只报数据结构名字，不说「因为需要 XX 特性所以选它」。显得像背答案。
  3. 不主动说代价：任何方案都有代价，主动说出来才显得成熟。尤其要说「这个方案在什么规模下会崩」。
  4. 不知道边界就硬答：被问到不熟悉的领域，可以说「这块我没深入实践过，我的理解是……，可能有偏差」。诚实比编造好得多。
