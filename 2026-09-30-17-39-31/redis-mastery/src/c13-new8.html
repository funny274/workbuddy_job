Day4.4 · Redis 8.x 新特性全景（8.0 → 8.6）

一句话结论

Redis 8.x 是「模块内置化 + 检索一体化 + 可观测性增强」的大版本。对面试最有价值的三个点：① 8.0 把 Bloom/Cuckoo/JSON/TimeSeries 等模块直接内置（不再需要单独编译加载）；② 8.x 引入 Vector Set 与 FT.HYBRID，把 Redis 推向「AI 应用的向量检索层」；③ 8.2 的 CLUSTER SLOT-STATS + 8.4 的原子槽迁移 + 8.6 的 HOTKEYS 构成了一套完整的「集群可观测性与平滑扩缩容」能力。

⚠️ 本节内容以官方发布说明为准。版本号和具体特性在不同的小版本可能有调整，面试时如果被追问细节，可以诚实说明「我了解的是 8.x 的大方向，具体小版本特性我会查 release notes」——这比编造细节好得多。

面试官问「你用过 Redis 什么版本」，诚实回答很重要。如果你的生产环境是 6.x/7.x（这是大多数公司的现状），就大方说「生产是 7.2，我关注过 8.x 的新特性但还没在生产验证」。
然后补一句加分的话：「不过我注意到 8.x 有几个特性和我们的痛点直接相关——比如 8.6 的 HOTKEYS 能原生做热 key 检测，我们目前是靠客户端埋点，如果升级可以省掉这部分自研成本。」

2. Redis 8.0：模块内置化（最有实际价值的变化）

✅ 从「自己编译模块」到「开箱即用」

过去（7.x 及以前）：想用布隆过滤器、JSON、时序数据，需要：

  1. 单独下载 RedisBloom / RedisJSON / RedisTimeSeries 源码；
  2. 编译成 .so 文件；
  3. 在 redis.conf 里 loadmodule 加载；
  4. 跟着 Redis 版本升级时，还要重新编译模块（版本兼容性是持续的痛苦来源）。

Redis 8.0 之后：这些模块直接内置，安装完 Redis 就有全部命令，不需要 loadmodule。

内置的数据结构/能力（8.0）：

能力命令前缀典型用途
JSONJSON.SET/GET/ARRAPPEND存对象、局部更新 JSON 字段（不用整体取出再写回）
Bloom FilterBF.RESERVE/ADD/EXISTS缓存穿透拦截
Cuckoo FilterCF.ADD/EXISTS/DEL支持删除的布隆过滤器

面试价值：这是能体现你「跟进新技术」的具体证据。而且这些模块和 Day4.1/4.3 的内容直接对应——布隆过滤器解决穿透、TopK/CMS 用于热 key 发现。

########## Redis 8.x 内置模块实战 ##########

# ===== 1. JSON：局部更新，不用整体读改写 =====
JSON.SET user:1001 $ '{"name":"张三","age":30,"tags":["java","redis"]}'

# 只改 age 字段（原子操作，不需要把整个 JSON 取出来再写回）
JSON.SET user:1001 $.age 31

# 往数组追加
JSON.ARRAPPEND user:1001 $.tags '"mysql"'

# 只取需要的字段（减少网络传输）
JSON.GET user:1001 $.name $.age

# 条件查询（比取出来在应用层过滤高效）
JSON.GET user:1001 '$..tags'

# ===== 2. Bloom：穿透拦截 =====
BF.RESERVE sku:filter 0.001 10000000   # 误判率 0.1%，容量 1000 万
BF.MADD sku:filter sku001 sku002 sku003
BF.EXISTS sku:filter sku001            # 1
BF.EXISTS sku:filter sku999            # 0 → 一定不存在，直接返回

# ===== 3. TopK：近似统计热搜/热 key =====
TOPK.RESERVE hotsearch 10              # 只保留 Top 10
TOPK.ADD hotsearch "redis教程" "java面试" "redis教程"
TOPK.QUERY hotsearch "redis教程"      # 1 = 在 Top-K 中
TOPK.LIST hotsearch                    # 列出当前 Top-K

# ===== 4. t-digest：分位数统计（延迟监控）=====
TDIGEST.CREATE latency
TDIGEST.ADD latency 12 15 18 120 200 15 18
TDIGEST.QUANTILE latency 0.5 0.95 0.99   # P50 / P95 / P99

# ===== 5. TimeSeries：时序数据 =====
TS.CREATE temperature RETENTION 86400000   # 保留 1 天
TS.ADD temperature * 25.3                  # * = 当前时间戳
TS.RANGE temperature - +                   # 查询全部
TS.RANGE temperature - + AGGREGATION avg 60000   # 按分钟聚合平均

3. Redis 8.0：Vector Set 与向量检索

✅ Vector Set：Redis 进军 AI 应用层

背景：RAG（检索增强生成）、语义搜索、推荐系统都需要「向量相似度检索」——把文本/图片编码成向量（embedding），然后找最相似的 Top-K。

传统做法要用专门的向量数据库（Milvus / Qdrant / Pinecone / pgvector）。Vector Set 让 Redis 原生支持这个能力——好处是「向量和你的业务数据在同一个 Redis 里」，不需要维护两套系统。

核心命令：

  • VADD key [REDUCE dim] element vector [SETATTR json] — 添加向量
  • VSIM key query [COUNT n] [WITHSCORES] [WITHSCORES] [FILTER expr] — 相似度检索
  • VDIM key / VCARD key / VREM key element / VLINKS / VINFO — 元信息与维护

特性与限制：

  • 支持 HNSW（分层可导航小世界图）索引——近似最近邻搜索，速度快。
  • 支持量化压缩（如 Q8 把 float32 压到 int8），大幅降低内存。
  • 支持属性过滤（FILTER），能在向量检索时同时按业务属性筛选。
  • 8.0 是 beta 状态——API 可能变化，生产使用需谨慎评估。
  • 相比专业向量库，在超大规模（亿级以上）、复杂索引类型上仍有差距。
########## Vector Set 实战 ##########

# 添加向量（element 是元素名，后面是向量值）
VADD doc:vectors "doc1" VALUES 3 0.1 0.2 0.3 SETATTR '{"title":"Redis入门"}'
VADD doc:vectors "doc2" VALUES 3 0.9 0.8 0.7 SETATTR '{"title":"Redis集群"}'
VADD doc:vectors "doc3" VALUES 3 0.15 0.25 0.35 SETATTR '{"title":"Redis持久化"}'

# 相似度检索：找与 query 向量最像的 2 个
VSIM doc:vectors VALUES 3 0.12 0.22 0.32 COUNT 2 WITHSCORES
# 返回：doc1 (最像), doc3

# 带属性过滤
VSIM doc:vectors VALUES 3 0.12 0.22 0.32 FILTER '.title == "Redis入门"' COUNT 1

# 量化压缩：把 float32 压成 int8，内存降到 1/4
VADD doc:vectors Q8 "doc4" VALUES 3 0.5 0.6 0.7

# 查看信息
VINFO doc:vectors
VDIM doc:vectors     # 维度
VCARD doc:vectors    # 元素数

########## RAG 场景的完整数据流（面试可讲）##########
# ① 文档入库：文本 → embedding 模型 → 向量 → VADD 存入 Redis
# ② 用户提问：问题 → embedding → VSIM 找最相似的 Top-K 文档片段
# ③ 把检索到的片段作为上下文，拼进 prompt 交给 LLM
# ④ LLM 生成答案返回
#
# Redis 在这里的优势：向量检索 + 会话上下文（会话存 Redis）+ 结果缓存（缓存 LLM 回答）
# 都能用同一个 Redis 完成，减少系统复杂度
💡 面试话术：Redis 在 AI 时代的定位

「Redis 8.x 的 Vector Set 体现了一个方向——Redis 从『缓存/数据结构服务』向『AI 应用的记忆层与检索层』扩展。

在 RAG 场景里，Redis 能承担三个角色：① 向量检索（VSIM 找相关文档）；② 会话记忆（多轮对话的上下文）；③ 结果缓存（缓存 LLM 回答，降低成本）。用一个 Redis 解决三个问题，比引入专业的向量库 + 会话存储 + 缓存三层要简单。

但我会诚实地评估：如果向量规模到了亿级、或者需要复杂的多路召回和重排，专业向量库（Milvus 等）仍然更合适。Redis 的 Vector Set 更适合『中小规模、且已经重度使用 Redis』的场景。」

4. Redis 8.x：可观测性与运维增强

✅ 8.6 HOTKEYS：原生热 key 检测（Day4.3 的官方答案）

解决了什么：以前找热 key 要靠 --hotkeys（必须先切到 LFU 策略）或者自己写客户端埋点。8.x 提供了服务端原生的热 key 检测，不依赖淘汰策略。

HOTKEYS START     # 开始采样统计
# ... 让业务运行一段时间 ...
HOTKEYS GET       # 获取当前热 key 列表（含访问计数）
HOTKEYS STOP      # 停止统计
HOTKEYS RESET     # 重置统计

# 配置
hotkeys-enabled yes
hotkeys-sampling-factor 10

面试价值：能说出「8.6 有原生的 HOTKEYS 命令，我们目前用的是客户端埋点，后面可以考虑用原生能力替代自研」——展示你既了解现状也关注演进方向。

✅ 8.2 CLUSTER SLOT-STATS：找到「热槽」

解决了什么：Cluster 扩容时，怎么知道该迁哪些槽？只知道「某个节点 CPU 高」，但不知道是哪个槽造成的。

# 开启槽位统计
CONFIG SET cluster-slot-stats-enabled yes

# 按 CPU 使用排序，找出最耗 CPU 的槽 ⭐
CLUSTER SLOT-STATS ORDERBY CPU LIMIT 10

# 其他排序维度
CLUSTER SLOT-STATS ORDERBY KEY-COUNT LIMIT 10    # 按 key 数量
CLUSTER SLOT-STATS ORDERBY MEMORY  LIMIT 10      # 按内存
CLUSTER SLOT-STATS ORDERBY NETWORK LIMIT 10      # 按网络

# 输出示例：
# 1) 1) (integer) 866         ← 槽号
#    2) 1) "key-count"        ← 统计维度
#       2) (integer) 152300
#    3) 1) "cpu-usec"
    #    2) (integer) 8943210

面试关键洞察：「先找热槽，再找槽内热 key」是一个非常有价值的排查路径：

  1. CLUSTER SLOT-STATS ORDERBY CPU → 定位到最热的槽。
  2. HOTKEYS（在对应节点上）→ 定位到槽内的具体热 key。
  3. 针对具体热 key 做治理（本地缓存/多副本/业务打散）。

⚠️ 但要做对判断：如果热槽里是「一个热 key」造成的，迁移槽解决不了问题（热 key 迁到新节点，新节点照样被打满）。只有「一大堆不同的热 key」才适合靠迁移分摊。这个判断能体现你真的理解了原理。

✅ 8.4 原子槽迁移（Atomic Slot Migration）：平滑扩缩容

传统槽迁移的问题（Day3.2 讲过）：

  • 逐个 key MIGRATE，慢（百万 key 要几十分钟）。
  • MIGRATE 阻塞源和目标节点主线程。
  • 中间状态（槽一半在源、一半在目标）需要靠 ASK 重定向维持，期间大量重定向影响性能。
  • 迁移中断会留下不一致的中间状态，需要人工介入。

8.4 的原子槽迁移：

  • 把「一个槽的迁移」变成一个原子操作——要么全部成功，要么完全回滚，不留中间状态。
  • 使用类似「全量快照 + 增量同步 + 短暂停顿切换」的机制（类似主从复制的思路）。
  • 相关命令：CLUSTER MIGRATION。
  • 收益：① 迁移速度大幅提升；② 迁移期间对业务影响极小；③ 支持零停机扩缩容；④ 失败可自动重试/回滚。

为什么这个特性重要：Cassandra/DynamoDB 这类系统早就支持「自动分片再平衡」，Redis Cluster 一直在这方面比较弱（需要人工用 redis-cli --cluster reshard 慢慢迁）。原子槽迁移让 Redis Cluster 的弹性能力追上来了。

5. 版本选型：生产上该怎么选

✅ 版本选型的决策框架（面试能答出这个就很好）
考虑因素选择倾向
稳定性优先选「已被大规模验证」的版本，通常是上一个 major 的最新小版本（如现在选 7.4 而不是 8.6）
需要新特性如果确实需要 Vector Set / 原子槽迁移，评估后用 8.x
云托管跟着云厂商走——云服务商支持的版本是经过他们验证和运维的，比自己搭更稳
社区版 vs 商业版⚠️ 重要背景：Redis 7.4 起改成了 RSALv2/SSPLv1 许可（不再完全是 BSD）。这导致 Linux 基金会分叉出了 Valkey（基于 7.2.4）。很多公司在评估或已经迁到 Valkey。
已有系统升级收益 vs 升级风险。如果 6.x/7.x 稳定运行且没有需要的特性，不升也是一种正确决策——这句话在面试里很加分
⚠️ 关于 Redis 许可证与 Valkey（重要背景知识）

事件背景：

  • 2024 年 3 月，Redis Ltd. 宣布从 BSD-3-Clause 改为 RSALv2 / SSPLv1 双许可——这两个许可不是 OSI 认可的开源许可，主要限制是「不能把 Redis 作为托管服务出售」。
  • 这引发社区强烈反应。Linux 基金会随后将 Redis 7.2.4 分叉为 Valkey，由 AWS、Google Cloud、Oracle、Ericsson 等公司支持，保持 BSD 许可。
  • 2025 年 5 月，Redis 宣布 Redis 8.0 重新采用 AGPLv3 许可（AGPL 是 OSI 认可的开源许可），并重新加入部分开源社区组织。

对工程师的实际影响：

  • 技术层面：Valkey 与 Redis 高度兼容——命令、协议、数据结构基本一致（因为同源）。所以本教程的知识对 Valkey 同样适用。
  • 选型层面：如果用云厂商的托管服务，可能已经是 Valkey（如 AWS ElastiCache 提供 Valkey 选项）。面试时知道这个背景，能说明你关注生态而不只是技术细节。
  • 面试话术：「我关注到 Redis 的许可证变更和 Valkey 分叉这件事。从工程师角度，好消息是两者技术同源、命令兼容，所以底层原理（数据结构、持久化、集群）是通用的，学习成本很低。选型上主要看：① 是否依赖 Redis 商业版特性（如某些高级模块）；② 云厂商支持哪个；③ 公司对开源许可的合规要求。」

6. 把 8.x 新特性映射到你的项目（面试加分点）

8.x 特性解决的痛点面试时的表述
BF.* 布隆过滤器内置 穿透拦截需要额外引入 RedisBloom 「我们以前用 Guava 的 BloomFilter 放在应用层，重启就要重建。如果升级到 8.x，可以用 Redis 原生的 BF，多实例共享、持久化不用自己管。」
HOTKEYS 原生热 key 检测 热 key 发现要靠客户端埋点自研 「我们的热 key 监控是自己写的客户端埋点 + Kafka 聚合。8.6 的 HOTKEYS 可以省掉这套自研成本，而且服务端采样比客户端聚合更准确。」
CLUSTER SLOT-STATS 槽位统计 扩容时不知道迁哪些槽 「以前扩容只能凭经验估，或者全量对比。SLOT-STATS 能直接按 CPU/内存/网络排序看哪些槽最重，迁移决策有数据支撑了。」
原子槽迁移 传统迁移慢、有中间状态、需人工介入 「我们的集群扩缩容要选在凌晨低峰、分批发、人工盯着。原子槽迁移能做到零停机平滑扩缩容，这是运维效率的质变。」
Hash field 级过期（7.4+） 整个 Hash 只能整体过期 「我们有个场景是『用户维度的多个限流计数器』放在一个 Hash 里，但每个计数器的窗口不同。以前只能拆成多个 key，现在可以用 HEXPIRE 精细化控制。」
Vector Set AI 场景要额外维护向量库 「如果做 RAG，Redis 可以同时承担向量检索、会话记忆、结果缓存三个角色，减少系统复杂度。但我会评估规模——亿级向量还是用专业向量库。」
XADD 幂等（IDMP） Stream 作为 MQ 时的重复投递 「用 Stream 做 MQ 时，生产者重试会导致重复消息，消费者必须自己做幂等。IDMP 把幂等能力下沉到了 Redis 层，简化了消费者逻辑。」

面试深度问答

Redis 8.x 有哪些重要新特性？进阶

按「能力类别」组织回答，比按版本罗列更好：

一、模块内置化（8.0，最实用的变化）

Bloom、Cuckoo、Count-Min Sketch、TopK、t-digest、JSON、TimeSeries 等从「需要单独编译加载模块」变成开箱即用。这解决了长期以来的版本兼容痛点。

二、AI / 检索能力

  • Vector Set（8.0 beta）：VADD/VSIM 支持 HNSW 索引的向量相似度检索，支持量化压缩和属性过滤。让 Redis 能参与 RAG、语义搜索场景。
  • FT.HYBRID（8.2）：向量 + 全文的混合检索。

三、可观测性与运维

  • HOTKEYS（8.0/8.6 增强）：原生热 key 检测，不再要求 LFU 策略。
  • CLUSTER SLOT-STATS（8.2）：按槽统计 CPU/内存/网络/key 数，用于定位热槽和指导扩容。
  • 原子槽迁移（8.4）：槽迁移变成原子操作，支持零停机扩缩容。

四、其他

  • LRM 淘汰策略（8.0）：LRU + LFU 混合。
  • XADD 幂等 IDMP（8.6）：生产者幂等，解决 Stream 的重复投递。
  • mTLS 自动认证（8.6）、TimeSeries NaN（8.6）。

加分收尾：「从趋势看，Redis 8.x 在做两件事：一是『把生态收进来』（模块内置，减少拼装成本）；二是『向 AI 和数据平台延伸』（向量检索、混合检索、时序数据）。后者是战略级的方向变化——Redis 不再只是缓存。」

Vector Set 是什么？能替代专业向量数据库吗？专家

是什么：Redis 8.0 引入的原生向量集合数据类型。用 VADD 添加向量（可选带属性），用 VSIM 做近似最近邻检索。底层用 HNSW 索引，支持量化压缩（如 Q8 把 float32 压到 int8）。

优势：

  • 与业务数据同库：向量、会话、缓存都在 Redis，不需要维护两套系统。
  • 支持属性过滤：VSIM ... FILTER '.category == "tech"'，能在检索时同时做业务筛选。
  • 运维成本低：如果公司已经重度使用 Redis，不需要引入新的技术栈。

局限（要说清楚，才显得客观）：

  • 8.0 是 beta，API 可能变化，生产使用有风险。
  • 规模上限：Redis 是内存型，亿级向量的内存成本高。专业向量库有磁盘索引、更激进的压缩。
  • 功能深度：专业向量库支持多种索引（IVF、PQ）、更复杂的过滤、分布式检索、更强的召回调优能力。
  • 生态：专业库有更成熟的与 LangChain / LlamaIndex 等框架的集成。

选型判断：

  • 用 Redis Vector Set：中小规模（百万级以内）、已经重度用 Redis、需要「向量 + 业务数据」协同、想减少系统复杂度。
  • 用专业向量库：亿级以上、需要复杂索引/重排、对召回率有很高要求、团队有能力维护。

面试话术：「我会把它理解为『Redis 把向量检索作为一个内置能力提供，而不是要取代专业向量库』。对大部分中小规模的 AI 应用，用 Redis 一个组件解决『检索 + 会话 + 缓存』是性价比最高的；但对大规模、高要求的场景，专业库的深度优势还是明显的。关键是按规模和需求判断，而不是非此即彼。」

你们公司用的 Redis 什么版本？如果升级你会考虑什么？高级

这是「务实性」考察。诚实 + 有方法论是得分的核心。

第一步：诚实说明现状

「我们生产是 Redis 7.2」（或你的实际版本）。不要编造用了 8.x。

第二步：说清不升级的理由（这是加分的）

「暂时没升级的原因有三个：

  • 收益不足：我们目前遇到的痛点（热 key 发现、大 key 治理）都能用现有版本 + 自研方案解决，8.x 的特性是『锦上添花』而非『解决卡脖子问题』。
  • 风险考虑：Redis 是大促核心链路，升级涉及全链路压测、客户端兼容性验证（Lettuce/Jedis 版本）、运维流程改造。没有明确收益的升级是在引入风险。
  • 我们做了版本冻结：大促前后 2 周禁止任何中间件版本变更，这是铁律。」

第三步：说清如果要升级会怎么做（展示方法论）

  1. 明确目标：升级是为了哪个具体特性？解决什么痛点？（比如「为了 HOTKEYS 替代自研埋点」）没有目标不升级。
  2. 兼容性评估：命令兼容性（新版本弃用的命令）、客户端兼容（Lettuce/Jedis/Redisson 版本）、持久化格式兼容（RDB 版本）、模块依赖。
  3. 搭建影子环境：用灰度/影子流量验证新版本，对比延迟、内存、CPU 指标。
  4. 分阶段灰度：先非核心业务 → 再核心业务的一个分片 → 逐步放量。每阶段有明确的回滚预案。
  5. 回滚方案：保留旧版本实例、数据格式双向兼容、准备好切回流程。
  6. 观察期：升级后至少观察一个完整业务周期（含峰值）。

第四步：加分的一句

「其实很多公司在升级 Redis 版本时，会顺便评估 Valkey——因为技术同源、命令兼容，迁移成本低，而且许可是 BSD。所以我做版本规划时会把『Redis 8.x 还是 Valkey』作为一个并列选项一起评估，而不是默认只有升级这一条路。」

CLUSTER SLOT-STATS 怎么用？扩容时怎么决定迁哪些槽？专家

命令：

CONFIG SET cluster-slot-stats-enabled yes    # 先开启
CLUSTER SLOT-STATS ORDERBY CPU LIMIT 10
CLUSTER SLOT-STATS ORDERBY MEMORY LIMIT 10
CLUSTER SLOT-STATS ORDERBY KEY-COUNT LIMIT 10
CLUSTER SLOT-STATS ORDERBY NETWORK LIMIT 10

扩容决策的正确流程（关键在于「判断根因」）：

  1. 先看是哪个节点过载：通过监控确认是「单节点过载」还是「整体过载」。
  2. 再看是哪些槽造成过载：CLUSTER SLOT-STATS ORDERBY CPU。如果是「很多槽的 CPU 都较高」→ 说明是整体负载问题，扩容能解决（把槽打散到更多节点）。
  3. 但如果发现「一两个槽的 CPU 极高」——这时必须继续往下查（这一步是分水岭）：
# 在过载节点上检查这个热槽里的 key 分布
CLUSTER COUNTKEYSINSLOT 866          # 槽内有多少 key
CLUSTER GETKEYSINSLOT 866 20         # 取 20 个 key 看看

# 用 HOTKEYS 定位槽内的具体热 key（8.x）
HOTKEYS START
HOTKEYS GET
  1. 做出关键判断：
    • 情况 A：槽内是「一堆不同的热 key」 → 迁移槽有效。把这些槽分散到新节点，负载就摊开了。用 --cluster reshard 或 8.4 的原子槽迁移。
    • 情况 B：槽内是「某一个超级热 key」 → 迁移槽无效！ 因为这个 key 无论迁到哪个节点都会打满那个节点。必须做业务治理：本地缓存、多副本 key、业务层打散。
  2. 限速分批执行：如果决定迁移，每批 100-500 个槽，每批之间观察延迟、CPU、ASK/MOVED 次数。不要在高峰期迁。

面试关键句：「SLOT-STATS 的价值不只是『告诉你迁哪些槽』，更重要的是让你能判断『迁移到底有没有用』——如果过载是单个热 key 造成的，迁移只会把问题搬个地方。这个判断能避免一次无效的运维操作。」

Redis 的许可证变更是怎么回事？Valkey 是什么？高级

事件经过：

  1. 2024 年 3 月，Redis Ltd. 把许可从 BSD-3-Clause 改为 RSALv2 / SSPLv1 双许可——这两个许可不是 OSI 认可的开源许可，核心限制是「不能将 Redis 作为托管服务出售」。
  2. 这触发了社区强烈反弹。Linux 基金会将 Redis 7.2.4 分叉为 Valkey，由 AWS、Google Cloud、Oracle、Ericsson 等支持，保持 BSD 许可。
  3. 2025 年 5 月，Redis 8.0 宣布回归 AGPLv3 许可（OSI 认可的开源许可）。

技术关系：Valkey 与 Redis 同源——命令、协议（RESP）、数据结构、持久化格式基本一致。所以底层知识完全通用。差异主要在：新特性跟进速度、部分企业级功能、以及各自社区的方向。

对工程师的实际影响：

  • 学习成本低：本教程的知识对 Valkey 同样适用。
  • 云服务选型：AWS ElastiCache 等云服务已提供 Valkey 选项。你实际用的「Redis」可能底层就是 Valkey。
  • 合规考虑：公司如果有开源合规审查，SSPL/RSAL 这类许可可能被禁止使用。

面试话术：「我认为这件事给工程师的启示是：技术选型不只看技术，还要看许可、社区和生态。好消息是 Valkey 与 Redis 同源，所以我的 Redis 知识不会浪费，切换成本很低。实际选型时我会看三点：① 云厂商/公司基础设施支持哪个；② 是否依赖某个版本独有的特性；③ 公司的开源合规要求。」
