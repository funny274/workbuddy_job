我把这套 Checklist 分成五类：部署前、配置项、上线前、监控告警、故障应急。每一类都是可以直接拿去用的「生产标准」，也是你入职大厂后第一天就会用到的规范。

一、部署前 Checklist

机器与系统层（这些不做好，后面全白搭）
✔检查项命令 / 配置为什么
☐关闭透明大页（THP）echo never > /sys/kernel/mm/transparent_hugepage/enabled最重要的项。fork 时 COW 复制代价从 4KB 变 2MB，延迟暴增
☐overcommit_memory=1vm.overcommit_memory = 1否则 fork 可能直接失败，BGSAVE 报错
☐swappiness=1vm.swappiness = 1不要 0（某些内核会导致 OOM），1 是最优
☐somaxconn 调大net.core.somaxconn = 1024默认 128 太小，高并发下会丢连接
☐TCP backlognet.ipv4.tcp_max_syn_backlog = 1024配合 somaxconn
☐文件描述符上限ulimit -n 65535 / LimitNOFILE=65535默认 1024，客户端一多就 Too many open files
☐禁用 NUMA 或绑核numactl --interleave=all避免跨 NUMA 节点访问内存导致延迟不稳
☐磁盘用 SSD—AOF 刷盘频繁，HDD 会成为瓶颈
☐禁掉机器上的其他重负载进程—Redis 对 CPU 抢占极其敏感
☐单机不部署多实例（或至少绑核）taskset -c 0-3多实例互相抢 CPU，延迟抖动
 
# 一键检查脚本（把这些做成一个 check_env.sh）
#!/bin/bash
echo "=== THP ==="
cat /sys/kernel/mm/transparent_hugepage/enabled
# 期望：[never] always madvise

echo "=== overcommit ==="
cat /proc/sys/vm/overcommit_memory
# 期望：1

echo "=== swappiness ==="
cat /proc/sys/vm/swappiness
# 期望：1

echo "=== somaxconn ==="
cat /proc/sys/net/core/somaxconn
# 期望：>= 1024

echo "=== ulimit -n ==="
ulimit -n
# 期望：>= 65535

echo "=== NUMA ==="
numactl --hardware 2>/dev/null | head -3

echo "=== swap使用 ==="
free -h
# !!!! swap used 必须接近 0

二、redis.conf 生产配置清单

下面是可直接使用的生产配置模板（按重要度分级）
########################################
# 1. 网络与安全（P0）
########################################
bind 0.0.0.0                    # 或指定内网IP
protected-mode yes
port 6379
tcp-backlog 1024
tcp-keepalive 300               # 探测死连接，防止连接泄漏
timeout 0                       # 连接空闲不断开（由客户端控制）

# ⚠️ 生产必须配密码（或 ACL）
requirepass <强密码>
masterauth <同上>               # 从库连主库的密码

# 危险命令禁用（rename-command 在 7.0 后已废弃，用 ACL 替代）
# 7.0+ 用 ACL：
# ACL SETUSER default on >pass ~* +@all -@dangerous

########################################
# 2. 内存（P0）
########################################
maxmemory 12gb                  # ⚠️ ≤ 机器内存 50%
maxmemory-policy allkeys-lru    # 纯缓存用这个；有持久数据用 volatile-lru
maxmemory-samples 5             # LRU 采样数，5 够用，10 更准但费CPU

# 内存碎片整理
activedefrag yes
active-defrag-ignore-bytes 100mb
active-defrag-threshold-lower 10
active-defrag-threshold-upper 100
active-defrag-cycle-min 1
active-defrag-cycle-max 25

########################################
# 3. 持久化（P0）
########################################
# --- RDB ---
save 900 1                      # 15分钟至少1个key变化
save 300 10                     # 5分钟至少10个
save 60 10000                   # 1分钟至少10000个
stop-writes-on-bgsave-error yes  # 持久化失败则拒绝写入（保一致性）
rdbcompression yes
rdbchecksum yes
dbfilename dump.rdb
dir /data/redis                 # ⚠️ 必须是独立大盘，别放系统盘

# --- AOF（混合持久化，推荐）---
appendonly yes
appendfilename "appendonly.aof"
appendfsync everysec            # 性能与安全的平衡点
no-appendfsync-on-rewrite no    # ⚠️ 保持no，重写期间也刷盘（安全优先）
auto-aof-rewrite-percentage 200 # 增长200%触发（默认100太频繁）
auto-aof-rewrite-min-size 64mb
aof-load-truncated yes          # AOF末尾损坏时容忍并继续
aof-use-rdb-preamble yes        # ⚠️ 混合持久化，必开

########################################
# 4. 主从复制（P0，从库配）
########################################
replicaof <master-ip> 6379
masterauth <密码>
replica-read-only yes
replica-serve-stale-data yes
replica-priority 100            # 越小越优先被选为主，0=永不参选

# 防数据丢失（主库配）
min-replicas-to-write 1         # 至少1个从库确认
min-replicas-max-lag 10         # 且延迟不超过10秒

# 复制积压缓冲区（网络抖动容忍度）
repl-backlog-size 64mb          # ⚠️ 默认1mb太小，网络一抖就全量同步
repl-backlog-ttl 3600

# 复制参数
repl-diskless-sync yes          # 无盘复制（磁盘快则开，网络快则开）
repl-diskless-sync-delay 5
repl-disable-tcp-nodelay no     # 不合并小包，保证低延迟（同机房推荐no）

########################################
# 5. 慢查询与延迟（P1）
########################################
slowlog-log-slower-than 10000   # 10ms，微秒单位
slowlog-max-len 512

latency-monitor-threshold 100   # 100ms，超过就记录延迟事件

########################################
# 6. 客户端缓冲区（P1，防大key打爆）
########################################
client-output-buffer-limit normal 0 0 0
client-output-buffer-limit replica 256mb 64mb 60
client-output-buffer-limit pubsub 32mb 8mb 60

########################################
# 7. 数据结构阈值（P1，影响内存和性能）
########################################
hash-max-listpack-entries 128
hash-max-listpack-value 64
list-max-listpack-size -2       # 8KB，负数有特殊含义
list-compress-depth 0
set-max-intset-entries 512
set-max-listpack-entries 128
set-max-listpack-value 64
zset-max-listpack-entries 128
zset-max-listpack-value 64

########################################
# 8. 后台任务与性能（P2）
########################################
hz 10                           # 事件循环频率，10够用
dynamic-hz yes
lazyfree-lazy-eviction no
lazyfree-lazy-expire no
lazyfree-lazy-server-del no     # ⚠️ 保守选择，让删除行为可预期
replica-lazy-flush no
lazyfree-lazy-user-del no       # 显式用 UNLINK 替代 DEL

# IO 多线程（6.0+，4核以上才开）
io-threads 4                    # 4核设2-3，8核设6，不要超过8
io-threads-do-reads no          # ⚠️ 默认no，压测后再决定是否开

########################################
# 9. 日志（P2）
########################################
loglevel notice
logfile /var/log/redis/redis.log
syslog-enabled no

########################################
# 10. Cluster 专属
########################################
cluster-enabled yes
cluster-config-file nodes.conf
cluster-node-timeout 15000      # 15s，故障判定阈值
cluster-replica-validity-factor 10
cluster-migration-barrier 1
cluster-require-full-coverage yes  # ⚠️ 有槽不可用时是否停止服务
cluster-allow-reads-when-down no

四、监控告警体系

分层告警：不是每个指标都要告警，要分级

P0 告警（立即响应，电话/短信）

指标阈值含义
cluster_state!= ok集群不可用
master_link_status!= up主从断开
used_memory / maxmemory> 90%即将 OOM
connected_clients> maxclients × 0.8连接数将满
rejected_connections> 0 持续 1 分钟连接被拒，说明配置或异常
进程存活down实例挂了
rdb_last_bgsave_status!= ok持久化失败
aof_last_write_status!= okAOF 写失败

P1 告警（30 分钟内响应）

指标阈值含义
used_memory / maxmemory> 80%内存偏高，需关注
mem_fragmentation_ratio> 1.5 或 < 1.0碎片严重 或 在用 swap
master_last_io_seconds_ago> 10复制延迟大
latest_fork_usec> 100000 (100ms)fork 耗时过长
blocked_clients> 10有客户端阻塞
instantaneous_ops_per_sec环比降 50%QPS 骤降，可能有问题
缓存命中率（客户端）< 85%穿透或数据问题
慢查询数量每分钟 > 10有慢命令
evicted_keys持续增长内存不足在淘汰数据

P2 告警（日报/周报关注）

指标阈值含义
used_memory_peak—历史峰值，用于容量规划
total_net_input_bytes—网络流量趋势
total_commands_processed—命令量趋势
命令分布（commandstats）—发现异常命令类型
expired_keys—过期量，异常增长要查
key 数量趋势—识别是否有泄漏

五、故障应急手册

五大高频故障的标准处置流程（照着做就行）

故障 1：CPU 100% / 延迟飙升

# 1. 快速定性
INFO cpu
SLOWLOG GET 20                # 是否有慢命令？
LATENCY DOCTOR                # 是否有延迟事件？
INFO stats | grep ops         # QPS 是否异常高

# 2. 定位
top -H -p $(pgrep redis-server)   # 哪个线程吃CPU
# 主线程高 → 业务命令问题
# bio线程高 → 持久化/删除问题

# 3. 常见原因与处置
# ├─ 大key操作 → 找到key，业务侧改造，临时 UNLINK
# ├─ 全量扫描（KEYS）→ 找到调用方，立即停止
# ├─ QPS突增 → 限流/加机器
# ├─ fork频繁 → 检查主从频繁全量同步
# └─ THP没关 → 立即关闭

# 4. 应急止血
# - 如果定位到某个客户端，CLIENT KILL
# - 如果无法定位，考虑临时扩容或切主

故障 2：内存满 / OOM / 大量淘汰

# 1. 看内存构成
INFO memory
MEMORY STATS
MEMORY DOCTOR                 # 直接给诊断建议

# 2. 找大key（从库执行）
redis-cli --bigkeys -i 0.1
redis-cli --memkeys

# 3. 处置
# ├─ 短期：临时提高 maxmemory（如果有空间）→ 必须重启才生效！
# ├─ 短期：删除无用大key（UNLINK，低峰期）
# ├─ 中期：清理无TTL的key，补上TTL
# ├─ 中期：业务侧检查是否有key泄漏
# └─ 长期：扩容分片 或 数据冷热分离

# ⚠️ 注意：maxmemory 是启动时读取的？不，它可以 CONFIG SET 动态改
CONFIG SET maxmemory 14gb
CONFIG GET maxmemory

故障 3：主从断开 / 全量同步风暴

# 1. 看复制状态
INFO replication
# master_link_status: down → 链路断了
# master_sync_in_progress: 1 → 正在全量同步

# 2. 看日志
tail -f /var/log/redis/redis.log | grep -i "sync\|replica"

# 3. 常见原因
# ├─ 网络抖动 → 增大 repl-backlog-size
# ├─ 主库内存不足，repl_chars不够 → 调大 client-output-buffer-limit
# ├─ 从库磁盘满 → 清理
# └─ 从库处理不过来 → 减少从库数量或加资源

# 4. 反复全量同步的排查
# 查看 backlog 是否足够
CONFIG GET repl-backlog-size
# 检查 master_repl_offset 与从库 slave_repl_offset 的差距
# 差距 > backlog → 必然全量

# 5. 处置
# - 增大 repl-backlog-size（64mb → 256mb）
# - 低峰期修复
# - 必要时重建从库（COPY 全量RDB更可靠）

故障 4：Cluster 部分槽不可用

# 1. 看集群状态
CLUSTER INFO
# cluster_state:fail  → 有槽不可用
# cluster_slots_assigned:16384（要等于16384）
# cluster_slots_ok / pfail / fail

# 2. 找问题节点
CLUSTER NODES
redis-cli --cluster check 127.0.0.1:6379

# 3. 常见原因
# ├─ 某主库挂了且没有从库 → 该分片不可用
# ├─ 槽迁移中断，槽处于中间态
# └─ 节点被误删/网络隔离

# 4. 处置
# - 如果有从库：等自动切换，或手动 CLUSTER FAILOVER
# - 如果无从库：把未分配的槽手动分配，或从备份恢复
# - 极端情况：CLUSTER-ALLOW-READS-WHEN-DOWN yes 临时允许读

故障 5：缓存雪崩 / 大批 key 同时过期

# 1. 现象
# - 客户端缓存命中率骤降
# - 数据库 QPS 暴涨，连接池打满
# - 应用响应时间飙升

# 2. 应急止血（顺序很重要！）
# Step1: 保护DB —— 立即在DB层限流
#        如果有限流开关，马上打开
# Step2: 快速预热 —— 把热点数据重新灌进 Redis
#        用脚本批量 SET，注意分批 + 限速
# Step3: 降级 —— 非核心功能返回兜底数据
#        打开降级开关

# 3. 根因修复
# ├─ TTL 加随机抖动（避免再次同时过期）
# └─ 加多级缓存（本地缓存兜底）

# 4. 预热脚本模板
#!/bin/bash
for key in $(cat hot_keys.txt); do
    value=$(mysql -N -e "SELECT ... WHERE id=$key")
    redis-cli SET "cache:$key" "$value" EX $((1800 + RANDOM % 300))
    # 限速，避免把 Redis 和 DB 同时打爆
    sleep 0.001
done

动手实践建议（比看书重要 10 倍）

  1. 搭一套本地 Cluster（6 节点），完整做一遍槽迁移、故障转移、扩容。这个过程能让抽象的 Slot 概念变具体。
  2. 写一个缓存框架：包含穿透/击穿/雪崩防护 + 本地缓存 + 降级。这是面试项目的绝佳素材。
  3. 用 redis-benchmark 做完整压测：分别测单机/主从/Cluster，测 P=1 vs P=16，测开启 BGSAVE 前后。
  4. 读一次 t_zset.c：跳表的插入、删除、范围查询，代码不多（几百行），读完对跳表的理解会质变。
  5. 做一次故障演练：在测试环境 kill -9 主库，观察哨兵/Cluster 的切换过程，用日志和 CLUSTER NODES 追踪整个流程。
  6. 分析一次真实的 RDB：用 redis-rdb-tools 分析，看每个 key 的实际内存占用，理解「为什么 100 万个 key 会占那么多内存」。
最后一段话

学完这 19 节，你手里应该有了三样东西：

  1. 一套完整的知识体系——从部署到源码，从单机到集群，从缓存到分布式锁。
  2. 一套排查问题的方法论——遇到任何 Redis 问题，你知道从哪开始查、按什么顺序查。
  3. 一份可以直接用的 Checklist——上线、监控、应急，都有标准动作，不靠记忆靠流程。

但真正让你在面试中脱颖而出的，从来不是「你知道多少」，而是「你踩过什么坑、怎么定位、怎么解决、怎么预防」。所以最后一件事：去动手。 搭一套环境，写一段代码，制造一次故障，读一次源码。

知识会在实践中变成能力。祝你在面试中拿到满意的 Offer。
