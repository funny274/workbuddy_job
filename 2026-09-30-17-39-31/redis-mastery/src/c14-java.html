Day5.1 · Java 生态：Jedis / Lettuce / Redisson / Spring Data Redis

一句话结论

四个客户端的定位：Jedis（同步、简单、一连接一线程）、Lettuce（Netty 异步、连接共享、Spring Boot 2.x+ 默认）、Redisson（分布式对象与锁，不是单纯客户端）、Spring Data Redis（统一抽象层，底层可切 Jedis/Lettuce）。

面试深水区在四处：① Lettuce 为什么用 Netty 就能「一个连接多线程共享」而 Jedis 不能；② 连接池到底该配多大（有公式）；③ Pipeline / Lua / 事务 三者的区别与选择；④ Spring 的序列化器配错会导致什么线上事故。

1. 四大客户端定位对比

客户端IO 模型线程安全性连接模型核心优势典型场景
Jedis 阻塞 IO（BIO） ❌ 线程不安全 一连接一线程，需要连接池 API 直观、与 Redis 命令一一对应、上手快 简单项目、对命令有精确控制需求
Lettuce Netty NIO ✅ 线程安全 单连接可多线程共享（也可配池） 异步/响应式、高并发下连接数少、支持响应式编程 Spring Boot 2.x+ 默认，高并发服务
Redisson Netty NIO ✅ 线程安全 连接共享 分布式对象（RLock/RMap/RQueue）+ 看门狗 + 集群/哨兵自动化管理 分布式锁、分布式集合、需要高级封装
Spring Data Redis 抽象层 依赖底层 依赖底层 统一 API、模板化、可与 Spring Cache 集成 Spring 项目标配（底层一般用 Lettuce）
✅ 为什么 Lettuce 能「一个连接多线程共享」而 Jedis 不能（高频面试题）

Jedis 的问题：Jedis 使用阻塞式 IO。一次命令调用会「读 socket 直到拿到完整响应」。如果多个线程共用一个连接，线程 A 的响应可能被线程 B 读走（因为 TCP 流没有「消息边界」的概念，谁先 read 谁拿到）→ 数据错乱。所以 Jedis 必须一个线程一个连接。

Lettuce 的解法：基于 Netty 的异步事件驱动模型。所有命令通过一个 Channel 发出，每条命令在发送时生成一个唯一的序号，服务端的响应按 FIFO 顺序回来，Netty 的回调按发送顺序依次匹配到对应的 Future 上。这样多个线程可以安全地共用同一个连接——因为「谁发的命令对应谁的响应」是由客户端自己按顺序维护的，不依赖 TCP 边界。

关键结论：

  • Redis 的协议是 「请求-响应」严格交替的（同一个连接上，发一个命令、收一个响应、再发下一个）。Lettuce 正是利用了这个特性做「命令流水线化」。
  • 所以 Lettuce 在高并发下连接数远少于 Jedis（Jedis 需要「并发线程数」量级的连接，Lettuce 可能只需要几个）。
  • 但要用 Pipeline 批量发命令时要注意：Lettuce 的自动 flush 策略可能影响批量效率（所以要显式用 pipeline 或批量 API）。

⚠️ 三个必须配的「保命」参数
  1. timeout（命令超时）：不设的话，如果 Redis 网络抖动/某个命令卡住，线程会无限等待，最终打满 Tomcat 线程池 → 整个服务雪崩。经验值 1-3 秒。
    注意：超时时间要大于「最慢命令的 P99」，否则会误伤正常请求。如果有 KEYS 或有慢命令，先治理命令再调超时。
  2. max-wait（连接池获取超时）：默认是 -1（无限等待）！这是最容易踩的坑——连接池满了以后请求会无限排队，而 Queue 会吃掉所有内存。必须设成 500ms~2s，拿不到连接就快速失败（fail-fast）。
  3. min-idle（最小空闲连接）：建议设成「稳态并发量」，让连接池预热好。否则每次流量高峰都要新建连接（TCP 三次握手 + AUTH + 可能的选择库），有延迟尖刺。

3.1 集群 + 拓扑刷新（Day3.2 已提过，这里给完整版）

/**
 * Cluster 生产级配置：拓扑刷新 + 连接池 + 超时 + 重试
 * ⚠️ 这是 Cluster 场景下最容易出问题的地方
 */
@Configuration
public class RedisClusterConfig {

    @Bean
    public LettuceConnectionFactory connectionFactory() {
        // ① 集群节点（不必全列，客户端会通过 CLUSTER SLOTS 发现完整拓扑）
        RedisClusterConfiguration clusterConfig = new RedisClusterConfiguration(
            Arrays.asList("10.0.0.11:7001", "10.0.0.12:7001", "10.0.0.13:7001"));
        clusterConfig.setPassword(RedisPassword.of(password));
        clusterConfig.setMaxRedirects(3);         // MOVED/ASK 最大重定向次数

        // ② 连接池
        GenericObjectPoolConfig<StatefulConnection<byte[], byte[]>> pool =
            new GenericObjectPoolConfig<>();
        pool.setMaxTotal(32);
        pool.setMaxIdle(16);
        pool.setMinIdle(8);
        pool.setMaxWait(Duration.ofMillis(1000));     // ⚠️ 必须设，不能是 -1
        pool.setTestOnBorrow(false);                  // 关闭借出检测（有性能开销，Lettuce 有保活机制）
        pool.setTestWhileIdle(true);                  // 空闲检测（配合 time-between-eviction-runs）

        // ③ 客户端选项：拓扑刷新是 Cluster 的命脉
        ClusterTopologyRefreshOptions refreshOptions = ClusterTopologyRefreshOptions.builder()
            // 定期刷新（兜底，防止漏掉变更）
            .enablePeriodicRefresh(Duration.ofSeconds(60))
            // ⭐ 自适应刷新（关键）：遇到 MOVED 重定向、连接失败、或节点恢复时
            //    立即触发一次拓扑刷新
            .enableAllAdaptiveRefreshTriggers()
            .adaptiveRefreshTriggersTimeout(Duration.ofSeconds(30))
            .build();

        ClusterClientOptions clientOptions = ClusterClientOptions.builder()
            .topologyRefreshOptions(refreshOptions)
            .autoReconnect(true)                          // 自动重连
            .disconnectedBehavior(ClientOptions.DisconnectedBehavior.REJECT_COMMANDS)  // ⭐ 断连时快速失败
            .validateClusterNodeMembership(false)             // 关闭节点成员校验（性能优化）
            .socketOptions(SocketOptions.builder()
                .connectTimeout(Duration.ofSeconds(3))
                .keepAlive(true)
                .build())
            .timeoutOptions(TimeoutOptions.enabled(Duration.ofSeconds(3)))
            .build();

        // ④ 组装
        LettuceClientConfiguration clientConfig = LettuceClientConfiguration.builder()
            .clientOptions(clientOptions)
            .commandTimeout(Duration.ofSeconds(3))
            .shutdownTimeout(Duration.ofMillis(200))
            .poolConfig(pool)
            .build();

        return new LettuceConnectionFactory(clusterConfig, clientConfig);
    }

    // ⑤ 序列化器（见 3.3 节的详细讨论）
    @Bean
    public RedisTemplate<String, Object> redisTemplate(
            LettuceConnectionFactory factory) {
        RedisTemplate<String, Object> template = new RedisTemplate<>();
        template.setConnectionFactory(factory);

        Jackson2JsonRedisSerializer<Object> jsonSerializer =
            new Jackson2JsonRedisSerializer<>(Object.class);
        ObjectMapper om = new ObjectMapper();
        om.setVisibility(PropertyAccessor.ALL, JsonAutoDetect.Visibility.ANY);
        om.activateDefaultTyping(LaissezFaireSubTypeValidator.instance,
            ObjectMapper.DefaultTyping.NON_FINAL, JsonTypeInfo.As.PROPERTY);
        jsonSerializer.setObjectMapper(om);

        StringRedisSerializer stringSerializer = new StringRedisSerializer();

        // ⭐ key 用 String 序列化（保证 redis-cli 能看到可读的 key）
        template.setKeySerializer(stringSerializer);
        template.setHashKeySerializer(stringSerializer);
        // value 用 JSON 序列化（可读 + 跨语言）
        template.setValueSerializer(jsonSerializer);
        template.setHashValueSerializer(jsonSerializer);

        template.afterPropertiesSet();
        return template;
    }
}
🚨 三个 Cluster 客户端致命配置（漏一个就出事）
  1. disconnectedBehavior 不要用默认值：默认是 DEFAULT（断连时把命令缓存起来等重连）。这会导致：Redis 挂了以后命令在客户端堆积，内存暴涨，重连后一次性涌入把 Redis 再打挂。
    正确做法：REJECT_COMMANDS（立即失败），配合上层熔断降级。
  2. 没开自适应拓扑刷新：故障转移后客户端路由表是旧的 → 持续收到 MOVED 错误，业务大量失败，直到定期刷新（60 秒）才恢复。60 秒的故障窗口，在大促是不可接受的。
  3. 重定向次数设太小：maxRedirects 默认 5，一般够。但如果拓扑严重过期，可能需要更多次重定向（每次重定向都是一轮 RTT）。更好的做法是保证拓扑刷新及时，而不是靠增加重定向次数。

3.2 序列化器：最容易出线上事故的地方

/**
 * ❌ 反例：使用默认的 JdkSerializationRedisSerializer（Spring Boot 默认！）
 *
 * 后果：
 *  ① redis-cli 里看到的是乱码：
 *     "\xac\xed\x00\x05t\x00\x05value"  —— 完全不可读，排查问题极其痛苦

 */

/**

@Autowired

/**
 * ✅ 推荐方案二：GenericJackson2JsonRedisSerializer（自动 JSON，带类型信息）
 */
@Bean
public RedisTemplate<String, Object> jsonRedisTemplate(
        RedisConnectionFactory factory) {
    RedisTemplate<String, Object> template = new RedisTemplate<>();
    template.setConnectionFactory(factory);

    // 泛型化的 JSON 序列化器：自动在 JSON 里加 "@class" 字段保存类型
    GenericJackson2JsonRedisSerializer serializer =
        new GenericJackson2JsonRedisSerializer();

    template.setKeySerializer(RedisSerializer.string());
    template.setHashKeySerializer(RedisSerializer.string());
    template.setValueSerializer(serializer);
    template.setHashValueSerializer(serializer);
    template.afterPropertiesSet();
    return template;
}

3.3 连接池大小：到底该配多少（有公式）

✅ 连接池配置的经验公式

核心认知：Redis 是单线程处理命令的，连接数多并不能提升 Redis 的吞吐——只会增加 Redis 的 fd 开销和上下文切换。

那连接池该多大？取决于两件事：

  1. 应用侧的并发数：如果有 200 个 Tomcat 线程同时访问 Redis，那池至少要能支撑这个并发。
  2. 每个请求的 Redis 耗时占比：如果用 maxTotal 个连接，每个命令平均耗时 T，那理论 QPS = maxTotal / T。

实用公式（Lettuce 场景）：

# 需要的连接数 ≈ 峰值并发请求数 × 单请求的 Redis 命令耗时 / 单请求总耗时

# 例：Tomcat 200 线程，每个请求平均 50ms，其中 Redis 占 5ms
# 并发访问 Redis 的连接需求 ≈ 200 × (5/50) = 20
# 所以 maxTotal = 32 完全够用（留了余量）

Lettuce vs Jedis 的差异（重要）：

  • Jedis：一个线程一个连接，池大小必须 ≥ 并发线程数。200 线程 → 至少 200 个连接。连接数多的劣势很明显。
  • Lettuce：单连接可多线程共享（得益于 Netty 的异步模型）。理论上 1 个连接就能承受很高的并发。但实践中还是会配池，原因是：① 分担网络阻塞的影响；② 某些操作（如阻塞命令 BLPOP、订阅）会独占连接。

关键警惕：不要盲目配大

  • 连接数 × 应用实例数 = 总连接数。50 个实例 × 64 连接 = 3200 个连接，很容易撞到 Redis 的 maxclients（默认 10000）上限。
  • Cluster 下更要注意：如果对每个节点都建池，实际是「池大小 × 节点数」。
  • 配大了的坏处：① Redis 侧 fd 和内存开销增加；② 大量空闲连接浪费；③ 更容易触发 maxclients。

监控指标（判断池大小是否合理）：

  • 活跃连接数 vs 空闲连接数：如果活跃长期接近 maxTotal，说明池太小。
  • 等待连接的次数 / 平均等待时间：如果频繁触发 maxWait 超时，说明池太小或命令太慢。
  • 连接创建速率：如果持续创建新连接（而不是复用），说明 min-idle 太小或连接被频繁关闭（可能超时设置有问题）。

4. Pipeline / 事务 / Lua：三种「批量」的区别

✅ 三者对比（高频面试题）
特性Pipeline（管道）MULTI/EXEC（事务）Lua 脚本
目的减少 RTT（网络往返）批量执行 + 不被其他命令打断原子性 + 复杂逻辑
原子性❌ 不保证（可能中间插入其他命令）✅ 执行期间不被插入（但不回滚）✅ 执行期间不被插入
回滚不适用❌ 不回滚（某条失败，其余照常执行）❌ 不回滚
条件逻辑❌ 不能（命令是预先确定的）❌ 不能（不能在事务中根据结果决定下一步）✅ 能（完整编程能力）
错误处理逐条返回结果，应用处理逐条返回结果脚本内可决定返回什么
性能最优（只省网络时间）好（省网络 + 减少调度）好（省网络 + 原子 + 少传输）
阻塞主线程否否（但队列本身在客户端）是（脚本执行期间阻塞）
典型场景批量读/写大量独立的 key需要「批量执行不被插入」的简单场景「检查后写入」的原子操作（限流、库存、锁）

最容易答错的一点：Pipeline 不保证原子性！很多人以为「一次性发多条命令」就是原子的——不是的。Pipeline 只是把命令**一次性发出去**（减少网络往返），但 Redis 仍然可能在这批命令之间插入其他客户端的命令。
要原子性必须用 MULTI/EXEC 或 Lua。

########## 1. 原生 Pipeline（RedisTemplate）##########
public void pipelineDemo() {
    List<Object> results = redisTemplate.executePipelined(
        new RedisCallback<Object>() {
            @Override
            public Object doInRedis(RedisConnection connection) {
                // 注意：connection 上的操作是"放进管道缓冲区"，不会立即执行
                for (int i = 0; i < 1000; i++) {
                    connection.set(("key:" + i).getBytes(), ("value" + i).getBytes());
                }
                return null;
            }
        });
    // results 是按顺序对应的结果列表
}

// Lettuce 的批量 API（更高效）
public void lettuceBatch() {
    io.lettuce.core.RedisClient client = ...;
    StatefulRedisConnection<String, String> conn = client.connect();
    // ⭐ 关闭自动 flush，手动控制批次
    conn.setAutoFlushCommands(false);
    RedisAsyncCommands<String, String> async = conn.async();
    for (int i = 0; i < 1000; i++) {
        async.set("key:" + i, "value" + i);
    }
    conn.flushCommands();     // 一次性发出去
}

// ⭐ 最佳实践：Pipeline 要分批（如每批 500-1000 条），避免一次塞太多导致内存和阻塞

########## 2. Spring 事务（MULTI/EXEC + WATCH 乐观锁）##########
public void transactionWithWatch() {
    redisTemplate.execute(new SessionCallback<Object>() {
        @Override
        public Object execute(RedisOperations operations) {
            // ① 监视 key（乐观锁）
            operations.watch("stock:1001");
            // ② 读取当前值
            Integer stock = (Integer) operations.opsForValue().get("stock:1001");
            if (stock == null || stock <= 0) {
                operations.unwatch();
                throw new BizException("库存不足");
            }
            // ③ 开启事务，修改（此时不会立即执行，会放到队列）
            operations.multi();
            operations.opsForValue().set("stock:1001", stock - 1);
            // ④ 执行。如果有其他客户端在 watch 之后改了 stock:1001，EXEC 会返回 null（失败）
            List<Object> result = operations.exec();
            if (result == null || result.isEmpty()) {
                throw new RetryException("并发冲突，请重试");   // 需要应用层重试
            }
            return result;
        }
    });
}

########## 3. Lua 脚本（推荐用于"检查后写入"）##########
private static final String DEDUCT_SCRIPT =
    "local stock = tonumber(redis.call('GET', KEYS[1]) or '-1') " +
    "if stock < tonumber(ARGV[1]) then return -1 end " +
    "redis.call('DECRBY', KEYS[1], ARGV[1]) " +
    "return stock - tonumber(ARGV[1])";

public long deductStock(String skuId, int num) {
    Long remain = redisTemplate.execute(
        new DefaultRedisScript<>(DEDUCT_SCRIPT, Long.class),
        Collections.singletonList("stock:" + skuId),
        String.valueOf(num));
    if (remain != null && remain < 0) {
        throw new BizException("库存不足");
    }
    return remain;
}
💡 选择建议（面试话术）
  • 要减少网络往返、命令之间无需原子性 → Pipeline。典型：批量写日志、批量读多个不相关的 key。记得分批（每批 ≤ 1000）。
  • 需要「一组命令连续执行不被插入」但逻辑简单 → MULTI/EXEC。注意它不回滚，且不支持条件判断，所以适用面比想象中窄。
  • 「读-判断-写」的原子操作 → Lua 脚本（首选）。因为它能表达条件逻辑，而且一条命令搞定（省 RTT）。典型：限流、库存扣减、分布式锁释放。
  • 超过 5-10 条命令要批量执行且逻辑复杂 → 考虑在应用侧用 Pipeline 分组 + Lua 处理需要原子的部分。不要把复杂业务逻辑塞进 Lua（难维护、难测试、阻塞主线程）。

5. Spring Cache 集成（@Cacheable 的坑）

/**
 * Spring Cache 抽象：用注解简化缓存
 */
@Configuration
@EnableCaching
public class CacheConfig {

    @Bean
    public RedisCacheManager cacheManager(RedisConnectionFactory factory) {
        RedisCacheConfiguration defaultConfig = RedisCacheConfiguration.defaultCacheConfig()
            .entryTtl(Duration.ofMinutes(30))              // ⭐ 默认 TTL，必须设！
            .disableCachingNullValues()                       // 是否缓存 null（配合防穿透时要开启）
            .serializeKeysWith(RedisSerializationContext.SerializationPair
                .fromSerializer(new StringRedisSerializer()))  // key 用 String
            .serializeValuesWith(RedisSerializationContext.SerializationPair
                .fromSerializer(new GenericJackson2JsonRedisSerializer()))  // value 用 JSON
            .computePrefixWith(name -> "cache:" + name + ":");   // key 前缀（可读、便于治理）

        // 不同 cacheName 用不同的 TTL
        Map<String, RedisCacheConfiguration> configs = new HashMap<>();
        configs.put("user", defaultConfig.entryTtl(Duration.ofHours(2)));
        configs.put("product", defaultConfig.entryTtl(Duration.ofMinutes(10)));
        // ⭐ 对这个 cache 加随机 TTL，防止雪崩
        configs.put("hotProduct", defaultConfig
            .entryTtl(Duration.ofMinutes(30))
            .entryTtl(...));   // 或用 TtlFunction 动态计算

        return RedisCacheManager.builder(factory)
            .cacheDefaults(defaultConfig)
            .withInitialCacheConfigurations(configs)
            .transactionAware()                        // 与 Spring 事务协同（见下方说明）
            .build();
    }
}

/**
 * 使用：注解式缓存
 */
@Service
public class ProductService {

    // 查询：先查缓存，未命中则执行方法并写缓存
    @Cacheable(value = "product", key = "#id", unless = "#result == null")
    public Product getById(Long id) {
        return productMapper.selectById(id);
    }

    // 更新：删缓存（默认策略是"更新缓存"，企业里通常改为删除）
    @CacheEvict(value = "product", key = "#product.id")
    public void update(Product product) {
        productMapper.updateById(product);
    }

    // 复杂条件缓存
    @Cacheable(cacheNames = "product",
               key = "#category + ':' + #page",
               condition = "#page <= 10")     // 只缓存前 10 页（深分页不缓存）
    public List<Product> listByCategory(String category, int page) { ... }
}
🚨 Spring Cache 的五个坑
  1. 不设 TTL 就等于永不过期：RedisCacheConfiguration.defaultCacheConfig() 默认不设过期时间！必须显式 entryTtl()。这是最常见的坑——缓存永远不失效，数据错了也自愈不了。
  2. 自调用不走缓存：@Cacheable 基于 Spring AOP 代理。同一个类里 A 方法调用 B 方法（this.b()），B 上的注解不会生效（因为不经过代理）。
    解法：注入自己（@Autowired private ProductService self; 然后 self.b()），或把 B 移到另一个 Bean。
  3. 序列化器默认是 JDK：RedisCacheConfiguration 默认用 JdkSerializationRedisSerializer，redis-cli 里是乱码。必须显式换成 JSON。
  4. 事务中的缓存不一致：@CacheEvict 默认在方法执行成功后执行，但如果在事务方法内，它可能在事务提交前就删了缓存（因为 AOP 顺序问题）。这时并发读会读到旧数据并写回缓存。
    解法：① 用 beforeInvocation = false（默认，方法成功后执行）配合事务同步；② 或直接用 TransactionSynchronizationManager.registerSynchronization() 在事务提交后删缓存；③ 或用 @TransactionalEventListener(phase = AFTER_COMMIT)。
  5. 空值缓存与 disableCachingNullValues() 冲突：如果开了 disableCachingNullValues()（默认行为是缓存 null 的），那么「防穿透的空值缓存」就失效了。
    解法：要么开启缓存 null（但要注意空值 TTL 要短），要么不用 @Cacheable 而手写缓存逻辑。
/**
 * ✅ 事务提交后再删缓存（解决坑 4 的正确姿势）
 */
@Service
public class ProductService {

    @Autowired
    private ApplicationEventPublisher eventPublisher;

    @Transactional
    public void update(Product product) {
        productMapper.updateById(product);
        // 发布事件，由监听器在事务提交后执行缓存删除
        eventPublisher.publishEvent(new ProductUpdateEvent(product.getId()));
    }
}

@Component
public class CacheEvictListener {

    // ⭐ AFTER_COMMIT：只在事务成功提交后才触发
    @TransactionalEventListener(phase = TransactionPhase.AFTER_COMMIT)
    public void onProductUpdate(ProductUpdateEvent event) {
        redisTemplate.delete("cache:product:" + event.getProductId());
    }
}

✅ 同时用 Lettuce（业务缓存）和 Redisson（分布式锁）的正确方式

问题：如果同时引入 spring-boot-starter-data-redis（Lettuce）和 redisson-spring-boot-starter，两者都会尝试创建 RedisConnectionFactory，可能冲突（Redisson 的 starter 会自动接管）。

方案一：只用 Redisson 做连接（不推荐）
Redisson 的 RedissonConnectionFactory 也能实现 Spring 的 RedisConnectionFactory，可以统一用它。但 Redisson 的 API 风格和 RedisTemplate 不太契合，性能上 Lettuce 更贴近原生。

方案二（推荐）：Lettuce 管连接 + Redisson 独立实例

// 不引入 redisson-spring-boot-starter（避免自动配置冲突）
// 只引入 org.redisson:redisson
// 然后手动创建 RedissonClient（独立连接）

@Configuration
public class RedissonConfig {

    @Bean(destroyMethod = "shutdown")
    public RedissonClient redissonClient(
            @Value("${redis.host}") String host,
            @Value("${redis.port}") int port,
            @Value("${redis.password}") String password) {

        Config config = new Config();
        config.useSingleServer()
            .setAddress("redis://" + host + ":" + port)
            .setPassword(password)
            .setConnectionPoolSize(32)
            .setConnectionMinimumIdleSize(8)
            .setTimeout(3000)
            .setRetryAttempts(3)
            .setRetryInterval(1500);

        // 关键：设置 codec，保证存进 Redis 的是可读的 JSON
        // 默认是 Kryo/FST 等二进制序列化，redis-cli 里是乱码
        config.setCodec(new JsonJacksonCodec());

        return Redisson.create(config);
    }
}

为什么推荐方案二：

  • 职责清晰：RedisTemplate（Lettuce）负责普通缓存读写；RedissonClient 负责分布式锁、分布式集合。
  • 避免冲突：不引入 starter，就不会有自动配置打架的问题。
  • 可独立调优：两者的连接池、超时可以分别配置。
  • 代价：会占用两套连接（Lettuce 的连接数 + Redisson 的 32 个连接）。要算进总连接数预算。

⚠️ Redisson 的 codec 坑：Redisson 默认用二进制序列化（Kryo/FST 等），写入 Redis 的值在 redis-cli 里是乱码。用 JsonJacksonCodec 可以解决。但要注意：如果混用 Redisson 和 Lettuce 操作同一个 key，两者必须用兼容的序列化方式，否则会读写出错。所以最佳实践是「Redisson 只管理它自己的锁/集合对象，业务缓存一律走 RedisTemplate」。

为什么 Lettuce 能共享连接：基于 Netty 的异步事件驱动——命令发送时记录顺序，响应按 FIFO 回来时按顺序匹配到各自的 Future。所以「谁的命令对应谁的响应」由客户端自己维护，不依赖 TCP 边界，多线程可以安全共用。

选型：新项目用 Lettuce（Spring Boot 默认，高并发下连接少）；需要极致简单的命令式控制或者老项目可能还在用 Jedis。两者都建议配合 commons-pool2 配连接池。

Redis 连接池怎么配置？进阶

核心参数：

  • maxTotal（最大连接数）：按并发量估。公式：峰值并发 × (Redis 耗时 / 请求总耗时)。例：200 线程 × (5ms/50ms) = 20，配 32 有充足余量。
  • maxIdle（最大空闲）：≈ maxTotal。
  • minIdle（最小空闲）：设成「稳态并发」，预热连接避免冷启动抖动。
  • maxWait（获取连接超时）：⚠️ 必须设！默认 -1 是无限等待，会导致请求堆积、内存暴涨。 建议 500ms ~ 2s。
  • timeBetweenEvictionRuns（空闲检测周期）+ testWhileIdle：及时发现失效连接，避免偶发 connection reset。

关键注意：

  1. Jedis 和 Lettuce 需求不同：Jedis 池大小必须 ≥ 并发线程数；Lettuce 单连接可共享，池可以小得多。
  2. 总算账：池大小 × 实例数不能超过 Redis 的 maxclients（默认 10000）。Cluster 下还要 × 节点数。
  3. 配大不是好事：Redis 单线程处理命令，连接多只增加 fd/上下文切换开销，不提升吞吐。
  4. 监控：活跃连接数、等待连接次数/时长、连接创建速率。活跃长期接近 maxTotal 或频繁等待超时 → 池太小（或命令太慢）。

加分：「我们遇到过一个问题：maxWait 用了默认的 -1，结果 Redis 抖动时请求全部在队列里等待，Tomcat 线程池被占满，整个服务不可用。后来改成 1 秒快速失败 + 上层熔断降级——这比『慢慢等待最终一起超时』要好得多。」

最容易答错的点：Pipeline 不保证原子性。它只是把命令一次性发出去节省网络往返，Redis 仍可能在批内插入其他客户端的命令。

选择建议：

  • 只需减少网络往返、命令间无依赖 → Pipeline（记得分批，每批 ≤1000）。
  • 需要「一组命令连续执行不被插入」→ MULTI/EXEC（但注意不回滚、不支持条件）。
  • 「读-判断-写」的原子操作 → Lua（首选）。
  • 不要把复杂业务逻辑塞进 Lua：难维护、难测试、阻塞主线程。

补充：Redis 7.0+ 的 Functions 是 Lua 的升级版（脚本在服务端注册，可复用，随 RDB/AOF 持久化）。新项目优先考虑 Functions。

为什么不能用 JDK 序列化？进阶

五个理由：

  1. 可读性差：redis-cli 里是 \xac\xed\x00\x05t\x00\x05value 这种乱码，线上排查问题时完全没法看（这是最痛的一点）。
  2. 体积大：Java 序列化会写入类名、字段名等元信息，比 JSON 大 30%~50%，更不用说 Protobuf。直接影响内存和带宽成本。
  3. 安全性：Java 反序列化是著名的漏洞来源（gadget chain 攻击）。如果 Redis 数据被污染，反序列化可能触发 RCE。
  4. 跨语言不可用：Python、Go 的服务读不了 Java 序列化的数据。
  5. 兼容性脆弱：类加字段、改包名、改类名，都可能导致反序列化失败（serialVersionUID 不匹配）。

推荐方案：

  • 通用场景：key 用 StringRedisSerializer，value 用 Jackson2JsonRedisSerializer 或 GenericJackson2JsonRedisSerializer。
  • 高性能场景：Protobuf（体积最小、性能最好，但需要 schema）。
  • Spring Boot 用户注意：默认的 RedisTemplate 就是 JDK 序列化！必须手动配置替换。StringRedisTemplate 则默认是 String，更安全。

面试话术：「我会统一用 JSON 序列化，核心考虑是『可运维性』——线上出问题时能用 redis-cli 直接看到内容，这个价值远大于那点性能差异。对性能极其敏感的少量超大 value，我们单独用 Protobuf。」

@Cacheable 有什么坑？高级
  1. 不设 TTL 就永不过期：defaultCacheConfig() 默认无过期时间，必须显式 entryTtl()。否则数据出错后永远无法自愈。
  2. 自调用失效：@Cacheable 基于 AOP 代理，同类内 this.method() 调用不经过代理，注解不生效。解法：注入自身（self.method()）或拆到另一个 Bean。
  3. 默认 JDK 序列化：redis-cli 乱码。必须显式配 JSON 序列化器。
  4. 事务与缓存的时序问题：@CacheEvict 在事务提交前执行时，并发读可能读到旧数据并写回缓存。解法：用 @TransactionalEventListener(phase = AFTER_COMMIT) 在事务提交后删缓存。
  5. 方法与注解的可见性：方法必须是 public，类必须被 Spring 管理。
  6. 空值与防穿透：默认不缓存 null，与「空值缓存防穿透」冲突，需要单独处理。
  7. 大 key 风险：@Cacheable 返回大列表（如全量列表查询）会生成大 key。要用 condition 限制（如只缓存前 N 页）。
  8. key 生成不当导致 key 爆炸：默认 key 生成器对复杂对象可能产生很大的 key，或 key 数量失控。

总结话术：「@Cacheable 适合『简单、明确的读缓存』场景，能大幅减少样板代码。但一旦涉及『防穿透、击穿、双写一致性』这些复杂需求，注解就不够用了，需要手写缓存逻辑。我的实践是：简单查询用注解，核心链路手写（把控制权握在自己手里）。」

Redisson 和 Lettuce 能同时用吗？高级

能，但要小心冲突。

冲突来源：spring-boot-starter-data-redis（Lettuce）和 redisson-spring-boot-starter 都会创建 RedisConnectionFactory Bean，可能导致 NoUniqueBeanDefinitionException 或者 Redisson 悄悄接管了 Spring 的 Redis 连接。

推荐方案：

  • 职责分离：Lettuce（通过 RedisTemplate）负责业务缓存读写；Redisson（RedissonClient）只负责分布式锁、分布式集合。
  • 不引入 redisson-spring-boot-starter，只引入 org.redisson:redisson，手动创建 RedissonClient Bean，避免自动配置冲突。
  • Redisson 配置 codec：默认是二进制序列化（Kryo 等），redis-cli 里是乱码。设 JsonJacksonCodec 提高可读性。
  • 不要混用两者操作同一个 key：如果 Redisson 和 Lettuce 用不同的序列化器读写同一个 key，会读写出错。所以最佳实践是「各自管理各自的 key 空间」。

成本：会占用两套连接（Lettuce 池 + Redisson 池）。要算进总的连接数预算（maxclients）。

面试话术：「我们的做法是『Lettuce 管缓存，Redisson 管锁，明确划分职责，不混用 key』。这样两个客户端的优势都能发挥——Lettuce 的轻量和与 RedisTemplate 的契合，Redisson 的分布式对象和看门狗。代价是两套连接，需要在 maxclients 预算里算清楚。」

Redis 客户端报连接超时，你怎么排查？专家

分层排查（从客户端到服务端）。

第一层：客户端侧

  • 连接池是否耗尽：看活跃连接数 vs maxTotal、等待连接的次数和时间。如果频繁等待超时 → 池太小，或有连接泄漏 / 慢命令占着连接。
  • 是否有连接泄漏：借了连接未归还（异常路径没在 finally 里释放）。用连接池的 abandonedConfig 检测泄漏。
  • 是否有阻塞命令占连接：BLPOP/BRPOP/SUBSCRIBE 会长时间独占连接。这类命令应该用独立连接，不能和普通命令共用池。
  • GC 情况：应用侧长 GC 会导致「看起来像 Redis 超时」（实际是应用没及时处理响应）。
  • 超时参数：timeout 是否设得太小（误伤正常的慢命令）？

第二层：网络侧

  • 网络延迟、丢包（ping / mtr）。
  • 带宽是否打满（大 key 传输是常见原因）。
  • 是否有防火墙/NAT 设备导致的连接中断。

第三层：Redis 服务端

  • INFO clients：连接数是否接近 maxclients。
  • SLOWLOG GET：是否有慢命令在阻塞（KEYS、大的 HGETALL）。
  • INFO latencystats / LATENCY LATEST：延迟事件（fork、expire-cycle 等）。
  • INFO persistence：是否有 fork 阻塞（RDB/AOF rewrite）。
  • INFO memory：mem_fragmentation_ratio < 1 说明内存被 swap 到磁盘，延迟会飙升。
  • 是否在做主从全量同步、故障转移、槽迁移。

第四层：区分「真超时」和「假超时」

  • 真超时：Redis 确实处理慢（慢命令、阻塞、CPU 打满）→ 治理命令、扩容、优化。
  • 假超时：Redis 很快，但客户端侧排队（连接池耗尽、应用 GC、网络拥塞）→ 优化客户端配置。

面试收尾：「我会先看『是客户端排队还是服务端慢』——通过对比『客户端观察到的延迟』和『Redis 侧的 latencystats』，能快速区分这两类。然后按客户端 → 网络 → 服务端的顺序逐层排除。 经验上，连接池配置不当（特别是 maxWait 和 maxTotal）和慢命令导致的阻塞，是这一类问题的两大主因。」
