Day2.3 · 过期删除与内存淘汰：Redis 如何管住内存

一句话结论

「过期」和「淘汰」是两件完全不同的事：过期删除（expire）管的是「key 到时间该消失了」；内存淘汰（eviction）管的是「内存满了要腾地方」。面试官最爱考的组合是：为什么 key 过期了内存没降？为什么设了 TTL 还会 OOM？——答案就在这两套机制的配合方式里。

1. 过期删除策略：惰性 + 定期（组合拳）

先看数据结构：怎么存 TTL

Redis 用两个 dict 存数据：

  • dict（键空间）：key → value
  • expires（过期字典）：key → 过期时间戳（毫秒，long long）

所以设 TTL 是有额外内存开销的——expires dict 里也要一份 dictEntry（约 24 字节）+ 一份 key 的引用。这也是「不是所有 key 都该设 TTL」的原因之一。

########## TTL 相关命令全集 ##########
# 设置过期（相对时间）
EXPIRE key 60                # 60 秒后过期
PEXPIRE key 60000            # 毫秒
SET key value EX 60          # 等价写法（推荐，一次原子完成）
SETEX key 60 value
PSETEX key 60000 value

# 设置过期（绝对时间）
EXPIREAT key 1790000000      # Unix 秒时间戳
PEXPIREAT key 1790000000000  # Unix 毫秒时间戳

# 查询
TTL key      # 剩余秒数：-1 = 永不过期，-2 = key 不存在（或已过期）
PTTL key     # 毫秒精度

# 移除过期
PERSIST key                  # 转为永久（返回 1 成功，0 表示 key 不存在或本来就没 TTL）

# 条件设置过期（7.0+）
EXPIRE key 60 NX             # 只在 key 没有 TTL 时设置
EXPIRE key 60 XX             # 只在 key 已有 TTL 时设置
EXPIRE key 60 GT             # 只在新 TTL 大于当前 TTL 时设置
EXPIRE key 60 LT             # 只在新 TTL 小于当前 TTL 时设置

# ⚠️ 重要：对 key 执行 SET / GETSET / *STORE 等操作会清掉 TTL！
SET k v EX 60
SET k v2                     # TTL 被清除！变成永久 key
SET k v3 KEEPTTL             # ✅ 保留 TTL（6.0+）
APPEND k suffix              # APPEND 不会清除 TTL
INCR counter                 # INCR 不会清除 TTL
DEL k / RENAME k k2          # 会（RENAME 后 TTL 跟随 key 走）

两种删除策略

策略机制优点缺点
惰性删除访问 key 时先检查是否过期（expireIfNeeded），过期则删除并返回 nilCPU 友好，不浪费算力在无人访问的 key 上内存不友好——冷 key 永远不被访问，就永远不会被删，内存泄漏
定期删除每 100ms（hz=10）执行一次：随机抽取 20 个设了 TTL 的 key，删除其中已过期的；若过期比例 > 25%，立刻再抽 20 个继续，循环直到比例 ≤25% 或本轮耗时超过 CPU 时间上限（默认 25% 的 CPU 时间）能清理冷 key，且通过限时限量避免阻塞抽样不是全扫，可能有「漏网之鱼」；受 CPU 时间上限约束，高负载时清理变慢
✅ 定期删除的算法细节（面试深挖高频）
// 伪代码（activeExpireCycle 简化版）
do {
    // 1) 从 expires dict 中随机抽取 20 个 key
    num = 20;
    expired = 0;
    while (num--) {
        if (当前 key 已过期) {
            删除该 key;
            expired++;
        }
    }
    // 2) 如果过期比例 > 25%，继续循环（说明过期 key 还很多）
} while (expired > 20 * 0.25 && 本轮未超过时间上限);

三个关键设计意图：

  1. 随机抽样而非全扫：全扫 O(N) 会阻塞，采样 20 个足以在统计上判断「过期密度」。
  2. 25% 阈值动态加速：如果抽出来 5 个以上都过期，说明过期 key 密集，就继续抽——这样能快速清理大量同时过期的 key（比如雪崩后的场景）。
  3. 时间上限保护：无论如何不能在清理上花超过 25% 的 CPU 时间（ACTIVE_EXPIRE_CYCLE_SLOW_TIME_PERC），到点就退出，把时间让给正常请求。这是「可用性优先于清理及时性」的取舍。
⚠️ 从库的过期策略完全不同（高频追问）

从库不会主动删除过期 key！

  • 从库对过期 key 的处理是：逻辑上认为它已过期（读的时候返回 nil），但不物理删除。
  • 只有主库删除（惰性 or 定期）后，会发送一个 DEL 命令同步给从库，从库收到后才真正删除。
  • 为什么这么设计：保证主从数据一致。如果从库自己删了，主库还没删，那主从数据就不一致了（主库还有这个 key，从库已经没了）。
  • 生产影响：如果主库长期不访问某个过期 key 且定期删除没抽到它，从库上这个 key 会一直占着内存。这就是「从库内存比主库高」的常见原因之一。

面试话术：「从库不会主动淘汰过期 key，只做逻辑过期判断，物理删除由主库的 DEL 命令驱动同步。这是为了保证主从数据一致——如果从库自己删了，主从数据就不一致了。所以运维上会看到从库内存略高于主库，这是正常现象。」

🚨 经典问题：为什么 key 过期了内存没降？

三个可能原因，按概率排序：

  1. 惰性删除 + 定期删除都没覆盖到：冷 key 一直没人访问，定期删除又是抽样的。这种情况用 INFO stats 看 expired_keys 是否在增长。解法：SCAN + TTL 主动清理，或调大 hz（10 → 100，代价是 CPU）。
  2. 内存碎片：key 确实被删了，但释放的内存是碎片化的，jemalloc 不会立刻还给操作系统。证据：看 mem_fragmentation_ratio = used_memory_rss / used_memory，大于 1.5 说明碎片严重。解法：开 activedefrag yes（在线碎片整理），或重启（不推荐）。
  3. 被编码转换或大 key 占住：比如一个 Hash 变成 hashtable 后，即使字段删到很少，也不会退回 listpack，内存不降。解法：重建 key。

还有一个容易忽略的：used_memory 是 Redis 分配器统计的，包含各种缓冲区（客户端输出缓冲区、AOF 缓冲区、复制缓冲区）。如果某个客户端因为慢连接积累了 500MB 输出缓冲区，删 key 也没用。看 INFO memory 里的 mem_clients_normal 和 mem_clients_slaves。

2. 内存淘汰策略：8 + 2 种

当 maxmemory 达到上限，且客户端还要写入时，Redis 按 maxmemory-policy 决定行为。

策略淘汰范围依据说明
noeviction

allkeys-lru

3. 近似 LRU：为什么不是「真 LRU」

✅ Redis 的 LRU 是「近似」的——这是刻意的取舍

标准 LRU 的问题：需要维护一个双向链表，每次访问都把节点移到链表头。这有两个代价：① 每个 key 需要两个额外指针（16 字节 × 所有 key，内存开销巨大）；② 每次访问都要改链表，在单线程下有性能开销。

Redis 的做法：

  1. 在 redisObject.lru（24 bit）里记录最后一次访问的时间戳（精度为秒级，2^24 秒 ≈ 194 天循环）。
  2. 需要淘汰时，随机采样 maxmemory-samples（默认 5）个 key，从中选空闲时间最长的那个淘汰。

效果：采样 5 个时，淘汰的 key 与「真正最久未使用」的重合度约 90%+；采样 10 个时可接近 100%。用一点准确度换大量内存和 CPU。

3.0 的改进：候选池（eviction pool）
纯随机采样有个问题：每次都要重新采样，可能错过之前找到的「很旧」的 key。Redis 3.0 引入了候选池——把历次采样找到的「较旧」的 key 放进一个 16 大小的池子里（按空闲时间排序），淘汰时从池子里选最旧的。这让淘汰更接近真 LRU，同时也让「淘汰分布」更均匀。

面试标准答法：「Redis 用的是近似 LRU，不维护完整链表，而是在 redisObject 里存 24 位的时间戳。淘汰时随机采样 N 个 key（默认 5），选最久未用的。3.0 之后引入候选池进一步提升准确度。这样做的原因是——真 LRU 需要每个 key 两个额外指针，内存开销大且每次访问都要改链表；Redis 用准确度的微小损失换取了内存和性能。」

4. LFU：比 LRU 更适合缓存

✅ 为什么需要 LFU？LRU 的致命缺陷

场景：一个 key 在过去 1 秒被访问了 10000 次（秒杀商品），但之后就再也没人访问。用 LRU 的话，这个 key 的时间戳最新，会一直被认为「很热」而保留，挤掉真正长期高频的 key（比如首页配置）。

LFU（Least Frequently Used）按「访问频率」淘汰，更符合缓存的本质——长期被频繁访问的才是好缓存。

Redis 的 LFU 实现（很巧妙的地方）：

redisObject 的 24 bit lru 字段在 LFU 模式下被拆成两部分：

字段位宽含义
ldt（last decrement time）16 bit上次衰减时间（分钟级，2^16 分钟 ≈ 45 天循环）
logc（logistic counter）8 bit访问频率计数器，范围 0-255

两个关键机制：

  1. 对数递增：每访问一次，计数器不是简单 +1，而是按概率增加——计数器越大，增加的概率越小（类似 1/(counter×lfu-log-factor + 1)）。lfu-log-factor（默认 10）越大，增长越慢。这使得 8 bit 就能表示很大的访问量级（百万级）。
  2. 时间衰减：为了防止「曾经很热但现在不热」的 key 永久占位，Redis 会按时间衰减计数器——每经过 lfu-decay-time（默认 1 分钟），计数器 -1。这样旧的热 key 会随时间自然降温。

参数：

CONFIG GET lfu-log-factor      # 默认 10：越大，计数器增长越慢（能区分更高的频次）
CONFIG GET lfu-decay-time       # 默认 1（分钟）：衰减速度，0 表示不衰减

# 调优思路：
# - 如果热点变化快，调小 lfu-decay-time（衰减更快，更"健忘"）
# - 如果热点稳定，调大 lfu-log-factor（能区分更细的频次差异）
💡 LRU vs LFU 怎么选（面试常问）
场景推荐理由
缓存有明显热点，且热点长期稳定allkeys-lfu能识别「持续高频」，不受偶发突发访问干扰
访问模式是「最近访问的还会再访问」（时间局部性）allkeys-lru符合该访问规律
数据有冷热分层，且都设了 TTLvolatile-lru / volatile-lfu只淘汰缓存区，不动持久数据
混合存储（缓存 + 持久数据在同一实例）volatile-*关键：绝对不要用 allkeys-*，否则会把不该淘汰的持久数据淘汰掉
所有 key 访问概率差不多allkeys-random此时 LRU/LFU 的计算开销是浪费
🚨 三个淘汰策略的致命误配（真实事故）
  1. 默认值 noeviction 用在纯缓存场景：内存满了，所有写请求报 OOM command not allowed when used memory > 'maxmemory'。业务侧如果没处理这个异常，会造成大面积失败。纯缓存必须有明确策略（通常 allkeys-lru）。
  2. 混合存储用了 allkeys-lru：把队列/持久数据也淘汰了。最典型的是——用同一个 Redis 实例既做缓存又做延时队列，结果队列数据被 LRU 淘汰，任务丢失。
  3. volatile-lru 但数据没设 TTL：淘汰范围为空，等价于 noeviction，同样 OOM。上线前必须用 INFO keyspace 和抽样确认「设了 TTL 的 key 占比」。

面试深度问答

Redis 的过期删除策略是什么？为什么要两种结合？基础

惰性删除 + 定期删除组合，理由是单一策略都有明显缺陷：

  • 只用惰性删除：CPU 省，但冷 key（再也不被访问）永远不删，内存泄漏。
  • 只用定期删除：内存能及时清理，但如果全量扫描，O(N) 会阻塞；即使抽样，也可能漏掉没被抽中的过期 key。

组合后：惰性删除兜底「被访问的过期 key 一定失效」，定期删除兜底「冷 key 也能被清理」。

定期删除的具体参数（这是区分深浅的关键）：

  • 频率：hz 默认 10，即每 100ms 一次。
  • 每次随机抽 20 个设了 TTL 的 key，删除过期的。
  • 如果过期比例 > 25%，立即再抽 20 个，循环。
  • 本轮总耗时不得超过 25% 的 CPU 时间（ACTIVE_EXPIRE_CYCLE_SLOW_TIME_PERC），超时就让出。# 这是可用性优先的取舍

还能再说一层：内存里还有个兜底——如果两种策略都漏了，最终靠淘汰策略（maxmemory-policy）清理。所以「过期 + 淘汰」是两层防线。

主库和从库的过期删除有什么不同？高级

核心差异：从库不主动物理删除过期 key。

维度主库从库
惰性删除访问时检查 → 删除 + 返回 nil访问时检查 → 返回 nil，但不删除
定期删除执行（随机抽样）不执行
物理删除来源自己删等主库发来的 DEL 命令

为什么这么设计：保证主从数据一致。如果从库自己删了而主库没删，主从数据就不一致——这在主从切换时会导致数据丢失或行为异常。

生产影响（这才是加分点）：

  • 从库内存可能长期略高于主库，因为过期 key 要等主库的 DEL 通知。这是正常现象，不需要处理。
  • 但如果差值很大（比如 30%），说明主库有大量过期 key 没被清理——可以调大 hz，或主动 scan + 清理。
  • 极端情况下（主库对该 key 长期无读写，定期删除又一直没抽中），这个 key 会一直占内存。所以「不要依赖 TTL 做内存管理」——TTL 是数据语义，内存管理要靠淘汰策略和容量规划。
Redis 的内存淘汰策略有哪些？你们生产用哪个？进阶

先说清分类维度：「淘汰范围」（allkeys / volatile）× 「淘汰依据」（lru / lfu / random / ttl），加上 noeviction 和 8.6 新增的 lrm 系列。

完整列出（不要漏）：

  1. noeviction（默认）：不淘汰，写报错。
  2. allkeys-lru / allkeys-lfu / allkeys-random：所有 key 中按 LRU / LFU / 随机淘汰。
  3. volatile-lru / volatile-lfu / volatile-random / volatile-ttl：只在设了 TTL 的 key 中淘汰。
  4. 8.6 新增：allkeys-lrm / volatile-lrm——按最近修改时间淘汰（LRM = Least Recently Modified），适合 AI 特征库、时序数据这类「写入时间」比「访问时间」更重要的场景。

生产选型（结合场景说）：

  • 纯缓存实例 → allkeys-lru（或访问有稳定热点时用 allkeys-lfu）。理由：所有数据都是可再生的，内存满了就淘汰最冷的。
  • 混用实例（缓存 + 业务数据） → volatile-lru，并且强制要求缓存必须设 TTL。理由：保护业务数据不被淘汰。
  • 绝对不能：混用实例配 allkeys-*——曾经有公司因此把延时队列的任务淘汰了，导致大量订单超时未处理。

追问准备：为什么不是 noeviction？
因为 noeviction 下内存满时写命令直接失败，业务会大面积报错，故障是「立刻可见的、全量的」；而淘汰策略下只是「部分数据被清掉、需要回源」，故障是「渐进的、部分降级的」。缓存场景下后者明显更好。

LRU 在 Redis 里是怎么实现的？和标准 LRU 有什么区别？进阶

标准 LRU：哈希表 + 双向链表，访问时把节点移到链表头，淘汰时取链表尾。O(1)，但需要每 key 两个额外指针，且每次访问都要改链表。

Redis 的近似 LRU：

  1. 在 redisObject 的 24 bit lru 字段里存最后访问时间戳（秒级精度，2^24 秒约 194 天循环）。
  2. 淘汰时随机采样 maxmemory-samples（默认 5）个 key，选空闲时间最长的淘汰。
  3. 3.0+ 引入候选池（eviction pool，大小 16）：把历次采样中较旧的 key 放进去按空闲时间排序，淘汰时从池里选最旧的。这让淘汰结果更接近真 LRU，分布更均匀。

区别总结：

对比项标准 LRURedis 近似 LRU
额外内存每 key 2 个指针（16 字节）0（复用 robj 里已有的 24 bit）
访问开销每次改链表只更新时间戳字段
准确度精确采样 5 约 90%+，采样 10 接近 100%
时间精度精确秒级（且 194 天循环）

加分细节：24 bit 的 lru 字段被设计成「从当前时间戳取低 24 位」，所以理论上存在「194 天前的 key 看起来比刚访问的更近」的时钟回绕问题。但实践中 key 活不到 194 天，可忽略。这种「知道设计边界」的表述很能加分。

LFU 是怎么实现的？为什么用 8 bit？专家

见本节第 4 部分。关键点：

  1. 复用 lru 的 24 bit：拆成 16 bit 的 ldt（衰减时间）+ 8 bit 的 logc（计数器）。
  2. 对数递增：访问时按概率增加计数器，P = 1/(logc × lfu-log-factor + 1)。logc 越小增长越快——这样 8 bit 也能覆盖 0 到百万级的访问量，因为它是「指数刻度」。
  3. 时间衰减：每 lfu-decay-time 分钟（默认 1），logc 减 1。防止「旧热点」永久占位。
  4. lfu-log-factor 的语义：默认 10 表示「计数器从 0 涨到 100 大约需要 1000 万次访问」；设为 100 则需要更多访问才能达到同样计数（能区分更高频次，但对低频次的分辨率下降）。

为什么非得用 8 bit：因为 lru 字段总共只有 24 bit。这在 redisObject 的位域里是硬约束——如果要多分配位，每个 key 都要多占内存，而 Redis 有几亿个 key。所以选择「用对数编码压缩计数范围」，而不是「扩大位宽」。

专家级洞察：这个设计体现了一个通用原则——在内存敏感的系统里，用「对数/概率编码」代替「线性编码」，可以在有限位宽下表达更大的动态范围，代价是精度损失。同样的思路也出现在 HyperLogLog（用桶内最大前导零个数）和 SkipList（用概率决定层数）里。能把这个原则抽象出来，说明你不只是记住了 Redis。

线上 Redis 内存持续增长，怎么排查？高级

给一套可执行的排查路径（这段可以直接当项目经验讲）：

第一步：区分是「逻辑内存」还是「碎片」
INFO memory | grep -E 'used_memory:|used_memory_rss:|mem_fragmentation_ratio'

若 used_memory 也在涨 → 是真实数据在涨（继续第二步）。
若只有 rss 涨、ratio > 1.5 → 内存碎片，开 activedefrag 或优化分配器。

第二步：区分是「key 数量」还是「单个 key 大小」
INFO keyspace        # keys 数量增长趋势
DBSIZE
redis-cli --memkeys  # 低峰期执行，找内存最大的 key

key 数量暴涨 → 检查业务是否忘了设 TTL、是否有 key 命名带时间戳导致无限堆积（如 rate:uid:1001:202609301730 这种按分钟分桶的限流 key，如果没设 TTL 就是灾难）。
单个 key 巨大 → 大 key 问题，进第四步。

第三步：看是不是「非数据内存」在涨
INFO memory | grep -E 'mem_clients_normal|mem_clients_slaves|mem_aof_buffer|mem_replication_backlog'
CLIENT LIST | awk '{print $2,$3,$12,$18}' | sort -k4 -hr | head

mem_clients_normal 大 → 有慢客户端（网络差或消费慢）导致输出缓冲区堆积。这是最容易被忽略的内存泄漏来源，配合 client-output-buffer-limit 处理。

第四步：定位到具体业务

用 key 前缀统计（写个 SCAN + 分组统计的脚本），找出「哪个前缀的 key 在涨」或「哪个前缀的总内存最大」，然后去找对应的业务方。

# 统计各前缀的 key 数量（示例，生产用 Lua 或 SCAN+管道更高效）
redis-cli --scan --pattern '*' | awk -F: '{print $1":"$2}' | sort | uniq -c | sort -rn | head -20
第五步：确认淘汰策略是否生效
INFO stats | grep evicted_keys
CONFIG GET maxmemory-policy
INFO keyspace   # 看 expires 占比，验证 volatile-* 是否有效

若 maxmemory 为 0（不限制）→ 这是最大的隐患，内存涨到物理上限会被 OOM Killer 杀掉，比报错严重得多。

长效治理：① 所有缓存强制 TTL（可以通过中间件或代码规范检查）；② 接入大 key / 热 key 定期巡检；③ 建立 key 前缀清单与负责人制度；④ 内存使用率 70% 告警，而不是等到 90%。
