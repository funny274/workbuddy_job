Day 4 · 第 2 节 预计 85 分钟 面试必考

Day4.2 · 分布式锁、Lua 脚本与 Functions

一句话结论

分布式锁的演进是一条「不断补漏洞」的线：SETNX（无过期 → 死锁）→ SET NX PX（过期了但误删别人的锁）→ value 存唯一标识 + Lua 原子释放（业务超时锁提前释放）→ Redisson 看门狗自动续期（基本可用）。

面试深水区在三处：① 为什么释放锁必须用 Lua；② 看门狗续期的原理与它自身的缺陷；③ Redlock 到底「对不对」——这题没有标准答案，考官要的是你能说清双方的论据和适用边界。

1. 从零开始：SETNX 的四个坑

✅ 第一版：SETNX（Set if Not eXists）

最朴素的想法：用一个 key 表示锁，谁能 SET 成功谁就拿到锁。

SETNX lock:order:1001 "1"
# 返回 1 = 抢到锁；返回 0 = 别人持锁
# 用完删除
DEL lock:order:1001

致命缺陷：如果持锁的进程在 DEL 之前崩溃了（宕机、被 kill、网络断开），这个 key 永远存在 → 死锁，后续所有请求都拿不到锁。

✅ 第二版：SET NX EX（加过期时间）
# 抢锁的同时设置 30 秒过期（必须是一条命令，保证原子性！）
SET lock:order:1001 "1" NX EX 30

# ⚠️ 反例：分成两条命令 — 中间崩溃就会死锁
SETNX lock:order:1001 "1"
EXPIRE lock:order:1001 30     # ← 如果上一句成功、这一句没执行，就死锁了

解决了死锁问题（最多 30 秒后自动释放）。

又引入新问题（坑 2）：误删别人的锁。

场景：

  1. 线程 A 抢到锁，设置 30 秒过期。
  2. 线程 A 的业务执行了 35 秒（比如发生了 Full GC、或者下游接口特别慢）。
  3. 30 秒时锁自动过期，被 B 抢到。
  4. A 执行完，执行 DEL lock —— 把 B 的锁删掉了！
  5. C 又抢到了锁，此时 B 和 C 同时持有锁，互斥性被破坏。
✅ 第三版：value 存唯一标识 + Lua 原子释放

解法：锁的 value 存一个「只有自己知道」的唯一标识（UUID + 线程 ID）。删除时必须先校验这个标识是不是自己的。

为什么必须用 Lua（关键面试点）：

// ❌ 错误：判断和删除不是原子的，中间有时间窗口
String id = redis.get(lockKey);
if (myId.equals(id)) {       // ← 此刻锁可能刚好过期、被别人抢到
    redis.del(lockKey);       // ← 删掉的是"别人的锁"！
}

虽然这个窗口极小（两条命令之间），但「极小概率」在生产的高并发下也会发生（想想每秒几万次的锁获取释放，一天就是几十亿次，百万分之一的概率也会命中）。而用 Lua 脚本，Redis 保证脚本执行的原子性（单线程执行整个脚本，中间不会被其他命令插入），所以「判断 + 删除」成为一个不可分割的操作。

-- unlock.lua：只有持有者才能释放锁
-- KEYS[1] = 锁的 key, ARGV[1] = 客户端唯一标识
if redis.call('GET', KEYS[1]) == ARGV[1] then
    return redis.call('DEL', KEYS[1])
end
return 0
/**
 * 完整的自制分布式锁（第三版）
 * 这是"能讲清楚原理"的版本，但生产上建议直接用 Redisson
 */
public class SimpleRedisLock {

    private static final String UNLOCK_SCRIPT =
        "if redis.call('GET', KEYS[1]) == ARGV[1] then " +
        "  return redis.call('DEL', KEYS[1]) " +
        "else return 0 end";

    private final StringRedisTemplate redis;
    private final String lockKey;
    // 每个锁实例一个唯一 ID（UUID 在构造时生成，代表"这个锁实例"）
    private final String clientId = UUID.randomUUID().toString();

    public SimpleRedisLock(StringRedisTemplate redis, String bizId) {
        this.redis = redis;
        this.lockKey = "lock:" + bizId;
    }

    public boolean tryLock(long timeoutSeconds) {
        // SET key value NX EX timeout —— 一条命令，原子
        Boolean ok = redis.opsForValue()
            .setIfAbsent(lockKey, clientId, Duration.ofSeconds(timeoutSeconds));
        return Boolean.TRUE.equals(ok);
    }

    public void unlock() {
        // 用 Lua 保证"判断 + 删除"的原子性
        redis.execute(new DefaultRedisScript<>(UNLOCK_SCRIPT, Long.class),
            Collections.singletonList(lockKey), clientId);
    }
}
⚠️ 第四版要解决的问题：业务超时 → 锁提前释放

第三版虽然解决了「误删」，但没解决根本问题：如果业务执行时间超过锁的过期时间，锁被自动释放、别人拿到锁，此时两个线程真的在同时执行临界区代码——互斥性实质上被破坏了。此时你的删除操作不会误删（因为有防误删），但并发已经发生了。

两种应对思路：

  1. 把过期时间设得足够长（比如业务的 P99.9 耗时的 3 倍）。缺点是如果进程真崩了，要等很久才能解锁。
  2. 自动续期（看门狗）：后台起一个定时任务，在锁快过期时自动延长。这就是 Redisson 的做法。

2. Redisson：生产级方案

✅ Redisson 加锁的完整流程与看门狗机制

加锁（Redisson 的 Lua 脚本逻辑）：

  1. 用 EXISTS lockKey 判断锁是否存在。
  2. 不存在 → HSET lockKey clientId 1 + PEXPIRE lockKey 30000，抢锁成功。
  3. 存在且是自己的锁（HEXISTS lockKey clientId）→ HINCRBY lockKey clientId 1（重入计数 +1）。
  4. 存在且不是自己的 → 返回剩余 TTL，客户端订阅 __redis__:unlock 消息等待通知，或按剩余时间自旋。

为什么用 Hash 结构而不是 String：为了支持可重入（同一个线程多次加锁）——Hash 的 field 是 clientId，value 是重入次数。

看门狗（Watch Dog）机制：

  • 触发条件：只要你不显式指定 leaseTime，Redisson 就启用看门狗，默认锁超时时间 30 秒（lockWatchdogTimeout）。
  • 原理：加锁成功后，Redisson 会起一个后台定时任务（TimerTask），每隔 30/3 = 10 秒（lockWatchdogTimeout / 3）检查一次，如果客户端仍持有锁，就把过期时间重置为 30 秒。
  • 停止条件：客户端释放锁时，取消定时任务；如果客户端崩溃，定时任务自然消失，锁在 30 秒后自动过期（这就是为什么它能防死锁，同时又能支持长时间业务）。

⚠️ 最重要的一条实践经验：

// ✅ 不传 leaseTime → 启用看门狗，业务多久都能续期
RLock lock = redisson.getLock("lock:order:1001");
lock.lock();

// ❌ 传了 leaseTime → 看门狗不生效！锁到点就释放，业务没做完也会释放！
lock.lock(30, TimeUnit.SECONDS);   // 危险！
lock.tryLock(10, 30, TimeUnit.SECONDS);  // 危险！

try {
    // 业务逻辑
} finally {
    // ⚠️ 必须判断是不是自己持有的锁再释放
    if (lock.isHeldByCurrentThread()) {
        lock.unlock();
    }
}

面试必答的这个坑：很多人在用 tryLock(waitTime, leaseTime, unit) 时传了 leaseTime，结果以为有看门狗保护，实际上锁会在 leaseTime 后释放——业务超时就会出现并发。这是一个非常常见、也非常致命的线上坑。

🚨 看门狗自身的三个问题
  1. 看门狗依赖客户端存活：如果客户端发生了长时间的 Full GC（比如 STOP-THE-WORLD 10 秒），看门狗线程也被暂停，无法续期 → 锁可能在这期间过期。这是 JVM 层面的问题，看门狗救不了。
    缓解：优化 GC（用 G1/ZGC）、把锁粒度做小、把长业务拆短。
  2. 看门狗会产生额外流量：每 10 秒一次续期请求。如果有 10 万个并发锁，就是每秒 1 万次续期——不可忽视。所以锁的粒度应该尽量小（按业务 ID 而不是全局）。
  3. 续期失败会导致锁提前释放且不自知：如果续期时网络抖动、Redis 短暂不可用，续期失败，锁过期了，但客户端以为还持有锁。
    缓解：Redisson 在续期失败时会尝试重试；但最终还是要靠「业务侧的幂等 + 乐观锁」做最后一道防线。

3. 用锁的正确姿势：业务侧保护

✅ 分布式锁不是「银弹」：必须配合业务侧保护

核心认知：分布式锁是「减少并发」，不是「彻底消除并发」。因为锁可能失效（网络分区、GC、Redis 故障），所以临界区内的操作必须自身是幂等的，或者用乐观锁保证正确性。

三层保护（面试高分点）：

  1. 第一层：分布式锁（减少并发，提高性能，避免大部分冲突）
  2. 第二层：数据库乐观锁 / 版本号（保证即使锁失效，数据也不会错）
  3. 第三层：唯一索引 / 幂等表（防止重复插入）
-- 第二层：乐观锁，保证即使锁失效也不会超卖
UPDATE stock
SET num = num - 1, version = version + 1
WHERE id = #{id}
  AND version = #{expectedVersion}
  AND num >= 1;
-- 影响行数 = 0 → 说明被别人改了，交易失败（重试或返回失败）
-- 关键：即使锁因为意外失效导致两个线程同时进来，这个 SQL 也只会成功一次（行锁 + version 校验）
-- 第三层：唯一索引防重复
CREATE TABLE order_pay_record (
  id BIGINT PRIMARY KEY AUTO_INCREMENT,
  order_no VARCHAR(64) NOT NULL,
  request_id VARCHAR(64) NOT NULL,
  UNIQUE KEY uk_request (request_id)   -- 同一个请求 ID 只能插一条
);
💡 一句话总结

「分布式锁是为了性能和体验，数据库约束是为了正确性。永远不要指望锁保证正确性。」

面试官听到这句话，会知道你不但会用锁，还知道它的边界在哪。

4. Redlock：争议与真相

✅ Redlock 是什么

背景：单 Redis 实例的锁有个根本问题——如果 Redis 是主从架构且发生了故障转移，锁可能丢失：

  1. 客户端 A 在 master 上抢到锁。
  2. master 在把锁同步到 slave 之前宕机。
  3. slave 被提升为新 master（它没有这条锁记录）。
  4. 客户端 B 也能抢到同一把锁 → 两个客户端同时持锁。

antirez 的方案（Redlock）：部署 N（一般 5）个完全独立的 Redis 主节点（不是 Cluster，是独立的实例）。加锁时：

  1. 记录开始时间 T1。
  2. 依次向这 5 个节点发送加锁请求（每个请求带很短的超时，如 50ms）。
  3. 如果在超过半数（≥3 个）节点上成功加锁，且总耗时 < 锁的过期时间，则加锁成功。
  4. 锁的有效时间 = 初始过期时间 - 加锁总耗时（避免在「加锁过程中」锁就过期了）。
  5. 如果失败，则向所有节点发送解锁请求（包括没加成功的）。
⚠️ Martin Kleppmann 的质疑（面试要能说出来）

《Designing Data-Intensive Applications》的作者 Martin Kleppmann 写了一篇著名文章 How to do distributed locking，系统性地批评 Redlock。核心论据：

  1. 依赖时钟假设：Redlock 的安全性依赖「所有节点的时钟单调递增且漂移不大」。但现实中 NTP 校时会导致时钟跳跃——一个节点的时钟跳快，会让锁提前过期，破坏安全性。这是最致命的一条。
  2. GC / 网络延迟无法避免：即使时钟没问题，客户端进程发生 STW GC 也会导致它在「锁已过期」的情况下继续执行临界区代码。Redlock 没有解决这个问题（这个问题的解法是 fencing token，见下文）。
  3. 性能代价：Redlock 需要 5 个独立 Redis 实例，而且加锁要串行请求 5 次（或并发但取多数）。延迟和资源成本都显著上升，但它提供的「安全性」并不比单实例 + fencing token 更好。
  4. 用途错配：Redlock 更适合「效率型锁」（防止重复劳动，偶尔失效无所谓）；如果用在「正确性型锁」（如扣款，失效会导致资金错误），那它不够安全——正确性应该由fencing token + 存储层的校验保证。

antirez 的反驳：Clock 跳变的问题可以通过「不依赖系统时钟、只在锁的有效期内使用墙钟」等方式缓解；且在实际工程中，时钟跳变的概率很小。他还强调 Redlock 的设计目标就是「在大多数故障下可用且安全」，不是「理论上 100% 安全」。

✅ Fencing Token：真正解决「锁失效」的方案

核心思想：让锁服务为每次加锁分配一个单调递增的编号（fencing token）。客户端在访问存储时必须带上这个编号，存储层拒绝比已记录编号更小的请求。

流程：

  1. 客户端 A 获取锁，拿到 token = 33。
  2. A 发生 GC，锁过期，客户端 B 获取锁，拿到 token = 34。
  3. B 先写入存储（带 token 34），存储记录「最新 token = 34」。
  4. A 从 GC 中恢复，向存储写入（带 token 33）。存储发现 33 < 34，拒绝写入。 ✅

结论：fencing token 把「防止并发」的责任从锁转移到了存储层，这是唯一能真正保证正确性的方式。面试里能讲出 fencing token，基本上可以确认你读过 DDIA 或有过认真的分布式系统思考。

💡 Redlock 面试话术（这是最稳的回答）

「Redlock 的争议本质上是两种目标的错配：

  • 如果锁是用来做「效率优化」（比如避免多个线程重复计算、重复发短信），那把偶尔的失效看作可接受的风险，Redlock 够用，甚至单实例就够用——因为失效最坏的结果只是「多做了一次无用功」。
  • 如果锁是用来保证「正确性」（比如扣款不能重复），那任何基于 Redis 的锁都不够安全，包括 Redlock。正确做法是 fencing token + 存储层校验，或者干脆用数据库的行锁/唯一索引。

所以我的实际选择是：生产上用 Redisson 单实例（或哨兵）+ 业务侧幂等/乐观锁。理由：Redlock 增加的 5 个实例带来的复杂度和延迟，换来的是一个「理论上仍然不完美」的保证——性价比不高。把同样的精力花在「业务侧幂等设计」上，收益更大。」

5. Lua 脚本：原子性操作的瑞士军刀

✅ Lua 脚本的原子性从哪来

Redis 在执行 Lua 脚本时，会把整个脚本当作一个命令来执行——在脚本执行期间，不会插入任何其他客户端的命令。（因为 Redis 的命令执行本身是单线程的，脚本作为一个整体被提交给这个单线程。）

所以 Lua 的价值是：把「读-判断-写」这种本来需要多条命令的操作，合并成一个原子操作——避免中间被其他请求插入。

⚠️ 重要澄清（面试常考）：

  • Lua 的「原子性」只是「不被其他命令打断」，不是「事务的回滚」。如果脚本执行到一半报错（比如类型错误），已经执行的命令不会回滚，后续命令也不会执行。
  • 所以 Lua 是「原子执行」而非「原子事务」。要写出正确的脚本，必须自己保证「要么全部执行成功，要么在错误前不做任何写操作」（把校验都放在写操作之前）。
  • 另外：Lua 脚本会阻塞 Redis 主线程。长时间运行的脚本（比如循环一个大集合）会卡住整个实例。Redis 7.0 起有 lua-time-limit（默认 5 秒），超过后其他命令会返回 BUSY 错误，但脚本本身不会自动被杀。
-- ⭐ 实战 1：安全的分布式锁释放（前面已见）
if redis.call('GET', KEYS[1]) == ARGV[1] then
    return redis.call('DEL', KEYS[1])
end
return 0
-- ⭐ 实战 2：限流（滑动窗口计数器，配合 INCR + EXPIRE 的原子化）
-- KEYS[1] = 限流 key（如 rate:ip:1.2.3.4）, ARGV[1] = 窗口秒数, ARGV[2] = 阈值
local current = redis.call('INCR', KEYS[1])
if current == 1 then
    -- 第一次访问才设置过期，避免每次刷新 TTL 导致窗口永不过期
    redis.call('EXPIRE', KEYS[1], ARGV[1])
end
if current > tonumber(ARGV[2]) then
    return 0   -- 超限
end
return 1      -- 放行
-- ⭐ 实战 3：批量扣减库存（保证"够扣才扣"，避免超卖）
-- KEYS = 多个库存 key, ARGV = 对应的扣减数量
local results = {}
-- 第一阶段：全部校验（不做任何写操作）
for i = 1, #KEYS do
    local stock = tonumber(redis.call('GET', KEYS[i]) or '-1')
    if stock < tonumber(ARGV[i]) then
        return {0, 'insufficient stock at item ' .. i}   -- 有任一不足则整体失败
    end
end
-- 第二阶段：全部执行（此时一定不会失败）
for i = 1, #KEYS do
    redis.call('DECRBY', KEYS[i], ARGV[i])
end
return {1, 'ok'}
🚨 Lua 脚本的四个注意点
  1. 不要写长循环：Lua 是阻塞的。遍历几万个 key 的脚本会卡死整个 Redis。批量操作应该分批（比如每次 100 个）。
  2. 不要在脚本里做复杂计算：Lua 的性能不如原生 C。复杂逻辑应该放到应用侧。
  3. redis.call vs redis.pcall：前者在命令出错时会中断脚本并抛错；后者会捕获错误并返回错误对象，脚本继续执行。需要「优雅处理错误」时用 pcall。
  4. 脚本要预先加载（SCRIPT LOAD）+ EVALSHA：每次都传完整脚本会浪费带宽。生产上应该先 SCRIPT LOAD 拿到 SHA1，之后用 EVALSHA 调用。但要注意 NOSCRIPT 错误的处理（Redis 重启后脚本缓存丢失）——客户端应该捕获 NOSCRIPT 并自动重传脚本。

Java 调用 Lua 的完整封装

/**
 * Lua 脚本的工程化封装：预加载 + EVALSHA + NOSCRIPT 兜底
 */
@Component
public class RedisLuaExecutor {

    private final StringRedisTemplate redis;
    // 脚本 → SHA1 的缓存
    private final Map<String, String> shaCache = new ConcurrentHashMap<>();

    public <T> T execute(String script, Class<T> resultType,
                                List<String> keys, Object... args) {
        String sha = shaCache.computeIfAbsent(script, s -> {
            // 首次：SCRIPT LOAD 并缓存 SHA
            return redis.execute(new DefaultRedisScript<>("return redis.sha1hex(ARGV[1])", String.class),
                Collections.emptyList(), s);
        });

        try {
            DefaultRedisScript<T> redisScript = new DefaultRedisScript<>(script, resultType);
            redisScript.setSha1(sha);
            return redis.execute(redisScript, keys, args);
        } catch (RedisSystemException e) {
            // NOSCRIPT：Redis 重启/脚本被清空 → 重新加载并重试
            if (e.getCause() instanceof RedisCommandExecutionException
                && e.getCause().getMessage() != null
                && e.getCause().getMessage().contains("NOSCRIPT")) {
                shaCache.remove(script);
                return execute(script, resultType, keys, args);
            }
            throw e;
        }
    }
}

// 使用示例
private static final String UNLOCK =
    "if redis.call('GET', KEYS[1]) == ARGV[1] then return redis.call('DEL', KEYS[1]) else return 0 end";

public void unlock(String lockKey, String clientId) {
    luaExecutor.execute(UNLOCK, Long.class, Collections.singletonList(lockKey), clientId);
}

6. Redis Functions（7.0+）：Lua 的替代者

✅ Functions 解决了 Lua 脚本的什么问题

Lua 脚本（EVAL）的三个痛点：

  1. 脚本内容每次都要传输（虽然 EVALSHA 能缓解，但要客户端缓存 SHA，还要处理 NOSCRIPT）。
  2. 脚本由客户端管理：不同客户端可能上传同名但不同逻辑的脚本，难以统一版本。运维无法知道线上跑了哪些脚本。
  3. 不支持复用：脚本之间无法互相调用，公共逻辑要重复写。

Functions 的设计：把脚本作为库（Library）注册到 Redis 服务端，持久化在 RDB/AOF 里，随实例一起复制到从节点。调用时用 FCALL 函数名 参数，不需要传输脚本内容。

核心命令：

  • FUNCTION LOAD [REPLACE] <code> — 加载一个函数库
  • FCALL <function> <numkeys> <key...> <arg...> — 调用函数
  • FCALL_RO — 只读版本的调用（可路由到从节点）
  • FUNCTION LIST [LIBRARYNAME x] [WITHCODE] — 列出已注册的库
  • FUNCTION DELETE <lib> — 删除库
  • FUNCTION DUMP / RESTORE — 备份与恢复
  • FUNCTION STATS — 运行统计
########## 定义一个函数库 ##########
# 语法：redis.register_function('函数名', function(keys, args) ... end)

FUNCTION LOAD "#!lua name=mylib
redis.register_function('my_unlock', function(keys, args)
    if redis.call('GET', keys[1]) == args[1] then
        return redis.call('DEL', keys[1])
    end
    return 0
end)

redis.register_function('my_rate_limit', function(keys, args)
    local current = redis.call('INCR', keys[1])
    if current == 1 then
        redis.call('EXPIRE', keys[1], args[1])
    end
    if current > tonumber(args[2]) then return 0 end
    return 1
end)
"
# 返回库名 mylib

# 调用（不需要传脚本内容！）
FCALL my_unlock 1 lock:order:1001 "client-uuid-xxx"
FCALL my_rate_limit 1 rate:ip:1.2.3.4 60 100

# 查看已注册的库
FUNCTION LIST

# 更新库（必须加 REPLACE）

面试深度问答

怎么用 Redis 实现分布式锁？基础

演进路径（这样答能体现深度）：

  1. SETNX + DEL：有死锁风险（持锁进程崩溃后 key 永存）。
  2. SET key value NX EX 30：解决了死锁，但会误删别人的锁（业务超时后锁自动释放，自己被唤醒后又 DEL 了别人的锁）。
  3. value 存唯一标识（UUID+线程ID）+ Lua 原子校验删除：解决误删。必须用 Lua，因为「判断 + 删除」两条命令之间有窗口。
  4. Redisson 看门狗自动续期：解决「业务超时导致锁提前释放」。

生产建议：直接用 Redisson，并注意不要传 leaseTime（传了看门狗就不生效）。同时业务侧要加幂等 + 乐观锁做兜底——因为锁本身在极端情况下（GC、网络分区）会失效。

释放锁为什么必须用 Lua 脚本？进阶

因为「判断锁是不是自己的」和「删除锁」这两步必须是原子的。

如果用两条命令：

String v = redis.get(lockKey);
if (myId.equals(v)) {
    redis.del(lockKey);   // ← 在这两句之间，锁可能刚好过期并被别人抢到
}

极端场景：

  1. 客户端 A 的锁刚好在 GET 之后、DEL 之前过期。
  2. 客户端 B 抢到了锁。
  3. A 执行 DEL → 删掉了 B 的锁。
  4. C 也能抢到锁 → B 和 C 同时持锁，互斥性破坏。

虽然时间窗口极短，但在每秒几万次的锁操作下，一天几十亿次调用，小概率事件必然发生。

Lua 保证原子性：Redis 执行脚本时，整个脚本作为一个整体执行，中间不插入其他命令，所以「判断+删除」不可分割。

加分：类似地，很多「检查后写入」的场景都需要 Lua（或 WATCH/MULTI 事务）来保证原子性。这也是 Lua 在 Redis 里最主要的价值。

Redisson 的看门狗机制是什么？进阶

目的：解决「业务执行时间超过锁过期时间」的问题。

触发条件：调用 lock() 或 tryLock(waitTime, unit)（不传 leaseTime）时启用。默认锁超时 30 秒（lockWatchdogTimeout）。

原理：

  1. 加锁成功后，注册一个后台定时任务（基于 Netty 的 HashedWheelTimer）。
  2. 每隔 lockWatchdogTimeout / 3（即 10 秒）执行一次续期。
  3. 续期时用 Lua 脚本先校验锁是否还属于自己，是则把 TTL 重置为 30 秒。
  4. 释放锁时取消定时任务；客户端崩溃时定时任务随之消失，锁在 30 秒内自动过期（不会死锁）。

为什么是每 10 秒续一次：10 秒 = 30/3，即「在锁过期前有两次续期机会」，避免单次失败就丢锁。

⚠️ 关键坑：一旦传了 leaseTime，看门狗就不生效。lock(30, TimeUnit.SECONDS) 和 tryLock(10, 30, TimeUnit.SECONDS) 都会禁用看门狗——锁 30 秒后无条件释放。这是生产上非常常见的误用。

看门狗的局限：① 长 Full GC 会让续期线程也暂停（JVM 层问题）；② 续期本身消耗流量（10 万把锁 = 每秒 1 万次续期）；③ 续期失败时客户端可能「不自知地失去锁」。

Redlock 算法了解吗？它可靠吗？专家

Redlock 的做法：N（通常 5）个独立的 Redis 主节点。加锁时依次（或并发）请求全部节点，在 ≥ N/2+1 个节点上成功且总耗时 < 锁过期时间才算成功；有效时间 = 初始过期时间 − 加锁耗时。释放时向所有节点发送解锁。

它能防住什么：单实例主从切换导致的锁丢失（因为现在有 5 个独立实例，不依赖主从复制）。

质疑（Martin Kleppmann《How to do distributed locking》）：

  1. 依赖时钟：安全性建立在「各节点时钟单调且漂移可控」上，但 NTP 校时可能造成时钟跳跃，导致锁被提前判定过期。这是最致命的一条。
  2. GC 暂停无法避免：客户端 STW 期间锁已过期，但客户端仍在执行临界区——Redlock 对此无能为力。
  3. 性能与复杂度代价高，但安全性并没有比「单实例 + fencing token」更好。
  4. 用途错配：只适合「效率型锁」，不适合「正确性型锁」。

反驳（antirez）：时钟跳跃可通过约束「不依赖系统时间、用相对时间」来缓解，现实中概率极低；Redlock 的目标是「绝大多数故障下可用且安全」，而非理论上的完美。

更根本的解法：Fencing Token

锁服务每次加锁分配单调递增的编号，客户端访问存储时带上编号，存储层拒绝编号更小的请求。这样即使锁失效，也能保证正确性。这才是解决「锁失效导致并发」的正道。

我的结论（面试话术）：「我会把锁分两类看待——效率型（防重复劳动）用 Redisson 单实例就够，失效的代价是多做一次无用功；正确性型（扣款、库存）不会指望 Redis 锁，而是靠数据库的行锁 / 唯一索引 / 乐观锁版本号来保证，锁只是用来降低冲突的『性能优化』。Redlock 我基本不用——它多付出 5 个实例的复杂度和延迟，但换来的保证仍然是不完备的。」

  • 选 ZooKeeper：对可靠性要求高、已维护 ZK、且并发量不极端。老一代的分布式系统（如 Dubbo、Kafka 早期）常用 ZK 做选主和锁。

关键洞察（加分）：ZK 也不是绝对安全——客户端 GC 导致会话超时，临时节点被删，客户端却以为还持有锁，同样会出现并发。所以「哪把锁更安全」这个问题的正确答案是：不管用哪把锁，正确性都不能只靠锁，必须配合业务侧的 fencing token / 幂等 / 乐观锁。

Lua 脚本为什么能保证原子性？它的事务回滚吗？高级

原子性的来源：Redis 执行命令本身是单线程的（命令执行阶段）。Lua 脚本被当作一个整体命令提交给这个单线程执行——脚本执行期间不会穿插其他客户端的命令。所以「读-判断-写」这一串操作对外表现为一个不可分割的整体。

⚠️ 但它不是「事务」，不会回滚：

  • 这是高频易错点。Lua 脚本执行中途如果报错（比如 INCR 一个字符串），已经执行的命令不会撤销，后面的命令也不会执行。
  • 所以正确写法是「把所有校验/失败可能性都放在写操作之前」——校验全部通过后再统一执行写操作（见本节「批量扣减库存」示例）。

为什么要用 Lua：为了消除「多条命令之间被其他客户端插入」的窗口。在分布式锁释放、限流、库存扣减这些「检查后写入」的场景，这是必须的。

和 MULTI/EXEC 事务的区别：

  • MULTI/EXEC 是「打包发送、顺序执行」，不支持条件判断（不能在事务里根据读到的值决定下一步），也没有回滚。
  • Lua 支持完整的条件逻辑、循环、变量，能力更强。
  • 两者都保证「不被打断」，都不支持回滚。

性能注意：脚本阻塞主线程。不要写长循环；批量操作要分批；lua-time-limit 默认 5 秒，超时后其他命令返回 BUSY。

项目里怎么用分布式锁？举一个具体场景高级

场景一：防止重复下单 / 幂等提交

「用户重复点击提交订单。我们在 userId + productId 维度加锁：lock:order:{userId}:{productId}，用 Redisson 的 tryLock(0, 10, TimeUnit.SECONDS)——等待 0 秒（拿不到就快速失败返回『请勿重复提交』）。
关键点：这里的锁是「效率型」——即使锁失效导致两次请求都进去了，我们也靠订单表的唯一索引（user_id + product_id + 活动ID）保证最终只生成一单。锁只是用来改善用户体验（快速失败），不承担正确性责任。」

场景二：定时任务防重复执行

「我们有多个实例同时跑定时任务。用 lock:job:dailySettle，Redisson 的 tryLock(0, -1, null)——不设 leaseTime，启用看门狗，因为结算任务耗时不定（可能几分钟）。
关键点：① 必须在 finally 里释放，且判断 isHeldByCurrentThread()；② 任务本身要**幂等**（用「任务执行记录表」记录 status，重复执行直接跳过）——因为如果实例网络抖动导致锁丢失，两个实例可能同时跑。」

场景三：缓存重建的互斥（Day4.1 提过）

「热点 key 失效时用锁保证只有一个线程去查 DB 重建。这里用 tryLock(0, 5, SECONDS)——因为重建耗时短（几十毫秒），5 秒足够；拿不到锁的线程自旋等待并读缓存。」

场景四：分布式环境下的「唯一性」操作

「比如给用户生成唯一的邀请码、唯一的短链。用 lock:invite:{userId} 保证同一用户不会并发生成多个。但更重要的是 DB 的唯一索引兜底。」

⚠️ 一段可以背的总结

「我在项目里用分布式锁的原则是：锁只用来『减少冲突、提升体验』，正确性一律交给数据库约束和幂等设计。 具体来说：① 锁 key 的粒度要细（按业务 ID，不要全局）；② 优先用 tryLock 快速失败而不是无限等待（避免线程堆积）；③ 需要长时间执行的任务不传 leaseTime（用看门狗）；④ 每个用锁的地方都要问自己『如果这把锁完全失效，我的数据会错吗』——如果答案是『会』，那说明兜底没做好。」
