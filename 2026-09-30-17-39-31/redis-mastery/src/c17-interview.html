L1 · 入门级（必答，答不出直接挂）

1. Redis 是什么？它和 MySQL 的区别是什么？L1

一句话答案：Redis 是基于内存的 Key-Value 数据库，MySQL 是磁盘的关系型数据库。

维度RedisMySQL
存储介质内存（可持久化到磁盘）磁盘
数据模型Key-Value，8+ 种结构表/行/列，关系模型
读写性能10 万+ QPS数千 QPS（单机）
事务弱事务（MULTI/EXEC，无回滚）ACID 完整事务
查询能力只能按 key 查，无法复杂查询SQL、join、索引、聚合
容量受内存限制（几十 GB）TB/PB 级
定位缓存、加速、特殊场景数据可靠存储

🎯 加分点：「我们不是二选一，而是组合用。MySQL 是 source of truth，Redis 是加速层。Redis 挂了业务降级查库，库挂了才是真故障。」

3. Redis 为什么快？L1高频

一句话答案：纯内存操作 + 单线程无锁 + epoll IO 多路复用 + 精心设计的数据结构 + 合理的底层协议。

  1. 纯内存：内存访问 ~100ns，磁盘寻道 ~10ms，差 5 个数量级。这是最根本的原因。
  2. 单线程：避免多线程上下文切换（每次 ~1.5μs）和锁竞争。不需要加锁，就没有锁开销。
  3. IO 多路复用：一个 epoll 实例管几万个连接，谁有数据就处理谁，不用为每个连接开线程。
  4. 高效数据结构：SDS O(1) 取长度、跳表 O(logN) 范围查询、listpack 紧凑内存布局、渐进式 rehash。
  5. 自定义协议 RESP：解析简单，二进制安全，比 HTTP 轻量得多。
  6. 内核优化：避免 NUMA、关闭 THP、合理设置 somaxconn。

🎯 加分点：一定要补一句「但单线程是双刃剑」——慢命令（KEYS、HGETALL 大 key）会阻塞所有请求。这就是为什么我们要有 SLOWLOG 和大 key 治理。

4. Redis 是单线程的吗？L1高频

一句话答案：命令执行是单线程的，但整个 Redis 进程不是单线程。

时间线线程说明
4.0 之前1 主线程连后台删除都是同步的
4.0+主线程 + 后台线程UNLINK、FLUSHASYNC、lazy-free 交给后台
6.0+主线程 + IO 线程 + 后台线程IO 读写可以多线程（io-threads）
8.x同上，IO 线程更成熟命令执行仍然单线程

关键：「解析请求」和「写回响应」可以多线程，「执行命令」永远单线程。因为执行部分要访问共享数据结构，多线程反而要加锁，得不偿失。

🎯 加分点：「IO 多线程不是并发执行命令，而是把网络读写这个 CPU 占比不大的环节并行掉。我们线上 8 核机器设 io-threads 4，注意是总线程数，不是额外线程数。」

5. Redis 的持久化有哪几种？区别是什么？L1高频

一句话答案：RDB（快照）、AOF（日志）、混合持久化（推荐）。

对比RDBAOF混合（7.0+ 默认）
原理fork 子进程写二进制快照追加写命令日志AOF 文件头是 RDB，后面追加命令
文件大小小大中
恢复速度快慢（要重放命令）快
数据安全差（丢最后一次快照后的数据）好（everysec 最多丢 1s）好
fork 阻塞有（数据量越大越久）只在重写时有只在重写时有
默认开启是7.0 之前默认 no是（aof-use-rdb-preamble yes）

AOF 刷盘策略：always（每条都 fsync，最安全最慢）、everysec（每秒 fsync，默认，最多丢 1s）、no（交给 OS，不可控，可能丢 30s）。

🎯 加分点：「生产环境我们用的是混合持久化。另外 7.0 引入了 Multi-Part AOF，把 manifest 和各个 base/incr 文件分离，重写时不用再 fork 一个大文件，解决了 AOF 重写时的内存膨胀问题。」

6. RDB 的 fork 是怎么工作的？会阻塞吗？L1

一句话答案：fork 用 Copy-On-Write，fork 本身会短暂阻塞，且阻塞时间与内存页表大小正相关。

  1. fork 做了什么：复制父进程的页表给子进程（不是复制数据！）。父子进程共享物理内存，只有写操作才复制页面。
  2. 阻塞点在哪：fork 系统调用本身要复制页表。10GB 内存大约 250 万个页表项，fork 耗时可达 数十到数百毫秒。
  3. COW 的代价：fork 之后，父进程每修改一个页面，就要复制一份。所以 fork 期间写入越频繁，内存膨胀越严重——最坏情况是 内存翻倍。
  4. 进程退出时：子进程写完后父进程要 wait，这也会短暂阻塞。

🎯 加分点：「所以我们的经验是：（1）单实例内存控制在 10GB 以内，fork 才可控；（2）用 bgsave 而不是 save，绝不在主线程做持久化；（3）fork 期间避免大批量写，我们曾在大促前清缓存，结果 COW 把内存从 12G 干到 23G，触发了 OOM Killer。另外 vm.overcommit_memory=1 是必须的，否则 fork 会直接失败。」

7. Redis 的过期键是怎么删除的？L1高频

一句话答案：惰性删除 + 定期删除，两者结合。

策略触发时机优点缺点
惰性删除访问 key 时检查是否过期CPU 友好，不浪费没被访问就永远占内存（内存泄漏）
定期删除每 100ms 随机抽查 20 个 key能回收冷数据抽样有遗漏，需多轮

定期删除的细节（必答）：每秒执行 server.hz（默认 10）次，每次：

  1. 从「已设置过期时间」的字典中随机取 20 个 key。
  2. 删除其中已过期的 key。
  3. 如果过期比例 > 25%，重复步骤 1。
  4. 给这次任务设置一个 25ms 的时间上限，超时立即退出（防止阻塞主线程）。

🎯 加分点：「这里有个经典问题：如果大量 key 同时过期，定期删除会反复循环，可能阻塞主线程。所以生产上我们给 TTL 加随机抖动（expire = base + random(0, 300)），这也是防止缓存雪崩的同一招。」

8. Redis 的内存淘汰策略有哪些？L1高频

一句话答案：8 种策略 = 4 种淘汰范围（noeviction/allkeys/volatile）× 多种算法。

策略淘汰范围算法适用场景
noeviction—不淘汰，内存满则写报错数据不能丢（当 DB 用）
allkeys-lru所有 key最近最少使用纯缓存，最常用
allkeys-lfu所有 key最不经常使用缓存，且热点明显（4.0+）
allkeys-random所有 key随机访问均匀，几乎不用
volatile-lru仅带 TTL 的 keyLRU缓存+持久数据混存
volatile-lfu仅带 TTL 的 keyLFU同上，热点明显
volatile-random仅带 TTL 的 key随机很少用
volatile-ttl仅带 TTL 的 key剩余 TTL 最小优先快要过期的先删

LRU vs LFU 的核心区别：LRU 只看「最近有没有用」，LFU 看「用的频率」。LFU 能解决「冷数据偶尔被访问一次就把热数据挤掉」的问题。

Redis 的 LRU 是近似 LRU：不维护完整链表，而是随机采样 maxmemory-samples（默认 5）个 key，淘汰其中最久未使用的。采样数越大越准，但越耗 CPU。

🎯 加分点：「Redis 的 LFU 有个 8bit 的计数器，高 8 位记录访问频率（对数增长，最大 255），低 8 位记录最后一次衰减时间。默认每分钟衰减一次，lfu-decay-time 控制。注意 LFU 计数器不会因为重启清零——因为它在对象头里，会在 RDB 里保存。」

10. Redis 的 String 为什么比 C 的 char* 好？L1

一句话答案：Redis 用 SDS（Simple Dynamic String）替代 C 字符串，解决了 4 个问题。

问题C char*SDS
取长度O(n) 遍历到 '\0'O(1)，有 len 字段
二进制安全不安全，遇到 \0 截断安全，靠 len 判断结尾
缓冲区溢出strcat 可能溢出自动扩容（空间预分配）
内存分配次数每次修改都 realloc预分配 + 惰性释放，减少 realloc

SDS 有三种头部：sdshdr5（<32 字节，只存 flags）、sdshdr8、sdshdr16、sdshdr32、sdshdr64，按字符串长度选最小的，节省内存。

空间预分配规则：扩容后 len < 1MB 时，alloc = 2 × len；len ≥ 1MB 时，alloc = len + 1MB。最多浪费 1MB。

🎯 加分点：「SDS 的扩容是惰性释放的：缩短字符串时不立即回收内存（free 字段记录空闲），留给后续 append 复用，避免频繁 realloc。」

11. Redis 的 key 最大能存多大？L1

512 MB。这是 String 的硬上限。但生产上强烈不建议超过 10KB，超过 100KB 就属于「大 key」，1MB 以上就是必须治理的严重问题。

原因：单线程模型下，一次 GET 一个 100MB 的 value，网络传输 + 反序列化会阻塞其他所有请求。

L2 · 进阶级（区分度开始出现）

13. Redis 的 Hash 什么时候用 listpack，什么时候转 hashtable？L2

两个阈值（Redis 7.x 默认值）：

hash-max-listpack-entries 128      # 字段数上限
hash-max-listpack-value 64         # 单个字段/值的字节上限

任一条件突破，就转成 hashtable。转换是单向的，转过去就不会转回来。

为什么要有这个设计：listpack 是紧凑的连续内存，省内存但查找是 O(n)；hashtable 查找 O(1) 但有指针开销和 hash 桶浪费。小 Hash 用 listpack 省内存，大 Hash 用 hashtable 保性能。

结构内存开销查找
listpack极低（连续内存）O(n)，n≤128 可接受
hashtable高（每项一个 dictEntry 24B + 指针）O(1)

🎯 加分点：「这里有个坑：如果你建了一个 500 字段的 Hash，它就永远是 hashtable 了。所以设计时要么控制字段数 < 128，要么拆成多个 key。反过来，我们在做用户画像时故意把 user:123:base 和 user:123:extra 拆开，就是为了让各自都能用 listpack。」

14. ZSet 的底层是怎么实现的？跳表为什么能替代平衡树？L2高频

一句话答案：元素少时用 listpack，超过阈值用「跳表 + 字典」双结构。

zset-max-listpack-entries 128
zset-max-listpack-value 64

为什么是双结构：

需求结构复杂度
按 score 范围查（ZRANGEBYSCORE）跳表O(logN)
按 member 查 score（ZSCORE）字典O(1)

只用跳表的话，ZSCORE 要 O(logN)；只用字典的话，范围查询做不到有序。所以两个都要。

跳表 vs 平衡树（必答的对比）：

维度跳表红黑树/AVL
范围查询简单，找到起点沿 level 0 顺序遍历即可要做中序遍历，实现复杂
实现复杂度简单（~200 行）复杂（旋转、染色）
并发友好局部修改，锁粒度小旋转影响大范围
平均复杂度O(logN)（期望）O(logN)（最坏）
内存略高（多层指针，平均 1/(1-p) ≈ 1.33 个指针/层）较低（每节点 2 指针）

跳表的分层规则：每次插入随机决定层数，p = 0.25，即第 k 层的概率是 0.25k-1。最大 32 层（支持 4 亿+ 元素）。

🎯 加分点：「antirez 自己说过，选跳表而不是平衡树，主要是范围查询和实现简单。ZRANGEBYSCORE 从跳表出发只要顺序遍历，平衡树则要中序遍历，代码量和 bug 面积都大得多。」

15. Redis 的渐进式 rehash 是怎么做的？L2

问题背景：Hash 表扩容需要把所有元素重新 hash 到新表，如果一次性做完，几百万 key 会阻塞主线程几秒。所以要「渐进式」。

实现：维护两个哈希表 ht[0]（旧）和 ht[1]（新），加一个 rehashidx 游标。

  1. 触发扩容：负载因子 ≥ 1（未做 bgsave 时）或 ≥ 5（在做 bgsave 时）触发扩容。缩容阈值是 0.1。
  2. 开始 rehash：为 ht[1] 分配空间（扩容为 ≥ 2×used 的 2 次幂），rehashidx = 0。
  3. 渐进迁移：每次对字典做增删改查时，顺便把 ht[0] 在 rehashidx 上的桶迁移到 ht[1]，然后 rehashidx++。
  4. 定时迁移：如果长期没有请求，还有 serverCron 每 100ms 迁移 1ms 的量（防止一直不完成）。
  5. 完成：ht[0] 空了，把 ht[1] 赋给 ht[0]，ht[1] 置空，rehashidx = -1。

rehash 期间的操作规则（易考）：

  • 查找：先查 ht[0]，再查 ht[1]。
  • 新增：只往 ht[1] 加，保证 ht[0] 只减不增，最终一定收敛。
  • 删除/修改：两个表都找，找到就操作。

🎯 加分点：「为什么 bgsave 时扩容阈值要提到 5？因为 fork 之后 COW 机制下，扩容会复制大量页面，导致内存暴涨。所以宁可让它更满也不轻易扩容。」

16. Pipeline 是什么？它和事务有什么区别？L2高频

一句话答案：Pipeline 是批量发命令省 RTT，事务是保证命令不被别人插队，两者解决不同的问题。

维度PipelineMULTI/EXEC 事务Lua 脚本
目的减少网络往返命令原子执行原子 + 逻辑
原子性无，中间可能插别人的命令有（EXEC 时连续执行）有（整个脚本原子）
回滚不适用不支持回滚（运行时错误不中断）不支持回滚，但可写判断逻辑
条件判断不支持不支持（WATCH 只能处理简单 CAS）支持（if/else、循环）
性能极高（1 次 RTT 发 N 条）高（1 次 RTT 发 N+2 条）高，但大脚本会阻塞
适用批量读写、初始化简单原子操作复杂原子逻辑（扣库存）

关键点：Redis 事务为什么不回滚？antirez 的设计哲学是：运行时错误（如对 String 做 INCR）是编程错误，应该在开发期发现，而不是靠数据库回滚。回滚需要额外的 undo log，复杂且影响性能。

🎯 加分点：「我们在秒杀场景做过压测：同样扣 1000 次库存，Pipeline 耗时约 12ms，MULTI/EXEC 约 15ms，Lua 约 18ms。但 Lua 能保证『判断+扣减』原子，前两者做不到。所以能用 Lua 就用 Lua，能用 Pipeline 批量读就用 Pipeline。」

17. 什么是缓存穿透？怎么解决？L2高频

一句话答案：查一个数据库也不存在的 key，每次都绕过缓存打到 DB。

三种解决方案：

方案做法优点缺点
空值缓存查不到就缓存 null，TTL 短一些（60s）简单，能挡住重复攻击占内存；数据变更后有短暂不一致
布隆过滤器启动时把所有存在的 key 灌进去，查询前先过 BF内存极省（1 亿 key 约 100MB）有误判率；删除困难；需预热
参数校验id<0 或格式不对直接拒绝零成本只能挡低级攻击

布隆过滤器原理：k 个哈希函数映射到 m 位的位数组。查询时若所有位都是 1 则「可能存在」，任一位是 0 则「一定不存在」。

误判率公式：P ≈ (1 - e^(-kn/m))^k，最优 k = (m/n)·ln2 ≈ 0.693·(m/n)。

Redis 8.x 内置了布隆过滤器（之前要装 RedisBloom 模块）：

BF.RESERVE users 0.001 1000000     # 误判率0.001，预期100万元素
BF.ADD users user:123
BF.EXISTS users user:456
BF.MADD users a b c
BF.INFO users                       # 查看统计

🎯 加分点：「我们线上是组合拳：参数校验挡住 90% 的无效请求，布隆过滤器挡住剩余的存在性检查，空值缓存兜底防止同一 key 反复穿透。另外要监控缓存命中率——一旦命中率从 99% 掉到 80%，基本就是被穿透了。」

18. 什么是缓存击穿？怎么解决？和穿透有什么区别？L2高频

击穿：单个热点 key 过期瞬间，大量并发请求同时打到 DB。（注意：key 在 DB 里是存在的）

穿透 vs 击穿：

维度穿透击穿
数据是否存在不存在（DB 也没有）存在（DB 有，只是缓存过期了）
攻击量大量不同 key单个热点 key
后果DB 压力线性增长DB 瞬时压力尖峰

两种解决方案：

方案一：互斥锁（强一致，牺牲可用性）

public Product getProduct(Long id) {
    String key = "product:" + id;
    String cached = redis.get(key);
    if (cached != null) return JSON.parseObject(cached, Product.class);

    // 缓存未命中，抢锁重建
    String lockKey = "lock:" + key;
    // SET NX EX 一条命令搞定，原子
    Boolean locked = redis.set(lockKey, "1", SetParams.setParams().nx().ex(10));
    if (Boolean.TRUE.equals(locked)) {
        try {
            // 双重检查：可能别的线程已经重建好了
            cached = redis.get(key);
            if (cached != null) return JSON.parseObject(cached, Product.class);
            Product p = productMapper.selectById(id);
            redis.set(key, JSON.toJSONString(p), 300);
            return p;
        } finally {
            redis.del(lockKey);   // 生产环境要按 value 校验后删，见分布式锁章节
        }
    } else {
        // 没抢到锁，短暂休眠后重试（或直接返回旧值）
        Thread.sleep(50);
        return getProduct(id);
    }
}

方案二：逻辑过期（高可用，牺牲一致性）

// value 里不带 TTL，而是自己存一个 expireAt 字段
@Data
class CacheData {
    Object data;
    Long expireAt;      // 逻辑过期时间
}

public Object getProduct(Long id) {
    CacheData cd = (CacheData) redis.get("product:" + id);
    if (cd == null) return null;
    if (cd.getExpireAt() > System.currentTimeMillis()) {
        return cd.getData();       // 没过期，直接返回
    }
    // 逻辑已过期：异步重建，当前请求仍返回旧数据
    if (tryLock("lock:product:" + id)) {
        ASYNC_EXECUTOR.execute(() -> {
            try {
                Product p = productMapper.selectById(id);
                redis.set("product:" + id,
                    new CacheData(p, System.currentTimeMillis() + 300_000));
            } finally { unlock("lock:product:" + id); }
        });
    }
    return cd.getData();   // 永远不阻塞，返回旧值
}

怎么选：

方案一致性可用性适用
互斥锁强（拿到的一定是新数据）差（其他线程要等，可能超时）对一致性要求高、并发不极端
逻辑过期弱（短暂返回旧数据）极好（永不阻塞）秒杀、大促、超高并发

🎯 加分点：「还有一种『永不过期』方案——后台定时任务主动刷新。这样既没有重建时的并发问题，也能保证最终一致。我们做首页楼层数据就是这么干的：热点数据不设 TTL，用 XXL-Job 每 5 分钟推一次。」

19. 什么是缓存雪崩？怎么解决？L2高频

三种雪崩形态（这个分层讲很加分）：

形态原因现象
① 大批 key 同时过期统一 TTL，或零点刷新全量缓存缓存命中率骤降到 0，DB 瞬间被打爆
② Redis 实例宕机单节点故障、内存满、被 OOM Kill所有流量直接打到 DB
③ Redis 集群整体不可用机房断电、网络分区灾难性，需要降级方案

对应解法：

针对 ①：TTL 加随机抖动

// ❌ 所有 key 都是 1800 秒，会在同一秒集体失效
redis.set(key, value, 1800);

// ✅ 抖动 300 秒，把失效时间散开
int ttl = 1800 + ThreadLocalRandom.current().nextInt(300);
redis.set(key, value, ttl);
// 上线时预热也别一次性全灌，加个随机延迟或分批

针对 ②：高可用架构 + 多级缓存

  1. 高可用：哨兵 / Cluster，主从切换控制在秒级。这是基础设施层。
  2. 多级缓存：JVM 本地缓存（Caffeine）+ Redis。Redis 挂了，本地缓存还能顶一阵。
  3. 熔断降级：Sentinel 对 DB 调用限流，宁可拒掉部分请求也不让 DB 死。
  4. DB 限流保护：给 DB 层加连接数上限，超出直接返回兜底数据。

针对 ③：业务降级 + 预案

  • 兜底数据：把静态兜底数据放本地文件/本地缓存，Redis 全挂时返回兜底（如「服务繁忙，请稍后」）。
  • 开关预案：大促前准备好降级开关，一键关闭非核心功能。
  • 压测预案：提前测「缓存全失效」场景，DB 到底能扛多少。

🎯 加分点（大厂真题级回答）：「我经历过一次真实雪崩。背景：运维做 Redis 主从切换，切了 40 秒。现象：40 秒内所有请求穿透到 MySQL，QPS 从 2000 涨到 3 万，MySQL 连接池打满，整个系统雪崩。根因：没有本地缓存层，没有 DB 限流。改造：（1）核心商品数据加 Caffeine 一级缓存；（2）DB 层加 Hystrix 限流；（3）切主改在低峰期，并用 Lua 脚本让客户端在切换期间返回旧值。效果：后来再切主，Redis 挂了 15 秒，业务无感知。」

20. 缓存和数据库怎么保证一致性？L2超高频

一句话答案：没有完美方案，只能根据业务容忍度在「一致性/性能/复杂度」之间取舍。

先排除一个错误答案：「先删缓存再更新 DB」❌ —— 并发下必然不一致。

方案一：先更新 DB，再删缓存（Cache Aside，最常用）

// 写路径
public void updateProduct(Product p) {
    // 1. 先更新数据库（在事务内）
    productMapper.updateById(p);
    // 2. 事务提交后再删缓存
    //    ⚠️ 注意：必须在事务提交后执行！否则事务还没提交，
    //       其他线程可能读到旧数据又写回缓存
    transactionSynchronizationManager.registerSynchronization(
        new TransactionSynchronization() {
            @Override public void afterCommit() {
                redis.del("product:" + p.getId());
            }
        });
}

// 读路径
public Product getProduct(Long id) {
    String key = "product:" + id;
    String cached = redis.get(key);
    if (cached != null) return JSON.parseObject(cached, Product.class);
    Product p = productMapper.selectById(id);
    if (p != null) redis.set(key, JSON.toJSONString(p), 300);
    return p;
}

为什么是「删缓存」而不是「更新缓存」？

方式问题
更新缓存并发写时，A 更新成 1、B 更新成 2，但可能 A 的后操作覆盖 B，缓存变成 1（脏数据）。而且如果这个缓存值没人读，就是白算一次，浪费。
删缓存下次读时懒加载重建，天然避免并发写覆盖问题。且「删」是幂等的，「更新」不是。

Cache Aside 的不一致窗口：

时刻   线程A（写）              线程B（读）             缓存     DB
 t1    更新DB=1                                          -       1
 t2                           读缓存 miss                -       1
 t3                           读DB → 1                   -       1
 t4                           写缓存 = 1                 1       1
 t5    删除缓存                                         -       1
 t6                           写缓存 = 1（旧值！）       1       1   ← 不一致！

这个窗口极短（要求 B 的写缓存在 A 的删缓存之后），但理论上存在。解法是延时双删：

public void updateProduct(Product p) {
    redis.del("product:" + p.getId());   // 第一次删
    productMapper.updateById(p);
    // 延迟一段时间再删一次，覆盖掉读线程可能写回的旧值
    // 延迟时间 = 读数据耗时（几十ms）+ 主从同步耗时，一般 500ms~1s
    delayExecutor.schedule(
        () -> redis.del("product:" + p.getId()),
        800, TimeUnit.MILLISECONDS);
}

⚠️ 延时双删不是银弹：延迟时间怎么定？删第二次时如果又有读请求……所以只能把窗口压到极小，无法消除。

方案二：订阅 binlog（Canal，最终一致，最强）

MySQL binlog ──> Canal ──> MQ ──> 消费端删缓存
                                  │
                                  ├─ 天然解耦，不影响主业务流程
                                  ├─ 顺序消费保证最终一致
                                  ├─ 即使业务代码漏删，也能兜住
                                  └─ 缺点：引入 Canal + MQ，复杂度高

方案三：强一致场景 —— 直接读 DB 或加分布式锁

如果业务真的不能容忍任何不一致（如金融余额），就别用缓存，或对写路径加分布式锁串行化。

🎯 加分点（这是面试官最想听的）：「我的选型逻辑是按业务分级：

业务容忍度方案
商品详情、评论秒级不一致可接受Cache Aside + 短 TTL（300s）。TTL 是最后一道保险
库存、优惠券不能超卖不用缓存读，直接 Lua 在 Redis 里原子扣减
配置、字典分钟级可接受Cache Aside + 长 TTL + 主动刷新
订单状态秒级可接受Canal 订阅 binlog 删缓存

核心认知：「缓存一致性」本质是分布式一致性问题，CAP 里只能选 AP + 最终一致。想要强一致，代价是不用缓存或者加锁，性能会掉一个数量级。 所以第一步永远是问清楚：业务能容忍多少不一致？」

21. Redis 的主从复制是怎么工作的？L2

三个阶段：

阶段一：建立连接、协商同步（PSYNC）

  1. 从库启动，配置 replicaof <masterip> <port>，向主库发 PING。
  2. 主库返回 PONG，认证（如果有 requirepass）。
  3. 从库发送 REPLCONF listening-port <port>，上报自己的端口。
  4. 从库发送 PSYNC <runid> <offset>。首次是 PSYNC ? -1，表示全量同步。

阶段二：主库同步数据给从库

  1. 主库执行 BGSAVE 生成 RDB（fork 子进程）。
  2. 把 RDB 文件发给从库。
  3. 关键：生成 RDB 期间的新写命令，会写入 repl_buffer（复制积压缓冲区）。
  4. 从库收到 RDB 后先清空自己的数据（flushall），再加载 RDB。
  5. 主库把 repl_buffer 里的增量命令发给从库重放。

阶段三：命令传播（持续同步）

之后主库每执行一个写命令，就异步发给所有从库。从库执行后回复 REPLCONF ACK <offset>。

全量同步 vs 增量同步：

类型触发条件代价
全量（FULLRESYNC）从库首次连接；或 offset 不在 repl_backlog 范围内高：BGSAVE + 传大文件 + 从库清空
增量（CONTINUE）网络闪断后重连，offset 还在 backlog 里低：只补发差量命令

repl_backlog（复制积压缓冲区）：主库上的一个环形缓冲区，默认 1MB。repl-backlog-size 太小会导致网络一断就要全量同步。

🎯 加分点：「repl-backlog-size 我们线上设成 64MB。计算公式是 大小 = 平均写入速率 × 预计最长断连时间。我们写入峰值约 5MB/s，希望扛住 10 秒断连，所以 ≥ 50MB。设小了，网络抖一下就从增量退化成全量，主库 fork 一次就卡一下。」

22. 主从复制是全同步还是异步的？会有数据丢失吗？L2

一句话答案：默认全异步，会丢数据。要防丢必须开 WAIT 或 min-replicas。

默认行为：主库执行完命令就返回给客户端，不等从库确认。所以主库刚写完就宕机，还没同步给从库，数据就丢了。

防丢的三个配置：

# 1. 至少要有 N 个从库 ack 才算写成功（默认0=不检查）
min-replicas-to-write 1
min-replicas-max-lag 10     # 且延迟不超过 10 秒

# 2. 客户端可用 WAIT 命令，等 N 个副本确认
WAIT 1 1000                 # 等 1 个副本确认，超时 1000ms

# 3. 从库只读（默认开）
replica-read-only yes

⚠️ 注意：min-replicas-to-write 有可用性代价——从库全挂时主库会拒绝写入。这是典型的 CP 选择。

🎯 加分点：「这里有个面试高频陷阱：WAIT 不保证强一致。它只是把「写入同步给了 1 个副本」这个信息返回给你，但如果这个副本也挂了、主库也挂了，还是有丢失风险。真正的强一致要用 Raft（比如 Redis 不支持，得用 etcd/ZooKeeper）。Redis 官方定位是 AP。」

23. 哨兵（Sentinel）是干什么的？它怎么判断主库挂了？L2

三个职责：监控、通知、自动故障转移。

主观下线（SDOWN）→ 客观下线（ODOWN）

  1. 每个 Sentinel 每秒向所有节点发 PING。
  2. 如果超过 down-after-milliseconds（默认 30s）没回 PONG，该 Sentinel 把主库标记为主观下线（SDOWN）。
  3. 这个 Sentinel 向其他 Sentinel 发 SENTINEL is-master-down-by-addr，询问意见。
  4. 如果超过 quorum 个 Sentinel 都认为它挂了，标记为客观下线（ODOWN）。
  5. 接下来选举 leader Sentinel 执行故障转移（Raft 式投票，需 majority：N/2+1 票）。

quorum 和 majority 的区别（容易混淆）：

概念含义作用
quorum配置项，判定 ODOWN 需要的票数「几个人说它死了」
majority计算值 = sentinel总数/2 + 1「几个人同意换主」，是选举 leader 的门槛

例：3 个 Sentinel，quorum=2，majority=2。若 quorum 配成 3，那挂 1 个就永远无法 ODOWN。

选新主库的规则（优先级从高到低）

  1. replica-priority：数字越小优先级越高（0 表示永不参选）。
  2. 复制 offset 最大（数据最新）的胜出。
  3. runid 字典序最小的胜出。

故障转移过程

  1. 选出的从库执行 SLAVEOF NO ONE 升级为主库。
  2. 其他从库 SLAVEOF 指向新主库。
  3. 旧主库恢复后变成新主库的从库。
  4. 通过发布订阅通知客户端新主库地址（客户端要订阅 +switch-master）。

🎯 加分点：「哨兵有脑裂风险：网络分区时，旧主库还在接受写入，新主库已经选出。等网络恢复，旧主库的数据会被清空（变成从库时全量同步）。所以必须配 min-replicas-to-write 1——让被隔离的主库发现自己没有从库，主动拒绝写入，减少数据丢失。」

24. 为什么大厂都用 Cluster 而不是哨兵？L2
维度哨兵Cluster
分片无，单主容量受限有，16384 槽分布在多主
水平扩展不行，只能加从库读扩展可以，加主库扩容
单机内存上限约 10-20GB（fork 考虑）每主库都能到 10GB+
写入能力单主写入多主并行写入
客户端复杂度低（订阅+switch-master）高（需处理 MOVED/ASK）
运维复杂度低高
适用数据量< 20GB可到 TB 级

核心原因：Cluster 解决了「单机内存上限」这个根本瓶颈。 一台机器 32GB 内存，扣掉系统和 fork 开销，Redis 单实例安全线在 10GB 左右。数据到了 50GB 就只能上 Cluster。

🎯 加分点：「不过 Cluster 也不是越大越好。槽越多，运维越复杂，跨槽操作越受限。 我们线上是 6 主 6 从（每个主 1 个从），大约 60GB 数据。为什么不搞 100 个主？因为（1）Cluster 的 Gossip 通信是 O(N²) 量级，节点太多心跳风暴；（2）redis-cli --cluster rebalance 会变得很慢；（3）故障转移时选举范围太大，速度下降。」

25. Cluster 的 16384 个槽是怎么回事？为什么要 16384？L2

槽 = 数据分片单位。 slot = CRC16(key) mod 16384，每个主节点负责一部分槽。

为什么是 16384（2^14）而不是 65536？这是 antirez 亲自回答过的问题（GitHub issue #2575），四个原因：

  1. 心跳包大小：每个节点心跳要带「我负责哪些槽」的 bitmap。16384 位 = 2KB；65536 位 = 8KB。Gossip 每秒都要发，2KB 已经够大了。
  2. 集群规模：Redis Cluster 设计上限约 1000 个节点。16384 槽 / 1000 节点 ≈ 16 槽/节点，够用。再多也用不到 65536。
  3. 位图压缩：节点少时，16384 位的 bitmap 压缩率高（大部分是 0）；65536 位则压缩效果差。
  4. 槽区间表示：节点负责的槽通常是一段连续区间，可用「起始槽 + 结束槽」压缩表示，16384 个槽在实现和传播时更轻量。

🎯 加分点：「注意槽的分配不需要均匀。比如你预估某个业务 key 特别多，可以多分一些槽给它。但一般还是均分，用 redis-cli --cluster rebalance 自动均衡。还有一点：16384 个槽固定不可改，这是写死在代码里的，Cluster 模式下不能用 SELECT 切库（只有 db0）。」

26. Cluster 的 MOVED 和 ASK 有什么区别？L2高频

一句话答案：MOVED 表示「槽永久迁走了」，ASK 表示「这个 key 正在迁走，这次先来我这」。

对比MOVEDASK
触发场景槽已经完成迁移，永久归属新节点槽正在迁移中，key 恰好已迁到目标节点
客户端动作更新本地槽映射表，以后都去新节点不更新本地映射，只在本次请求加 ASKING 前缀重试
是否刷新路由是（永久）否（临时）
返回格式MOVED 3999 127.0.0.1:6381ASK 3999 127.0.0.1:6381

为什么 ASK 不能更新路由表：因为槽还在迁移中，目标节点只接收了「这一个 key」，其他 key 还在源节点。如果客户端更新了映射，下次请求别的 key 就会打到目标节点，但目标节点还没有这个 key，会返回 MOVED。所以只能「本次临时」重定向。

迁移流程（槽迁移的三步）：

# 1. 源节点：把这个槽标记为 MIGRATING
CLUSTER SETSLOT 3999 MIGRATING <目标节点ID>

# 2. 目标节点：把这个槽标记为 IMPORTING
CLUSTER SETSLOT 3999 IMPORTING <源节点ID>

# 3. 逐个迁移 key
CLUSTER GETKEYSINSLOT 3999 100        # 取100个key
MIGRATE <target-ip> <target-port> "" 0 5000 KEYS key1 key2 ...

# 4. 迁移完成后，通知所有节点新归属
CLUSTER SETSLOT 3999 NODE <目标节点ID>

迁移期间，客户端请求已迁走的 key 会收到 ASK；迁移完成后收到 MOVED。

🎯 加分点：「Redis 8.4 引入了原子槽迁移，解决了老版本迁移过程中『槽处于中间态』的问题。老版本迁移时如果源节点挂掉，这个槽可能两边都不认。8.4 用一个类似两阶段提交的机制，保证槽的归属切换是原子的。这是新版本一个挺实用的改进。」

27. Cluster 的故障转移是怎么做的？和哨兵有什么不同？L2

核心区别：Cluster 没有独立 Sentinel 进程，故障检测和仲裁都内建在数据节点里，用 Gossip 协议。

PFAIL → FAIL

  1. 节点 A 给节点 B 发 PING，超时未回 → A 把 B 标记为 PFAIL（疑似下线，本地状态，不广播）。
  2. A 通过 Gossip 消息的 gossip 段落，向其他节点传播「我觉得 B 可能挂了」。
  3. 当超过半数主节点都认为 B 是 PFAIL 时，会把 B 标记为 FAIL（客观下线），并立即广播。
  4. B 的从库发现主库 FAIL，开始竞选。

从库竞选（和 Raft 类似）

  1. 从库把自己的 currentEpoch + 1，广播 FAILOVER_AUTH_REQUEST。
  2. 只有持有槽的主节点才有投票权，每个 epoch 只能投一票。
  3. 从库拿到多数票（N/2+1，N 是主节点总数）后，晋升为主库。
  4. 执行 SLAVEOF NO ONE，接管原来主库的槽，并广播 pong 消息宣告。
  5. 其他节点收到后更新自己的槽映射。

Cluster vs 哨兵的故障转移对比：

维度哨兵Cluster
检测者独立 Sentinel 进程数据节点自身（Gossip）
投票者所有 Sentinel只有持槽的主节点
需要额外部署是（3+ Sentinel）否
切换粒度整个主库单个分片
其他分片影响无（只有一套）无（不受影响）

🎯 加分点：「Cluster 默认没有自动故障转移的时限保护，主库挂了到切换完成可能需要 10-30 秒（取决于 cluster-node-timeout，默认 15s）。这个时间窗口内该分片的请求全部失败。所以客户端必须配重试机制：捕获 CLUSTERDOWN 异常，带退避重试。Lettuce 的 cluster-node-timeout 和 timeout 是两个独立配置，别搞混。」

30. 分布式锁怎么实现？SETNX 演进到 Redisson 的完整历程？L3超高频

四代演进（这是标准答法）：

第一代：SETNX + DEL（有致命 bug）

// ❌ 错误示范
if (redis.setnx("lock", "1") == 1) {
    try {
        doBusiness();
    } finally {
        redis.del("lock");   // 问题1：如果业务抛异常前宕机，锁永远不释放
    }
}

问题：① 没设过期时间 → 死锁；② del 会删掉别人的锁。

第二代：SET NX EX（原子设置 + 过期时间）

SET lock value NX EX 30

必须用一条命令，不能 SETNX 后再 EXPIRE（两条命令之间宕机就死锁）。

但仍有问题：删锁可能删错。A 的业务执行了 35 秒（超过 30 秒 TTL），锁自动过期，B 拿到了锁。此时 A 执行完去 del，删的是 B 的锁。

第三代：value 存唯一标识 + Lua 原子校验删除

-- unlock.lua
-- KEYS[1] = 锁key, ARGV[1] = 客户端唯一标识
if redis.call('GET', KEYS[1]) == ARGV[1] then
    return redis.call('DEL', KEYS[1])
else
    return 0
end
// Java 侧
String clientId = UUID.randomUUID().toString();
String result = redis.set("lock", clientId, SetParams.setParams().nx().ex(30));
if ("OK".equals(result)) {
    try {
        doBusiness();
    } finally {
        // Lua 保证「判断+删除」原子，不会删错
        redis.eval(UNLOCK_LUA, Collections.singletonList("lock"),
                   Collections.singletonList(clientId));
    }
}

但仍有问题：业务执行超过 TTL 怎么办？锁提前释放了。

第四代：Redisson 看门狗自动续期（生产标准）

RLock lock = redisson.getLock("order:lock");
lock.lock();          // ✅ 不传 leaseTime，启用看门狗
try {
    doBusiness();
} finally {
    lock.unlock();
}

// ❌ 千万别这么写：
// lock.lock(30, TimeUnit.SECONDS);   // 传了 leaseTime，看门狗失效！

看门狗机制（必须讲清楚）：

  1. lock() 不传超时时间时，Redisson 默认用 lockWatchdogTimeout = 30000ms（30 秒）。
  2. 加锁成功后，启动一个定时任务，每隔 1/3 时间（10 秒）检查业务是否还在执行。
  3. 如果还持有锁，就用 Lua 脚本把 TTL 重置回 30 秒（PEXPIRE）。
  4. 业务执行完 unlock()，取消定时任务，删除锁。
  5. 只要客户端没宕机，锁就一直续期，业务可以执行任意长时间。

⚠️ 看门狗的三个坑：

坑后果
传了 leaseTime看门狗不启动，锁到期自动释放，业务还在执行 → 并发
unlock 时不是持有者抛 IllegalMonitorStateException，要用 isHeldByCurrentThread() 判断
Redisson 客户端进程挂了续期停止，锁在 30 秒后自动释放（这是设计而非 bug）

🎯 加分点（三层保护，这是 P7 级别的回答）：「我们的订单场景用了三层保护：

  1. 第一层：Redis 分布式锁（Redisson）——挡住 99% 的并发，快速失败。
  2. 第二层：数据库乐观锁（update stock set num = num - 1 where id = ? and num >= 1）——即使锁失效，DB 层的条件更新也能保证不超卖。返回影响行数 0 就说明抢失败了。
  3. 第三层：数据库唯一索引——如果是「一人一单」，直接给 (user_id, activity_id) 建唯一索引，物理层面无法重复。

为什么要三层？因为分布式锁本身不是 100% 可靠的——主从切换、网络分区都可能让锁失效。真正的正确性必须由数据库来兜底。 这是我做了 8 年分布式系统最深的体会。」

31. Redlock 到底可不可靠？Kleppmann 和 antirez 吵的是什么？L3专家

背景：单实例 Redis 锁在主从切换时会失效（主库写完锁，还没同步给从库就宕机，从库升主后锁丢了）。所以 antirez 提出 Redlock：向 N（通常 5）个独立的 Redis 实例加锁，超过半数成功且总耗时小于锁有效期，才算加锁成功。

Kleppmann（《Designing Data-Intensive Applications》作者）的批评

  1. 时钟依赖：Redlock 假设各节点时钟大致同步且不会跳变。但 NTP 校时、虚拟机暂停都会让时钟跳变。如果某节点时钟前跳，它的锁提前过期，Redlock 却以为还有效。
  2. GC 暂停：客户端拿到锁后如果发生长时间 GC（比如 10 秒），锁在 GC 期间过期，其他客户端拿到锁，两个客户端同时持有锁。
  3. 无 fencing token：即使意识到锁可能失效，也没有机制阻止「旧持有者」继续写。Kleppmann 提出应该用 fencing token——每次加锁返回一个单调递增的数字，存储层拒绝比当前已见过更小的 token 的写入。
  4. 结论：依赖时钟的分布式锁不能保证正确性，应该用 Paxos/Raft 这类共识算法（如 etcd、ZooKeeper）。

antirez 的反驳

  1. 时钟跳变可以用运维手段规避（不用 NTP 大步调，用 slew 模式）。
  2. GC 问题不是 Redlock 的锅——是客户端的问题，任何锁都有这个问题，包括 ZooKeeper。
  3. fencing token 需要存储层配合，而很多存储层根本不支持。如果没有这个能力，讨论 fencing token 也没意义。
  4. Redlock 的定位是「效率锁」而非「正确性锁」——用它来避免重复劳动（如重复计算），而不是保护资金安全。

怎么回答这个问题（面试标准答案）

结论先行：

场景推荐方案理由
效率锁（防重复计算、防缓存击穿重建）单实例 Redis 锁 / Redisson偶尔失效只是多做一次，无损失
正确性锁（资金、库存）不用分布式锁，用「DB 条件更新 + 唯一索引」或 etcd/ZooKeeper正确性不能依赖有时钟假设的锁

🎯 加分点：「Kleppmann 那篇文章最狠的一句话是：『如果你需要保证正确性，就不要用 Redis 锁；如果你只是为了避免重复工作，那单实例 Redis 锁就够了，Redlock 是过度设计。』 我觉得这话是对的。我们的实践是：库存扣减从不用锁，直接用 UPDATE ... WHERE stock > 0 的条件更新，或者 Redis Lua 脚本原子扣减。锁只在『防止重复触发』这类场景用，比如防止定时任务重复执行。」

32. 缓存和 MySQL 双写，为什么推荐「先更新 DB 再删缓存」？L3

四种组合逐一分析（这是最严谨的答法）：

方案并发问题结论
① 先更缓存，再更 DB缓存成功但 DB 失败 → 缓存永久脏❌ 不推荐
② 先更 DB，再更缓存并发写时，A 后写却先更新缓存，B 先写却后更新 → 缓存是 A 的旧值❌ 不推荐
③ 先删缓存，再更 DB删完缓存、还没更 DB 时，读请求把旧值读回来写进缓存 → 长期脏❌ 不推荐
④ 先更 DB，再删缓存理论上仍有不一致窗口，但概率极低（要求读线程写缓存在删缓存之后）✅ 推荐

为什么 ④ 的窗口极小：要出现不一致，必须满足「读线程在『读 DB』之后、『写缓存』之前，写线程完成了『更 DB + 删缓存』」。这个时间窗口只有几毫秒，且要求一次读操作横跨一次完整的写操作。

为什么「删」优于「更新」：

  1. 幂等性：DEL 是幂等的，重复执行无害。UPDATE 缓存不是——两次并发更新，执行顺序可能颠倒。
  2. 懒加载：删了之后，如果这个 key 再也没人访问，就不需要重建，省一次计算。而更新缓存是「无论如何都要算一次」。
  3. 避免写放大：如果缓存值需要复杂计算（聚合多个表），更新缓存会引入写路径的复杂计算，影响写性能。

🎯 加分点：「还有一个关键细节很多人不知道：必须等事务提交后再删缓存。如果代码是这样：

// ❌ 错误：事务未提交就删缓存
@Transactional
public void update() {
    mapper.update(p);       // 事务还没提交
    redis.del(key);         // 此时删缓存
}
// 事务真正提交是在方法返回后

// 危险时序：
// T1: 更新DB（未提交）→ 删缓存
// T2: 读缓存miss → 读DB（读到旧值，因为T1未提交）→ 写缓存旧值
// T3: T1事务提交
// 结果：缓存是旧值，DB是新值，长期不一致！

正确做法是用 TransactionSynchronizationManager.registerSynchronization 的 afterCommit 回调，或者用 AOP 在事务提交后删。」

33. 大 key 怎么发现和处理？L3

定义（量化标准）：

类型大 key 阈值
String> 10 KB（严格）、> 1 MB（严重）
Hash/List/Set/ZSet元素数 > 5000（严格）、> 10000（严重）
总体单个 key 内存 > 1 MB

五大危害：

  1. 网络阻塞：单次 GET 传 100MB，占用带宽，其他请求排队。
  2. 命令阻塞：单线程下 HGETALL 一个大 Hash 要几秒，全局阻塞。
  3. 删除阻塞：DEL 一个大 key 会同步释放内存，可能阻塞数秒（要用 UNLINK）。
  4. 持久化阻塞：大 key 在 fork + COW 时会复制大量页面，内存暴涨。
  5. 集群倾斜：大 key 所在节点内存远超其他节点，甚至 OOM。

四种发现手段：

# 1. 官方工具（离线扫描，会占用CPU，建议从库执行）
redis-cli --bigkeys                    # 按类型找最大的key
redis-cli --bigkeys -i 0.1             # 每次扫描间隔，降低影响
redis-cli --memkeys                    # 按内存大小找

# 2. 精确查单个key
MEMORY USAGE mykey
STRLEN mykey                           # String 长度
HLEN mykey / LLEN / SCARD / ZCARD      # 集合元素数

# 3. RDB 离线分析（推荐，零影响）
# 用 redis-rdb-tools 分析 RDB 文件，生成 CSV 报告
rdb -c memory dump.rdb --bytes 1024 --filters db=0 > memory.csv
# 然后排序 SQL 分析
# 或 rdb -c memory dump.rdb | sort -k4 -nr | head -20

# 4. 慢查询日志反推
SLOWLOG GET 100                        # 找耗时长的命令，通常是操作大key

# 5. 客户端埋点（最推荐）
# 在 RedisTemplate 或 AOP 里统计每次操作返回的字节数，
# 超过阈值就上报 Prometheus

四种删除方法：

# ❌ DEL：同步删除，会阻塞，别在生产用
DEL bigkey

# ✅ UNLINK：异步删除，先摘除key，实际内存在后台线程慢慢释放
UNLINK bigkey

# ✅ Hash 分批删除（用 HSCAN 遍历，每次删一批）
HSCAN bigkey 0 COUNT 100
HDEL bigkey field1 field2 ...

# ✅ 更稳妥：先改名再删（保证业务立即看不到，删除延迟执行）
RENAME bigkey bigkey:del:{timestamp}
# 然后后台任务在低峰期 UNLINK
UNLINK bigkey:del:1699999999

🎯 加分点（大厂实践）：「大 key 治理我们分三步：

  1. 发现：RDB 离线分析（每天跑一次）+ 客户端 AOP 埋点（实时告警）。不做线上 --bigkeys，因为它是 O(N) 全量扫描，会在主线程跑很久。
  2. 改造：大 Hash 拆成多个小 Hash（如 cart:user:123:1、cart:user:123:2），用 hash tag 保证同槽。大 List 按时间分片。
  3. 清理：用 RENAME + UNLINK，在凌晨低峰期做。绝不直接 DEL。

另外，我们还改过一个坑：lazyfree-lazy-user-del yes 可以让 DEL 也变成异步，但我们没开——因为这让删除行为不可预期，运维更难排查。宁可显式用 UNLINK。」

34. 热 key 怎么发现和处理？为什么扩容没用？L3

热 key：单位时间内访问频率极高的 key。（注意和大 key 完全不同——热 key 可能很小，就是访问量太大）

为什么扩容没用（关键问答）：

假设：key=「iPhone 14 详情页」，QPS 8 万

单实例 Redis 极限约 10 万 QPS（简单 GET）

情形A：哨兵模式
  └─ 加从库也没用！因为从库是只读副本，
     但客户端读同一个 key 会因负载均衡到不同从库，
     如果客户端只连主库 → 完全没用
  └─ 即使读从库，也是「分散压力」而非「解决热点」

情形B：Cluster 模式
  └─ 但这个 key 只在一个槽 → 只在一个节点 → 该节点 QPS 8万
  └─ 加其他节点完全没用！因为槽是固定的

结论：扩容解决的是「整体容量」，热 key 是「单点压力」，

37. Redis 的线程模型演进，IO 多线程是怎么实现的？L3

演进路线：

版本变化解决的问题
1.0纯单线程—
4.0引入后台线程（lazyfree）大 key 删除阻塞
6.0引入 IO 多线程网络 IO 成为瓶颈
8.xIO 线程更成熟，默认配置优化更好的多核利用

IO 多线程的工作流程（关键！）：

配置：
io-threads 4                    # 总线程数，主线程 + 3 个 IO 线程
io-threads-do-reads yes         # 读也交给 IO 线程（6.0 默认 no）

# 注意：io-threads 是「总线程数」，不是「额外线程数」
# 官网建议：4核设2-3，8核设6；超过8个没意义（主线程会成为瓶颈）

一次请求的完整流程：

  1. 主线程通过 epoll 监听所有连接，发现可读的 socket。
  2. 主线程把「读就绪」的 socket 分给 IO 线程（round-robin 或取模）。
  3. IO 线程并行执行 read() 把数据读到用户态缓冲，然后通知主线程。
  4. 主线程阻塞等待所有 IO 线程读完，然后单线程串行执行所有命令。
  5. 主线程把写回任务分给 IO 线程，IO 线程并行 write()。
  6. 主线程等所有 IO 线程写完，进入下一次 epoll 循环。

为什么 IO 多线程有效？因为 read()/write() 涉及内核态拷贝（从 socket buffer 拷到用户态），这部分是纯 CPU 消耗，能并行。而命令执行必须串行（共享数据结构），所以保持单线程。

为什么 io-threads 不能设太大？

  1. 主线程是瓶颈：所有命令执行还是主线程干的，IO 线程再多也帮不上。
  2. 同步开销：主线程要等所有 IO 线程完成（barrier），线程越多，等待和协调开销越大。
  3. 上下文切换：线程多了，CPU 在切换上浪费。

🎯 加分点：「io-threads-do-reads 默认是 no！很多人以为开了 io-threads 就自动开启读多线程，其实不是。写多线程默认开，读多线程要显式打开。官方文档也提醒：开启读多线程在部分场景下收益不明显甚至下降，建议压测后再开。我们线上是 io-threads 6 + io-threads-do-reads no，压测下来 QPS 提升约 35%。」

Redis 的三个核心职责：

① 库存预扣（Lua 原子操作，防超卖）

-- seckill.lua
-- KEYS[1] = 库存key (stock:sku:1001)
-- KEYS[2] = 已购用户集合 (bought:sku:1001)
-- ARGV[1] = 用户ID
-- ARGV[2] = 限购数量(一般1)

-- 1. 判断是否重复购买
if redis.call('SISMEMBER', KEYS[2], ARGV[1]) == 1 then
    return -2      -- 重复下单
end

-- 2. 判断库存
local stock = tonumber(redis.call('GET', KEYS[1]))
if stock == nil or stock <= 0 then
    return -1      -- 无库存
end

-- 3. 扣减库存 + 记录用户
redis.call('DECR', KEYS[1])
redis.call('SADD', KEYS[2], ARGV[1])
return stock - 1   -- 返回剩余库存

为什么必须用 Lua？「判断库存」+「扣减库存」+「记录用户」三步必须原子。用 MULTI/EXEC 做不到——事务里不能根据前一条命令的返回值做判断。

② 一人一单（Set 去重）

上面的 bought:sku:1001 就是 Set，SISMEMBER O(1) 判重。但要注意：如果用户量大（百万级），这个 Set 会变成大 key。优化方案：用 Bitmap（用户 ID 作为 offset）或分片成多个 Set。

③ 限流（防止恶意刷）

-- 滑动窗口限流
-- KEYS[1] = 限流key, ARGV[1] = 窗口秒数, ARGV[2] = 上限
local now = tonumber(ARGV[1])
local key = KEYS[1]
redis.call('ZREMRANGEBYSCORE', key, 0, now - 1000)   -- 清理旧记录
local count = redis.call('ZCARD', key)
if count >= tonumber(ARGV[2]) then
    return 0
end
redis.call('ZADD', key, now, now .. '-' .. math.random())
redis.call('EXPIRE', key, 2)
return 1

完整时序（关键是「异步落库」）：

  1. 用户点「立即抢购」→ 网关限流（令牌桶，用户维度 + IP 维度）。
  2. 应用层调 Redis Lua 预扣库存。这一步在内存里完成，耗时 < 1ms。
  3. 扣减成功 → 发 MQ 消息（orderId + userId + skuId）→ 立即返回「排队中」。
  4. 消费者异步创建订单、扣 MySQL 库存、扣款。这里才做真正的持久化。
  5. 前端轮询订单状态，或服务端主动推送结果。

🎯 加分点（这是拉开差距的地方）：

  1. 为什么 Redis 预扣 + MQ 异步？因为 MySQL 单机写入 ~2000 TPS，秒杀瞬间可能 10 万 QPS。Redis 把 10 万削到 2000，MQ 再做一层缓冲。
  2. Redis 扣减成功了，MQ 发失败怎么办？这是经典的「本地消息表」问题。做法：在 Redis 里扣减后，把消息写进本地消息表（同事务），再用定时任务补偿投递。或者用 RocketMQ 的事务消息。
  3. Redis 扣减成功，但用户一直不付款？用 Redis 延时队列（ZSet）做超时未付款回滚：ZADD order:timeout <deadline> <orderId>，定时任务 ZRANGEBYSCORE 0 now 捞出超时的订单，回滚库存（INCR 库存 + SREM 用户）。
  4. 怎么防止「扣了 Redis 但 MySQL 最终失败」导致的不一致？对账任务。定时比对 Redis 库存和 MySQL 库存，不一致就告警 + 人工介入。这是最后一道防线，任何异步方案都必须有对账。

完整答法总结：「秒杀的本质是『把并发的写操作，转化成串行的内存操作 + 异步的持久化』。Redis 承担了『高并发计数』和『幂等判重』两个最重的活，因为它是内存操作、单线程无锁、Lua 保证原子。MySQL 只负责最终的持久化，压力被削掉了 98%。」

39. 如何用 Redis 实现延时队列？L3

ZSet 方案（最经典）：

// 投递延时消息：score 是执行时间戳
public void delay(String topic, String msgId, long delaySeconds) {
    long executeAt = System.currentTimeMillis() / 1000 + delaySeconds;
    redis.opsForZSet().add("delay:" + topic, msgId, executeAt);
}

// 消费（可以用多个实例并行，但要加锁防重复消费）
@Scheduled(fixedDelay = 1000)
public void consume() {
    String topic = "order-timeout";
    String key = "delay:" + topic;
    long now = System.currentTimeMillis() / 1000;

    // 分布式锁，防止多实例重复消费
    RLock lock = redisson.getLock("lock:consume:" + topic);
    if (!lock.tryLock()) return;

    try {
        // 捞出到期的消息（LIMIT 100 防止一次太多）
        Set<String> msgs = redis.opsForZSet()
            .rangeByScore(key, 0, now, 0, 100);
        for (String msgId : msgs) {
            // 原子：先移除，移除成功才处理（防止重复）
            Long removed = redis.opsForZSet().remove(key, msgId);
            if (removed != null && removed > 0) {
                handleMessage(topic, msgId);
            }
        }
    } finally {
        lock.unlock();
    }
}

ZSet 方案的三个缺陷：

缺陷说明解决
① 轮询延迟每秒扫一次，最多延迟 1 秒要求高精度就缩短间隔，代价是 CPU
② 消息只能被消费一次ZREM 后如果处理失败，消息丢了用 Stream 替代，或 ZREM 前先存到处理中列表
③ 空轮询浪费没消息也在扫用 Lua 或先 ZCARD 判断

Stream 方案（5.0+ 更好）：用 XADD 时指定 ID 为未来时间戳，消费时用 XREAD BLOCK 阻塞等待，能减少空轮询。但 Stream 本身不原生支持「延时」，还是要配合 ZSet 或定时检查。

🎯 加分点：「生产上我不推荐用 Redis 做延时队列，除非延时精度要求很低（秒级）且消息量不大。原因有三个：

  1. 可靠性不足：Redis 主从切换可能丢消息，而延时任务往往涉及钱（订单超时关单、优惠券过期）。
  2. 没有重试机制：处理失败就是失败，要自己实现重试 + 死信。
  3. 成本高：空轮询浪费 CPU，且消息堆积在内存里。

我们的选型：用 RocketMQ 的延时消息（支持 18 个等级），或 RabbitMQ 的 TTL + 死信队列，或专门的分布式任务调度（XXL-Job）。Redis 延时队列只在『轻量、允许丢失』的场景用，比如『5 秒后刷新缓存』这种。」

40. Lua 脚本有什么坑？操作系统级问题是什么？L3

Redis 用的是 Lua 5.1（不是 5.2/5.3），且做了沙箱化改造。这带来一批坑：

坑说明解决
① 没有全局变量写 x = 1 会报错（未声明全局变量）用 local x = 1
② 随机命令结果被固定RANDOMKEY、SRANDMEMBER 在脚本里每次都返回同一个（写入 AOF 时要保证幂等）理解这是设计而非 bug
③ 所有 key 必须在同一个槽Cluster 下，脚本里操作的 key 必须同槽，否则报 CROSSSLOT用 hash tag：{user1001}:stock、{user1001}:order
④ 不能用 KEYS[1] 动态拼接 key只能通过 KEYS 数组传，不能脚本里拼提前把 key 传进来
⑤ 脚本不能太慢整个脚本执行期间阻塞 Redis脚本控制在 1ms 内，超时用 lua-time-limit（默认 5s，超了只记日志不中断）
⑥ 不支持浮点数的精确比较Lua 里 0.1 + 0.2 ~= 0.3用整数运算（金额用分）

EVALSHA 的正确用法：

// ❌ 每次传完整脚本，浪费带宽
redis.eval(luaScript, keys, args);

// ✅ 先加载获取 SHA，之后只传 SHA
String sha = redis.scriptLoad(luaScript);        // 返回 SHA1
redis.evalsha(sha, keys, args);

// ⚠️ 但 Redis 重启后脚本缓存丢失，EVALSHA 会报 NOSCRIPT
// 必须捕获 NOSCRIPT 异常，降级用 EVAL 重新加载
try {
    redis.evalsha(sha, keys, args);
} catch (RedisException e) {
    if (e.getMessage().contains("NOSCRIPT")) {
        redis.eval(luaScript, keys, args);      // 降级
    }
}
// 生产推荐：直接封装一个「优先 EVALSHA，失败降级 EVAL」的工具方法

# 2. 调用
FCALL my_lock_release 1 mykey myvalue

# 优势：
# - 函数随 AOF/RDB 持久化，重启不丢（不像 EVALSHA 会 NOSCRIPT）
# - 有命名空间，可管理（FUNCTION LIST/STATS/DUMP）
# - 支持函数库级别的元数据

操作系统级问题（这个点很加分）：

  1. Lua 脚本执行超时后，Redis 不中断脚本——它只是开始接受 SCRIPT KILL 请求。如果脚本有写操作，SCRIPT KILL 也杀不掉，只能 SHUTDOWN NOSAVE 重启。这是 Lua 最危险的特性。
  2. 脚本内的 os.time() 返回的是固定的时间（脚本开始执行的时间），不是实时的。因为要保证 AOF 重放的幂等性。
  3. Redis 8.x 的 Script 有内存限制：lua-memory-limit，防止脚本申请过多内存。

🎯 加分点：「我们有个血泪教训：一个同事写了段 Lua 脚本做批量数据处理，结果脚本里有个 while 循环因为边界条件写错，死循环了。SCRIPT KILL 杀不掉（因为已经执行了写命令），最后只能重启 Redis。所以我们的规范是：Lua 脚本必须有明确的循环上限，且必须做 Code Review，脚本里绝对不写不确定次数的循环。」

41. Redis 集群的数据倾斜怎么办？L3

数据倾斜的两种形态：

类型原因现象
槽倾斜槽分配不均（如某节点分了 5000 槽，另一个只有 1000）整体上某节点内存/CPU 高
key 倾斜大量 key 落到同一个槽（如都用同一个 hash tag）单个节点内存暴涨

槽倾斜的排查与解决：

# 查看槽分配
CLUSTER SLOTS
redis-cli --cluster check 127.0.0.1:6379

# 查看每个节点的槽数
CLUSTER SHARDS                  # 7.0+
redis-cli --cluster info 127.0.0.1:6379

# Redis 8.x 新增：槽级别统计（超实用！）
CLUSTER SLOT-STATS ALL              # 所有槽的key数、CPU使用
CLUSTER SLOT-STATS SLOTSRANGE 0 100
# 这能精确发现「哪个槽是热点」

# 重新均衡
redis-cli --cluster rebalance 127.0.0.1:6379
redis-cli --cluster rebalance --cluster-use-empty-masters 有数据也要用空节点

key 倾斜的解决：

  1. 避免全局 hash tag：不要所有 key 都用 {global}，那等于放弃分片。
  2. 热点 key 打散：hotkey → hotkey:1 ~ hotkey:N，写时全写，读时随机。这就是前面讲的「key 复制」。
  3. 大 key 拆分：一个 5000 字段的 Hash 拆成 50 个 100 字段的 Hash。
  4. 监控告警：对每个节点的 used_memory 做监控，偏差超过 20% 就告警。

🎯 加分点：「CLUSTER SLOT-STATS 是 Redis 8.0 的新命令，我特别推荐。以前排查倾斜要写脚本统计，现在一条命令直接给出每个槽的 key 数量、CPU 时间、网络流量。它能直接告诉你『3999 这个槽 CPU 占了 40%』，定位效率提升巨大。这也是我认为 Redis 8 值得升级的理由之一。」

42. Redis 如何保证消息不丢？L3

消息丢失的三个环节（必须分层讲）：

生产者 ──①──> Redis ──②──> Redis 持久化 ──③──> 消费者
环节丢失原因解决
① 生产端网络抖动，发了但 Redis 没收到生产端重试 + 幂等（消息带唯一 ID，消费端去重）
② 服务端Redis 宕机，内存数据没落盘AOF everysec/always；主从同步；WAIT 命令
③ 消费端取走了但处理失败/进程崩溃Stream 的 XPENDING + XACK + XCLAIM 机制

用 List 做队列，消息一定会丢（要讲清为什么）：

# ❌ List 方案的致命缺陷
BLPOP queue 0              # 从队列取出消息
# 此时消息已经从 Redis 删除了！
doBusiness();              # 如果这里进程崩溃，消息永久丢失
# 没有任何机制能找回来

用 Stream 才能保证：

# 1. 创建消费组
XGROUP CREATE orders g1 0

# 2. 消费者读消息（读后消息进入 PEL：Pending Entries List，不是立即删除）
XREADGROUP GROUP g1 c1 COUNT 1 STREAMS orders >

# 3. 处理成功后显式 ACK
XACK orders g1 <msgId>

# 4. 如果消费者崩溃，消息会留在 PEL 里
XPENDING orders g1
# 输出：[消息数, 最小ID, 最大ID, [[消费者, 消息数], ...]]

# 5. 其他消费者认领超时未 ACK 的消息（故障转移）
XAUTOCLAIM orders g1 c2 60000 0-0 COUNT 10
# 60000 = 最小空闲时间 60 秒，超过就认为原消费者挂了

# 6. 查看认领结果
XINFO GROUPS orders

🎯 加分点：「完整的不丢消息方案应该是：

  1. 生产端：消息带 msgId（业务唯一 ID），发送失败重试，消费端用 msgId 做幂等。
  2. 存储端：appendonly yes + appendfsync everysec（最多丢 1 秒）。更严格用 WAIT 1 0 同步到副本。
  3. 消费端：Stream + 消费组 + 显式 ACK + XAUTOCLAIM 认领超时消息 + 死信处理（超过 N 次重试的进死信队列）。

但必须诚实地说：Redis 永远做不到「绝对不丢」。 因为它是 AP 系统，主从异步复制。真要金融级不丢，用 Kafka（多副本 ISR + acks=all）或 RocketMQ。Redis 的定位是「高吞吐、可容忍少量丢失」。

43. 讲讲 Redis 的 Bitmap 和 HyperLogLog，什么时候用？L3

Bitmap：用 bit 位存布尔值，极致省内存

SETBIT sign:20260930:1001 0 1      # 用户1001 第0天签到
GETBIT sign:20260930:1001 0
BITCOUNT sign:20260930:1001         # 这个 key 里有多少个1

# 统计连续签到（用 BITFIELD 更灵活）
BITFIELD sign:user1001 GET u7 0     # 取7个bit

# 统计活跃用户（按天建一个bitmap，用户id作为offset）
SETBIT active:20260930 1001 1
SETBIT active:20260930 1002 1
BITCOUNT active:20260930            # 当天活跃数
BITOP AND active:week active:mon active:tue ...  # 一周都活跃的用户（位图与运算）

内存对比（1 亿用户标签）：

方案内存
Set（存 userId）约 1GB+（每个元素约 50 字节开销）
Bitmap12.5MB（1 亿 bit = 12.5MB）

HyperLogLog：基数统计，误差 0.81%，内存固定 12KB

PFADD uv:20260930 user1001 user1002 user1003
PFCOUNT uv:20260930                  # 近似去重计数
PFMERGE uv:week uv:mon uv:tue        # 合并多天

HLL 的核心权衡：

能力BitmapHyperLogLog
内存（1亿元素）12.5MB（需知道 id 范围）12KB（固定）
能否判断单个元素是否存在✅ 可以（GETBIT）❌ 不能
误差0（精确）0.81%（近似）
大范围 id❌ offset 太大会爆内存✅ 与 id 大小无关

Bitmap 的坑（必须讲）

# ❌ 危险：如果 userId 是雪花ID（19位数字，如 1900000000000000001）

# offset = 1.9 × 10^18 bit = 237 PB！！
# 直接 OOM

# ✅ 解决：
# 1. 用自增的小 ID 或用户表主键（从0开始）
# 2. 或用 HashMap 把 userId 映射到紧凑的 offset
# 3. 或直接用 HLL（不关心具体是谁）
# 4. Redis 8 对 sparse bitmap 有优化，但仍需注意 offset 上限

🎯 加分点：「选型口诀：『要精确、要判断个体 → Bitmap；只要总数、能容忍误差、id 很大 → HyperLogLog』。

具体案例：签到用 Bitmap（要判断某人某天是否签到，且用户 id 通常不大）；UV 统计用 HLL（只关心总数，且 4 亿用户用 Bitmap 要 50MB/天，HLL 只要 12KB）；行为标签（是否买过、是否浏览过）用 Bitmap 做位运算，能一次算出「既浏览又购买」的交集，这是 Set 做不到的（Set 的 SINTER 是 O(N) 且内存高）。」

44. GEO 是怎么实现的？为什么能算距离？L3

底层就是 ZSet + GeoHash 编码。

  1. GeoHash 编码：把经纬度（2 个浮点数）编码成一个 52 位的整数。做法是「二分区间 + 交替取位」：经度二分一次得 1 bit，纬度二分一次得 1 bit，交替进行 26 轮得到 52 位。
  2. 存进 ZSet：这个 52 位整数就是 ZSet 的 score，member 是地点名。
  3. 距离查询：用 ZSet 的范围查询，找出 GeoHash 相近的点（GeoHash 前缀相同的点在空间上相近）。
  4. 精确距离：用 Haversine 公式算球面距离，过滤掉 GeoHash 相近但实际较远的点。
# 添加位置
GEOADD restaurants 116.404 39.915 "海底捞(王府井)"
GEOADD restaurants 116.410 39.920 "星巴克(东单)"

# 查询距离
GEODIST restaurants "海底捞(王府井)" "星巴克(东单)" km

# 附近的人（以某点为中心，半径 5km 内，按距离升序，返回10个）
GEOSEARCH restaurants FROMLONLAT 116.404 39.915 BYRADIUS 5 km ASC COUNT 10 WITHDIST

# 查某个地点附近的
GEOSEARCH restaurants FROMMEMBER "海底捞(王府井)" BYRADIUS 3 km ASC

# 取坐标
GEOPOS restaurants "海底捞(王府井)"
# 返回经纬度

# 取 GeoHash 字符串
GEOHASH restaurants "海底捞(王府井)"

🎯 加分点：「GEOSEARCH 是 6.2 新增的，统一了之前的 GEORADIUS（已废弃）。GeoHash 有个经典问题：边界问题——两个点实际很近，但因为跨越了 GeoHash 的分界线，前缀完全不同。Redis 的处理是查询时同时查相邻的 8 个格子。还有个坑：GeoHash 精度随纬度变化，高纬度地区误差大，所以 Redis 最后一定要用 Haversine 公式复算真实距离。」

45. 为什么 Redis 用跳表不用 B+ 树？顺便说说 B+ 树和跳表的区别。L3
维度B+ 树跳表
设计场景磁盘（减少磁盘 IO 次数）内存（追求简单高效）
节点大小一个节点存多个 key（一页 16KB）一个节点一个 key
树高低（3-4 层支持千万数据）高（约 logN 层，但每层只跳关键节点）
范围查询叶子节点链表底层链表
实现复杂度高（分裂、合并、平衡）低
内存开销较高（页内可能有空隙）较低（平均 1.33 指针/节点）
并发修改难（旋转/分裂影响大）易（局部修改）

Redis 不用 B+ 树的三个理由：

  1. 内存数据库不需要 B+ 树：B+ 树的价值在于「一次磁盘 IO 读一页」，把树高压低。但 Redis 数据在内存，随机访问代价极低，树高不是问题。B+ 树的优势被抹平了。
  2. 跳表实现更简单：antirez 明确说过，跳表代码量是平衡树的 1/5，且不需要考虑 rebalance。「可维护性」在长期项目里价值极高。
  3. 范围查询和并发更友好：跳表的 ZRANGEBYSCORE 找到起点后沿底层链表走就行，不需要中序遍历。而且局部修改不影响大范围结构。

🎯 加分点：「总结一句：『B+ 树是为磁盘设计的，跳表是为内存设计的』。如果面试官追问『那 MySQL 为什么不用跳表』，答案是：MySQL 数据在磁盘，一次 IO 代价 10ms（相对内存的 100ns 差 10 万倍），必须用 B+ 树把树高压到 3-4 层。而 Redis 在内存，访问任何地址代价一样，跳表的 O(logN) 完全够用，简单才是美。」

46. Redis 的 Pipeline 会不会有问题？批量多少合适？L3

Pipeline 的三个风险：

  1. 内存暴涨：Pipeline 会把所有命令和结果都缓存在客户端和 Redis 的输出缓冲区。一次发 10 万条命令，可能出现「客户端 OOM」或「Redis 输出缓冲超限被断开连接」（client-output-buffer-limit normal）。
  2. 阻塞其他请求：虽然 Pipeline 里每条命令还是分开执行的（不阻塞），但 Redis 一口气读 10 万条命令 + 一口气写 10 万个响应，这个 IO 过程会占用主线程，影响其他请求的响应延迟。
  3. 错误处理困难：中间某条命令失败，Pipeline 不会中断，你要自己遍历所有结果判断。而且无法根据前一条结果决定后一条（那是 Lua 的活）。

批量大小建议（经验值）：

批量数评价
< 100安全，收益明显
100 - 1000推荐区间，收益最优
1000 - 10000需要压测，注意内存
> 10000危险，建议分批
 
// 分批 Pipeline 的正确写法
private static final int BATCH_SIZE = 500;

public void batchSet(Map<String, String> data) {
    List<Map.Entry<String, String>> list = new ArrayList<>(data.entrySet());
    for (int i = 0; i < list.size(); i += BATCH_SIZE) {
        int end = Math.min(i + BATCH_SIZE, list.size());
        List<Map.Entry<String, String>> batch = list.subList(i, end);

        redis.executePipelined((RedisCallback<Object>) conn -> {
            RedisSerializer<String> ser = redis.getStringSerializer();
            for (Map.Entry<String, String> e : batch) {
                conn.set(ser.serialize(e.getKey()), ser.serialize(e.getValue()));
            }
            return null;
        });
    }
}

// ✅ Lettuce 的 async 模式天生支持 pipeline（自动攒批）
// ✅ 也可以用 Redisson 的 RBatch
RBatch batch = redisson.createBatch();
for (String key : keys) {
    batch.getBucket(key).setAsync(value);
}
BatchResult<?> result = batch.execute();

47. 主从复制中，从库的数据为什么可能比主库多？L3

这是个很刁的题，答案涉及三个机制：

原因一：从库有自己独立的过期策略

从库不会主动删除已过期的 key（因为要等主库的 DEL 命令同步过来）。所以从库的 DBSIZE 可能比主库大——主库已经惰性删除了，从库还没收到删除命令。

# 主库：访问一个过期key → 发现过期 → 删除
GET expired:key
# 触发惰性删除，主库 DBSIZE 减少

# 从库：同样访问
GET expired:key
# 从库不删除！返回 nil，但 key 还在，DBSIZE 不减

但从库读已过期 key 时会返回 nil，因为从库会检查「逻辑过期」（不是物理删除）。所以数据是「看起来不存在，但物理还在」。

原因二：全量同步时主库有新写入

BGSAVE 期间主库的新写入会进 repl_buffer。如果这个 buffer 溢出（client-output-buffer-limit replica），会断开连接重来。而如果从库加载完 RDB 后又重放 buffer 中的命令，理论上应该一致。

原因三：主库的 key 被淘汰了

如果主库开启了 LRU/LFU 淘汰，主库内存满了会淘汰一些 key。淘汰操作会不会同步给从库？

Redis 版本行为
3.2 之前从库自己也淘汰（可能和主库淘汰的不一样，导致不一致）
3.2 之后从库不主动淘汰，等主库的 DEL 同步。但主库淘汰时会同步 DEL 给从库（4.0+）

🎯 加分点：「这个问题的标准答案是：『主从数据量不一致是正常现象，不一定是 bug。』 核心原因是从库不主动做过期删除，只依赖主库的 DEL 同步。

但这带来一个实际问题：从库内存可能比主库高。因为过期 key 的物理内存还没释放。所以运维上要注意：从库的 maxmemory 要设得比主库大一些，或者定期在从库上做一次 replica-read-only no 下的手动清理（不推荐，会破坏复制）。更好的做法是用 replica-ignore-maxmemory yes（默认 yes），让从库忽略自己的 maxmemory 限制。」

# 建议 1（不是 0，0 在某些内核会导致 OOM）

🎯 加分点（这是完整版的标准答法）：「我的排查口诀是『五层递进：网络 → 命令 → 资源 → 客户端 → 内核』。

实际经验里，80% 的 Redis 变慢是这三个原因：

  1. 大 key 操作（占 40%）——SLOWLOG 一眼看出。解决：拆 key + 用 SCAN 替代 KEYS。
  2. THP 没关（占 20%）——最隐蔽，因为 CPU、内存都正常，就是 fork 时延迟尖刺。解决：echo never > /sys/kernel/mm/transparent_hugepage/enabled。
  3. 连接泄漏 / 连接池配置不当（占 20%）——CLIENT LIST 看到几千个 ESTABLISHED 但 idle 很久的连接。解决：检查客户端有没有正确 close()，连接池 maxIdle 是否合理。

剩下的 20% 是 AOF always + 慢盘、内存碎片、网络带宽打满、从库同步风暴。

最重要的一条经验：先看 SLOWLOG 和 LATENCY，不要在没定位到根因时就重启 Redis。 重启只是掩盖问题，而且会丢数据。」

49. 如果让你设计一个支撑百万 QPS 的 Redis 架构，你怎么做？L4架构题

先反问澄清（这一步最重要，体现架构思维）：

  1. 读多写少还是读写均衡？读写比例决定了架构方向。
  2. 能容忍多少数据丢失？决定持久化和复制策略。
  3. 能容忍多少延迟？决定是否用本地缓存。
  4. 数据量多大？决定是哨兵还是 Cluster。
  5. 一致性要求？决定读写路径。

假设：读 95% / 写 5%，数据 100GB，可容忍秒级不一致。架构设计：

第一层：客户端本地缓存（削掉 80% 读）

Caffeine 缓存，TTL 1-5 秒
├─ 命中率 60-90%
├─ 那 100 万 QPS 到这一层就只剩 10-40 万
├─ 关键：TTL 一定要短（防一致性差），且要加随机抖动
└─ 配合 Redis Pub/Sub 做跨实例失效通知（可选）

第二层：Redis Cluster 读写分离（承担剩余读 + 全部写）

┌─────────────────────────────────────────────────┐
│              Redis Cluster（6主6从）              │
│                                                  │
│  shard1: master1 ──── replica1                   │
│  shard2: master2 ──── replica2                   │
│  shard3: master3 ──── replica3                   │
│  shard4: master4 ──── replica4                   │
│  shard5: master5 ──── replica5                   │
│  shard6: master6 ──── replica6                   │
│                                                  │
│  写入：走 master（6 个分片并行，总写入能力 × 6）    │
│  读取：READONLY 走 replica（读能力 × 12）          │
└─────────────────────────────────────────────────┘
容量：6 × 16GB = 96GB（每主库控制 16GB 以内，fork 可控）
读能力：12 节点 × 8万 QPS ≈ 96 万
写能力：6 节点 × 8万 QPS ≈ 48 万

第三层：多级降级（保命层）

L1: Caffeine（本地）
L2: Redis Cluster（主）
L3: Redis 备用集群（异地/独立机房，通过 MQ 双写）
L4: 本地文件兜底数据（Redis 全挂时返回静态数据）
L5: 限流熔断（Sentinel 保护 DB）

每一层都要有「跳闸开关」，能一键降级

关键设计决策

决策点选择理由
分片数6 主单实例 ≤ 16GB，fork 可控；6 主足够 100GB
副本数1 从/主成本与可用性平衡；要求高就 2 从
是否读写分离是读 95%，分离能省一半机器
持久化混合持久化AOF everysec 保证秒级；RDB preamble 保证恢复快
热点 key本地缓存 + key 复制Cluster 无法解决单 key 热点

🎯 加分点（这是决定你能不能上 P8 的地方）：「架构设计最重要的是『知道哪里会先崩』。 我会明确说出这个架构的三个瓶颈：

  1. 单分片写入瓶颈：如果某业务写入集中在少数 key，那个分片会成为瓶颈。对策：业务层设计 key 时避免热点，或用 key 复制打散。
  2. Cluster 故障转移窗口：主库挂到从库升主约 10-30 秒，期间该分片不可用。对策：客户端重试 + 降级到本地缓存。
  3. 网络带宽：100 万 QPS × 平均 1KB = 1GB/s，需要万兆网卡。要提前算清楚。

还有一个经常被忽略的点：『百万 QPS』是整个集群的能力，不是单 key 的能力。 如果面试官追问『单个 key 要 100 万 QPS 怎么办』，答案是：唯一的办法是本地缓存，因为 Redis Cluster 对一个 key 只能提供一个节点的能力。」

50. Redis 在你项目里的定位是什么？如果 Redis 挂了会怎样？L4架构题

这是我最喜欢问的题，因为它能看出你有没有「生产思维」。

标准回答框架：先分类，再说降级

第一步：明确 Redis 承担的三类职责，按严重程度排序

职责挂了的后果严重度降级方案
① 纯缓存（商品详情、用户信息）穿透到 DB，DB 压力 ×10🟡 中限流 + 本地缓存 + DB 兜底
② 分布式锁锁失效，可能重复执行🟠 高DB 唯一索引兜底 + 乐观锁
③ 数据存储（库存、Session、分布式 ID）业务不可用🔴 极高基本无解，必须高可用

第二步：针对每一类说具体方案

① 纯缓存场景 —— 允许降级，关键是别把 DB 打死

// 多级缓存 + 熔断
Product getProduct(Long id) {
    // L1: 本地缓存（Redis挂了还有效）
    Product p = caffeine.get(id);
    if (p != null) return p;

    try {
        // L2: Redis
        p = redisGet(id);
        if (p != null) { caffeine.put(id, p); return p; }
    } catch (Exception e) {
        // Redis 异常：记录 + 继续走 DB（但要限流）
        log.warn("redis down", e);
        metrics.counter("redis.fail").increment();
    }

    // L3: DB（必须限流保护！）
    if (!dbRateLimiter.tryAcquire()) {
        throw new BizException("系统繁忙，请稍后重试");   // 快速失败
    }
    p = db.get(id);
    // 回种缓存（Redis 恢复后自动生效）
    return p;
}

② 分布式锁场景 —— 必须有 DB 兜底

「这就是我在第 30 题强调『三层保护』的原因：锁失效时，DB 的唯一索引和条件更新能保证正确性。 如果业务只依赖 Redis 锁而没有任何 DB 层面的保护，那这个设计本身就有问题。」

③ 存储场景 —— 只能靠高可用，不能靠降级

库存扣减：
❌ 错误做法：库存只存在 Redis
   Redis 挂了 → 库存数据丢失 → 灾难

✅ 正确做法：Redis 是「预扣」，MySQL 是「最终账本」
   Redis 挂了 → 停止秒杀入口（开关降级）→ 订单继续异步落库
   → Redis 恢复后从 MySQL 重建库存缓存

关键：Redis 只做「加速」，不能做「唯一真相来源」

🎯 加分点（大厂级回答）：「我们的实践有四条铁律：

  1. Redis 永远不能是唯一数据源。 所有关键数据必须能从我 DB 重建。Redis 只是「可丢弃的加速层」。
  2. 所有 Redis 调用必须有超时。 我们统一设 timeout=1000ms，maxWait=500ms。绝不无限等待。
  3. 所有 Redis 调用必须能降级。 用 Sentinel 或 Hystrix 包裹，异常时走 fallback，而不是抛出异常让请求失败。
  4. 必须有全链路压测。 我们会在预发环境直接 SHUTDOWN Redis，看系统能不能扛住——这叫「混沌工程」，Netflix 的 Chaos Monkey 就是这个思路。第一次演练我们就把 DB 打挂了，所以才加了 DB 限流。

一句话总结：『评估 Redis 故障影响时，不能只问「Redis 挂了怎么办」，而要问「Redis 挂了之后，我的流量会打到哪一层，那一层扛得住吗」。』」

ZooKeeper 为什么能无惊群？（这是加分点）

ZK 的锁实现：
  1. 在 /lock 下创建临时顺序节点 lock-0001, lock-0002...
  2. 每个客户端判断自己是不是最小的节点
  3. 如果不是，Watch「前一个节点」（不是 Watch 父节点！）
  4. 前一个节点删除时收到通知，再判断

结果：释放锁时只唤醒一个客户端，其他继续等。
而 Redis 锁释放后，所有等待者同时自旋抢（惊群）。

选型决策树：

是否已有 ZooKeeper/etcd？
├─ 是 → 用它（避免引入新组件）
└─ 否 → 业务的正确性要求有多高？
        ├─ 很高（资金、库存）→ 引入 etcd/ZK，或用 DB 条件更新
        └─ 一般（防重复、防并发）→ 用 Redis（Redisson）

性能敏感 + 已有 Redis → Redis
强一致 + 已有 ZK → ZK
新项目 + 强一致 → etcd（比 ZK 更好维护）

🎯 加分点：「我的实际选型是：99% 的场景用 Redis 锁，因为已经有 Redis 了，而且性能高。 但我会做两件事来补齐正确性：

  1. 关键业务加 DB 层的兜底（条件更新 / 唯一索引）——这是根本。
  2. 锁的粒度设计得足够小（按 orderId 而不是全局锁），这样即使偶发失效，影响面也极小。

只有在真的需要强一致且没有 DB 兜底可能时（比如分布式选主、分片调度），我才会引入 etcd。因为 ZK 的运维成本太高了——我们的 ZK 集群有专门的运维团队维护，普通业务团队碰不起。」

52. Redis 6/7/8 版本升级要注意什么？L4

先给版本演进与取舍：

版本关键变化升级价值
6.0IO 多线程、RESP3、ACL、SSL中（多核利用、安全）
6.2GEOSEARCH、CLIENT NO-EVICT、ZADD GT/LT低
7.0Multi-Part AOF、Function、Sharded PubSub、ACL v2高（持久化大幅改进）
7.2性能优化、CLUSTER 改进中
7.4Hash field TTL、内存优化中
8.0模块内置化（BF/JSON/TS/Vector）、HOTKEYS、ACL 增强高（功能大爆发）
8.2/8.4原子槽迁移、LRM 淘汰、XADD 幂等 IDMP、mTLS中高

升级的五个注意点：

  1. RDB/AOF 格式兼容性：新版能读老版 RDB，反之不行。升级后无法回滚，除非备份了老版本的 RDB。必须先在测试环境验证。
  2. 默认配置变化：7.0 默认开启 AOF（之前默认关）；8.0 模块内置后某些命令行为变化（如 BF.ADD 可能和第三方模块冲突）。要 diff 两版的 redis.conf。
  3. 废弃命令：如 GEORADIUS 在 6.2 后建议用 GEOSEARCH；SUBSCRIBE 在 Cluster 下要用 SSUBSCRIBE。
  4. 客户端兼容性：Lettuce 5.x 对 Redis 7 的支持有限，建议 Lettuce 6.x+。升级 Redis 前先升级客户端。
  5. Cluster 滚动升级顺序：先从库 → 再主库 → 最后升级哨兵/客户端。主从切换前要确认从库已升级且复制正常。

🎯 加分点：「我们的升级流程是『三步走』：

  1. 影子验证：新版本部署一套影子集群，把线上流量镜像过去（用 Redis 的 copy 能力或业务双写），跑一周对比数据一致性。
  2. 灰度升级：先升一个非核心分片，观察 3 天。指标看：LATENCY、SLOWLOG、INFO memory、客户端错误率。
  3. 全量升级：低峰期（凌晨 2-5 点）滚动升。每升一个节点，等 10 分钟观察。

关于是否升级到 8.0，我的判断是：如果你在用 RedisBloom/RedisJSON 这些模块，8.0 内置化是巨大收益（省掉模块运维的坑）；如果你只是当缓存用，7.2/7.4 更稳。不要为新特性而升级，要为痛点而升级。」

53. 怎么设计一个高可用的 Redis 架构？说清 RTO 和 RPO。L4

先定义两个指标（这是专业度的体现）：

指标含义Redis 场景下的取值
RTO（Recovery Time Objective）故障后多久能恢复服务哨兵：10-30 秒；Cluster：10-30 秒；手动：分钟级
RPO（Recovery Point Objective）能容忍丢失多少数据everysec：最多 1 秒；always：0

四种架构方案与 RTO/RPO 对比：

方案RTORPO成本适用
单机∞（需要人工）取决于持久化最低开发/测试
主从 + 手动切换分钟级秒级低容忍长时间故障
哨兵（3节点）10-30 秒秒级中数据 < 20GB
Cluster（3主3从）10-30 秒（分片级）秒级高数据 > 20GB
多机房（同城双活）< 5 秒（VIP 漂移）秒级极高金融级

高可用的四个层次（缺一不可）：

① 数据层：副本 + 持久化

# 一主两从（更高可用）
replicaof master 6379
min-replicas-to-write 1        # 至少1个从库确认才写成功
min-replicas-max-lag 10        # 且延迟 < 10 秒

# 持久化双保险
appendonly yes
appendfsync everysec
aof-use-rdb-preamble yes
save 900 1                     # 保留RDB兜底

② 检测层：监控 + 告警

必须监控的指标（缺一个都是隐患）：
├─ master_link_status（主从链路）
├─ master_last_io_seconds_ago（复制延迟，>10s 告警）
├─ instantaneous_ops_per_sec（QPS 突降说明有问题）
├─ used_memory / maxmemory（> 80% 告警）
├─ rejected_connections（连接被拒）
├─ blocked_clients（阻塞客户端数）
├─ latest_fork_usec（fork 耗时，> 100ms 告警）
├─ mem_fragmentation_ratio（碎片率）
└─ cluster_state（ok / fail）

用 Prometheus + redis_exporter + Grafana，配 5 级告警

③ 切换层：自动故障转移

哨兵配置关键点：
sentinel monitor mymaster <ip> <port> 2      # quorum=2
sentinel down-after-milliseconds mymaster 5000   # 5秒判定SDOWN
sentinel failover-timeout mymaster 60000         # 60秒超时
sentinel parallel-syncs mymaster 1               # 一次只同步1个从库

⚠️ 重要：客户端必须实现「哨兵感知」
   - Jedis: JedisSentinelPool
   - Lettuce: RedisSentinelConfiguration
   不要硬编码 master IP！否则切了主客户端不知道

④ 降级层：兜底方案

Redis 全挂时的三级兜底：
L1: 本地缓存（Caffeine）—— 顶住 30% 请求
L2: 静态兜底数据（本地文件）—— 返回默认值/热门数据
L3: 限流 + 友好提示 —— 保护 DB，快速失败

🎯 加分点（这是专家的回答）：「高可用设计有三个反直觉的真相：

  1. 『高可用』不等于『不丢数据』。 哨兵能在 10 秒内切主（高可用），但主库宕机前没同步的数据会丢（RPO > 0）。要 RPO=0 必须 appendfsync always + 同步复制，性能会掉一个数量级。这是必须和业务方确认的取舍。
  2. 『脑裂』比『宕机』更可怕。 网络分区时，如果旧主库还在接受写入，会产生两个「真相」。必须配 min-replicas-to-write，让隔离的主库主动拒绝写入。
  3. 客户端不感知故障转移 = 没有高可用。 我见过很多团队配了哨兵，但客户端硬编码了 master IP，切主后所有请求打到旧主库（现在是只读从库），全部报 READONLY 错误。必须用 SentinelPool / ClusterClient，并在压测时真的 kill 掉主库验证。」
54. 跨机房（异地多活）的 Redis 怎么设计？L4

先明确：Redis 官方不支持多主（Multi-Master），所以异地多活要自己做。

方案一：单向同步（主备机房）—— 最简单

┌─────────────┐          ┌─────────────┐
│  机房A（主） │ ──异步──> │  机房B（备） │
│  Cluster    │  复制    │  Cluster    │
│  读写       │           │  只读       │
└─────────────┘           └─────────────┘
        ↑
     所有流量

优点：简单，一致性靠 Redis 原生复制
缺点：机房A挂了，机房B要人工/自动提升为主
     跨机房复制延迟高（同城 1-5ms，异地 30-100ms）

方案二：双写 + 冲突解决 —— 真双活

// 业务层双写两个机房
public void set(String key, String value) {
    // 并行双写，任一成功即可（用 CompletableFuture）
    CompletableFuture<Void> f1 = CompletableFuture.runAsync(
        () -> redisA.set(key, value));
    CompletableFuture<Void> f2 = CompletableFuture.runAsync(
        () -> redisB.set(key, value));
    // 等两个都完成（或超时）
    CompletableFuture.allOf(f1, f2).join();
}

// 冲突解决：依赖业务语义
// - 如果是覆盖写（SET），用「最后写入胜」（靠时间戳）
// - 如果是计数（INCR），必须用 CRDT 或统一到一个机房计数

方案三：单元化（大厂主流）

按用户维度分片，每个单元（机房）只服务一部分用户：
┌──────────────┐        ┌──────────────┐
│  机房A        │        │  机房B        │
│  用户 0-4999  │        │  用户 5000+   │
│  Redis A     │        │  Redis B     │
│  （完整服务）  │        │  （完整服务）  │
└──────────────┘        └──────────────┘
        │                        │
        └──── 元数据同步 ────────┘

用户5000访问机房A → 网关路由到机房B
关键：数据不跨机房，天然无冲突

优点：无冲突、延迟低、能做真双活
缺点：架构复杂、资源利用率低（要留冗余）

跨机房复制的三个技术难题：

难题说明应对
① 延迟异地带宽有限 + RTT 高（30-100ms）只同步必要数据；用增量同步；带宽 QoS 保障
② 带宽成本跨机房流量贵，且全量同步会打满带宽调大 repl-backlog-size 避免全量；压缩
③ 脑裂机房之间网络断开，两边都认为自己是主用「多数派」仲裁；必要时人工介入

🎯 加分点：「说实话，Redis 做异地多活是很痛苦的，因为官方没有多主方案。 我们的实践是：

  1. 核心数据不做异地多活，用「同城双活 + 异地备份」。 同城双机房（延迟 < 3ms），异地的只做冷备（只为容灾，不承载流量）。
  2. 非核心数据用单元化。 比如用户 Session 按 userId 分片到不同机房，天然隔离。
  3. 数据同步用 DTS（数据传输服务）而不是 Redis 原生复制。 阿里云 DTS、美团 DTS 支持跨机房、断点续传、冲突检测，比裸复制可靠得多。

最重要的一点：异地多活要先问业务值不值。 双活的成本是单机房的 2-3 倍（冗余 + 复杂性），但收益是「机房级故障不中断」。如果业务 SLA 是 99.9%（年停机 8.7 小时），双活完全没必要；如果是 99.99%，才需要认真考虑。」

55. 如何给 Redis 做容量规划？L4

容量规划四步法：

Step 1：算内存

总内存 = 数据量 × 单条开销 × (1 + 碎片率) × (1 + 预留系数)

示例：1000 万用户信息，每个 value 1KB
├─ 原始数据：1000万 × 1KB = 10GB
├─ key 开销：平均 30 字节 → 300MB
├─ redisObject 开销：16 字节 → 160MB
├─ dictEntry + SDS 头部：约 50 字节 → 500MB
├─ 小计：约 11GB
├─ 碎片率 1.3：14.3GB
├─ fork 预留（COW 最坏翻倍）：需要 28GB 可用内存
└─ 结论：单机 32GB 内存，单实例控制在 14GB 数据以内

⚠️ 关键：fork 时的 COW 会复制页面，最坏情况内存翻倍
   所以 maxmemory 不能设成机器内存，要留 50% 给 fork

Step 2：算 QPS

峰值 QPS = 日活 × 人均请求数 × 峰值系数 / 86400

示例：
├─ 日活 100 万，人均 50 次请求 = 5000 万请求/天
├─ 平均 QPS = 5000万 / 86400 ≈ 580
├─ 峰值系数 10（电商业务峰谷比大）→ 5800 QPS
├─ 单实例能力 8 万 QPS → 1 个实例绰绰有余
└─ 但要考虑：读写比、大key影响、命令复杂度

通常：单实例 5-8 万 QPS 是安全线

Step 3：算分片数

分片数 = max(内存需求 / 单实例上限, QPS 需求 / 单实例能力)

示例：
├─ 内存：100GB / 16GB = 6.25 → 7 个分片
├─ QPS：50万 / 8万 = 6.25 → 7 个分片
├─ 取 max(7, 7) = 7
└─ 但考虑冗余，配 8 主 8 从

⚠️ 分片数建议取 2 的幂或整数，便于后续扩容时均分
⚠️ 槽数 16384 是固定的，分片数不能太多（否则每片槽太少）

Step 4：算带宽

带宽 = 峰值 QPS × 平均请求/响应大小 × 2（收发）

示例：
├─ 峰值 50 万 QPS（整个集群）
├─ 平均请求 200B + 响应 1KB = 1.2KB
├─ 带宽 = 50万 × 1.2KB × 2 = 1.2 GB/s ≈ 9.6 Gbps
└─ 结论：需要万兆网卡（10GbE）

⚠️ 主从复制还要额外消耗带宽！
   如果写入 5万 QPS × 1KB = 50MB/s 的复制流量
   要单独预留带宽，否则复制会拖慢主库

🎯 加分点：「容量规划里最容易被忽略的是『fork 的内存预留』。很多人把 maxmemory 设成机器内存的 80%，结果 BGSAVE 时 COW 让内存翻倍，直接被 OOM Killer 干掉。

我们的规范是：maxmemory ≤ 机器内存 × 50%。32GB 机器，maxmemory 最多 16GB。看起来浪费，但这是保命的。

还有一个经验值：单实例内存最好控制在 10GB 以内。因为这个量级下 fork 耗时在 100ms 内（可接受），全量同步一个从库约 30 秒（可接受）。20GB 以上，fork 就到几百毫秒，会出现明显的延迟尖刺。

最后提醒：容量规划不是一次性的。 要定期（每季度）复盘：实际内存增长曲线 vs 预测，QPS 峰值变化，识别哪些业务在快速增长。我们有个「Redis 容量看板」，能看到每个业务的增速和剩余容量。」

56. AOF 重写（rewrite）是怎么做的？会阻塞吗？L4

为什么需要重写：AOF 是「追加命令日志」，如果对一个 key 做了 100 次 INCR，AOF 就有 100 条命令。重写后会合并成 SET key 100 一条。

重写的完整流程：

  1. fork 子进程（和 BGSAVE 一样）。子进程拥有 fork 时刻的数据快照。
  2. 子进程遍历内存，把每个 key 的当前值转成最少的写命令，写入新的 AOF 临时文件。
  3. 父进程同时把新收到的写命令，追加到：
    • 旧的 AOF 文件（保证不丢）
    • AOF 重写缓冲区（aof_rewrite_buf，这是关键）
  4. 子进程完成后，通知父进程。父进程把 AOF 重写缓冲区的内容追加到新 AOF 文件末尾。
  5. 原子替换：用新 AOF 文件替换旧文件。

会阻塞吗？会，但很短：

阶段是否阻塞原因
fork阻塞（几十~几百 ms）复制页表
子进程重写不阻塞子进程独立工作
写入 aof_rewrite_buf不阻塞内存操作
追加缓冲区到新文件可能阻塞要看缓冲区大小
rename 替换几乎不阻塞文件系统原子操作

7.0 的 Multi-Part AOF 改进（重要）：

老版本（单文件 AOF）：
├─ 重写时要生成一个完整的新文件
├─ 如果 AOF 有 50GB，就要写 50GB 临时文件
├─ 磁盘空间要 2 倍，且写入耗时长
└─ 重写期间若崩溃，整个文件可能损坏

7.0 Multi-Part AOF：
├─ manifest 文件（清单）
├─ base.rdb / base.aof（基础快照，全量）
├─ incr.aof（增量命令）
└─ 重写时只需合并成新的 base，不用重写全部

优势：
├─ 磁盘占用更少（不用 2 倍空间）
├─ 重写更快
├─ 崩溃恢复更安全（文件小，损坏范围小）

触发重写的条件：

auto-aof-rewrite-percentage 100    # 增长100%时触发
auto-aof-rewrite-min-size 64mb     # 且文件至少64MB

# 例：当前AOF是100MB，增长到200MB时触发重写
BGREWRITEAOF                       # 手动触发

# ⚠️ 注意：7.0 默认开启 AOF，如果不配 auto-aof-rewrite，
#    某些场景下 AOF 会无限增长

🎯 加分点：「AOF 重写最大的坑是『重写期间的写入放大』。因为父进程要把新命令同时写到旧 AOF 和重写缓冲区，等于写两份。如果重写期间写入压力很大，旧 AOF 会快速增长，可能触发「重写风暴」——重写还没完成，又触发了下一次重写。

我们的对策是：

  1. 调大 auto-aof-rewrite-percentage（我们设 200%），减少重写频率。
  2. 监控 aof_rewrite_in_progress，如果长期是 1，说明重写卡住了。
  3. 控制单实例大小（10GB 以内），这样重写很快（几十秒）。
  4. 用 Multi-Part AOF（7.0+），从根本上减少重写成本。

另外一个重要认知：『RDB 和 AOF 不能互相替代』。 RDB 负责「快速恢复」（加载快），AOF 负责「少丢数据」（增量）。生产环境用混合持久化，两者兼得。」

57. 说一下 Redis 的 RESP 协议，为什么它比 HTTP 快？L4

RESP（REdis Serialization Protocol）：Redis 的客户端-服务端通信协议，设计目标是简单、可读、解析快。

五种数据类型（首字节标识）：

类型首字节格式示例
Simple String++OK\r\n
Error--ERR unknown command\r\n
Integer::1000\r\n
Bulk String$$6\r\nfoobar\r\n
Array**2\r\n$3\r\nfoo\r\n$3\r\nbar\r\n

RESP3（6.0+）新增：%（Map）、~（Set）、>（Push）、_（Null）、#（Boolean）、,（Double）。解决了 RESP2 无法区分「空数组」和「空字符串」等歧义。

为什么 RESP 比 HTTP 快：

维度HTTPRESP
header 大小几百字节（User-Agent、Cookie、Accept...）0 字节，没有 header
解析要考虑 header 分割、chunked、gzip按首字节 + \r\n 分割，状态机极简
连接复用HTTP/1.1 要 keep-alive，HTTP/2 要多路复用长连接，天然多路复用（按顺序响应）
语义REST 风格（GET/POST/PUT/DELETE）命令 + 参数，无冗余
文本/二进制通常文本（JSON）二进制安全（Bulk String 带长度）

一个实际对比：

HTTP 请求：
POST /api/cache HTTP/1.1\r\n
Host: redis.example.com\r\n
User-Agent: Java/1.8\r\n
Content-Type: application/json\r\n
Content-Length: 25\r\n
\r\n
{"key":"user:1","cmd":"GET"}
总计约 150 字节

RESP 请求：
*2\r\n$3\r\nGET\r\n$6\r\nuser:1\r\n
总计 25 字节

差距：6 倍

🎯 加分点：「Redis 的单线程模型能跑到 10 万 QPS，RESP 的极简解析是重要原因之一。对比 MySQL 的协议——MySQL 协议复杂得多（握手、认证、prepare、execute），单条查询的协议开销就有几十微秒。Redis 的解析器是个状态机，处理一个 GET 请求只需几百纳秒，几乎可以忽略不计。

另外要提一点：RESP3 是 6.0 引入的，但默认还是 RESP2。 需要客户端显式协商（Lettuce 支持 HELLO 3）。RESP3 的价值主要在客户端能做更精确的类型映射（比如 Map 直接映射成 Java Map，不用自己解析数组）。」

58. 什么情况下 Redis 会成为系统瓶颈？怎么突破？L4

识别五个瓶颈点（按出现顺序）：

瓶颈特征突破方案
① 单线程 CPU单核 100%，QPS 上不去开 IO 多线程；水平分片（多实例）
② 内存上限used_memory 接近 maxmemory，开始淘汰Cluster 分片；内存优化（压缩 value）
③ 网络带宽网卡打满，延迟上升减少响应大小（只取需要的字段）；升级网卡
④ 单 key 热点某分片 CPU 远超其他本地缓存；key 复制；读写分离
⑤ 大 key 阻塞延迟尖刺，SLOWLOG 有记录拆 key；用 SCAN/HSCAN 分批

突破的三个层次：

层次一：优化现有（成本最低）

# 1. 开 IO 多线程
io-threads 6
io-threads-do-reads yes    # 需压测决定

# 2. 关闭不必要的开销
# - 关闭 THP
# - 合理设置 hz（默认10，太高浪费CPU，太低过期不及时）

# 3. 减少网络往返
# - 用 Pipeline 批量
# - 用 Lua 合并多命令
# - 用 MULTI/EXEC

# 4. 客户端优化
# - Lettuce 共享连接（Jedis 每线程一连接，连接数爆炸）
# - 合理设置连接池

# 5. 减少数据量
# - 用 HASH 代替多个 String（省 key 开销）
# - 用 protobuf 代替 JSON
# - 精简 key 名

层次二：水平扩展

读扩展：
├─ 加从库 + 读写分离（READONLY）
├─ 本地缓存（Caffeine）—— 最有效
└─ 多个只读副本 + 负载均衡

写扩展：
├─ Cluster 分片（按 key 分散）
├─ 业务层分片（如按 userId 路由到不同实例）
└─ 写合并（把多次 INCR 合并成一次批量）

⚠️ 注意：分片能扩展「整体能力」，不能解决「单 key 热点」

层次三：架构替换（成本最高）

场景替代方案理由
海量 KV（TB 级）Redis on Flash / 阿里云 Tair内存成本太高，用 SSD 做二级存储
持久化 MQKafka / RocketMQRedis 内存有限，不适合堆积
复杂查询Elasticsearch / ClickHouseRedis 只支持 key 查询
强一致 KVetcd / TiKVRedis 是 AP
大 value（图片、文件）对象存储（S3/OSS）Redis 存大对象成本极高

🎯 加分点：「我的经验是『先优化，再扩展，最后替换』，因为成本递增。

但有个反直觉的点：很多时候瓶颈不在 Redis，而在客户端或网络。 我遇到过「Redis 慢」的案例，最后一查是：

  1. 客户端用的是 Jedis，每个线程一个连接，200 个线程 = 200 个连接，连接数太高导致 Redis 上下文切换频繁。换成 Lettuce 共享连接后 QPS 翻倍。
  2. 客户端没有配连接池，每次请求都新建连接（三次握手 + 认证）。加连接池后延迟从 5ms 降到 0.5ms。
  3. 序列化用 JDK 序列化，一个 1KB 的对象序列化成 3KB。换 protobuf 后网络流量降 60%。

所以我排查 Redis 性能问题时，一定先看客户端配置，再看 Redis 本身。 这个顺序很重要，能省很多冤枉路。」

59. 如果要在 Redis 里存 10 亿条数据，你会怎么设计？L4

先算账（架构师的第一反应）：

10 亿条 × 每条平均 500 字节 = 500 GB
├─ 加 key 和对象开销：约 600 GB
├─ 加碎片率 1.3：约 780 GB
└─ 加 fork 预留：需要 1.5 TB 可用内存（峰值）

结论：单机绝无可能，必须 Cluster 分片

分片方案：

方案A：Redis Cluster（大集群）
├─ 每分片 16GB，需 780 / 16 ≈ 49 个分片
├─ 建议 64 主 64 从（取整，便于槽分配）
├─ 问题：节点太多，Gossip 通信是 O(N²)
│        64 节点的心跳风暴会消耗大量带宽
└─ 可行但运维复杂

方案B：客户端分片（多套独立 Cluster）
├─ 业务层按 key 前缀路由到不同 Cluster
├─ 每个 Cluster 16 主 16 从
├─ 4 个 Cluster = 64 主
├─ 优势：每个 Cluster 独立，故障隔离
├─ 劣势：业务层要维护路由逻辑，扩缩容麻烦

方案C：分层存储（最推荐）
├─ 热数据（20%，占 80% 访问）→ Redis（内存）
├─ 温数据（30%）→ Redis on Flash / Tair（SSD）
├─ 冷数据（50%）→ MySQL / 对象存储
└─ 用 LRU 或业务规则定期把冷数据下沉

数据建模要点（这才是关键）：

要点做法收益
① 用 Hash 聚合小对象10 个相关字段存一个 Hash，而不是 10 个 String省 90% 的 key 开销和 redisObject 开销
② 控制单 value 大小用 protobuf 压缩；只存必要字段省 50%+ 内存
③ 用 Bitmap / HLL布尔值、计数场景不要用 Set省 99% 内存
④ 合理 TTL所有 key 都设过期，且 TTL 分散自动淘汰冷数据
⑤ key 名精简但可读u:1:p 而非 user:1:profile10 亿 key 省几十 GB

必须考虑的问题（专家视角）：

  1. 全量同步怎么办？ 16GB 数据全量同步一个从库要几分钟，期间主库 fork + COW 压力大。对策：从库预热（先从其他从库复制）+ 低峰期加从库。
  2. 扩容怎么做？ 加节点要迁移槽，迁移 10 亿 key 中的一部分，耗时长且影响性能。对策：提前预留 30% 容量；用 --cluster rebalance 渐进迁移；选低峰期。
  3. 监控怎么做？ 64 个节点，每个都要监控。对策：Prometheus + redis_exporter + 统一的 Grafana 大盘；告警聚合（不要 64 个节点告 64 次）。
  4. 成本怎么控？ 780GB 内存，按 1GB 内存 30 元/月算，月成本 2.3 万。对策：冷热分离，把 50% 冷数据下沉到 MySQL，内存成本降一半。

🎯 加分点（这是 P8 级别的思考）：「我会先反问：『这 10 亿条数据，全部都需要用 Redis 吗？』

这是最关键的问题。10 亿条数据如果是「用户画像」这种，80% 的访问集中在 20% 的热门用户上。正确的做法不是「怎么存 10 亿条」，而是「怎么只存那 2 亿条热的」。

具体做法：

  1. 大数据侧跑离线任务，统计每个 key 的访问频率（比如过去 7 天）。
  2. 只把 Top 20% 的热数据灌进 Redis，其余留在 HBase/MySQL 或存 HDD。
  3. 访问冷数据时，走一个「回源 + 预热」的异步流程（用户第一次访问稍慢，然后把数据提升到 Redis）。

这样 Redis 只需要 156GB（2 亿条），成本降 75%，而命中率可能还有 90%+（因为 80% 的访问集中在热数据）。这是典型的『用业务特征降维，而不是用技术硬扛』。」

60. 总结：一个资深 Redis 工程师应该具备哪些能力？L4

四层能力模型（可以对照自评）：

层级能力对应年限
L1 会用掌握常用命令、会配连接池、会写缓存代码、知道五种数据结构1-3 年
L2 懂原理能讲清底层结构、持久化、主从、哨兵、Cluster 原理；能排查常见问题（大key、慢查询、内存）3-5 年
L3 能设计能设计缓存架构、分布式锁、热点治理、限流方案；能定位线上复杂故障；能给出容量规划5-8 年
L4 能权衡能在一致性/性能/成本间做取舍；能判断何时不该用 Redis；能设计跨机房架构；能主导技术选型和演进8-12 年

五个必须刻进本能的原则：

  1. Redis 不是数据源，是可丢弃的加速层。 任何「Redis 挂了就完蛋」的设计都是错的。所有数据必须能从 DB 重建。
  2. 所有调用必须有超时和降级。 无限等待、异常直接抛——这两个是线上事故的常见根因。
  3. 单线程模型决定了「一个慢命令阻塞所有人」。 所以 SLOWLOG、大 key 治理、禁用 KEYS 是纪律而非建议。
  4. 分布式锁不能保证正确性，正确性必须由 DB 兜底。 锁只是「提高效率」，不是「保证正确」。
  5. 先量化，再优化。 内存多少？QPS 多少？延迟多少？瓶颈在哪？没有数据的优化都是猜。

三个常见的能力陷阱：

陷阱表现纠正
