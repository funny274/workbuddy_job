Day4.1 · 缓存三大问题与双写一致性

一句话结论

缓存治理的四个关键词：穿透（查不到）→ 空值缓存 / 布隆过滤器、击穿（单个热点 key 失效）→ 互斥重建 / 逻辑过期、雪崩（大批 key 同时失效）→ 过期时间打散 / 多级缓存、一致性（缓存与 DB 不同步）→ Cache Aside + 延时双删 / Canal 订阅 binlog。

面试真正拉分的地方不是背这四句话，而是：① 为什么「先删缓存再更新 DB」是危险的；② 延时双删的「延时」到底该延迟多久；③ 缓存一致性到底要不要做到强一致（答案：绝大多数场景不需要，但你要说清代价）。

1. 为什么需要缓存：一次容量推算

先算清楚缓存给你带来什么，才能在面试里说清「成本收益」。

指标MySQL（单实例）Redis（单实例）倍数
读 QPS约 3,000 ~ 8,000约 100,000+（简单命令）约 20-50×
写 QPS约 3,000 ~ 5,000约 100,000+约 20-30×
P99 延迟1 ~ 10 ms（含网络）0.3 ~ 1 ms约 10×
成本高（磁盘、主从、高配）低（内存为主）—
🚨 一个真实的比例：90% 读 + 10% 写

互联网业务的典型读写比是 9:1 甚至 99:1。假设 QPS 是 10 万，读 9 万、写 1 万。
不加缓存：9 万读全打到 MySQL，需要至少 15 台 MySQL（按 6000 QPS/台）。
加缓存且命中率 95%：只剩 4500 读打到 MySQL，1 台数据库就够了。
结论：缓存的价值 = 用 1/10 的成本扛住 10 倍的流量。但前提是命中率高——这就引出下面的三大问题。

2. 缓存穿透：查一个「不存在」的数据

✅ 定义与本质

定义：请求查询一个数据库里根本不存在的数据。因为不存在，所以缓存里也永远没有（正常流程是「查缓存没有 → 查 DB → 写缓存」，DB 也查不到，于是不会写缓存）。结果每次请求都穿透到 DB。

本质：缓存「拦截住了有数据的请求，但拦截不住无数据的请求」。所以穿透攻击的杀伤力在于——恶意请求可以完全绕过缓存，直接打 DB。

典型攻击：用一个脚本疯狂请求 GET /user/999999999999（ID 不存在）。如果 QPS 是 100 万，DB 直接被打死。

区别于「缓存击穿」：穿透 = 数据根本不存在；击穿 = 数据存在但缓存失效了。这是两个最容易被混淆的概念。

方案一：缓存空值（最简单，首选）

/**
 * 缓存空值方案：DB 查不到时，缓存一个特殊值（如空字符串），并设置较短的过期时间
 */
public User getUser(Long userId) {
    String key = "user:" + userId;
    String cached = redis.get(key);

    // ① 命中缓存（含"空值"这个特殊标记）
    if (cached != null) {
        if (EMPTY_FLAG.equals(cached)) {
            return null;   // 明确的"空"，直接返回，不查 DB
        }
        return JSON.parseObject(cached, User.class);
    }

    // ② 回查 DB
    User user = userMapper.selectById(userId);

    if (user == null) {
        // ③ DB 也没查到 → 缓存空值，过期时间要短（30~60 秒）
        redis.setex(key, 60, EMPTY_FLAG);
        return null;
    }

    // ④ 正常数据缓存，过期时间较长（30 分钟 ~ 数小时）
    redis.setex(key, 1800, JSON.toJSONString(user));
    return user;
}
⚠️ 缓存空值的两个关键细节
  1. 空值的过期时间必须远小于正常值（比如正常 30 分钟、空值 60 秒）。
    原因：数据可能后来被创建了。如果空值缓存 30 分钟，那这段时间内新注册的用户一直查不到。60 秒是一个经验值——既能挡住主要的攻击流量，又能容忍数据延迟。
  2. 空值占内存。如果攻击者用大量不同的随机 ID 攻击，会写入海量的空值 key，把内存打满（这本身变成了一种攻击）。
    对策：① 空值加随机前缀，便于批量清理；② 增加 key 数量告警；③ 对明显异常的请求（ID 格式非法、超范围）直接在最外层拦截，不要进 Redis；④ 用布隆过滤器挡在最前面。

方案二：布隆过滤器（海量数据场景）

✅ 布隆过滤器原理（面试必答）

数据结构：一个很长的位数组（bitmap）+ K 个独立的哈希函数。

写入：对元素 x 用 K 个哈希函数算出 K 个位置，把这 K 位都置 1。

查询：对元素 y 用同样的 K 个哈希函数算出 K 个位置，只要有任意一位是 0，就说明 y 一定不存在；如果全是 1，说明 y 可能存在（因为有可能是别的元素把这些位置置 1 的——这就是误判）。

核心特性（必须背下来）：

  • ✅ 说不存在 → 一定不存在（零假阴性）
  • ❌ 说存在 → 可能不存在（有假阳性 / 误判率）
  • ✅ 空间极省：1 亿个元素、1% 误判率，只需约 114 MB（11.4 bit/元素）；如果用 HashSet 存 1 亿字符串，至少要几 GB。
  • ❌ 不支持删除（把某位置 0 会影响其他元素）——除非用 Counting Bloom Filter（每个位置用计数器）
  • ❌ 不支持更新，只能重建

误判率公式（面试加分）：
设位数组长度 m、哈希函数个数 k、元素个数 n，则误判率约为：
P ≈ (1 - e^(-kn/m))^k
最优的哈希函数个数是 k = (m/n)·ln2 ≈ 0.7·(m/n)。

########## Redis 8.x 原生布隆过滤器（RedisBloom 已内置）##########
# 注意：Redis 8.0 起，RedisBloom（含 Bloom / Cuckoo / TopK / CMS / TDigest）
#      已作为内置模块集成，无需单独编译加载

# 创建：误判率 1%，容量 100 万
BF.RESERVE user:filter 0.01 1000000

# 添加（user:filter 不存在会自动创建）
BF.ADD user:filter 1001
BF.MADD user:filter 1002 1003 1004

# 判断是否存在
BF.EXISTS user:filter 1001     # 1 = 可能存在
BF.EXISTS user:filter 9999     # 0 = 一定不存在 ✅
BF.MEXISTS user:filter 1001 9999

# 查看信息（用了多少位、误判率）
BF.INFO user:filter

########## 布隆过滤器在业务里的位置 ##########
# 请求流：客户端 → 布隆过滤器 → 缓存 → DB
#   ① 布隆过滤器说不存在 → 直接返回，DB 完全不感知 ✅
#   ② 布隆过滤器说可能存在 → 继续走缓存 → DB（此时几乎都是真数据）
🚨 布隆过滤器的三个工程坑（面试官爱追问）
  1. 数据新增怎么办？ 用户注册后必须同步把新 ID 加进布隆过滤器。如果漏了，就会出现「用户存在但过滤器说不存在」——这才是真正的故障（相对而言，误判为「可能存在」只是多查一次 DB，无害）。
    所以：必须保证「写入 DB 成功后，一定写入布隆过滤器」，一般用「先写 DB，再写 Bloom，写 Bloom 失败就重试 + 告警」。
  2. 数据删除怎么办？ 布隆过滤器不支持删除。所以只能用「只会新增不会删除」的数据集（如用户 ID、商品 ID）。
    如果需要支持删除 → 用 Cuckoo Filter（Redis 8 的 CF.* 命令），它支持删除，空间效率也不错。
  3. Redis 重启后布隆过滤器会丢。 因为它是模块数据，需要 RDB/AOF 持久化。Redis 8 的模块数据支持持久化，但要确认配置正确。
    生产建议：① 开启 AOF；② 或者用「启动时从 DB 全量重建」的兜底方案（1 亿数据重建约需要几十秒到几分钟，可接受）；③ 重建期间降级为「直接查缓存 + DB」。

加分回答：「我们在生产里用的是分层过滤——最外层用布隆过滤器挡掉 99% 的无效请求，再往里是空值缓存兜底。即使布隆过滤器因为重启丢失了，空值缓存也能撑住一段时间，给我们重建的时间窗口。这种『双保险』的思路在大厂很常见。」

3. 缓存击穿：热点 key 突然失效

✅ 定义与本质

定义：某个被高频访问的热点 key 突然过期（或因为淘汰被删掉），此时大量并发请求同时发现「缓存没了」，于是全部涌向 DB 去重建缓存，DB 瞬间被打爆。

关键词是「同时」。如果只有 1 个请求来重建，那没问题；问题是 1 万个请求同时来。所以击穿的本质是「缓存重建时的并发失控」。

典型场景：首页秒杀商品详情、明星微博主页、大促主会场配置。这类数据的特点是「访问量极大 + 缓存失效的瞬间就是灾难」。

方案一：互斥锁重建（Mutual Exclusion，最常用）

/**
 * 互斥锁方案：保证只有一个线程去重建缓存，其他线程等待后读缓存
 * 优点：实现简单，一致性好
 * 缺点：等待线程会阻塞，吞吐量受限于"重建耗时"；持锁线程挂了要有兜底
 */
public User getUserWithMutex(Long userId) {
    String key = "user:" + userId;
    String cached = redis.get(key);
    if (cached != null) {
        return EMPTY_FLAG.equals(cached) ? null : JSON.parseObject(cached, User.class);
    }

    // 缓存未命中 → 尝试抢锁（只让一个线程去查 DB）
    String lockKey = "lock:user:" + userId;
    // SET NX + 过期时间，保证原子性（详见 Day4.2 分布式锁）
    boolean locked = redis.setIfAbsent(lockKey, "1", Duration.ofSeconds(10));

    if (!locked) {
        // 没抢到锁 → 等待一小会儿再重试读缓存（自旋）
        try {
            sleep(50);
            String retry = redis.get(key);
            if (retry != null) {
                return EMPTY_FLAG.equals(retry) ? null : JSON.parseObject(retry, User.class);
            }
        } catch (InterruptedException e) {
            Thread.currentThread().interrupt();
        }
        // 重试仍无数据 → 走降级（返回兜底数据 / 直接查 DB，视业务容忍度）
        return fallback(userId);
    }

    try {
        // 二次检查（Double Check）：可能在等锁期间别人已经重建好了
        String again = redis.get(key);
        if (again != null) {
            return EMPTY_FLAG.equals(again) ? null : JSON.parseObject(again, User.class);
        }

        User user = userMapper.selectById(userId);
        if (user == null) {
            redis.setex(key, 60, EMPTY_FLAG);
            return null;
        }
        redis.setex(key, 1800, JSON.toJSONString(user));
        return user;
    } finally {
        // ⚠️ 释放锁要用 Lua 保证"判断是自己的锁才删"（详见 Day4.2）
        redis.eval(UNLOCK_SCRIPT, Collections.singletonList(lockKey), "1");
    }
}

方案二：逻辑过期（Logical Expiration，高并发首选）

✅ 逻辑过期：不设 TTL，把过期时间写进 value

核心思想：key 永不物理过期，而是在 value 里存一个逻辑过期时间字段。查询时判断逻辑时间是否过期：

  • 未过期 → 直接返回（绝大多数情况）
  • 已过期 → 仍然返回旧数据（保证不阻塞），同时异步开一个线程去重建缓存并更新逻辑过期时间

优点：没有任何请求需要等待——所有请求都立刻拿到数据（哪怕短暂是旧数据）。吞吐量远高于互斥锁方案。

缺点：牺牲了强一致性，重建期间返回旧数据。所以只适用于「能接受短暂旧数据」的场景（商品详情、排行榜、配置）。金融余额、库存这类绝对不能用。

另一个坑：需要在业务层感知「逻辑过期时间」这个字段，对数据结构有侵入。

/**
 * 逻辑过期方案：value 里带 expireTime，永不过期
 */
// 存储结构（Redis Hash 或 JSON 字符串）
// { "data": {...业务数据...}, "expireTime": 1759161600000 }

public User getUserWithLogicalExpire(Long userId) {
    String key = "user:logic:" + userId;
    String cached = redis.get(key);

    // ① 缓存从未建立 → 走互斥锁方案兜底（只有第一次）
    if (cached == null) {
        return getUserWithMutex(userId);
    }

    CacheData<User> data = JSON.parseObject(cached, new TypeReference<CacheData<User>>() {});

    // ② 逻辑时间未过期 → 直接返回
    if (data.getExpireTime().after(new Date())) {
        return data.getData();
    }

    // ③ 逻辑时间已过期 → 尝试异步重建（抢到锁的那个线程去重建）
    if (redis.setIfAbsent("lock:rebuild:" + userId, "1", Duration.ofSeconds(10))) {
        REBUILD_EXECUTOR.submit(() -> {
            try {
                // 开新事务/新线程，避免和主流程共享事务上下文
                User fresh = userMapper.selectById(userId);
                CacheData<User> newData = new CacheData<>(
                    fresh,
                    Date.from(Instant.now().plus(30, ChronoUnit.MINUTES))
                );
                // ⚠️ 不设 TTL，或设一个很长的 TTL（如 7 天）作为"最终清理"
                redis.set(key, JSON.toJSONString(newData));
            } finally {
                redis.del("lock:rebuild:" + userId);
            }
        });
    }

    // ④ 无论是否抢到锁，都立刻返回旧数据（不阻塞）
    return data.getData();
}

方案三：热点 key 永不过期 + 主动刷新

如果是「少量、可枚举」的超级热点（比如首页配置、大促主会场），最土但最有效的办法是：

  • 不设 TTL（或设超长 TTL）
  • 用定时任务 / 消息通知在数据变更时主动刷新缓存
  • 加本地缓存（Caffeine）做二级缓存，Redis 抖动也不影响
💡 击穿方案的选型话术

「我会按数据量级和一致性要求选：

  • 普通热点 key（比如某个商品详情） → 互斥锁方案。实现简单，一致性有保证，重建耗时一般也就几十毫秒，可接受。
  • 超级热点（百万 QPS，比如明星主页、大促会场） → 逻辑过期 + 本地缓存。因为让一万个线程排队等锁，即使只有一个查 DB，其他线程的排队等待时间本身就是延迟，用户体验差。逻辑过期让所有人立即拿到数据（哪怕旧一点）。
  • 强一致要求（价格、库存） → 不用缓存兜底，直接走「互斥锁 + 短 TTL + 主动刷新」这套保守方案，或者干脆用 DB + 乐观锁。

4. 缓存雪崩：大批 key 同时失效 / Redis 整体不可用

✅ 雪崩有两种形态（面试要说全）

形态一：同一时刻大批 key 同时过期

原因：如果给缓存设置过期时间时用了统一的时长（比如都在凌晨 0 点系统预热、全部设 30 分钟 TTL），那么 30 分钟后这几十万个 key 同时失效，所有请求一起打到 DB。

解法：

  • 过期时间加随机值：TTL = 基础时间 + random(0, 基础时间 × 20%)。这是最简单有效的一招。
  • 分级过期：把 key 分成几组，每组用不同的基础 TTL（如 25、30、35 分钟）。
  • 热点数据永不过期：用主动更新代替被动过期。

形态二：Redis 集群整体挂掉 / 网络分区

原因：Redis 崩了、机房断电、网络抖动导致客户端全部连不上。此时不只是「缓存不命中」，而是「缓存层完全消失」，所有流量同时砸向 DB。

解法（这是真正的架构级方案）：

  • 多级缓存：本地缓存（Caffeine）→ Redis → DB。Redis 挂了，本地缓存还能扛住一部分（缓存一致性问题变大，但可用性提升）。
  • 熔断 / 限流 / 降级：Sentinel / Hystrix / Resilience4j 做熔断，DB 前面加限流；非核心功能直接降级返回兜底数据。
  • DB 层保护：DB 连接池限流、慢查询保护、只读副本分流。
  • Redis 高可用：哨兵 / Cluster + 多可用区部署，避免单机房故障。
  • 预热：大促前把热点数据提前灌进缓存（这时不要给这些 key 设短 TTL，或设长 TTL + 随机值）。
/**
 * 过期时间打散：基础 TTL + 随机扰动
 */
public void setWithJitter(String key, String value, long baseSeconds) {
    // 在基础 TTL 上叠加 ±20% 的随机扰动
    long jitter = ThreadLocalRandom.current().nextLong(-baseSeconds / 5, baseSeconds / 5);
    long ttl = baseSeconds + jitter;
    redis.setex(key, ttl, value);
}

// 批量预热时更要注意：分批次、分时段写入，避免同一批 key 同时过期
for (Product p : products) {
    // 每个 key 的 TTL 都不同，避免"整齐划一地过期"
    setWithJitter("product:" + p.getId(), JSON.toJSONString(p), 3600);
}
🚨 真实故障复盘：某电商大促首分钟雪崩

现象：大促 0 点开抢，第一分钟系统正常，第二分钟开始 DB CPU 飙到 100%，接口大面积超时。

根因：预热脚本在 23:59:30 把 50 万个商品详情 key 一次性写入，TTL 统一设为 1800 秒。于是 30 分 29 秒后，这 50 万个 key 在同一秒集中失效，请求全部穿透到 DB。

教训：

  • 预热脚本必须打散 TTL，并且分批写入（拉长写入时间窗口）。
  • 预热数据的 TTL 应该长于大促时长的 1.5 倍以上，并在大促期间禁止被动过期（改为主动刷新）。
  • 要有「缓存命中率」的实时告警——命中率从 99% 掉到 60%，就是雪崩的前兆信号。

5. 三大问题对比总表（面试速查）

问题本质触发条件解决方案（按推荐度排序）
穿透 查不存在的数据，缓存永远拦不住 恶意攻击 / 非法参数 / 数据被删 ① 参数校验 + 法定范围拦截（最外层）
② 缓存空值（30-60s，短 TTL）
③ 布隆过滤器（海量数据）
④ Cuckoo Filter（需支持删除时）
击穿 单个热点 key 失效，并发重建失控 热点 key 过期 / 被淘汰 / 被主动删除 ① 逻辑过期 + 异步重建（超高并发）
② 互斥锁重建（普通热点）
③ 热点 key 永不过期 + 主动刷新
④ 本地缓存兜底
雪崩 大批 key 同时失效，或缓存层整体消失 统一 TTL / Redis 宕机 / 机房故障 ① TTL 加随机扰动（必做）
② 多级缓存（本地 + Redis）
③ 熔断限流降级
④ Redis 高可用 + 多可用区
⑤ 提前预热（长 TTL）
💡 一句话记忆法

穿透是「没有」，击穿是「一个」，雪崩是「一片」。
穿透 → 数据不存在（挡不住的查询）
击穿 → 一个热点 key（同时重建的压力）
雪崩 → 一片 key 或整个缓存层（系统性失效）

6. 双写一致性：缓存与 DB 怎么同步

✅ 先说结论：一致性是有层级的

面试官问「如何保证缓存和 DB 一致」，如果你直接回答「延时双删」，说明你只是在背方案。正确的回答是先把「一致性」分级：

一致性级别含义做法适用
强一致任何时刻读到的都是最新值分布式锁 / 读写都串行化 / 干脆不用缓存金融余额、库存扣减（性能代价极大）
最终一致短暂不一致，但最终会同步Cache Aside + 延时双删 / Canal 订阅 binlog绝大多数业务（商品、用户、订单查询）
弱一致（可接受）允许较长时间的旧数据定时刷新 / 逻辑过期排行榜、统计报表、配置缓存

关键洞察：「生产上 99% 的场景要的是最终一致，而不是强一致。因为强一致的代价是牺牲缓存的性能优势——那就没必要用缓存了。所以正确的思路是：把「允许不一致的窗口」压缩到业务能接受的范围内（比如 100ms 内），并且设计好兜底机制。」

6.1 四种经典写策略对比

策略做法优点缺点
① 先更新 DB，再更新缓存 UPDATE DB 成功 → SET cache 思路直观 ❌ 并发写会覆盖（A 先更 DB 后更缓存，B 插在中间，缓存最终是 A 的旧值）
❌ 更新缓存可能是无用功（写多读少的场景）
② 先删缓存，再更新 DB DEL cache → UPDATE DB 比 ① 好 ❌ 并发读会写回脏数据：
① 线程A 删缓存
② 线程B 读缓存未命中 → 读 DB（旧值）
③ 线程A 更新 DB
④ 线程B 把旧值写进缓存 → 长期脏数据
③ 先更新 DB，再删缓存
Cache Aside（推荐）		 UPDATE DB → DEL cache ✅ 出现脏数据的概率极低（需要「读请求恰好卡在更新DB前后 + 读比写还慢」） ⚠️ 仍有理论上的极端情况；删除失败会留下脏缓存
④ 更新 DB + 延时双删 DEL cache → UPDATE DB → sleep → DEL cache ✅ 进一步压缩不一致窗口，是③的加强版 ⚠️ 延迟时间难以精确设定；第二次删除可能失败；延迟本身阻塞/占用线程
✅ 为什么「先更新 DB，再删缓存」（Cache Aside）是最优的

核心论证（面试必须说清这个推理链）：

假设并发场景：事务 T1 是「更新」，T2 是「查询读」。极端不利的情况是：

  1. T1：UPDATE DB（写新值）
  2. T2：读缓存 → 未命中
  3. T2：读 DB → 读到新值（因为 T1 已经更新了）〔如果是读旧值才有问题，所以这里要求 T2 的读 DB 发生在 T1 的 UPDATE 之后〕
  4. T1：DEL cache
  5. T2：SET cache（把新值写进去）

这个顺序结果是正确的。要产生脏数据，必须满足：T2 读 DB 发生在 T1 的 UPDATE 之前，但 T2 写缓存发生在 T1 的 DEL 之后。这意味着「T2 的读 DB → 写缓存」整个耗时比 T1 的 UPDATE → DEL 还长。

现实中的情况是：写 DB（带锁、要落盘）通常比读 DB（可能命中索引、走缓存页）慢得多。所以「读的整个链路比写还慢」这件事概率极低。

结论：Cache Aside 的脏数据窗口是「毫秒级且概率极低」，对绝大多数业务完全够用。「概率极低」这个论证本身就是面试的高分点。

6.2 三种工程级落地方案

方案 A：Cache Aside + 删除失败重试

/**
 * 方案 A：先更新 DB，再删缓存 + 删除失败重试（保证最终一致性）
 * 这是最简单也最常用的落地方式
 */
public void updateProduct(Product product) {
    // ① 先更新数据库
    productMapper.updateById(product);

    // ② 再删缓存（注意：是"删除"，不是"更新"）
    String key = "product:" + product.getId();
    try {
        redis.del(key);
    } catch (Exception e) {
        // ③ 删除失败 → 丢进消息队列异步重试（不能吞掉！）
        log.error("缓存删除失败，进入重试队列: {}", key, e);
        mqTemplate.send("cache:delete:retry", key);
    }
}

// 消费者：带重试次数上限，超限告警
@RabbitListener(queues = "cache:delete:retry")
public void onCacheDeleteRetry(String key, Channel channel, @Header(AmqpHeaders.DELIVERY_TAG) long tag) {
    try {
        redis.del(key);
        channel.basicAck(tag, false);
    } catch (Exception e) {
        Map<String, Object> headers = new HashMap<>();
        Integer retry = (Integer) headers.get("retry");
        int count = retry == null ? 1 : retry + 1;
        if (count > 3) {
            // 超过重试上限 → 告警 + 让 key 自然过期，避免无限循环
            alertService.warn("缓存删除重试耗尽: " + key);
            channel.basicAck(tag, false);
        } else {
            headers.put("retry", count);
            channel.basicNack(tag, false, true);
        }
    }
}

方案 B：延时双删（应对「先删缓存再更新 DB」的场景）

/**
 * 方案 B：延时双删
 * 顺序：删缓存 → 更新 DB → 延迟 N 毫秒 → 再删缓存
 *
 * 为什么需要在"更新 DB 前先删一次"？
 *   目的是让"已经读到旧数据的请求"在第二次删除时被清掉，避免它把旧值写回缓存。
 */
public void updateWithDoubleDelete(Product product) {
    String key = "product:" + product.getId();
    long oldVersion = ...;  // 可选的版本号机制

    // ① 第一次删除：清掉旧缓存
    redis.del(key);

    // ② 更新数据库
    productMapper.updateById(product);

    // ③ 延迟后第二次删除：清掉"更新期间被读请求写回的旧值"
    // ⚠️ 关键问题：延迟多久？
    scheduleExecutor.schedule(() -> {
        // 为了更安全，删除前可以做一次"版本比对"：
        //   如果缓存里的值版本 < DB 版本，说明缓存是旧的 → 删
        redis.del(key);
    }, 500, TimeUnit.MILLISECONDS);
}
⚠️ 延时双删的「延时」到底该延迟多久（面试深挖点）

理论上的答案是：「大于『一次读请求的耗时（读缓存 + 读 DB + 写缓存）』」。

工程上的答案是：没有标准答案，只能靠压测和经验值。一般取 200ms ~ 1s。理由是：

  • 如果你延迟太短（如 50ms），可能读请求还没走完，就被你「提前删除」了，然后它又把旧值写回来。
  • 如果你延迟太长（如 5s），那不一致窗口就是 5s 以上，业务可能无法接受。
  • 聪明的做法是「用版本号代替时间猜测」：缓存 value 里带一个 version（来自 DB 的 version 字段或 update_time）。删缓存前先比对——如果缓存里的 version 更旧，才删除或覆盖。

面试加分句：「延时双删的『延时』本质上是一个靠统计推断出来的经验值，不是精确保证。所以它只适合『不一致窗口几百毫秒可接受』的场景。如果要求更严格，我会用版本号比对这个更精确的方案，或者直接上 Canal 订阅 binlog。」

方案 C：Canal 订阅 binlog（大厂主流，最彻底）

✅ Canal：把「缓存失效」变成 DB 变更的副产品

核心思想：应用只负责写 DB，完全不管缓存。Canal 伪装成 MySQL 的从库（发送 dump 协议），实时订阅 binlog，解析出数据变更，然后异步地把变更同步到 Redis。

数据流：
应用 → UPDATE MySQL → binlog → Canal Server → MQ（Kafka/RocketMQ）→ 缓存同步消费者 → 更新/删除 Redis

优势：

  • 业务代码零侵入：不需要在业务代码里写「删缓存」的逻辑，天然避免「忘记删缓存」的 bug。
  • 解耦：缓存同步失败不影响主流程，可以无限重试 + 人工兜底。
  • 可靠：binlog 是 DB 的持久化日志，不丢（只要 binlog 不丢）。
  • 统一治理：所有缓存更新都走同一套链路，方便加日志、监控、灰度。
  • 支持多目标：同一份 binlog 可以同时同步到 Redis、ES、HBase 等多个下游。

缺点：

  • 引入额外组件（Canal Server + MQ + 消费者），运维复杂度上升。
  • 延迟更高：binlog → Canal → MQ → 消费者，端到端延迟通常是几十毫秒到几百毫秒，比「业务代码里直接删缓存」的 ms 级要慢。
  • 需要处理binlog 格式（ROW 模式才能拿到变更前后的完整数据）、DDL 事件等。
  • MQ 积压时缓存会长时间不更新。

# canal.properties（服务端）
canal.instance.master.address=mysql-master:3306
canal.instance.dbUsername=canal
canal.instance.dbPassword=canal_password
canal.instance.filter.regex=.*\\..*          # 订阅所有库表

# instance.properties（目标实例）
canal.instance.mysql.slaveId=1234              # 伪装成从库的 serverId（不能和现有从库冲突！）
canal.instance.filter.regex=mall\\.product,mall\\.order   # 只订阅这两张表
canal.instance.connectionCharset=UTF-8
canal.instance.tsdb.enable=true
/**
 * Canal 消费者：解析 binlog 事件 → 删除对应缓存
 */
@Component
public class CacheSyncConsumer {

    @KafkaListener(topics = "canal-product")
    public void onCanalMessage(String message) {
        CanalMessage msg = JSON.parseObject(message, CanalMessage.class);
        if (!"product".equals(msg.getTable())) return;

        for (CanalRowData row : msg.getData()) {
            String id = row.get("id");
            String key = "product:" + id;

            if ("DELETE".equals(msg.getType())) {
                redis.del(key);
            } else if ("UPDATE".equals(msg.getType())) {
                // 直接删缓存（下次读时重建），而不是更新缓存
                // 为什么删而不是更新？避免"更新时并发读写的覆盖问题"
                redis.del(key);
            } else if ("INSERT".equals(msg.getType())) {
                // 新增：可以选择预热缓存，或什么都不做（等首次读时加载）
                // 一般选择不做，避免写入无用的缓存
            }
        }
    }
}

「我会分三档选：

  1. 业务初期 / 中小系统：直接用 Cache Aside——先更新 DB 再删缓存，加一个「删除失败进 MQ 重试」的兜底。实现成本最低，理论上的脏数据窗口是毫秒级且概率极低，够用。

但无论哪种方案，我都会加三样东西：① 缓存过期时间（最终兜底，即使同步失败也会自愈）；② 缓存命中率监控（不一致往往表现为命中率异常）；③ 关键业务的对账任务（定时比对缓存和 DB）。」

7. 强一致场景的替代思路

✅ 当业务真的需要强一致时（库存、余额）

思路一：不用缓存，让 DB 扛

库存扣减这类操作用 UPDATE stock SET num = num - 1 WHERE id = ? AND num > 0 直接在 DB 做，靠行锁保证原子性。QPS 不够就分库分表 + 热点商品单独处理。

思路二：Redis 作为「唯一数据源」，DB 只做异步落库

库存数字放在 Redis（DECR 是原子的），DB 只做异步持久化 + 对账。这样 Redis 就是强一致的（单线程原子操作），但要求 Redis 高可用做得足够好（否则 Redis 挂了库存就没了）。大厂秒杀常用这套。

思路三：分布式锁 + 串行化

对同一个商品的读和写都加同一把锁，强制串行。性能差，只适合极低频的强一致操作。

思路四：Lua 脚本保证 Redis 侧原子性

把「判断 + 扣减 + 记录」写成一个 Lua 脚本，利用 Redis 单线程执行脚本的特性实现原子性。

-- 库存扣减 Lua 脚本（原子性保证）
-- KEYS[1] = 库存 key, ARGV[1] = 扣减数量
local stock = redis.call('GET', KEYS[1])
if not stock then
    return -1    -- 库存未初始化
end
stock = tonumber(stock)
local need = tonumber(ARGV[1])
if stock < need then
    return -2    -- 库存不足
end
redis.call('DECRBY', KEYS[1], need)
return stock - need    -- 返回剩余库存

面试深度问答

什么是缓存穿透？怎么解决？基础

定义：查询一个数据库里不存在的数据，缓存无法拦截（因为不存在所以也缓存不到），导致每次请求都穿透到 DB。恶意攻击可以利用这点，用无效 ID 高频请求直接打爆 DB。

解决方案（按优先级）：

  1. 参数校验（最外层）：ID 格式非法、超出业务范围（如负数、超过最大 ID）直接拦截，连 Redis 都不查。这是成本最低、最先该做的一层。
  2. 缓存空值：DB 查不到时也写一个空值缓存，TTL 设短（30-60s）。优点是实现简单；缺点是要注意空值占内存、以及数据新增后要等 TTL 过期。
  3. 布隆过滤器：把所有存在的 key 预先加载进布隆过滤器，请求先过过滤器。优点是空间极省，缺点是误判率、不支持删除（需删除场景用 Cuckoo Filter）。
  4. 接口限流 + 黑名单：对同一 IP / 用户的高频异常请求做限流与封禁。

面试加分：说清「穿透和击穿的区别」——穿透是数据不存在，击穿是数据存在但缓存失效。

布隆过滤器的原理？有什么优缺点？进阶

原理：位数组 + K 个独立哈希函数。写入时用 K 个哈希算出 K 个位置并置 1；查询时算出 K 个位置，只要有一个是 0 就说明一定不存在，全是 1 则「可能存在」。

核心特性：

  • 零假阴性：说不存在就一定不存在（这个特性是它能用于「拦截无效请求」的根本原因）。
  • 有假阳性：说存在可能实际不存在，误判率由 m（位数）、n（元素数）、k（哈希函数数）决定，公式 P ≈ (1 - e^(-kn/m))^k。
  • 空间极省：1% 误判率下约 9.6 bit/元素，1 亿元素约 114MB。
  • 不支持删除：因为一个位可能被多个元素共享，置 0 会误伤。

Redis 8 中的用法：RedisBloom 已内置，命令是 BF.RESERVE / BF.ADD / BF.EXISTS / BF.INFO。需要支持删除的场景用 Cuckoo Filter（CF.*）。

工程坑：① 新增数据必须同步写过滤器，否则会误判为不存在（严重故障）；② 重启后需要重建（靠 RDB/AOF 或从 DB 全量重建）；③ 大量随机无效 ID 会撑爆空值缓存或过滤器，需要在最外层做参数与频率校验。

缓存击穿是什么？互斥锁和逻辑过期怎么选？进阶

定义：某个高频访问的热点 key 突然失效，大量并发请求同时发现缓存未命中，全部涌向 DB 重建缓存，DB 被打爆。本质是「缓存重建时的并发失控」。

方案对比：

维度互斥锁重建逻辑过期
一致性好（等锁后拿到新数据）弱（重建期间返回旧数据）
吞吐量受限于重建耗时（其他线程排队等待）高（所有请求立即返回，无等待）
实现复杂度中（需处理锁超时、重试、二次检查）中高（需在 value 里加逻辑过期字段，需要异步线程池）
适用普通热点、强一致要求超级热点（百万 QPS）、可接受短暂旧数据

选型逻辑：普通热点选互斥锁（简单、一致）；超级热点选逻辑过期（不能让一万个线程排队）。关键判断是「重建耗时 × 并发量」——如果排队等待时间本身就不可接受，就必须用逻辑过期。

补充：无论哪种方案，都要有「重建失败」的兜底（返回兜底数据 / 触发告警），以及「锁超时」保护，避免持锁线程挂了导致所有请求都拿不到数据。

缓存雪崩怎么预防？进阶

两种形态要分开说：

形态一：大批 key 同时失效

  • TTL 加随机扰动（必做，最简单有效）：TTL = base + random(-20%, +20%)。
  • 分级 TTL：把 key 分组用不同基础 TTL。
  • 热点数据永不过期 + 主动刷新。

形态二：Redis 整体不可用

  • 多级缓存：Caffeine 本地缓存 → Redis → DB。本地缓存能在 Redis 挂掉时顶一段时间。
  • 熔断降级限流：Sentinel/Resilience4j 熔断，DB 前加限流，非核心功能降级。
  • Redis 高可用：哨兵/Cluster + 多可用区部署。
  • 提前预热：大促前把热点数据灌入缓存，且 TTL 要长于大促时长。

监控是预防的关键：缓存命中率是雪崩的先行指标（从 99% 掉到 60% 就要告警）；DB 的 QPS、连接数、慢查询也要设阈值。

如何保证缓存和数据库的一致性？高级

先分级再说方案（这是高分的关键）：

  • 强一致：任何时刻读到最新值 → 用分布式锁串行化，或干脆不用缓存（用 DB 行锁）。代价是牺牲缓存的性能优势。
  • 最终一致：99% 的业务场景，用 Cache Aside / 延时双删 / Canal。核心是把「不一致窗口」压缩到业务可接受的范围。
  • 弱一致：可接受较长旧数据 → 定时刷新 / 逻辑过期。

为什么「先更新 DB 再删缓存」是最优解：

产生脏数据需要同时满足「读请求读 DB 在 UPDATE 之前」+「读请求写缓存在 DEL 之后」，即「读的整链路比写的整链路还慢」。而写 DB（加锁、落盘）通常远慢于读 DB，所以这个条件概率极低。

三种方案：

  1. Cache Aside + 删除失败重试：先更新 DB 再删缓存，删除失败丢 MQ 重试。最简单，首选。
  2. 延时双删 + 版本号：删缓存 → 更新 DB → 延迟后（200ms-1s）再删。用版本号比对避免「延迟时间靠猜」。
  3. Canal 订阅 binlog：业务只写 DB，Canal 订阅 binlog 异步同步到 Redis。零侵入、最可靠、适合大型系统，代价是引入 Canal + MQ，延迟上升。

无论哪种都要加的三样：① 缓存过期时间（最终自愈兜底）；② 命中率监控；③ 关键业务对账。

为什么是「删除缓存」而不是「更新缓存」？高级

三个理由：

  1. 避免并发覆盖：两个写请求 A、B 依次更新 DB（DB 最终是 B 的值）。但如果是「更新缓存」，A 和 B 更新缓存的操作可能交错——B 先写缓存、A 后写缓存，导致缓存里是 A 的旧值。删除就不会有这个交错问题。
  2. 懒惰重建，避免无用功：如果某数据「写多读少」，每次写都去更新缓存，可能更新了几十次却没人读——纯属浪费。删除缓存后，只有真正有人读的时候才重建。
  3. 避免「值计算复杂」的问题：有些缓存值是多张表 join 或聚合出来的，更新时重新计算成本高，甚至可能算错。删除缓存让「读时重建」用统一逻辑，更安全。

延伸：如果是「写少读多 + 数据量大」的场景（如商品详情），也可以考虑「更新缓存」，但必须配合版本号或加锁。所以标准答案是：默认删除，特殊场景可考虑更新（但要额外机制保证）。

延时双删的「延时」应该设多久？专家

理论答案：大于「一次读请求的完整耗时」（读缓存 + 读 DB + 写缓存）。

工程答案：没有精确值，只能靠压测和经验，一般取 200ms ~ 1s。原因：

  • 延迟太短（如 50ms）→ 读请求可能还没走完就被删除，它随后又把旧值写回来。
  • 延迟太长（如 5s）→ 不一致窗口过长，业务可能不接受。
  • 而且「写请求的耗时」和「读请求的耗时」都是分布，不是定值。为了覆盖极端情况，理论上应该取 P99.9，那延迟就太长了。

更精确的替代方案（加分点）：

  1. 版本号比对：缓存 value 里带上 DB 的 version / update_time。第二次删除前先比对版本，只有「缓存版本落后」才删。这样不依赖时间猜测。
  2. 分布式锁：对同一个 key 的读写加锁串行化，从根本上消除竞态。代价是性能。
  3. Canal：从「时间推断」升级为「基于 binlog 事件驱动」，是更彻底的方案。

结论话术：「延时双删的『延时』是一个靠工程经验给出的近似值，不是精确保证。所以我会用它，但一定会配合『缓存过期 + 命中率监控 + 对账』这几层兜底。如果业务真的要求严格，我会直接上版本号或 Canal。」

缓存和数据库一致性能不能做到强一致？专家

能，但不值。 这是这个问题的正确切入角度。

能做到强一致的方案：

  1. 不用缓存：直接用 DB 事务和行锁。最简单也最可靠，代价是性能。
  2. 分布式锁 / 读写串行化：对同一 key 的所有读写加同一把锁。能做到强一致，但吞吐量大幅下降（锁竞争）。
  3. 2PC / 分布式事务：DB 和 Redis 做两阶段提交。但 Redis 不支持真正的 2PC，实现起来非常脆弱。
  4. Redis 作为唯一数据源：库存放 Redis，DB 只异步落库。Redis 单线程保证原子性，此时 Redis 就是「强一致的」，但一致性范围变成了「Redis 内部」，还要处理 Redis 挂机丢数据的问题（AOF always + 多副本）。

为什么「不值得」：

  • 缓存的全部价值在于「用更低的成本、更高的性能扛读流量」。一旦要求强一致，就必须加锁/串行化，性能优势被吃掉，这时候「用缓存」就失去了意义——还不如直接上更好的 DB。
  • 分布式锁本身也有可用性问题（锁服务挂了），引入了新的失败模式。

正确的工程思路：

  1. 承认最终一致，然后把不一致窗口压缩到业务能接受的范围（如 100ms）。
  2. 用「业务兜底」弥补：比如下单时读缓存拿价格，但支付前再用 DB 校验一次——把强一致要求局限在最关键的那一步。
  3. 对账机制：定时任务比对缓存和 DB，发现偏差自动修复 + 告警。

面试话术：「一致性是可以『分层』的——让 95% 的普通读走缓存（最终一致），把强一致的要求收敛到「扣减/支付」这类关键动作上，用 DB 事务保证。这比全局强一致要好得多：既拿到了缓存的性能，又保证了关键业务的正确性。」

讲讲你项目里怎么用缓存的（场景题）高级

这是「项目场景题」的典型问法。给一个可复用的回答框架（建议结合你自己的项目改写）：

一、缓存分层

「我们做的是多级缓存：本地缓存（Caffeine）→ Redis 集群 → DB。本地缓存存最热的、变化极少的配置类数据（TTL 5 分钟 + 主动失效）；Redis 存业务数据。」

二、读写策略

「写操作统一走 Cache Aside：先更新 DB，再删缓存；删除失败丢 MQ 重试，超过 3 次告警。变更频繁、涉及多张表的（比如商品信息聚合了 SKU、库存、价格），走 Canal 订阅 binlog，避免业务代码里到处写删缓存逻辑。」

三、防三大问题

「穿透：接口层做参数校验 + 布隆过滤器（商品 ID 全集）+ 空值缓存（60s）。
击穿：我们商品详情的 QPS 高，用的是逻辑过期 + 异步重建；排行榜之类的用互斥锁。
雪崩：所有 TTL 都加 ±20% 随机扰动；大促前用预热脚本分批灌数据，TTL 设成大促时长的 2 倍；另外配了命中率告警，从 99% 跌到 90% 就触发。」

四、监控与兜底

「缓存命中率、大 key、热 key、慢查询都接进了监控大盘。核心链路有降级开关——Redis 不可用时，非核心数据直接返回兜底值，核心数据降级到直查 DB（DB 有连接池限流保护）。」

五、一个具体的故障复盘（关键加分项，讲一个你经历过的）

「有一次大促，某爆款商品详情的缓存 key 因为被主动删除（运营改了配置触发了刷新），导致短时间内大量请求穿透。虽然我们有互斥锁，但重建耗时 800ms（要 join 5 张表），1 万 QPS 的请求排队等待，接口 P99 直接飙到 3 秒。
改进措施：① 商品详情做了字段级的缓存拆分，把「变化少的基础信息」和「变化频繁的价格库存」分开缓存，重建耗时降到 50ms 内；② 加了本地缓存做二级兜底；③ 把重建逻辑改成异步预计算，不阻塞主请求。」

为什么这样回答：有分层、有方案、有数字、有故障、有改进——这是面试官在 10 年+ 岗位上真正想听的。

Redis 和 DB 的数据不一致，线上怎么发现和修复？专家

一、怎么发现

  1. 缓存命中率异常：命中率突降往往意味着大量 key 被删或过期，需要排查原因。
  2. 业务侧对账：定时任务（如每 5 分钟）抽取最近变更的数据，比对缓存和 DB 的 update_time / version。这是最直接的方式。
  3. 用户反馈 / 客服工单：用户看到旧价格、旧状态，是最直接的信号。
  4. 数据埋点：在读缓存时记录「缓存版本 vs DB 版本」的差异率，差异率超阈值告警。
  5. binlog 链路监控：如果是 Canal 方案，监控 MQ 积压、消费者延迟、处理失败的 key。

二、怎么修复

  1. 自动修复：对账任务发现偏差后，直接删除该 key（让下次读重建），或按 DB 的值覆盖缓存。优先删除——因为删除是幂等的，不会引入新的错误。
  2. 手动兜底：提供运维接口，按 key / 按业务范围批量刷缓存。
  3. 紧急场景：直接清空整批缓存（如 SCAN + DEL 或按前缀删除），让缓存自然重建。要评估这个操作的后果——清空缓存会导致大量请求穿透，必须有 DB 保护。

三、怎么预防（根治）

  • 所有缓存都设 TTL：保证任何不一致都会自愈（最长 TTL 就是不一致的最大窗口）。
  • 统一缓存写入入口：不要让多个服务/多处代码各自写缓存，否则「谁写的、什么规则」都说不清。
  • 版本号/时间戳：缓存里带上版本，读时校验。
  • 关键业务不依赖缓存做决策：读缓存只是「展示」，真正的校验（扣款、发货）还是要走 DB。

面试收尾：「我的原则是：接受最终一致，但要让不一致『可发现、可自愈、有上限』。可发现靠对账和命中率监控；可自愈靠 TTL 和自动修复；有上限靠『关键动作走 DB 校验』。」
