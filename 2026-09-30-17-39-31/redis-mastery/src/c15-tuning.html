Day 5 · 第 2 节 预计 90 分钟 SRE / 运维视角

Day5.2 · 性能调优与可观测性

一句话结论

调优的闭环是「度量 → 定位 → 优化 → 验证」。度量靠 INFO 全量指标 + SLOWLOG + LATENCY + --latency；定位靠命令级统计 + 大 key/热 key 分析；优化分三层——系统层（内核参数、网卡）→ 配置层（maxmemory、持久化、连接数）→ 应用层（命令、批量、Pipeline）；验证靠基准压测 + 灰度对比。

面试深水区：① 你能说出哪些 INFO 指标最关键、各自异常代表什么；② 内核参数该怎么调（THP、overcommit、somaxconn）；③ 慢查询怎么定位到具体的业务代码。

1. INFO 全量指标解读（监控体系的基础）

✅ INFO 的九大分类（每个都要知道看什么）
分类核心指标异常信号与含义
Server redis_version、uptime_in_days、process_id 版本确认；uptime 突然变小说明重启过（要查为什么）
Clients connected_clients、blocked_clients、maxclients connected_clients 接近 maxclients → 连接打满；blocked_clients 持续高 → 有大量阻塞命令（BLPOP）
Memory used_memory、used_memory_rss、mem_fragmentation_ratio、maxmemory、maxmemory_policy ratio > 1.5 碎片严重；ratio < 1 内存被 swap（延迟飙升！）；used_memory 持续接近 maxmemory → 频繁淘汰
Persistence rdb_last_bgsave_status、rdb_last_fork_usec、aof_last_write_status、aof_rewrite_in_progress、rdb_changes_since_last_save fork_usec 突增 → fork 阻塞变长（大内存 + THP）；bgsave_status:err → 持久化失败（可能是磁盘满）
Stats total_connections_received、total_commands_processed、instantaneous_ops_per_sec、expired_keys、evicted_keys、keyspace_hits、keyspace_misses、rejected_connections 命中率 = hits/(hits+misses)，< 90% 要警惕；evicted_keys 快速增长 → 内存不足在淘汰；rejected_connections > 0 → 连接被拒（超 maxclients）
Replication role、master_link_status、master_repl_offset、slave_repl_offset、slave_read_only 复制延迟 = master_offset − slave_offset；master_link_status:down → 主从断连（严重）
CPU used_cpu_sys、used_cpu_user、used_cpu_sys_children 把「主进程 CPU」和「子进程 CPU（fork 的）」分开看；子进程 CPU 高说明在做 RDB/AOF
Cluster cluster_enabled、cluster_state cluster_state:fail → 集群不可用
Keyspace db0:keys=xxx,expires=xxx,avg_ttl=xxx 看每个 db 的 key 数和「设了过期时间的 key 占比」；avg_ttl 为 0 或极大都需注意 
########## 单次获取全部 INFO ##########
redis-cli INFO

########## 只取某一分类（减少输出）##########
redis-cli INFO memory
redis-cli INFO stats
redis-cli INFO replication

########## 只取某个字段 ##########
redis-cli INFO memory | grep used_memory_human
redis-cli INFO stats | grep keyspace

########## ⭐ 计算缓存命中率 ##########
# 命中率 = keyspace_hits / (keyspace_hits + keyspace_misses)
redis-cli INFO stats | awk -F: '
  /keyspace_hits/   { hits=$2 }
  /keyspace_misses/ { misses=$2 }
  END {
    total = hits + misses;
    if (total > 0)
      printf "命中率 = %.2f%% (hits=%d, misses=%d)\n", hits*100/total, hits, misses
  }'

########## ⭐ 计算主从复制延迟（字节）##########
# 在主节点：
master_offset=$(redis-cli -h MASTER INFO replication | grep master_repl_offset | cut -d: -f2 | tr -d '\r')
# 在从节点：
slave_offset=$(redis-cli -h SLAVE INFO replication | grep slave_repl_offset | cut -d: -f2 | tr -d '\r')
echo "复制延迟 = $((master_offset - slave_offset)) 字节"

########## 监控上看什么（每秒采样）##########
# instantaneous_ops_per_sec   → 当前 QPS
# instantaneous_input_kbps    → 入向流量
# instantaneous_output_kbps   → 出向流量 ⭐ 突增常是大 key 造成
# keyspace_hits/misses 的增量 → 实时命中率
# evicted_keys 的增量          → 淘汰速率
⚠️ 六个「一眼看出问题」的指标（背下来）
  1. mem_fragmentation_ratio < 1 → 部分内存被 swap 到磁盘。延迟会飙到几十毫秒以上，是最危险的信号之一。原因：物理内存不足。必须立刻扩容。
  2. evicted_keys 持续增长 → 内存不足，在不断淘汰 key。意味着缓存命中率会持续下降，业务性能退化。
  3. rejected_connections > 0 → 有连接被拒绝（超过 maxclients）。客户端已经在报错了。
  4. blocked_clients > 0 持续 → 有阻塞命令（BLPOP/BRPOP/WAIT）在等待。如果业务没用这些命令，说明有异常代码。
  5. rdb_last_fork_usec 突增 → fork 耗时变长。直接原因是实例内存大 + 开启了 THP。fork 期间会阻塞主线程。
  6. keyspace_hits/misses 推导的命中率跌破 90% → 要么 key 被大量淘汰/过期，要么 key 设计有问题（大量一次性查询）。

2. 慢查询：SLOWLOG 与延迟监控

✅ SLOWLOG 配置与使用
# 两个参数控制慢日志
slowlog-log-slower-than 10000    # 超过 10000 微秒（=10ms）的命令记录为慢查询
slowlog-max-len 512             # 慢日志队列长度（超出后旧记录被挤出）

# 动态修改（不用重启）
CONFIG SET slowlog-log-slower-than 10000
CONFIG SET slowlog-max-len 1024

# ⭐ 实践建议：
#   生产建议设为 10000（10ms）——因为 Redis 正常命令都在 1ms 内，10ms 已经是明显的异常
#   如果发现慢日志刷屏，说明有问题命令，先治理再调阈值
#   如果把阈值设为 0，会记录所有命令 → 性能影响大，禁止生产使用

########## 查看慢日志 ##########
SLOWLOG GET 10        # 取最近 10 条
SLOWLOG LEN           # 慢日志总数
SLOWLOG RESET         # 清空（治理后重置，便于观察是否还有新的）

# 输出格式（每条的字段）：
#  1) (integer) 14                 ← 日志 ID
#  2) (integer) 1759161600         ← 时间戳（Unix）
#  3) (integer) 25000              ← 执行耗时（微秒，这里是 25ms）
#  4) 1) "HGETALL"                 ← 命令及参数
#     2) "product:detail:1001"
#  5) "10.0.0.5:54321"             ← 客户端地址
#  6) "app-worker-3"               ← 客户端名称（如果设置了 CLIENT SETNAME）

⭐ 关键实践：给客户端设置名字

// Java 客户端设置连接名，这样慢日志里能看出是哪个应用/线程做的
// 用 Lettuce 的 ClientOptions：
ClientOptions.builder()
    .clientName("order-service-worker-3")
    .build();

// 或直接发命令（每个连接只需执行一次）
// CLIENT SETNAME order-service-worker-3

为什么这很重要：慢日志里能看到「哪条命令慢」，但不知道是哪个应用发出来的。设置了 client name 后，就能直接定位到具体的应用和实例——这是从「发现问题」到「找到责任方」的关键一步。

🚨 SLOWLOG 的三个重要认知
  1. SLOWLOG 只记录「命令执行时间」，不含网络传输时间。
    所以一个「查询大 key 但网络慢」的操作，可能 SLOWLOG 里只显示 5ms，但客户端感受到 200ms。要区分「Redis 侧慢」和「网络侧慢」，需要对比客户端的埋点和 SLOWLOG。
  2. SLOWLOG 记录的是「命令执行完」之后写入的。
    如果命令执行时间极长（比如 5 秒的 KEYS），它会在执行完才写入慢日志。所以它不能用来「实时发现」正在阻塞的命令。发现正在阻塞的要用 CLIENT LIST 看 cmd 字段。
  3. 慢日志是采样性的、有容量上限的。
    slowlog-max-len 满了以后旧记录被挤出。所以如果慢日志持续刷屏，可能会丢失更早的关键记录——应该加大 max-len 或用外部工具持续采集入库。
########## 定位「正在阻塞」的命令（SLOWLOG 做不到的）##########
CLIENT LIST
# 输出字段（部分）：
#   id=123 addr=10.0.0.5:54321 name=order-service-3 age=3600 idle=0
#   flags=N db=0 sub=0 psub=0 ssub=0 multi=-1 qbuf=0 qbuf-free=20448
#   argv-mem=0 multi-mem=0 rbs=1024 rbp=0 obl=0 oll=0 omem=0 tot-mem=20520
#   events=r cmd=hgetall user=default redir=-1 resp=2

# ⭐ 关注这几个字段：
#   cmd        当前正在执行的命令（如果长时间不变 → 就是在执行这个慢命令）
#   age        连接存活时间
#   idle       连接空闲时间（很大说明连接没在用）
#   omem       output buffer 内存 ⭐ 很大说明有个"消费不过来的客户端"

# 找出所有正在执行"危险命令"的客户端
CLIENT LIST | grep -E "cmd=(keys|hgetall|smembers|flushall|sort)"

# 找出 output buffer 异常的客户端（可能是被推送打爆的订阅者）
redis-cli CLIENT LIST | awk '{for(i=1;i<=NF;i++){if($i ~ /^omem=/){split($i,a,"=");if(a[2]>10485760) print}}}'

########## 延迟监控（LATENCY）##########
# Redis 的延迟监控子系统：记录"耗时超过阈值的事件"
CONFIG SET latency-monitor-threshold 100    # 超过 100ms 的事件记录下来

LATENCY LATEST      # 查看最近的事件（每个事件类型只保留最后一次）
# 输出：event-name, timestamp, latest-latency, max-latency
# 常见事件类型：
#   command    — 命令处理耗时
#   fork       — fork 子进程耗时 ⭐
#   expire-cycle      — 过期删除循环
#   eviction-cycle    — 内存淘汰循环
#   aof-write         — AOF 写入
#   aof-fsync-always  — AOF always 策略的 fsync

LATENCY HISTORY fork      # 查看 fork 事件的历史（趋势）
LATENCY RESET             # 清空

# ⭐ fork 事件如果频繁超过 100ms，说明 fork 阻塞严重
#    原因通常是：实例内存大（fork 要复制页表）+ 开启 THP
#    解法：控制单实例内存（≤10-16GB）+ 关闭 THP
✅ 客户端侧延迟测量：redis-cli --latency（区分「Redis 慢」和「网络慢」）
########## 1. --latency：持续测量 PING 的延迟 ##########
redis-cli -h 10.0.0.5 --latency
# 输出：min: 0, max: 1, avg: 0.15 (1234 samples)
# 这个值包含"网络 RTT + Redis 处理 PING 的时间"
# Redis 处理 PING 极快（微秒级），所以这个值基本 = 网络 RTT

########## 2. --latency-history：按时间窗口展示延迟变化趋势 ⭐ ##########
redis-cli -h 10.0.0.5 --latency-history -i 5
# 每 5 秒输出一个统计窗口，观察延迟是否随时间波动
# 能看出"周期性抖动"（如果有，可能是定时任务/持久化导致）

########## 3. --latency-dist：延迟分布直方图 ⭐⭐ 最有用 ##########
redis-cli -h 10.0.0.5 --latency-dist
# 用色块展示延迟分布，能直观看出"长尾"
# 如果 P99 很高但均值正常，说明有偶发的长尾延迟
# 长尾的常见原因：fork、慢命令、网络抖动、CPU 争抢

########## 4. --intrinsic-latency：测量"宿主环境本身"的延迟基线 ⭐⭐⭐ ##########
redis-cli --intrinsic-latency 100
# 让 Redis 忙等 100 秒，测量"不做事时"的调度延迟
# 这是【判断宿主机是否适合跑 Redis 的关键依据】
#
# 输出示例：
# Max latency so far: 1 microseconds
# Max latency so far: 8 microseconds
# Max latency so far: 127 microseconds      ← 超过 100 微秒就要注意了
# ...
# 15324 total runs (avg latency: 6.5 microseconds / 6527.94 nanoseconds per run)
# Worst run took 19x longer than the average latency.
#
# ⭐ 判断标准（antirez 的建议）：
#   max latency < 100 微秒  → 环境优良
#   max latency > 1 毫秒    → 环境有问题（虚拟化/CPU 争抢/超卖）
#   这种情况再怎么调 Redis 都没用，要换机器

这四个命令的区别（面试可能问）：

命令测什么用途
--latency网络 RTT + Redis 处理 PING快速判断「网络 vs Redis」
--latency-history延迟随时间的趋势发现周期性抖动
--latency-dist延迟分布（含长尾）看 P99/P999，发现长尾问题
--intrinsic-latency宿主环境本身的调度延迟判断机器是否适合跑 Redis

3. 基准压测：redis-benchmark

########## 基础压测 ##########
# 默认：50 个客户端，10 万请求，测试常见命令
redis-benchmark -h 127.0.0.1 -p 6379 -n 100000 -c 50

# 常用参数
redis-benchmark \
  -h 127.0.0.1 \
  -p 6379 \
  -a "password" \        # 密码
  -n 1000000 \             # 总请求数
  -c 100 \                 # 并发客户端数
  -P 16 \                  # ⭐ Pipeline 深度（每批 16 条命令）——最能反映真实吞吐
  -d 100 \                 # value 大小（字节）
  -t set,get,incr,lpush,hset \  # 只测指定命令
  -r 100000 \              # 随机 key 空间
  -q                       # 简洁输出

########## 只测特定命令（更真实）##########
redis-benchmark -n 1000000 -c 100 -P 16 -t get,set -d 128 -q
# 输出：
# SET: 158730.16 requests per second, p50=0.479 msec
# GET: 166666.67 requests per second, p50=0.455 msec

########## 自定义命令压测（限流脚本等）##########
redis-benchmark -n 100000 -c 50 \
  eval "return redis.call('GET', KEYS[1])" 1 mykey

########## ⭐ 关键理解：-P 参数为什么重要 ##########
# 不加 -P（Pipeline）：每次请求都是"发命令 → 等响应"，吞吐受 RTT 限制
#   → 在 0.1ms RTT 下，单连接理论 QPS ≈ 10000
# 加 -P 16：一次发 16 条命令，吞吐能提升 5-10 倍
#   → 这才是 Redis 真实的能力上限
# ⭐ 所以"Redis 单机 10 万 QPS"这个说法，是指"有 Pipeline 或高并发连接"的情况

########## 完整压测示例（大厂标准）##########
# 场景一：模拟真实业务（读写混合、有 Pipeline）
redis-benchmark -h redis-host -p 6379 -a $PWD \
  -n 5000000 -c 200 -P 32 -d 256 -q \
  -t set,get,incr,hset,hget,lpush,lpop,sadd,zadd

# 场景二：纯写入（测持久化影响）
redis-benchmark -n 5000000 -c 100 -P 16 -t set -d 1024 -q

# 场景三：只读（测纯读能力）
# 先灌数据：
redis-benchmark -n 1000000 -c 50 -t set -r 1000000 -q
# 再压读：
redis-benchmark -n 5000000 -c 200 -P 32 -t get -r 1000000 -q
⚠️ 压测的四个注意事项（否则结果无意义）
  1. 必须在独立的机器上压测：如果 benchmark 和 Redis 在同一台机器上，两者会争抢 CPU，结果严重失真。而且压测机本身也可能成为瓶颈。
  2. 压测前要清理环境：
    · FLUSHALL 清空数据（否则测的是「已有大量数据」的状态，可能触发淘汰）
    · 确认没有其他业务在跑
    · 关闭或记录持久化状态（RDB/AOF 会显著影响写性能）
  3. 压测机本身也不能是瓶颈：压测机要够强（CPU 核数、网卡带宽），否则压不出 Redis 的上限。建议用多台压测机。
  4. 要监控压测期间的服务端指标：CPU、内存、网络、SLOWLOG、LATENCY。只知道 QPS 数字没有意义——必须知道「在这个 QPS 下，延迟是多少、资源用了多少」。
💡 面试话术：怎么评估一套 Redis 实例的能力

「我会做三件事：

  1. 测基线：redis-benchmark -P 16/32 测出这台实例在「理想情况」下的吞吐上限，作为参考。
  2. 测业务场景：用真实的 key 大小、读写比例、Pipeline 深度去压。因为 Redis 的性能高度依赖于「命令类型」和「value 大小」——一个 10KB 的 GET 和一个 100B 的 GET，吞吐差几十倍。
  3. 测容量拐点：逐步加压，找到「延迟开始非线性上升」的拐点。那个拐点的 70% 才是安全的运行水位。因为 Redis 是单线程，一旦 CPU 接近饱和，延迟会急剧劣化（没有「慢慢变慢」的缓冲）。

另外我会跑 --intrinsic-latency 确认宿主机环境本身没问题——如果宿主机的调度延迟就有问题，那压测结果再好也没有意义。」

4. 系统层调优（内核参数）

✅ 必须调整的 Linux 内核参数
########## 1. 禁用透明大页（THP）—— 最重要的一条 ⭐⭐⭐ ##########
# 查看当前状态
cat /sys/kernel/mm/transparent_hugepage/enabled
# [always] madvise never     ← 方括号表示当前值，如果在 always 就是问题！

# 临时关闭
echo never > /sys/kernel/mm/transparent_hugepage/enabled

# 永久关闭（加到 /etc/rc.local 或 systemd 服务）
# 在 /etc/rc.local 里加：
echo never > /sys/kernel/mm/transparent_hugepage/enabled
echo never > /sys/kernel/mm/transparent_hugepage/defrag

# ⭐ 为什么必须关（面试必答）：
#  ① Redis 做 RDB/AOF 时会 fork 子进程，用的是 COW（写时复制）
#  ② COW 的复制单位是【内存页】。普通页 4KB，THP 页是 2MB
#  ③ 使用 THP 时，只要父进程改了 2MB 页里的任意一个字节，
#     整个 2MB 页都要复制！
#  ④ 结果：COW 复制的内存量可能暴增几十倍（进而触发 OOM 或严重阻塞）
#  ⑤ 另外 THP 做页的合并/拆分本身也有延迟，会造成不可预测的停顿
#  → 所以官方强烈建议关闭 THP

########## 2. 内存 overcommit（允许 fork 时超量分配）##########
# 查看
cat /proc/sys/vm/overcommit_memory
# 0 = 启发式（默认，可能拒绝 fork）
# 1 = 总是允许超量分配 ⭐ 推荐
# 2 = 严格模式（禁止超量）

# 临时设置
echo 1 > /proc/sys/vm/overcommit_memory
# 永久（/etc/sysctl.conf）
vm.overcommit_memory = 1

# ⭐ 为什么：fork 时子进程虽然共享父进程内存（COW），但内核需要
#    分配页表等结构。如果 overcommit_memory=0 且内存紧张，
#    fork 会被拒绝 → RDB/BGSAVE 失败 → 无法持久化

########## 3. 网络相关参数 ##########
# 全连接队列大小（提高高并发下的建连成功率）
net.core.somaxconn = 65535              # 默认 128，高并发下不够
# Redis 的 tcp-backlog 配置要 <= 这个值

# 半连接队列
net.ipv4.tcp_max_syn_backlog = 65535

# TCP 连接复用（TIME_WAIT 快速回收要慎用，可能影响 NAT 环境）
net.ipv4.tcp_tw_reuse = 1             # 允许复用 TIME_WAIT 的连接
# net.ipv4.tcp_tw_recycle = 1        # ⚠️ NAT 环境禁用（4.12+ 内核已移除）

# 文件描述符上限 ⭐ 必调
fs.file-max = 1000000
# 进程级 limit（Redis maxclients 受此限制）
# /etc/security/limits.conf：
redis soft nofile 65535
redis hard nofile 65535

########## 4. 应用持久化配置（/etc/sysctl.conf 汇总）##########
vm.overcommit_memory = 1
vm.swappiness = 1                    # ⭐ 尽量不用 swap（默认 60 太激进）
net.core.somaxconn = 65535
net.ipv4.tcp_max_syn_backlog = 65535
net.ipv4.tcp_tw_reuse = 1
fs.file-max = 1000000

# 应用
sysctl -p
🚨 关于 swap（交换分区）：为什么必须避免

问题：Redis 是内存数据库，对延迟极其敏感。如果物理内存不足，操作系统会把部分内存页换出到磁盘（swap）。当 Redis 访问到这些被换出的页时，需要从磁盘读回来——磁盘延迟是内存的十万倍（微秒级 vs 毫秒级）。

后果：延迟从 0.1ms 飙到几十毫秒，甚至秒级。mem_fragmentation_ratio < 1 就是这个信号——used_memory（Redis 自己算的）大于 RSS（操作系统给的物理内存），说明有一部分被 swap 出去了。

正确做法：

  • vm.swappiness = 1（不是 0）：设成 1 而不是 0，是为了保留「极端情况下的最后一道防线」（0 会导致 OOM Killer 直接杀进程，1 允许极端时少量 swap）。但这只是缓解——根本解法是保证物理内存充足。
  • 监控 mem_fragmentation_ratio：低于 1 立刻告警。
  • 预留内存：实例内存不要超过物理内存的 70%-80%（给 fork 的 COW 和系统留空间）。
  • 容器环境注意：如果 Redis 在容器里，要确认容器的内存 limit 设置合理，避免被 cgroup OOM Kill。

✅ io-threads：I/O 多线程该怎么配（面试考点）

原理回顾：Redis 6.0 引入 I/O 多线程——网络数据的读写（socket read/write）由多个 IO 线程并行处理，但命令的解析和执行仍然是单线程。

配置建议：

  • io-threads 4：经验值 = 机器 CPU 核数的 3/4，最多 8。官方建议 4-8 核的机器配 2-3 个，8 核以上配 4-6 个。
  • io-threads-do-reads yes：默认是 no（只对写多线程）。开启后读也并行。一般建议开启。

⚠️ 关键认知：

  • io-threads 不会提升单命令的延迟，它提升的是「高并发下的整体吞吐」——因为减少了主线程在 socket 读写上的等待。
  • 如果瓶颈是 CPU（命令执行），io-threads 帮助有限。因为命令执行还是单线程。这种情况只能靠「读写分离」或「Cluster 分片」。
  • 不要盲目调大：线程数超过实际需要的会带来上下文切换开销。调大后要压测验证。
  • 8.0 对 I/O 线程做了重构，效率更高（在同样线程数下吞吐更好）。

面试话术：「io-threads 解决的是『网络 IO 成为瓶颈』的问题——比如大 value 的读写、高并发下的 socket 处理。但如果命令本身是 CPU 密集，或者瓶颈在命令执行上，IO 多线程帮不上忙，那时候要靠分片。所以我会先看瓶颈在哪（INFO cpu 看 CPU 是用户态还是系统态占用高，用户态高说明命令执行是瓶颈），再决定要不要调 io-threads。」

💡 告警设计的三条原则
  1. 分层告警：P0（服务不可用，立即电话）→ P1（性能劣化，10 分钟内响应）→ P2（趋势异常，工作时间处理）。不要把「慢日志多了一条」也搞成电话告警——告警疲劳会让人忽略真正重要的信号。
  2. 关注「变化率」而不是「绝对值」：
    「慢日志 100 条」这个绝对值没有意义，但「慢日志从 0 涨到 100 条/分钟」是明确的问题信号。
    「内存用了 8GB」要看相对于 maxmemory 的比例和增长趋势，而不是绝对值。
  3. 每个告警都要有明确的处理动作（Runbook）：
    告警触发时，值班同学应该知道「先做什么、再做什么」。比如「P99 延迟告警 → ① 查看 SLOWLOG → ② 查大 key → ③ 检查是否有 fork/AOF」。

优先级优化项预期收益成本

⚠️ 调优的三个反模式（常见错误）
  1. 没有度量就调优：不知道瓶颈在哪就改参数。结果：改了没效果，甚至引入新问题。
    正确：先 INFO + SLOWLOG + --latency-dist + 压测，定位瓶颈，再针对性优化。
  2. 一次改多个参数：无法知道哪个改动起了作用（或哪个引入了问题）。
    正确：每次只改一个变量，改完压测验证，再改下一个。
  3. 照搬网上的「最优配置」：不同业务场景（读多写少 vs 写多、缓存 vs 数据库、小 value vs 大 value）的最优配置完全不同。
    正确：理解每个参数的权衡（如 appendfsync always 最安全但最慢），根据自己的业务约束选择。

面试深度问答

Redis 性能怎么优化？进阶

按「度量 → 定位 → 三层优化」的结构回答：

一、先度量（不要盲调）

  • INFO 看全局指标（CPU、内存、命中率、连接数、淘汰数）。
  • SLOWLOG 看慢命令。
  • --latency-dist 看延迟分布（长尾）。
  • --intrinsic-latency 确认宿主机环境没问题。

二、三层优化

① 系统层：

  • 禁用 THP（最重要）——避免 fork 时 COW 复制整个 2MB 页。
  • vm.overcommit_memory = 1（避免 fork 被拒）。
  • vm.swappiness = 1（避免 swap，swap 会让延迟飙升）。
  • somaxconn / file-max / ulimit -n 调大。

② 配置层：

  • maxmemory + 合理淘汰策略（物理内存的 60-75%）。
  • 开启 lazyfree（异步删除）。
  • 客户端输出缓冲限制（防慢消费者）。
  • io-threads（如果瓶颈在网络 IO）。
  • 持久化策略权衡（纯缓存可关 RDB；用 everysec 而非 always）。

③ 应用层（收益往往最大）：

  • 治理大 key（消除主线程阻塞）。
  • 治理热 key（本地缓存/多副本）。
  • 批量操作改 Pipeline（分批）。
  • 禁用危险命令（KEYS、全量 HGETALL）。
  • 合理的 key 设计（避免大 value、避免 key 数量爆炸）。

三、验证：每次改一个变量，压测对比。

关键洞察：「大部分性能问题不在 Redis 配置上，而在应用怎么用它。 一个 KEYS * 或者一个 100MB 的大 key，就能让再好的配置也没用。所以我会先排查应用层的命令和数据结构问题，再去调优配置。」

为什么必须关闭 THP（透明大页）？高级

THP 是什么：Linux 的透明大页机制，把传统的 4KB 内存页合并成 2MB 的大页，目的是减少 TLB miss、提升内存访问效率。

为什么对 Redis 有害（核心论证）：

  1. Redis 做 RDB/AOF rewrite 时会 fork 子进程，依靠 COW（写时复制） 让父子进程共享内存。
  2. COW 的复制单位是「内存页」。普通页 4KB，THP 页是 2MB。
  3. 关键问题：使用 THP 时，只要父进程修改了 2MB 页里的任意一个字节，整个 2MB 页都要被复制。
  4. 后果：COW 需要复制的内存量可能暴增几十到几百倍 → ① 内存暴涨可能触发 OOM；② 大量内存复制导致严重的延迟尖刺（fork 事件延迟飙升）。
  5. 额外问题：THP 的页合并/拆分（khugepaged）在后台运行，也会造成不可预测的停顿。

配置：

echo never > /sys/kernel/mm/transparent_hugepage/enabled
echo never > /sys/kernel/mm/transparent_hugepage/defrag

验证：cat /sys/kernel/mm/transparent_hugepage/enabled 应该显示 always madvise [never]（方括号在 never 上）。

面试加分：「这个问题的本质是『COW 的粒度被 THP 放大了』。Redis 官方文档专门强调了这一点，也是我在任何新机器上部署 Redis 时第一件要检查的事——比调 maxmemory 还优先，因为它是『静默杀手』：平时看不出来，但每次 RDB/AOF 时就可能造成秒级的延迟尖刺。」

SLOWLOG 怎么用？它有什么局限？进阶

配置：

CONFIG SET slowlog-log-slower-than 10000   # 超过 10ms 记录
CONFIG SET slowlog-max-len 1024            # 队列长度
SLOWLOG GET 10                             # 查看最近 10 条
SLOWLOG LEN / SLOWLOG RESET

输出字段：日志 ID、时间戳、执行耗时（微秒）、命令及参数、客户端地址、客户端名称。

⭐ 实践关键：给客户端设置 CLIENT SETNAME（如 order-service-worker-3），这样慢日志里能直接定位到具体应用。这是从「发现问题」到「找到责任方」的关键一步。

三个局限（面试爱追问）：

  1. 不含网络传输时间：只记录「命令在 Redis 里执行的时间」。大 key 的网络传输慢不会体现在 SLOWLOG 里。所以要对比客户端埋点和 SLOWLOG，区分「Redis 慢」和「网络慢」。
  2. 是「事后记录」：命令执行完才写入。所以无法用来实时发现「正在阻塞」的命令——那个要用 CLIENT LIST 看 cmd 字段。
  3. 有容量上限：slowlog-max-len 满了会挤出旧记录。持续刷屏时会丢失历史。要加大 max-len 或用外部工具持续采集入库。

配套用的命令：

  • INFO commandstats：累计统计，能看出「哪类命令总耗时最多」（比 SLOWLOG 更能发现系统性问题）。
  • INFO latencystats（7.0+）：各命令的延迟分位数（P50/P99/P999）。
  • LATENCY LATEST：系统级事件延迟（fork、expire-cycle、aof-write 等）。
如何区分「Redis 慢」和「网络慢」？高级

核心方法：对比两个视角的测量值。

视角一：Redis 侧（服务端）

  • SLOWLOG：命令在 Redis 内的执行时间。
  • INFO latencystats：命令延迟分位数。
  • LATENCY LATEST：系统事件延迟。

视角二：客户端侧

  • redis-cli --latency：网络 RTT + PING 处理（PING 很快，所以基本 = RTT）。
  • --latency-dist：延迟分布，看长尾。
  • 应用侧埋点：记录每次 Redis 调用耗时（这个值包含「客户端排队 + 网络 + Redis 处理」）。

判断逻辑：

客户端耗时SLOWLOG结论
高高Redis 真的慢（慢命令、大 key、阻塞）
高低/无不是 Redis 执行慢 → 可能是：① 网络拥塞/大 value 传输；② 客户端连接池排队；③ 应用 GC
低高少见。可能是 SLOWLOG 记录了别的时间段的命令（对比时间戳）

进一步的区分手段：

  • 排除网络：--latency 显示 RTT 正常 → 网络通；--intrinsic-latency 正常 → 宿主机没问题。
  • 排除连接池排队：看连接池的「等待连接次数 + 平均等待时间」。如果等待时间占整体耗时的比例高 → 是池太小或有慢命令占着连接。
  • 排除应用 GC：看应用的 GC 日志，对比 GC 暂停时间和 Redis 调用耗时的时间戳。
  • 看大 key：如果是「GET 一个大 value」的网络传输慢，会体现在 instantaneous_output_kbps 突增。

面试话术：「我一般先看 --latency——如果 RTT 正常但业务耗时高，那问题就不在网络。然后用连接池的等待指标排除『池排队』，再看应用 GC 日志排除 JVM 问题。最后剩下的才是 Redis 本身的问题，这时用 SLOWLOG 和 INFO commandstats 定位具体命令。」

IO 多线程（io-threads）怎么配？为什么命令执行还是单线程？高级

为什么命令执行仍是单线程：

  • 简单：单线程不用处理并发问题（锁、原子性），代码和逻辑都简单。
  • 够快：纯内存操作 + 高效数据结构的瓶颈不在 CPU，而在网络 IO。
  • 原子性天然保证：所有命令串行执行，天然满足原子性需求（Lua/MULTI 的原子性正依赖于此）。

那为什么要 IO 多线程：随着硬件发展（多核 CPU + 万兆网卡），网络 IO 成为了瓶颈——单线程处理所有 socket 的读写（包括数据的拷贝、解析）占用了大量 CPU。所以 6.0 把「socket 读写」这部分并行化。

配置：

io-threads 4              # 经验值 = CPU 核数 * 3/4，最多 8
io-threads-do-reads yes   # 读也走多线程

关键认知：

  • 不会降低单命令延迟：它提升的是高并发下的整体吞吐（减少了主线程在 socket 读写上的等待）。
  • 如果瓶颈是命令执行（CPU 用户态高），io-threads 帮助有限。应付这种情况要靠分片（Cluster）或读写分离。
  • 不要盲目调大：线程数过多会带来上下文切换开销。调大后要压测验证。

怎么判断该不该开：

  • 看 INFO cpu：如果 used_cpu_sys（系统态，主要来自 socket 处理）占比高 → 网络 IO 是瓶颈 → 开 io-threads 有帮助。
  • 如果 used_cpu_user（用户态，主要来自命令执行）占比高 → 命令执行是瓶颈 → io-threads 帮助有限。
  • 如果 QPS 高但 CPU 使用率低 → 可能有网络 RTT 瓶颈或客户端排队问题。

面试话术：「我会先用 INFO cpu 区分瓶颈在『系统态（socket 处理）』还是『用户态（命令执行）』。系统态高才值得开 io-threads；用户态高说明要分片或优化命令。这样调优才有依据，而不是看到有这个参数就随手调大。」

线上 Redis 该监控哪些指标？高级

按「四层」组织回答：

第一层：可用性（P0，最关键）

  • PING 是否响应；cluster_state；master_link_status。

第二层：性能

  • QPS（instantaneous_ops_per_sec）、P99/P999 延迟、慢日志数量与增速。

第三层：资源与健康度

  • 内存：used_memory / maxmemory 比例、mem_fragmentation_ratio（<1 是 swap，必须告警）、evicted_keys 增量。
  • CPU：使用率（>70% 告警）、系统态 vs 用户态分布。
  • 连接：connected_clients / maxclients、rejected_connections、blocked_clients。
  • 网络：instantaneous_output_kbps（突增常是大 key）。

第四层：持久化与复制

  • rdb_last_bgsave_status / aof_last_write_status；
  • rdb_last_fork_usec（fork 阻塞，>500ms 告警）；
  • 复制延迟（offset 差值）；从节点数量；cluster_slots_fail。

业务层指标（容易被忽略但很有用）

  • 缓存命中率（keyspace_hits/(hits+misses)）：雪崩和 key 设计问题的先行指标，<90% 告警。
  • 大 key 扫描结果：定期扫描，新增大 key 告警。
  • 热 key：单 key QPS 超阈值告警。
  • 客户端连接池：活跃/空闲/等待数（这个指标往往比 Redis 侧指标更能提前发现应用问题）。

三条告警设计原则：

  1. 分层告警（P0 电话 / P1 即时消息 / P2 日报），避免告警疲劳。
  2. 关注变化率而非绝对值（「慢日志 100 条」无意义，「慢日志从 0 涨到 100/分钟」才是信号）。
  3. 每个告警有 Runbook（值班看到告警知道该做什么）。
