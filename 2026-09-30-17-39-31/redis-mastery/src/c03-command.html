Day1.3 · 命令行与 Java 客户端实战

一句话结论

命令行决定你排查问题的效率，客户端决定你代码的稳定性。这一节的核心是两个「反常识」结论：① Pipeline 的收益在局域网下远没有想象的大，且不是原子操作；② 连接池参数配错，比 Redis 本身慢十倍。

⚠️ --bigkeys 的统计口径陷阱（面试细节题）

--bigkeys 统计的是元素个数（String 是字节长度），不是内存占用。所以：

  • 一个含 10 万个超长字符串的 List，元素个数不多但内存可能巨大——--bigkeys 可能漏掉它。
  • 要按真实内存占用排查，用 --memkeys（7.0+）或 MEMORY USAGE key，或用 RDB 离线分析工具（redis-rdb-tools / rdr）。
  • 两条命令都基于 SCAN 遍历，不阻塞主线程但会占用 CPU 和网络，且集群模式下需要逐节点执行（一次连接只统计当前节点）。

2. Java 客户端选型：Jedis vs Lettuce vs Redisson

这是 Java 工程师面试的必问题，因为选型直接决定连接模型、并发能力和功能边界。

客户端连接模型核心特点适用场景
Jedis同步阻塞
连接池（非线程安全）		最贴近 Redis 命令原语，API 简单直接；每个线程需独占连接，靠 JedisPool 管理传统 Spring 项目、命令级精细控制、并发量中等
LettuceNetty 异步
（线程安全，单连接可多线程共享）		基于 Netty，支持异步/响应式（Reactive）、共享连接、自动重连；Spring Boot 2.x+ 默认高并发、响应式（WebFlux）、云原生环境
RedissonNetty（在 Lettuce/NIO 之上封装）提供分布式对象（RLock/RSemaphore/RMap/RBucket/RDelayedQueue）和看门狗续期需要分布式锁、分布式集合、延时队列等高级能力
Spring Data Redis封装层统一 API（RedisTemplate），底层可切 Jedis/Lettuce；提供序列化策略配置Spring 生态项目（绝大多数业务系统）
💡 选型口诀（面试直接说）

「基础命令用 Lettuce（Spring Boot 默认，异步高并发），需要分布式锁等高级能力用 Redisson，老项目或需要完全掌控连接用 Jedis。」
更进一步：「生产上通常两者混用——业务读写走 RedisTemplate(Lettuce)，分布式锁和限流走 Redisson，各取所长。」

4. 完整 Java 代码：Spring Data Redis 生产级封装

/**
 * RedisTemplate 生产级配置
 *
 * 关键决策点：
 * 1. Key 用 String 序列化（可读，便于排查和 ACL 授权）
 * 2. Value 用 JSON 序列化（跨语言兼容，但注意体积）
 * 3. 单机用 GenericJackson2JsonRedisSerializer，集群用 Jackson2JsonRedisSerializer 更省
 */
@Configuration
public class RedisConfig {

    @Bean
    public RedisTemplate<String, Object> redisTemplate(RedisConnectionFactory factory) {
        RedisTemplate<String, Object> template = new RedisTemplate<>();
        template.setConnectionFactory(factory);

        // ---- Key 序列化：字符串，保证 redis-cli 里能直接看懂 ----
        StringRedisSerializer keySerializer = new StringRedisSerializer();
        template.setKeySerializer(keySerializer);
        template.setHashKeySerializer(keySerializer);

        // ---- Value 序列化：JSON ----
        ObjectMapper om = new ObjectMapper();
        om.registerModule(new JavaTimeModule());                          // 支持 LocalDateTime
        om.disable(SerializationFeature.WRITE_DATES_AS_TIMESTAMPS);
        om.setVisibility(PropertyAccessor.ALL, JsonAutoDetect.Visibility.ANY);
        om.activateDefaultTyping(LaissezFaireSubTypeValidator.instance,       // ⚠️ 生产建议用白名单版本
                ObjectMapper.DefaultTyping.NON_FINAL, JsonTypeInfo.As.PROPERTY);

        GenericJackson2JsonRedisSerializer valueSerializer =
                new GenericJackson2JsonRedisSerializer(om);
        template.setValueSerializer(valueSerializer);
        template.setHashValueSerializer(valueSerializer);

        template.afterPropertiesSet();
        return template;
    }

    /**
     * 纯字符串模板：用于计数器、分布式锁等只需 String 的场景，避免 JSON 开销
     */
    @Bean
    public StringRedisTemplate stringRedisTemplate(RedisConnectionFactory factory) {
        return new StringRedisTemplate(factory);
    }
}
🚨 序列化踩坑警告（真实事故高发点）
  1. 默认 JDK 序列化：RedisTemplate 默认用 JdkSerializationRedisSerializer，存进去的是二进制，redis-cli 完全看不懂，排查困难、体积大、跨语言不可用。必须改。
  2. GenericJackson2JsonRedisSerializer 会写入 @class 字段：这带来两个问题——① 增加存储体积（有时超过 20%）；② 反序列化存在安全风险（若开启 defaultTyping 且未做白名单，可能有反序列化漏洞）。生产建议用明确类型的 Jackson2JsonRedisSerializer<T>，或对无多态需求的对象关闭 defaultTyping。
  3. 对象类结构变更导致反序列化失败：改了字段名/类型，历史缓存反序列化会抛异常。应对：缓存中不放易变结构、加版本号（user:v2:1001）、或统一用 Map/JSON 字符串存。
  4. LocalDateTime 序列化：不加 JavaTimeModule 会直接抛异常，这是最常见的启动失败原因之一。

/**
 * 推荐：用 Spring Cache 抽象 + 注解（简洁、统一、易维护）
 */
@Service
public class UserService {

    @Cacheable(cacheNames = "user", key = "#id",
               unless = "#result == null")                 // null 不缓存（防穿透需另行处理）
    public User getById(Long id) {
        return userMapper.selectById(id);
    }

    @CachePut(cacheNames = "user", key = "#user.id")      // 更新后刷新缓存
    public User update(User user) {
        userMapper.updateById(user);
        return user;
    }

    @CacheEvict(cacheNames = "user", key = "#id")          // 删除时清缓存
    public void delete(Long id) {
        userMapper.deleteById(id);
    }
}
/**
 * 生产级缓存工具：带 TTL 随机抖动、防穿透、防击穿
 */
@Component
@RequiredArgsConstructor
public class CacheHelper {

    private static final String NULL_PLACEHOLDER = "__NULL__";

    private final StringRedisTemplate redis;

    /**
     * 缓存读取（防穿透 + 防击穿 + 抖动 TTL）
     *
     * @param key        缓存 key
     * @param type       返回类型
     * @param baseTtl    基础过期秒数
     * @param jitter     抖动秒数（防雪崩）
     * @param loader     回源函数
     */
    public <T> T getWithProtect(String key, Class<T> type, long baseTtl, long jitter,
                                    Supplier<T> loader) {
        String cached = redis.opsForValue().get(key);

        // 1) 命中了「空值占位符」→ 直接返回 null（防穿透）
        if (NULL_PLACEHOLDER.equals(cached)) {
            return null;
        }
        if (cached != null) {
            return JSON.parseObject(cached, type);
        }

        // 2) 未命中 → 加分布式锁重建，防击穿（只有一个线程回源）
        String lockKey = "lock:cache:" + key;
        String token = UUID.randomUUID().toString();
        Boolean locked = redis.opsForValue()
                .setIfAbsent(lockKey, token, Duration.ofSeconds(10));

        try {
            if (Boolean.TRUE.equals(locked)) {
                // 双检：拿到锁后再查一次，可能已被其他线程写入
                cached = redis.opsForValue().get(key);
                if (cached != null) {
                    return NULL_PLACEHOLDER.equals(cached) ? null : JSON.parseObject(cached, type);
                }

                T value = loader.get();
                long ttl = baseTtl + ThreadLocalRandom.current().nextLong(0, jitter + 1);

                if (value == null) {
                    // 空值也要缓存（短 TTL），防止反复穿透到 DB
                    redis.opsForValue().set(key, NULL_PLACEHOLDER, Duration.ofSeconds(60 + ttl % 30));
                } else {
                    redis.opsForValue().set(key, JSON.toJSONString(value), Duration.ofSeconds(ttl));
                }
                return value;
            }

            // 3) 没抢到锁 → 短暂等待后重试读缓存，避免大量线程同时回源
            Thread.sleep(50);
            cached = redis.opsForValue().get(key);
            if (cached != null && !NULL_PLACEHOLDER.equals(cached)) {
                return JSON.parseObject(cached, type);
            }
            // 兜底：直接查库（保证可用性优先，不无限等待）
            return loader.get();

        } catch (InterruptedException e) {
            Thread.currentThread().interrupt();
            return loader.get();
        } finally {
            // 4) 释放锁：必须校验 token，防止误删别人的锁
            unlock(lockKey, token);
        }
    }

    /** 用 Lua 保证「比较 + 删除」的原子性 */
    private static final String UNLOCK_LUA =
            "if redis.call('get', KEYS[1]) == ARGV[1] then " +
            "  return redis.call('del', KEYS[1]) " +
            "else return 0 end";

    private void unlock(String key, String token) {
        redis.execute(new DefaultRedisScript<>(UNLOCK_LUA, Long.class),
                      Collections.singletonList(key), token);
    }
}

5. Pipeline：什么时候真有用

/**
 * Pipeline 实测：本机/局域网下，批量写 10000 个 key
 */
public void compareWrite() {
    int N = 10000;

    // ---- 方式 1：逐条 set（每次一个 RTT）----
    long t1 = System.currentTimeMillis();
    for (int i = 0; i < N; i++) {
        redis.opsForValue().set("k" + i, "v" + i);
    }
    System.out.println("逐条: " + (System.currentTimeMillis() - t1) + "ms");
    // 局域网 0.1ms RTT → 约 1000ms+；本机约 300-600ms

    // ---- 方式 2：Pipeline（一次发送多条，只等一次响应）----
    long t2 = System.currentTimeMillis();
    redis.executePipelined((RedisCallback<Object>) conn -> {
        for (int i = 0; i < N; i++) {
            conn.stringCommands().set(("k" + i).getBytes(), ("v" + i).getBytes());
        }
        return null;
    });
    System.out.println("Pipeline: " + (System.currentTimeMillis() - t2) + "ms");
    // 通常快 5-20 倍（取决于网络 RTT）

    // ---- 方式 3：Pipeline + 分批（避免单次过多命令导致内存暴涨）----
    int batchSize = 500;
    for (int start = 0; start < N; start += batchSize) {
        final int s = start;
        redis.executePipelined((RedisCallback<Object>) conn -> {
            for (int i = s; i < Math.min(s + batchSize, N); i++) {
                conn.stringCommands().set(("k" + i).getBytes(), ("v" + i).getBytes());
            }
            return null;
        });
    }
}
🚨 Pipeline 的四个关键认知（面试高频深挖点）
  1. Pipeline 不是原子的：它只是把多条命令一次性打包发送，Redis 仍然是逐条执行。中间可能插入其他客户端的命令。要原子性用 MULTI/EXEC 或 Lua。
  2. 不是「越批量越好」：单次 pipeline 命令太多，客户端和 Redis 都要缓存大量数据（Redis 要为回复分配输出缓冲区），可能触发输出缓冲区超限（client-output-buffer-limit）导致连接被断开。生产建议每批 100~1000 条。
  3. 收益取决于网络 RTT：局域网 RTT 0.1ms 时收益有限（主要是 syscall 次数减少）；跨机房 RTT 5ms 时收益巨大。「局域网下 Pipeline 收益不大」是很反直觉但正确的认知。
  4. 与 MULTI 一起用会变慢：在 MULTI 里放大量命令，Redis 会把整个事务的回复缓存在内存里，容易 OOM。正确做法是 pipeline 批量命令，每批单独 EXEC。

真实案例：有个线上事故就是「pipeline 一次塞 50 万条命令」，导致 Redis 输出缓冲区达到 1GB，触发 client-output-buffer-limit 被强制断开连接，客户端报 Unexpected end of stream。

6. 连接池：最常见的线上性能杀手

/**
 * JedisPool 生产级配置 + 使用规范
 */
@Configuration
public class JedisConfig {

    @Bean
    public JedisPool jedisPool(
            @Value("${redis.host}") String host,
            @Value("${redis.port}") int port,
            @Value("${redis.password}") String password) {

        JedisPoolConfig config = new JedisPoolConfig();

        // ---- 连接数 ----
        config.setMaxTotal(64);            // 最大连接数 = 单实例能扛的并发 × 安全系数
        config.setMaxIdle(16);             // 最大空闲连接（避免频繁创建销毁）
        config.setMinIdle(8);              // 最小空闲连接（预热，防突发流量抖动）
        config.setMaxWaitMillis(1000);     // ⚠️ 池耗尽时的等待时间，必须设置！否则线程无限阻塞

        // ---- 连接有效性检测 ----
        config.setTestOnBorrow(false);      // 借出时检测（有 RTT 开销，高并发下慎用）
        config.setTestOnReturn(false);
        config.setTestWhileIdle(true);       // ✅ 空闲时检测（推荐，配合下面两个参数）
        config.setTimeBetweenEvictionRunsMillis(30000);  // 30秒检测一次空闲连接
        config.setMinEvictableIdleTimeMillis(60000);     // 空闲超过60秒则回收
        config.setNumTestsPerEvictionRun(-1);              // 每次检测全部空闲连接

        // ---- 连接超时（防止网络故障时线程堆积）----
        int timeout = 3000;
        return new JedisPool(config, host, port, timeout, password);
    }
}

/**
 * ✅ 正确的使用方式：try-with-resources 保证归还
 */
public String getValue(String key) {
    try (Jedis jedis = jedisPool.getResource()) {   // 自动归还，即使抛异常
        return jedis.get(key);
    }
}

/**
 * ❌ 错误示范 1：忘记归还 → 连接泄漏 → 池耗尽 → 全站阻塞
 */
public String leak(String key) {
    Jedis jedis = jedisPool.getResource();
    return jedis.get(key);      // 没有 close()，这个连接永远不会回到池里！
}

「你的服务有 50 个实例，Redis 连接池 maxTotal=64，会有什么问题？」

答案：50 × 64 = 3200 个连接。如果 Redis 的 maxclients 是默认的 10000，看似够；但如果有 4 个服务都这么配，就是 12800 个连接，超过 maxclients，新连接直接被拒绝（ERR max number of clients reached），生产上会出现「部分实例正常、部分实例全部报错」的诡异现象。

正确做法：先算总连接预算（Redis 侧 maxclients 的 70%），再除以实例数得到单实例池上限。同时注意 Lettuce 的共享连接模型——Lettuce 默认是单连接多路复用，可以几百个线程共用一个连接，所以 Lettuce 的连接数需求远小于 Jedis。

关键认知（面试必讲）：Redis 事务不具备「回滚」能力，因为它追求简单和性能，没有像 MySQL 那样的 undo log。所以：

  • 想用 Redis 事务实现「扣库存 + 记流水」的原子性，是错误的——如果第二条命令失败，第一条已经生效了。
  • 正确做法：用 Lua 脚本（脚本中的错误会导致脚本中止，且脚本整体在 Redis 中是单线程原子执行的），或者用 WATCH 实现乐观锁（CAS）。
  • 所以面试回答的顺序应该是：需要原子性 → 优先考虑 Lua / Redis Function；需要高性能批量 → Pipeline；MULTI/EXEC 主要用于 WATCH 乐观锁 + 简单批量。

WATCH 的用法：WATCH key → 读值 → 计算 → MULTI → SET key newValue → EXEC；如果 key 在 WATCH 后被别人改过，EXEC 返回 nil（事务放弃）。这是 Redis 版的 CAS。

为什么 Redis 的 Lua 脚本能做到原子性？它有什么限制？高级

原子性的来源：Redis 执行 Lua 脚本时，整个脚本作为一个命令来处理，在单线程模型下执行期间不会处理其他客户端的命令（scripts are atomic）。这和普通命令的单线程执行是同一套机制——不是通过锁，而是通过「同一时间只有一个命令在执行」。

限制与风险（这几条很值钱）：

  1. 脚本必须快：脚本执行期间阻塞整个 Redis，所以严禁在脚本里做 O(N) 大操作（遍历大集合、大循环）。Redis 有 lua-time-limit（默认 5 秒），超时后 Redis 会开始回复 BUSY 错误，但脚本不会自动终止——只能 SCRIPT KILL（如果脚本还没写数据）或 SHUTDOWN NOSAVE（已经写了数据时）。这就是为什么「Lua 脚本写死循环」是经典的生产事故。
  2. 不能跨 slot：Cluster 模式下，脚本中用到的所有 key 必须在同一个 slot（用 hash tag 保证），否则报 CROSSSLOT 错误。
  3. 随机写与复制：脚本中如果用了 RANDOMKEY、SRANDMEMBER、TIME 等非确定性命令，在旧版本会导致主从数据不一致。Redis 5.0+ 通过「效果复制」（复制脚本产生的实际写命令而非脚本本身）解决了这个问题，但要知道这个历史细节。
  4. 调试困难：只能用 redis-cli --eval 或 Redis Insight 的调试器，日志输出到 Redis 日志（redis.log）。
  5. 7.0 起推荐 Function 替代 Lua：Function 支持持久化（FUNCTION LOAD 后可跨重启保留）、可命名调用、可复用，比「每次传整段脚本」更优。但要注意 Function 也需要在集群中部署到所有节点。

实战建议：「用 Lua 实现『判断-操作』的原子组合（比如释放分布式锁、滑动窗口限流、库存扣减），但脚本要短小、纯内存计算、不做批量遍历。」

你们项目 Redis 的 key 是怎么设计的？高级

按「规范 → 理由 → 工具」三段回答：

1. 命名规范：业务模块:实体:唯一标识[:子维度]，例如：

user:profile:1001              # 用户资料
order:detail:2026093010001     # 订单详情
product:stock:sku_2001         # 商品库存
cart:{user:1001}:items         # 用 hash tag 保证同用户的多 key 同 slot
rate:api:/order/submit:uid:1001   # 限流
lock:order:1001                # 分布式锁

2. 设计理由：

  • 冒号分隔：Redis Insight / 客户端可视化时能形成层级树，也便于 SCAN 按前缀遍历。
  • 前缀可枚举：便于 ACL 按 ~order:* 授权、便于按业务批量清理、便于监控按前缀统计内存。
  • 避免特殊字符：不用空格、换行、{}（除 hash tag）、避免超长 key（key 本身也占内存）。
  • 不带时间戳除非必要：会破坏 key 复用，导致内存碎片。

3. 配套工具与制度（这段最能体现成熟度）：

  • 维护一份 key 清单文档：前缀、结构类型、TTL、负责人、预估大小。听起来土，但接手三年老系统时能省下几天。
  • 接入规范检查：CI 阶段静态扫描代码中的 key 字面量，检查是否符合规范、是否设置 TTL。
  • 监控按前缀统计：识别哪个业务在膨胀、哪个前缀出了大 key。
  • 版本化：结构变更时用 user:v2:profile:1001，避免新旧结构反序列化冲突。
缓存该不该设置过期时间？设多久？进阶

结论：绝大多数缓存都应该设 TTL，但 TTL 是「兜底」而不是「失效手段」。

  1. 为什么不设 TTL 很危险：数据永久驻留，一旦业务逻辑有 bug 写了脏数据，或者数据量持续增长，最终内存打满触发淘汰——这时淘汰的 key 是随机/按 LRU 的，可能把还在用的数据淘汰掉，反而造成更严重的抖动。
  2. TTL 是「最终一致性的兜底」：比如商品价格改了但删除缓存失败（网络抖动、服务重启），TTL 到期后自动纠正。TTL 越短，不一致窗口越短，但缓存命中率越低、回源压力越大。
  3. 怎么定 TTL 的值：
    • 看数据变化的频率和业务对陈旧的容忍度。商品详情、用户资料这类可以容忍几秒到几分钟的，设 5-30 分钟。
    • 看回源（DB）的承受能力：TTL 太短，缓存 miss 率高，DB 压力大。用命中率指标反推：命中率 = 1 - 回源QPS/总请求QPS，一般要求 90%+。
    • 看内存预算：TTL 越长，内存占用越大（活跃数据堆积）。
  4. 一定要加随机抖动：TTL = base + random(0, jitter)，避免大量 key 同时过期导致缓存雪崩。这是必答点。
  5. 热点 key 用「逻辑过期」而非物理 TTL：物理 TTL 到期瞬间会有大量请求回源（击穿）。逻辑过期是——不设物理 TTL，value 里带一个 expireTime 字段；读到发现逻辑过期时，由一个线程异步更新，其他线程仍返回旧数据。这样任何时候都可用，不会击穿。
