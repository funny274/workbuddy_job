Day3.1 · 主从复制与哨兵：高可用的第一层

一句话结论

主从复制解决「数据多个副本 + 读写分离」，哨兵解决「主节点挂了自动切换」。面试的深水区在两处：① PSYNC 的全量/增量切换逻辑与 repl_backlog 的关系；② 脑裂（split-brain）导致的数据丢失，以及 min-replicas 怎么防。

1. 动手：搭建主从并观察复制

########## 方式 1：命令行（临时测试）##########
# 在从节点上执行
REPLICAOF 10.0.0.5 6379
# 或旧命令 SLAVEOF 10.0.0.5 6379（已弃用但兼容）

# 取消复制，变回主节点
REPLICAOF NO ONE

########## 方式 2：配置文件（生产标准）##########

replica-read-only yes          # 从节点只读（默认）
replica-serve-stale-data yes    # 与主节点断连时，是否继续响应（yes 用旧数据，no 报错）
replica-priority 100            # 哨兵选主的优先级，越小越优先
repl-diskless-sync yes          # 无盘复制（见下文）
repl-diskless-sync-delay 5      # 等待多个从节点一起同步（秒）

2. PSYNC：全量同步与增量同步

✅ 全量同步（Full Resynchronization）完整流程

从节点首次连接主节点（或无法增量同步）时执行：

从节点发起 PSYNC

发送 PSYNC ? -1（? 表示不知道主节点 replid，-1 表示没有偏移量）。

主节点回复 +FULLRESYNC

主节点返回 +FULLRESYNC <replid> <offset>，告诉从节点「我的复制 ID 是这个，当前偏移量是这个」。

主节点执行 BGSAVE

fork 子进程生成 RDB 文件。同时，主节点开始把这段时间的所有写命令写入「复制缓冲区（replication buffer）」——这个缓冲区是每个从节点一个。

传输 RDB

磁盘复制（默认）：RDB 写到磁盘再传给从节点。
无盘复制（repl-diskless-sync yes）：RDB 不落盘，直接通过 socket 边生成边发送。优势：省磁盘 I/O、对磁盘慢的机器更友好。劣势：如果从节点连接中断，整个传输白费。

从节点清空数据并加载 RDB

从节点先 FLUSHALL 清空自己的数据（！），再加载 RDB。所以 从节点上如果有本地数据会被清掉——不要往从节点写数据。

主节点发送复制缓冲区的增量

把步骤 3-5 期间积累的写命令发给从节点，从节点重放。至此主从数据一致。

进入命令传播阶段

之后主节点每执行一个写命令，就异步发给所有从节点（不等待确认）。同时主节点会把命令写入复制积压缓冲区（repl_backlog）。

✅ 增量同步（Partial Resynchronization）与 repl_backlog 的关系

场景：从节点与主节点断连（网络抖动、从节点重启），重连后如果可能，希望只同步「断连期间缺失的那部分」，而不是全量重传。

关键结构：repl_backlog（复制积压缓冲区）

  • 是一个固定大小的环形缓冲区（默认 repl-backlog-size 1mb），主节点把所有写命令都写进去。
  • 记录 master_repl_offset（主节点总偏移）、repl_backlog_first_byte_offset（最旧数据的位置）、repl_backlog_histlen（有效数据长度）。

增量同步的判定逻辑：从节点重连后发送 PSYNC <replid> <offset>，主节点检查：

  1. replid 是否匹配（是自己的 replid 或 replid2）？
  2. offset 是否在 backlog 范围内（即 offset >= repl_backlog_first_byte_offset）？

两个条件都满足 → 回复 +CONTINUE，只发送缺失那部分（增量同步）。
任一不满足 → 回复 +FULLRESYNC，走全量同步。

核心结论：backlog 越小，越容易退化到全量同步。如果从节点断连时间长、写入量大，backlog 早被覆盖了，只能全量重传——这时会出现「网络带宽打满 + 主节点 fork」的双重冲击。

容量估算公式（面试加分）：

repl-backlog-size = 平均写入速率(字节/秒) × 最大允许断连时间(秒) × 安全系数(2)
# 例：写入 5MB/s，允许断连 10 秒 → 5 × 10 × 2 = 100MB
# 所以生产上 repl-backlog-size 通常设置为 64MB ~ 512MB，而不是默认的 1MB

CONFIG SET repl-backlog-size 256mb
CONFIG GET repl-backlog-ttl   # backlog 在没有从节点后多久被释放（默认 3600 秒）
⚠️ replid 与 replid2：主从切换后的「血脉」问题

每个 Redis 实例启动时会生成一个 40 位的 replid（随机字符串），标识「这份数据集的血统」。

  • 从节点复制主节点后，继承主节点的 replid。
  • 主从切换后（哨兵选出新主），新主节点会改变自己的 replid（因为它成了新的数据源头）。为了不让其他从节点被迫全量同步，旧主节点的 replid 会被保存到 replid2。
  • 这样，其他从节点用旧 replid 来 PSYNC 时，主节点检查到 replid2 匹配，仍可走增量同步。

为什么重要：如果主从切换后所有从节点都要全量同步，会引发「同时全量同步风暴」——多个从节点同时请求 RDB，主节点要 fork 多次（实际是一次 BGSAVE 服务多个从节点，但复制缓冲区要各一份），网络和内存压力巨大。能讲清 replid2 的设计意图，说明你读过源码。

3. 哨兵（Sentinel）：自动故障转移

哨兵的四项工作

工作机制
监控每秒对主节点、从节点、其他哨兵执行 PING，判断是否可达；每 10 秒发送 INFO 更新拓扑；每 2 秒通过 __sentinel__:hello 频道交换信息
通知通过 Pub/Sub 把故障事件发布出去，供监控系统消费；可用脚本触发告警
自动故障转移主观下线 → 客观下线 → 选举 leader → 选新主 → 切换 → 通知客户端
配置提供者客户端连哨兵获取当前主节点地址，因此客户端要知道的是「哨兵地址」而不是「主节点地址」
✅ 故障转移的完整流程（面试必答）
主观下线（SDOWN）

某个哨兵发现主节点在 down-after-milliseconds（默认 30 秒，建议 5-10 秒）内一直没响应 PING，就把它标记为主观下线——只是这个哨兵自己认为它挂了。

客观下线（ODOWN）

该哨兵向其他哨兵发送 SENTINEL is-master-down-by-addr 询问。如果超过 quorum 个哨兵也认为主节点下线，就标记为客观下线。

quorum 在配置里指定（sentinel monitor mymaster 1.2.3.4 6379 2 里的 2）。quorum 是判定下线所需的最小票数，与实际选举 leader 所需票数是两件事。

选举领头哨兵（Leader Election）

基于 Raft 算法：

  • 发现客观下线的哨兵向其他哨兵请求投票。
  • 每个哨兵在一个任期（epoch）内只能投一票，先到先得。
  • 获得票数 ≥ max(quorum, 哨兵总数/2 + 1) 的哨兵成为 leader。
  • 如果没有哨兵拿到多数票，等待随机时间后发起新一轮选举（epoch +1）。

为什么需要「多数」而不是 quorum：quorum 只是「确认下线」的门槛。如果 quorum=2 而哨兵总数是 5，2 票不足以避免「网络分区两侧各选出一个 leader」的脑裂问题，所以要求过半数才能当 leader。

选择新的主节点

Leader 从合格的从节点中按以下顺序筛选：

  1. 过滤不健康的：主观下线、断连超过 down-after-milliseconds × 10、与主节点断连超过 down-after-milliseconds 的从节点被淘汰。
  2. 按 replica-priority 排序：优先级小的优先（replica-priority 0 表示永不选为master）。
  3. 优先级相同则看复制偏移量：offset 最大的（数据最新）。这是「尽量少丢数据」的关键。
  4. offset 也相同则看 runid：字典序小的。
执行切换

Leader 向选中的从节点发送 REPLICAOF NO ONE（升为主），向其他从节点发送 REPLICAOF <新主>（改跟随）。旧主节点恢复后，哨兵会把它降级为从节点，跟随新主。

通知客户端

哨兵通过 Pub/Sub 频道 +switch-master 广播新主地址。客户端必须实现订阅并刷新连接池（Jedis/Lettuce/Redisson 都内置了 Sentinel 支持）。

########## 生产级哨兵配置 ##########
port 26379
daemonize no
logfile "/var/log/redis/sentinel.log"
dir "/var/lib/redis/sentinel"       # 哨兵会在这里写配置（记录已知的从节点和状态）

# ---- 监控的主节点 ----
sentinel monitor mymaster 10.0.0.5 6379 2
#                                  ↑ quorum=2，至少 2 个哨兵同意才判客观下线

# ---- 认证 ----
sentinel auth-pass mymaster "主节点密码"

# ---- 下线判定 ----
sentinel down-after-milliseconds mymaster 5000   # 5 秒无响应判主观下线

# ---- 故障转移 ----
sentinel failover-timeout mymaster 60000       # 同一主节点的两次 failover 间隔至少 60s
sentinel parallel-syncs mymaster 1              # 每次只允许 1 个从节点同时同步新主
#   ⭐ parallel-syncs 很关键：值越大切换越快，但会有更多从节点同时进
#      入"不可用"状态（同步期间只读甚至不可读）。值小则切换慢但不影响可用性。

# ---- 安全 ----
requirepass "哨兵自己的密码"             # 6.2+ 支持哨兵间认证
sentinel sentinel-user default
sentinel sentinel-pass "哨兵密码"

# ---- 通知（可选，用于告警）----
sentinel notification-script mymaster /etc/redis/notify.sh
sentinel client-reconfig-script mymaster /etc/redis/reconfig.sh
#   client-reconfig-script 在切换完成后执行，可用来做 DNS 更新、网关配置刷新

# ---- 7.0+ 支持主机名解析 ----
sentinel resolve-hostnames yes
sentinel announce-hostnames yes
########## 哨兵运维命令 ##########
sentinel masters                                # 所有被监控的主节点及状态
sentinel master mymaster                        # 详查某个主节点（含所有从节点信息）
sentinel replicas mymaster                      # 从节点列表
sentinel sentinels mymaster                     # 其他哨兵节点
sentinel get-master-addr-by-name mymaster       # ⭐ 客户端用它获取当前主节点地址

# 手动触发故障转移（演练用！）
sentinel failover mymaster
#   ⭐ 生产应定期做「故障转移演练」，验证切换链路可用

# 修改配置（部分参数支持运行时修改）
sentinel set mymaster down-after-milliseconds 10000
sentinel set mymaster parallel-syncs 2
sentinel flushconfig                            # 把配置强制写回磁盘
sentinel reset mymaster                         # 重置状态（慎用）

4. 脑裂：主从架构最大的坑

🚨 脑裂（Split-Brain）导致数据丢失的完整推演

场景：主节点与「哨兵 + 从节点」之间的网络断了（但客户端与主节点还是通的）。

  1. 哨兵们判定主节点主观下线 → 客观下线 → 选举 leader → 把某个从节点提升为新主。
  2. 但旧主节点还活着，还在接受客户端的写请求！（因为客户端到它的网络是通的）
  3. 此时系统里有两个主节点：旧主（在写新数据）+ 新主（在服务读，且它没有旧主新写的数据）。
  4. 网络恢复后，哨兵会把旧主降级为从节点，让它 REPLICAOF 新主。
  5. 旧主上「断连期间写入的数据」被全部清空（因为全量同步会先 FLUSHALL 再加载新主的 RDB）！

这就是脑裂数据丢失：客户端以为写入成功了，但数据永久丢失。

典型案例：分布式锁场景。旧主上创建的锁 key 在同步后消失，另一个客户端又能拿到锁——两个客户端同时持锁，业务逻辑失效。这就是为什么「Redlock 也无法解决所有问题」的讨论中，脑裂总被提起。

防护手段（两个必须配的配置）：

# 主节点：至少要有 N 个从节点连接且延迟 ≤ M 秒，才接受写入
min-replicas-to-write 1
min-replicas-max-lag 10
# 含义：如果连不上 1 个从节点，或从节点延迟超过 10 秒，
#      主节点拒绝所有写请求，返回 NOREPLICAS 错误
# 效果：脑裂时旧主因为连不上从节点而拒绝写 → 不会产生"会丢的数据"

# 从节点：与主节点断连超过 N 秒后，不再响应客户端（返回错误）
replica-serve-stale-data no
# 效果：避免客户端读到过期数据

权衡（面试一定要说）：这两个配置降低可用性以换取一致性。配了 min-replicas-to-write 1 后，即使只有一个从节点短暂抖动，主节点也会拒绝写入，业务报错。所以要根据业务对「丢数据」和「不可写」的容忍度来选择——缓存场景可以不配，钱相关的必须配。

💡 关于 WAIT 命令

WAIT numreplicas timeout 会阻塞当前客户端，直到「至少 numreplicas 个从节点确认收到」或超时。

SET order:1001 '{"status":"paid"}'
WAIT 1 100        # 等 1 个从节点确认，最多等 100ms
# 返回实际确认的从节点数量

用途：把「异步复制」变成「同步确认」，用于对数据安全要求高的少数写操作。
注意：① WAIT 只保证「命令已到达从节点」，不保证从节点已经执行完；② 它不改变默认的异步复制语义（不影响其他客户端）；③ 会增加延迟，不能全量使用。

5. 读写分离的收益与陷阱

维度说明
收益读流量分摊到多个从节点，主节点专注写；可以横向加从节点提升读吞吐
陷阱 1：不一致复制是异步的，从节点可能读到旧数据。刚写完立刻读（写后读）大概率读到旧值。
陷阱 2：过期数据从节点上过期 key 不主动删（Day2.3 讲过），但读取时会做逻辑过期判断，返回 nil。不过如果 Redis 版本老或配置不当仍可能读到过期数据。
陷阱 3：从节点故障的影响如果客户端连接池没配好，某个从节点挂了会导致部分请求失败——需要客户端支持拓扑感知和故障剔除。
陷阱 4：从节点数增加放大写入每个从节点都要接收全量写命令，主节点的复制带宽和 CPU 开销（命令传播、缓冲区）随从节点数线性增长。从节点不是越多越好。

解决「写后读不一致」的方案：

  1. 关键读走主节点：对一致性敏感的读（如刚下单后查订单）强制路由到主节点。
  2. 基于偏移量的一致性读：写操作记录返回的 master_repl_offset，读时带上这个偏移量，客户端等待从节点追上再读（Lettuce 支持这种模式）。
  3. 本地缓存兜底：写完后把新值放本地缓存（短 TTL），读到本地缓存直接返回。
  4. 业务上规避：把「写后立刻读」的场景改成「写后前端用返回的数据渲染」，不依赖读。

面试深度问答

主从复制的原理？全量同步和增量同步的区别？基础

整体流程：

  1. 从节点连上主节点，发送 PSYNC ? -1（首次）或 PSYNC <replid> <offset>（断连重连）。
  2. 主节点判断能否增量：replid 匹配 且 offset 在 repl_backlog 范围内 → 回复 +CONTINUE，只发缺失部分（增量）。
  3. 否则回复 +FULLRESYNC <replid> <offset>，执行 BGSAVE 生成 RDB 发给从节点，期间新写命令存入复制缓冲区；从节点清空自己的数据、加载 RDB，再重放复制缓冲区的命令。
  4. 之后进入命令传播阶段：主节点每执行写命令，异步发给所有从节点，同时写入 repl_backlog。

全量 vs 增量对比：

维度全量同步增量同步
传输量整份 RDB（可能几 GB）仅缺失的命令
主节点开销fork + COW 内存 + 网络带宽几乎无
从节点开销FLUSHALL + 加载 RDB（从节点不可用）重放少量命令
依赖—repl_backlog 是否覆盖断连期间的写入

加分点：一定要提 repl-backlog-size 的容量估算公式，并指出默认 1MB 太小，生产应根据写入速率设置为几十到几百 MB，否则从节点每次网络抖动都会退化成全量同步，引发「网络打满 + fork 阻塞」的双重打击。

哨兵的工作原理？它怎么选新主？进阶

按「监控 → 判下线 → 选举 → 选主 → 切换 → 通知」六步回答（见本节第 3 节）。重点强调三个容易被追问的点：

  1. 主观下线 vs 客观下线：单个哨兵的判断是主观的（可能因网络抖动误判），必须超过 quorum 个哨兵都认为下线才算客观下线。这是为了避免单点误判引发无谓切换。
  2. quorum ≠ leader 选举票数：quorum 是「判下线」的门槛；选 leader 需要超过半数（哨兵总数/2 + 1）的票。这是 Raft 的要求，防止网络分区两侧各选一个 leader。这是最高频的深挖点。
  3. 选新主的顺序：过滤不健康的 → replica-priority 最小 → 复制偏移量 offset 最大（数据最新） → runid 最小。

部署建议：

  • 哨兵至少 3 个（奇数个），且分布在不同物理机/可用区。2 个哨兵时，挂 1 个就无法达到多数票，无法切换。
  • quorum 建议设为「哨兵总数/2 + 1」，与多数票一致，避免误判。
  • 哨兵本身不是主从的，哨兵之间通过 Pub/Sub 互相发现（不需要互相配置），只要配置同一个主节点即可自动组成集群。
  • down-after-milliseconds 不要太小（网络抖动会误判），也不宜太大（切换慢）。5-10 秒是比较通用的值。
什么是脑裂？怎么防止？高级

见本节第 4 节的完整推演。回答框架：

  1. 定义：网络分区导致「旧主仍然可写、新主已选出」，系统短时间存在两个主节点。
  2. 后果：网络恢复后旧主被降级为从节点，会执行全量同步（先 FLUSHALL），旧主在分区期间写入的数据全部丢失。业务侧无法感知（写请求都成功了）。
  3. 为什么危险：典型的「静默数据丢失」，比服务不可用更难发现和排查。分布式锁场景会导致互斥失效。
  4. 防护方案：
    • 主节点配 min-replicas-to-write 1 + min-replicas-max-lag 10——分区时旧主因连不上从节点而拒绝写。
    • 从节点配 replica-serve-stale-data no——断连时对外报错，避免读到过期数据。
    • 架构上考虑：如果数据极其关键，用 Redis Cluster（有更多节点参与投票，且分片降低影响面），或用 WAIT 命令做同步确认。
    • 业务上：关键数据不要只依赖 Redis，用 DB + 对账兜底。
  5. trade-off：这些配置都以降低可用性为代价（连不上从节点就拒绝写），要根据业务容忍度选择。

额外加分：提到「脑裂不仅存在于哨兵架构，Cluster 也有类似问题（分区时主节点可能仍接受写入）」，以及「Redis 的 min-replicas-to-write 在 Cluster 模式下每个主分片单独生效」。

从节点为什么要配 replica-read-only yes？能往从节点写吗？进阶

默认就是 yes，强烈建议保持。

为什么不能往从节点写：

  1. 数据会被覆盖：从节点执行全量同步时会 FLUSHALL，本地写入的数据全没了。
  2. 破坏一致性：从节点的数据是主节点的副本，本地写入会让主从数据不一致，主从切换后这些「本地数据」会丢失，且可能造成业务逻辑混乱。
  3. 无法传播：从节点上的写入不会传播给主节点或其他从节点（Redis 不支持双向复制）。

什么时候会设为 no：

  • 从节点上跑「临时计算」的场景（比如 Redis 作为计算节点的缓存），但这是很危险的做法。
  • 有些公司用「从节点做本地缓存预热」，但那应该用独立的 key 前缀并接受被清空的风险。

生产规范：保持 replica-read-only yes。如果需要在从节点做特殊操作，用独立实例而不是从节点。

Redis 主从复制是同步还是异步的？进阶

异步复制（生产环境默认）。

  1. 主节点执行完写命令后立即返回给客户端，然后异步发送给从节点。
  2. 主从之间不等待确认，所以主节点不会因为从节点慢而变慢——这是性能优势，也是数据丢失风险的来源。

为什么不用同步复制：性能和可用性。同步复制意味着主节点要等所有从节点确认，任何从节点慢都会拖慢主节点；从节点挂了主节点写不了，可用性下降。这与 Redis「高性能」的定位冲突。

如何让它「更同步」：

  • WAIT numreplicas timeout：按客户端粒度做同步等待，只对关键写操作使用。
  • min-replicas-to-write：强制「至少有 N 个从节点在线」才允许写，这是一种「弱同步」保证。

面试话术：「Redis 主从是异步复制，这是为了性能——主节点不必等待从节点确认。代价是主节点宕机时可能丢掉尚未同步的写命令（通常是毫秒到秒级）。如果需要更强的保证，可以用 WAIT 命令做单次同步确认，或用 min-replicas-to-write 在集群层面约束；但根本的解法是**‘不能丢的数据不要只放在 Redis’**。」

补充：主节点的复制相关配置 repl-disable-tcp-nodelay——设为 no（默认）时，复制命令会立即发送（延迟低但网络包多）；设为 yes 时合并发送（省带宽但延迟增加）。跨机房场景可以考虑设 yes。

主从延迟很大怎么办？高级

先量化，再定位，最后优化（这是标准的问题解决框架）：

量化延迟
redis-cli -h master info replication | grep -E 'master_repl_offset|slave'
redis-cli -h slave  info replication | grep -E 'slave_repl_offset|master_link_status|master_last_io_seconds_ago'
# 延迟字节 = master_repl_offset - slave_repl_offset
# 也可以看 slave0:...lag=N 这个字段（秒，最直观）

同时看 master_last_io_seconds_ago：如果持续 > 10 秒，说明连接有问题。

INFO stats | grep -E 'sync_full|sync_partial_ok|sync_partial_err'
# sync_full         → 全量同步次数（持续增长 = 增量同步失败，要紧！）
# sync_partial_ok   → 增量同步成功次数
# sync_partial_err  → 增量同步失败次数

如果 sync_full 在持续增长，说明每次断连都退化成全量同步 → 优先检查 repl-backlog-size。

业务侧应对
  • 对一致性敏感的读走主节点。
  • 读多写少的场景，从节点只承载「容忍延迟」的读（如统计、报表）。
  • 设置「最大可接受延迟」阈值，超过则降级到主节点读。
