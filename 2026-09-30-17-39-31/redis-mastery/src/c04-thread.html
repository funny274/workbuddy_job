Day2.1 · 线程模型：为什么单线程能扛 10 万 QPS

一句话结论

「Redis 快」不是因为单线程，而是因为纯内存 + 高效数据结构 + I/O 多路复用 + 避免锁竞争；单线程是「在那个前提下」的简化选择，且它的瓶颈是CPU 单核和网络，不是并发数。6.0 之后 I/O 线程化，但命令执行仍然单线程——这个区分是面试的核心考点。

1. 五个「快」的原因（分层回答，不要背名词）

原因机制量级/收益面试追问点
纯内存操作数据全在内存，读写是纳秒级，无磁盘 I/O内存随机访问 ~100ns vs SSD 随机读 ~100μs，差 1000 倍持久化怎么办？（异步 RDB/AOF，不阻塞主流程）
高效数据结构SDS、listpack、quicklist、跳表，都是为场景定制的紧凑结构对比通用结构（如 Java HashMap）省大量内存和指针跳转为什么不用通用结构？（内存碎片、指针开销、缓存不友好）
单线程无锁命令串行执行，天然原子，无线程切换、无锁竞争、无 CAS 失败重试省下锁开销与上下文切换（切换一次约 1-5μs）那并发怎么上来？（epoll 处理连接，单线程处理命令）
I/O 多路复用epoll 单线程监听海量连接，事件驱动10 万并发连接只需 1 个线程select/poll/epoll 区别？（见下）
RESP 简单协议文本协议，解析简单（状态、错误、整数、批量、数组 5 种类型）解析开销小，跨语言实现容易RESP3 新增了什么？（Map/Set/Double/Push 类型，支持客户端缓存）
⚠️ 一个常见错误答法

❌「Redis 是单线程的，所以快。」

这个逻辑是错的——单线程本身不会带来性能，反而限制吞吐（只能用 1 个核）。正确的表述是：

✅「Redis 把主要数据结构和算法做到了极致，然后选择了单线程来避免并发控制的复杂度——因为它的瓶颈在网络和内存访问，而不在 CPU 并行度。单线程让代码简单、行为确定性、每个命令天然原子。当网络成为瓶颈后，6.0 引入了多线程 I/O，但命令执行仍然单线程以保持原子性。」

2. epoll、select、poll 的对比（高频原题）

机制数据结构时间复杂度最大连接数核心缺陷
select位图（fd_set）O(N) 遍历所有 fd 找就绪的受限（FD_SETSIZE，通常 1024）① fd 数量受限 ② 每次调用都要把 fd 集合从用户态拷贝到内核态 ③ 返回后还要 O(N) 遍历哪些就绪了
poll数组（pollfd[]）O(N) 遍历无硬限制（受内存限制）仍需要拷贝整个数组 + O(N) 遍历；连接多时性能线性下降
epoll
Redis 使用		红黑树（管理 fd）+ 就绪链表O(1) 获取就绪事件无硬限制（受内存限制）代码更复杂；Linux 专有（BSD 是 kqueue，Windows 是 IOCP）
✅ epoll 为什么快？三个关键设计
  1. 红黑树管理 fd：epoll_ctl 增删改 fd 用红黑树，O(log N)，且只需注册一次，不用每次调用都传整个集合。
  2. 就绪链表（rdllist）避免遍历：fd 就绪时由内核回调把它挂到就绪链表上，epoll_wait 直接返回链表内容，O(1) 拿到就绪集合，不需要 O(N) 扫描全部 fd。这是相对 select/poll 最本质的改进。
  3. mmap 共享内存避免拷贝：内核与用户空间通过 mmap 共享一块内存存放 epoll 事件，避免 select/poll 那种「每次调用都要把 fd 集合从用户态拷贝到内核态」的开销。

两种触发模式（面试常追问）：

  • LT（水平触发，Level Triggered）：只要缓冲区有数据就持续通知，直到读完。是 epoll 默认模式，编程简单、不易漏事件，Redis 用的是 LT。
  • ET（边缘触发，Edge Triggered）：只在状态变化时通知一次，必须一次把数据读完（循环 read 到 EAGAIN），否则事件丢失。性能更高但编程复杂，Nginx 用 ET。

注意：ET 通常需要配合非阻塞 fd，否则最后一次 read 会阻塞住。

3. Redis 的线程演进史（版本维度回答）

版本线程模型变化要点
1.0 – 5.0纯单线程主线程做全部：socket 读 → 协议解析 → 命令执行 → 回复格式化 → socket 写。另有 3 个后台线程（bio_close_file、bio_aof_fsync、bio_lazy_free）处理关闭文件、AOF 刷盘、异步释放内存。
6.0单线程执行 + 多线程 I/O引入 io-threads，把 socket 读写和协议解析/回复格式化多线程化；命令执行仍在主线程，保证原子性。默认关闭（io-threads 1）。
7.x优化 I/O 线程改进任务分配与长连接处理，减少线程协作开销。
8.0I/O 线程重构I/O 线程采用「按客户端绑定」模型：I/O 线程负责特定客户端的完整读/解析周期，主线程批量处理已解析的查询并生成回复，再由 I/O 线程写回。8 核机器上吞吐最高提升 112%。同时 30+ 项命令级优化，149 个测试命令中 p50 延迟下降 5.4%~87.4%。

🚨 I/O 线程的两个坑
  1. io-threads 不是越大越好：建议为 CPU 核数的 1/2 ~ 3/4，且至少 4 核以上才有意义（因为主线程也要占一个核，还要考虑与业务进程争抢 CPU）。设置成 8 或 16 在 4 核机器上反而因为上下文切换变慢。
  2. io-threads 只加速网络 I/O，不加速命令本身。如果你的慢是「大 key 的 HGETALL 花了 50ms」，加 I/O 线程毫无帮助——那是单线程命令执行的瓶颈，唯一的解法是治理大 key。

4. 单线程的瓶颈在哪里（面试深挖点）

这是区分「背过」和「想过」的分水岭。

瓶颈为什么怎么缓解
单个 O(N) 命令单线程执行，一个慢命令（KEYS、大 key 的 HGETALL、SORT、SMEMBERS）会阻塞所有后续请求禁用危险命令；用 SCAN 替代；治理大 key；用 Lua 控制脚本复杂度
单个 CPU 核命令执行只能用 1 核，无法利用多核做命令并行部署多个 Redis 实例（分片）；用 I/O 线程分担网络
fork 阻塞RDB/AOF 重写时 fork 主线程，内存越大 fork 越慢（页表复制）控制单实例内存（如 <10GB~16GB）；用 vm.overcommit_memory=1；避免在 fork 时大量写入
大 key 删除DEL 大对象需同步释放，可能阻塞秒级用 UNLINK 异步回收；开 lazyfree-lazy-* 系列配置
AOF 刷盘策略always 时主线程每次都 fsync，吞吐暴跌用 everysec（后台线程 fsync）
swap内存被换到磁盘，延迟从微秒到毫秒级关闭 swap 或 vm.swappiness=0；监控 used_memory
网络带宽大 key 返回时网络打满，影响所有请求控制 value 大小；用 pipeline 减少报文头开销
✅ 一个「10 年经验」级别的回答模板

问：Redis 单线程的瓶颈是什么？线上遇到过吗？

「理论上 Redis 单线程的瓶颈有三个层面：① 单核 CPU——命令执行无法并行，所以单实例 QPS 有上限；② 单条慢命令——任何 O(N) 命令都会阻塞后面的所有请求，这是线上最常见的抖动原因；③ fork 与内存——RDB 快照或 AOF 重写时 fork 主线程，内存越大耗时越长，同时 COW 会导致内存峰值上升。

我们线上遇到过一次典型问题：某个商品活动缓存把 800 多个 SKU 的促销信息放在一个 Hash 里，代码用 HGETALL 全量拉取。大促时这个 key 变成热 key，单次 HGETALL 就要几十毫秒，直接把那个分片的 CPU 打到 99.97%，P99 延迟从 0.8ms 涨到 127ms。

解法分三步：止血——对该热点加本地缓存（Caffeine，1 分钟过期）；结构改造——把大 Hash 按 SKU 拆成独立的 String key，改造查询逻辑只取需要的字段；机制建设——接入热 key 探测 + 大 key 扫描巡检，把这类问题提前发现。」

👉 这个回答的价值在于：有理论分层 + 有真实数据 + 有分阶段解法 + 有长效机制。这就是 10 年经验该有的密度。

5. 一次命令的完整生命周期（把知识串起来）

客户端发送 GET user:1001 到收到回复，中间发生了什么：

  1. 建立连接（首次）：客户端 TCP 连接（可选 TLS），Redis 用 epoll 注册该 fd 到红黑树。
  2. 数据到达：内核把数据写入 socket 接收缓冲区，epoll 检测到可读事件，把该 fd 挂到就绪链表。
  3. 事件分发：主线程（或 I/O 线程）从 epoll_wait 返回，拿到就绪的 fd 列表。
  4. 读取与解析：从 socket 读取字节流，按 RESP 协议解析出命令名 + 参数（6.0+ 这部分可多线程）。
  5. 查找命令表：在 redisCommandTable 里按命令名找到对应的处理函数（这就是为什么 Redis 命令是固定集合，无法动态扩展）。
  6. 权限校验：ACL 检查用户是否有权限执行该命令、是否可访问该 key（Redis 6.0+）。
  7. 命令执行：调用 getCommand → 在 dict（全局哈希表）中查找 key → 检查是否过期（惰性删除）→ 返回 SDS。
  8. 传播与持久化：如果是写命令，追加到 AOF 缓冲区 + 复制到从节点缓冲区（repl backlog）。
  9. 回复格式化：把结果编码成 RESP（$5\r\nvalue\r\n）。6.0+ 这部分也可多线程。
  10. 写回 socket：把回复写入 socket 发送缓冲区，由 epoll 检测可写事件后发送（6.0+ 可多线程）。

面试深度问答

Redis 为什么这么快？是单线程吗？基础

四层回答：

  1. 纯内存：数据在内存，读写纳秒级，不用磁盘 I/O。内存随机访问约 100ns，SSD 随机读约 100μs，差三个数量级。
  2. 数据结构高效：SDS、listpack、quicklist、跳表都是为特定场景定制的紧凑结构，避免了通用数据结构的指针开销和内存碎片。
  3. I/O 多路复用 + 单线程执行：用 epoll 单线程管理海量连接，事件驱动；命令串行执行，天然原子，没有锁竞争、没有线程切换、没有 CAS 重试。
  4. 协议简单：RESP 文本协议解析开销小。

关键澄清（一定要主动说）：

  • 「单线程」指的是命令执行是单线程的，不是整个 Redis 只有一个线程。Redis 还有后台线程处理 AOF fsync、异步释放、关闭文件。
  • 6.0 起引入多线程 I/O：socket 读写和协议解析可以多线程，但命令执行仍单线程，以保证原子性、避免加锁。默认关闭。
  • 所以准确表述是：「Redis 用单线程做命令执行，用多线程做网络 I/O。」
为什么命令执行不改成多线程？高级

六个理由，按重要性排序：

  1. 并发正确性：一旦命令并行执行，就必须为每种数据结构引入细粒度锁。而 Redis 的复杂度优势（代码简单、bug 少）会立刻消失。INCR、LPUSH 这类操作在多线程下需要 CAS 或锁，性能反而可能下降。
  2. 数据结构不支持并发：跳表、dict、listpack 都没有线程安全设计。给它们加锁的成本远高于收益。
  3. 瓶颈不在 CPU：Redis 的瓶颈是网络 I/O 和内存带宽，不是 CPU 计算。10 万 QPS 时 CPU 使用率往往只有 30%-50%（大 key 场景除外）。既然瓶颈不在 CPU，加并行度没意义。
  4. 原子性带来的附加值：单线程让 INCR、SETNX、MULTI/EXEC 天然原子，用户不需要考虑并发问题。这是 Redis 的核心卖点之一。
  5. 多线程会引入延迟不确定性：线程调度、锁争抢会带来延迟毛刺。Redis 追求 P99 稳定。
  6. 有更好的横向方案：需要多核并行时，用集群分片（多个 Redis 实例）比单实例多线程更简单、隔离性更好（一个实例出问题不影响其他）。

专家补充：Redis 官方在 8.0 重构 I/O 线程时，仍然守住了「只有内存修改是串行的」这条底线——8.0 的做法是让 I/O 线程负责某个客户端的完整读取/解析周期，主线程批量取走已解析的查询并串行执行。这个架构既能利用多核做 I/O，又保住了原子性。这是「如何在现代化架构的同时保住核心不变量」的教科书级案例。

IO 多路复用中，epoll 和 select 的区别？进阶

从「数据结构 / 复杂度 / 限制 / 拷贝开销」四个维度对比，见上表。核心三点：

  1. select 用位图，fd 数量受限（1024），且每次调用都要传整个集合、内核要 O(N) 扫描、返回后用户态还要 O(N) 扫描。
  2. epoll 用红黑树管理 fd + 就绪链表：注册一次，之后 epoll_wait 直接返回就绪链表，O(1) 拿到就绪事件，不需要遍历全部连接。这是最本质的改进。
  3. epoll 用 mmap 共享内存避免用户态/内核态的 fd 集合拷贝，select/poll 每次调用都要拷贝。

追问：epoll 一定比 select 快吗？
不一定。连接数少且都很活跃时，select/poll 的 O(N) 遍历中 N 很小，开销可以忽略，epoll 的红黑树维护和回调注册反而有额外开销。epoll 的优势在「连接数多但活跃连接少」的场景（这正是互联网长连接服务的特征：10 万连接同时只有几百个在发数据）。能说出这个 trade-off，是通过面试的关键。

Redis 6.0 的多线程，和 Memcached 的多线程有什么不同？高级

这是「架构取舍」的经典对比题：

维度Redis 6.0+Memcached
多线程范围只有网络 I/O 和协议解析/回复格式化命令执行也是多线程（多 worker 线程并行处理请求）
并发控制无需加锁（命令串行）需要对 item 加锁（分段锁/引用计数），存在锁竞争
数据结构丰富（10+ 种），支持原子复合操作只有 KV（value 是不透明字节串）
CPU 利用命令执行只用 1 核，扩展靠分片能吃满多核
性能特征简单 KV 场景下单线程已够；复杂数据结构无锁优势明显大并发简单 KV 场景吞吐更高

核心洞察：Memcached 选多线程是因为它的价值就是「极致简单的 KV 缓存」，用分段锁把锁竞争控制在可接受范围。而 Redis 有多样的数据结构和原子复合操作（ZINCRBY、LPUSH+LTRIM 组合、Lua 脚本），这些操作的原子性价值远高于多核并行带来的吞吐提升。所以 Redis 宁可牺牲单机吞吐，也要保住原子性——需要吞吐就横向分片。

延伸：这也是为什么 KeyDB / Dragonfly / Valkey 这些「多线程 Redis」的实现，都在原子性语义上做了明确的取舍声明（比如某些复合命令不再保证原子，或需要显式开启）。

Redis 的请求处理流程是怎样的？高级

按本节第 5 部分的 10 步回答即可。重点突出三个「能体现深度」的环节：

  1. 命令查找走「命令表」：redisCommandTable 是一个静态数组，按命令名哈希查找。这解释了「为什么 Redis 不能像 MongoDB 那样随意扩展命令」——扩展靠 module 或 Function。
  2. ACL 校验在命令执行前：包括命令权限 + key 模式匹配，这是性能开销的一部分（8.6 专门优化了 ACL 权限校验）。
  3. 写命令的传播路径：AOF 缓冲区 + 复制缓冲区是两个独立的追加，这也是为什么 AOF 重写期间需要用「重写缓冲区」来记录期间的写命令（7.0 后被 MP-AOF 的增量文件替代）。这个细节能串起 Day2.4 的持久化内容。

加分点：提到 INFO commandstats 能看到每个命令的执行次数、总耗时、平均耗时——这是定位「哪个命令慢」的第一手数据，比只看慢日志更全面（慢日志只记录超过阈值的）。

Day2.2 · 底层数据结构：看懂 Redis 的「内存艺术」

一句话结论

Redis 的性能优势有一半来自「为每种场景选择最省内存的编码，并在数据量变大时自动转换」。你要掌握的不是背结构名，而是理解三组关键开关：listpack ↔ hashtable、intset ↔ listpack ↔ hashtable、listpack ↔ quicklist ↔ skiplist——以及它们背后的阈值参数怎么调、调错会怎样。

1. 全局视角：redisObject 与编码转换

每个 Redis 的 value 都是一个 redisObject：

typedef struct redisObject {
    unsigned type:4;      // 逻辑类型：OBJ_STRING / OBJ_LIST / OBJ_SET / OBJ_ZSET / OBJ_HASH / OBJ_STREAM
    unsigned encoding:4;  // 物理编码：int / embstr / raw / listpack / quicklist / intset / skiplist / hashtable
    unsigned lru:24;       // LRU 时间戳 或 LFU（16位时间 + 8位计数器）
    int refcount;            // 引用计数（共享整数对象 0~9999 会复用）
    void *ptr;               // 指向具体数据结构
} robj;
// 共 16 字节（在 64 位系统上）= 4bit + 4bit + 24bit + 4字节 + 8字节

用 OBJECT ENCODING key 可以直接观察编码：

########## 亲手验证编码转换 ##########

# ---- String 三态 ----
SET s1 12345
OBJECT ENCODING s1          # → "int"（纯数字且 ≤ 20 位）
SET s2 "hello world"
OBJECT ENCODING s2          # → "embstr"（≤ 44 字节）
SET s3 "aaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaa"   # 50 个字符

APPEND s2 "xxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxx"

2. listpack：Redis 的「紧凑内存之王」

listpack 是 Redis 7.0 引入的、用来替代 ziplist 的结构。理解它，就理解了 Redis 为什么能用很少内存存很多小对象。

特性ziplist（已废弃）listpack（7.0+）
结构连续内存块，每个 entry 记录前一个 entry 的长度连续内存块，每个 entry 只记录自己的长度
致命问题连锁更新（cascade update）：修改一个 entry 可能引发后续所有 entry 的长度字段更新，最坏 O(N²)✅ 每项只存自己的长度，插入/删除只影响前后两个 entry，无连锁更新
反向遍历靠 prevlen 往左走每个 entry 尾部有 entrylen，向左读它就能回退
内存效率高高（基本相当）
✅ 连锁更新（cascade update）为什么是 ziplist 的致命伤

ziplist 的每个 entry 头部有个 prevlen 字段记录前一个 entry 的长度，它只有 1 字节或 5 字节两种编码：前一个 entry 长度 < 254 用 1 字节，否则用 5 字节。

现在假设有一串 entry 长度都恰好是 253 字节。此时所有 prevlen 都是 1 字节。现在我在头部插入一个 254 字节的新 entry，那么第二个 entry 的 prevlen 要从 1 字节扩到 5 字节，它自身的长度就变成了 257 字节……于是第三个 entry 的 prevlen 也要从 1 字节扩到 5 字节……这条链会一直传递下去，最坏情况 O(N²)。

而且这个操作是在主线程上同步执行的，一旦触发，就会出现明显的延迟毛刺。Redis 7.0 用 listpack 彻底解决了这个问题——每个 entry 只记录自己的长度，插入删除的代价是确定的 O(1)（就改前后两项）。

面试怎么答：「ziplist 的问题是每个 entry 存前一个 entry 的长度，这个长度字段有 1 字节和 5 字节两种编码；当插入一个大元素导致长度跨越编码边界时，会引发连锁更新，最坏 O(N²)，且在单线程主线程上执行会造成延迟抖动。listpack 改为只记录自身的 entrylen，从根源上消除了这个问题。」

3. quicklist：List 的底层（双向链表 + listpack）

// quicklist 是一个双向链表，每个节点是一个 quicklistNode，内含一个 listpack
typedef struct quicklistNode {
    struct quicklistNode *prev;
    struct quicklistNode *next;
    unsigned char *entry;      // 指向 listpack（压缩时为压缩后的数据）
    size_t sz;                  // listpack 的字节数
    unsigned int count : 16;    // 该节点内元素个数
    unsigned int encoding : 2;  // RAW=1 或 LZF=2（压缩）
    unsigned int container : 2; // PLAIN=1 或 PACKED=2

设计哲学：链表保证头尾 O(1) 操作，listpack 保证内存紧凑。对比「纯链表」（每个元素一个节点，指针开销 16 字节/元素）和「纯数组」（插入删除 O(N)），quicklist 是折中。

压缩：list-compress-depth 控制链表中首尾各多少个节点不压缩（中间节点用 LZF 压缩以省内存）。

4. 跳表（skiplist）：ZSet 的核心

// Redis 的跳表节点
typedef struct zskiplistNode {
    sds ele;                              // 成员（member）
    double score;                         // 分值
    struct zskiplistNode *backward;        // 后退指针（支持反向遍历，只有一层）
    struct zskiplistLevel {
        struct zskiplistNode *forward;     // 前进指针
        unsigned long span;               // ⭐ 跨度：到下一个节点跨越了多少个节点
    } level[];                            // 柔性数组，层数随机（1~32）
} zskiplistNode;

typedef struct zskiplist {
    struct zskiplistNode *header, *tail;
    unsigned long length;                // 节点总数（O(1) 获取）
    int level;                            // 当前最大层数
} zskiplist;
✅ 跳表的核心机制

1) 层数随机生成（Redis 用 ZSKIPLIST_P = 0.25）：

int zslRandomLevel(void) {
    static const int ZSKIPLIST_MAXLEVEL = 32;
    static const int ZSKIPLIST_P = 0.25;
    int level = 1;
    while ((random() & 0xFFFF) < (ZSKIPLIST_P * 0xFFFF))
        level += 1;
    return (level < ZSKIPLIST_MAXLEVEL) ? level : ZSKIPLIST_MAXLEVEL;
}

即：25% 概率升一层。平均每个节点的指针数是 1/(1-0.25) ≈ 1.33，非常省内存。

2) span（跨度）实现 O(log N) 排名：

查找时，每经过一个节点的 span 就累加，最终得到的就是排名。例如要从表头走到目标节点，沿途 span 之和 = 该节点的排名。这就是 ZRANK 能达到 O(log N) 的关键——不需要遍历，只累加跨度。

3) 最大层数 32 的由来：
32 层 + p=0.25，理论可容纳元素数约为 4^32 ≈ 1.8 × 10^19，远超任何实际场景。这个推导能说出来，说明你真读懂了源码。

4) 为什么层数随机 + 不用再平衡：
插入时只需要「找到位置 + 改指针」，不需要任何旋转或再平衡操作。这是跳表实现简单的根本原因，也是它比红黑树更容易写对的原因。

5. 字典（dict）与渐进式 rehash

Hash 类型在超过阈值后用 dict（哈希表）存储，Set 也是。dict 的核心设计是渐进式 rehash。

typedef struct dict {
    dictType *type;
    dictht ht[2];        // ⭐ 两个哈希表！
    long rehashidx;      // rehash 进度：-1 表示未在进行
    unsigned long iterators;
} dict;
✅ 渐进式 rehash：为什么需要两个哈希表

问题：哈希表扩容要重新计算所有 key 的位置并搬移。如果一次性搬移，10 万 key 可能阻塞主线程几十毫秒——单线程模型下不可接受。

解法（渐进式）：

  1. 扩容时，ht[1] 分配为新尺寸，rehashidx = 0。
  2. 此后每次对 dict 的增删改查，都顺带把 ht[0] 的 rehashidx 位置上的桶迁移到 ht[1]，然后 rehashidx++。把 O(N) 的搬移成本分摊到每次操作。
  3. 同时 Redis 有定时任务（serverCron）在空闲时以 100 个桶/毫秒的速率帮忙迁移（dictRehashMilliseconds，每次最多 1ms）。
  4. 查找：两个表都查（先查 ht[0] 再查 ht[1]）。
  5. 新增：只往 ht[1] 写——这保证 ht[0] 的元素只减不增，rehash 必然收敛。
  6. 迁移完成后，ht[0] 与 ht[1] 互换，rehashidx = -1。

触发条件：

  • 扩容：负载因子（used/size）≥ 1（无 BGSAVE/BGREWRITEAOF 时），或 ≥ 5（有子进程时——因为 COW 期间要尽量减少内存写入）。
  • 缩容：负载因子 < 0.1，且无子进程（缩容不是必须的，所以用 0.1 这么低的阈值避免频繁抖动）。
  • 扩容大小：≥ 2 × used（向上取到 2 的幂）；缩容大小：≥ used 的最小 2 的幂。

面试追问：rehash 期间如果客户端执行 SCAN 会怎样？
SCAN 采用反向二进制迭代法（reverse binary iteration）保证 rehash 前后遍历不重复、不遗漏，这是 SCAN 能做到「只保证不遗漏但可能重复」的原因。而 iterators 字段就是为安全的迭代器准备的——如果有安全迭代器存在，rehash 会暂停，避免遍历时数据搬移。

6. intset：整数集合（Set 的省内存编码）

typedef struct intset {
    uint32_t encoding;   // INTSET_ENC_INT16 / INT32 / INT64
    uint32_t length;     // 元素个数
    int8_t contents[];   // 柔性数组，元素有序排列
} intset;

特点：

  • 有序存储：元素按升序排列，所以查找用二分查找 O(log N)。
  • 动态升级：初始用最小的 int16 编码。插入一个超过 int16 范围的值时，整体升级到 int32（重新分配数组并转换所有元素）。升级不可逆——如果删掉了大值，不会降级。
  • 为什么升级不可逆：避免在删除操作上增加复杂度，且概率上「降级后很快又要升级」的场景很常见。
  • 内存收益：存 1000 个小的整数，intset 用 2 字节/元素；如果用 hashtable，每个 entry 要几十字节。差距 10 倍以上。
# 验证 intset 与升级
SADD nums 1 2 3
OBJECT ENCODING nums        # → intset
# 插入一个超过 int32 的大数，触发升级到 int64
SADD nums 9999999999999999
OBJECT ENCODING nums        # 仍是 intset（升级的是编码，不是类型）
# 但插入非整数会立刻转为 listpack/hashtable
SADD nums abc
OBJECT ENCODING nums        # → listpack（7.2+）或 hashtable
# 注意：一旦转为 hashtable，永远不会变回 intset！
🚨 「编码不可逆」是重要的面试点

所有编码转换都是单向的：listpack → hashtable、intset → hashtable、listpack → skiplist，以及 embstr → raw，都不会因为数据变少而回退。

生产影响：这意味着如果某个 key 曾经「涨大过」，即使后来数据被删减，它仍然占用 hashtable/skiplist 的开销。所以：

  • 如果业务是「临时涨大」型（比如活动期间数据量激增），必须删掉 key 重新建，才能回到紧凑编码。
  • 典型场景：一个 Hash 在某次活动期间字段数超过 128 变成 hashtable，活动结束后即使字段降到 10 个，内存也不会降下来。运维会定期「重建」这类 key（用 RENAME 或 MIGRATE 做原子替换）。

💡 一个真实的内存优化案例（可以直接当项目经验讲）

问题：某业务用 Hash 存用户配置，每个用户一个 Hash，平均 5 个字段。上线半年后内存从 2GB 涨到 9GB。

排查：用 MEMORY USAGE 采样发现单个 Hash 只占约 70 字节，但 key 数量有 4000 万。根因不是数据变大，而是 key 的 dictEntry 开销——每个 key 在 Redis 的全局 dict 里都有一个 dictEntry（约 24 字节）+ key 的 SDS（约 40 字节）+ robj（16 字节），再加上 value 的 robj，空壳开销就有 90+ 字节。

优化方案：把「一个用户一个 Hash」改成「按用户 ID 取模分桶，每个桶一个 Hash 存 1000 个用户的配置」。这样 key 数量从 4000 万降到 4 万，省掉了 4000 万个 key 的固定开销，内存降到 3GB 左右。代价是读取时需要先算桶 + 取 field，但没有额外网络开销。

这就是「内存对齐到 Redis 的实现细节」的优化——面试官最想听到的就是这种从原理推导出方案的回答。

面试深度问答

Redis 的 SDS 和 C 字符串的区别？进阶

见 Day1.2 的解析。核心是五条：O(1) 长度、二进制安全、防缓冲区溢出、空间预分配与惰性释放、兼容 C 函数。

补充两个容易被追问的细节：

  • 为什么 embstr 阈值是 44 字节：jemalloc 64 字节内存块 - redisObject 16 字节 - SDS 头 3 字节 - 结尾 \0 1 字节 = 44。
  • embstr 为什么只读：embstr 的 redisObject 和 SDS 是一块连续内存。一旦需要修改，就得重新分配（因为原来分配的空间可能不够），所以 Redis 直接把 embstr 转成 raw。所以对 embstr 执行 APPEND 会导致编码升级。
ziplist 和 listpack 有什么区别？为什么 7.0 要换掉 ziplist？高级

核心差异是连锁更新（cascade update）：见本节的深度框。回答要点：

  1. ziplist 每个 entry 存 prevlen，且 prevlen 有 1 字节/5 字节两种编码。
  2. 插入或修改导致长度跨越 254 边界时，后续 entry 的 prevlen 编码要逐个更新，可能形成连锁反应，最坏 O(N²)。
  3. 这个操作在主线程同步执行，会造成明显延迟抖动——而且它是不可预测的（取决于数据长度分布），这比「慢」更糟，因为难以复现和定位。
  4. listpack 每个 entry 只记录自身长度，插入删除只改相邻两项，代价确定。反向遍历靠 entry 尾部的 entrylen。

加分：还可以提一句「Redis 的 listpack 还有一个好处是更利于 SSD/内存的连续访问，因为结构更规整」。另外从 7.0 起，Hash/Set/ZSet 的小对象编码都统一换成了 listpack，命名也从 hash-max-ziplist-entries 改成了 hash-max-listpack-entries——升级时配置项名字变了，是容易踩的坑。

渐进式 rehash 是什么？为什么需要它？进阶

见本节第 5 部分。回答框架：

  1. 问题：哈希表扩容需要搬移全部元素。Redis 是单线程，一次搬移 10 万 key 会阻塞几十毫秒，所有请求都卡住。
  2. 方案：维护 ht[0]（旧）和 ht[1]（新）两张表，用 rehashidx 记录进度。
  3. 分摊：每次增删改查顺带迁移一个桶；同时定时任务（serverCron 里的 dictRehashMilliseconds，每次最多 1ms）帮忙迁移。
  4. 关键约束：rehash 期间查找查两张表，新增只写 ht[1]——这保证 ht[0] 只减不增，rehash 必然完成。
  5. 触发：负载因子 ≥1 扩容（有子进程时 ≥5，因为要减少 COW 内存复制）；负载因子 <0.1 缩容。

深挖追问 1：为什么有子进程时扩容阈值提高到 5？
因为 RDB/AOF 重写期间 fork 了子进程，依赖 COW。如果此时扩容，会大量写内存页，触发大量页复制，内存峰值暴增。所以推迟扩容。

深挖追问 2：rehash 期间 SCAN 怎么保证不遗漏？
SCAN 用反向二进制迭代法：每次返回的游标是「高位加一、低位归零」的掩码，使得即使在 rehash 导致桶数量变化时，遍历也能覆盖所有元素（可能重复但不会遗漏）。这也是 SCAN 的「保证」比 KEYS 弱但更实用的原因。

为什么 Redis 6.x 的 Set 有 intset 和 hashtable，7.2 又加了 listpack？专家

这是「编码演进」的深度题，考察你是否关注版本细节。

编码适用查找复杂度内存
intset全整数且数量 ≤ 512O(log N) 二分极省（2/4/8 字节每元素）
listpack（7.2+）数量 ≤ 128 且元素 ≤ 64 字节O(N) 线性（N 小）省（连续内存，无指针）
hashtable超出以上阈值O(1)每个 entry 几十字节

7.2 加 listpack 的原因：在 6.x 时代，只要 Set 里有一个非整数，就立刻退化成 hashtable。而现实中大量场景是「元素少（几十个）、但包含字符串」的集合——比如一篇文章的标签。这些小集合用 hashtable 存储，每个元素要承担 dictEntry + robj + SDS 的开销，内存浪费极大。

7.2 引入 listpack 编码后，这类小集合能用连续内存存储，内存降低一个数量级。这是 Redis「持续优化内存」的一条主线：把紧凑编码的适用范围从纯整数扩展到小字符串集合。

专家级洞察：这个演进也解释了为什么 Redis 的配置参数名会随版本变化（*-ziplist-* → *-listpack-*），以及为什么升级大版本时一定要复核配置兼容性——旧配置项在新版本可能被忽略或改变行为。这是「升级 Redis 版本」时的真实风险点。

组成部分大小（64 位）说明
全局 dict 的 dictEntry24 字节key 指针 + value 指针 + next 指针
key 的 SDSSDS 头 3 + 长度 + 1如 "user:1001" = 3+9+1 = 13 → 对齐到 16
value 的 robj16 字节所有类型的 value 都有一个 robj
value 实际数据取决于编码listpack 紧凑；hashtable 每个 field 一个 dictEntry(24) + SDS
过期时间 dict（如设了 TTL）额外 24+ 字节expires dict 里也有一份 dictEntry
jemalloc 内存块对齐向上取整到最近的 size class可能浪费 10%-30%，这是碎片率 mem_fragmentation_ratio 的来源

经验公式：一个「小 key + 小 value」约占 100~150 字节。所以 1000 万个这样的 key 就要 1GB 以上——这就是为什么「key 数量爆炸」是内存问题的主要来源，而不是「value 太大」。

方法三：离线分析 RDB
用 redis-rdb-tools 或 rdr 把 RDB 文件解析成 CSV，能精确统计每个 key 的内存占用、类型、TTL，并生成报告。适合做容量规划和「大 key 月度盘点」。大厂通常把这一步做成定期任务。

回答价值：能说出「key 的固定开销约 100 字节，所以 key 数量比 value 大小更影响总内存」这一点，说明你真正做过内存规划，而不是只会看 used_memory。
