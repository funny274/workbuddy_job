Day1.1 · 环境与部署：一次性搭出「大厂同构」环境

一句话结论

学习阶段用 Docker 起一套完整拓扑（单机 + 主从 + 哨兵 + Cluster），比在物理机上折腾编译安装高效得多；但要知道生产环境标准姿势长什么样——关掉危险命令、设密码 + ACL、改持久化、调 maxmemory、绑内网、部署哨兵/集群而非单机。

1. 为什么先学部署，而不是先学命令

大厂面试有个习惯：问完八股，会突然切到「你线上的 Redis 是怎么部署的？怎么保证不丢数据？」。如果你只会 set/get，这一问就露底了。

更实际的是：你后面学的所有原理（主从复制、哨兵选举、Cluster 槽迁移、热 Key 打爆某分片），都需要一个多节点环境才能亲手验证。所以第一天先花 1 小时把环境搭起来，后面每一节都能立刻做实验。

🚨 生产环境的三个致命默认值

Redis 默认配置是「开发友好、生产危险」的。这三个必须改：

  • bind 0.0.0.0 + 无密码 → 公网裸奔，Redis 未授权访问是历史上最经典的入侵入口之一，会被写 SSH 公钥 / 挖矿。
  • protected-mode no → 关闭保护模式后无密码也能远程连。
  • maxmemory 0（不限制）+ maxmemory-policy noeviction → 内存涨满后所有写命令直接报错，业务瞬间雪崩。

另外 CONFIG、FLUSHALL、KEYS、EVAL 这类命令在生产应通过 rename-command 或 ACL 限制。

先建目录并写入主配置文件：

# 建议在教程目录下创建实验环境
mkdir -p redis-lab/conf redis-lab/data && cd redis-lab
# ===== conf/master.conf · 生产级单机配置（可直接复用到生产）=====

# ---- 网络与安全 ----
bind 0.0.0.0                  # 容器内需 0.0.0.0；物理机请绑内网 IP，如 bind 10.0.0.5
protected-mode yes           # 保护模式保持开启
port 6379
tcp-backlog 511
timeout 0                    # 不主动断开空闲连接（由客户端连接池管理）
tcp-keepalive 300

# ---- 密码（第 6 节会升级为 ACL 多用户）----
requirepass "你的强密码_至少32位随机串"
masterauth "你的强密码_至少32位随机串"   # 主从复制时从节点连主节点用
aclfile /usr/local/etc/redis/users.acl  # 启用 ACL 文件（配合 requirepass 使用）

# ---- 通用 ----
daemonize no                # Docker 中必须 no
loglevel notice
databases 16                 # 集群模式只能 1 个库

# ---- 持久化：RDB + AOF 混合（生产推荐）----
dir /data
dbfilename dump.rdb
save 900 1                   # 900秒内至少1次写则快照
save 300 10
save 60 10000
stop-writes-on-bgsave-error yes   # 快照失败则停止写入（暴露问题而不是静默丢数据）

appendonly yes
appendfilename "appendonly.aof"
appenddirname "appendonlydir"  # 7.0+ Multi-Part AOF 目录
appendfsync everysec        # 每秒刷盘，最多丢 1 秒（生产首选）
aof-use-rdb-preamble yes     # 混合持久化，恢复更快
auto-aof-rewrite-percentage 100
auto-aof-rewrite-min-size 64mb

# ---- 内存 ----
maxmemory 768mb              # 生产设为物理内存的 60%~75%，留出 fork/COW 空间
maxmemory-policy allkeys-lru   # 纯缓存场景；混合存储用 volatile-lru
maxmemory-samples 5

# ---- 慢查询（生产必开，阈值按需调）----
slowlog-log-slower-than 10000   # 单位微秒，10ms
slowlog-max-len 128

# ---- 危险命令限制（生产强烈建议）----
rename-command FLUSHALL ""
rename-command FLUSHDB ""
rename-command KEYS ""
rename-command SHUTDOWN ""

# ---- 客户端 ----
maxclients 10000
lazyfree-lazy-eviction yes   # 异步释放，避免大 key 淘汰阻塞主线程
lazyfree-lazy-expire yes
lazyfree-lazy-server-del yes
lazyfree-lazy-user-del yes

# ---- 8.0+ 多线程 I/O（多核机器建议开）----
io-threads 4                  # 建议 = CPU核数的 1/2 ~ 3/4，4核以上才有效果
io-threads-do-reads yes
💡 面试记忆点：为什么 maxmemory 只给 60%~75%

因为 RDB 快照和 AOF 重写都要 fork 子进程，靠 COW（写时复制）共享内存页。如果写入很频繁，被修改的内存页会被复制一份，最坏情况下内存占用接近翻倍。留出 25%~40% 的余量，是防止 OOM Killer 干掉 Redis 进程的关键。能说出这一点的候选人，立刻和「只会配 maxmemory」的拉开差距。

    image: redis:8.6
    container_name: redis-master
    command: ["redis-server", "/usr/local/etc/redis/redis.conf"]

    volumes:
      - ./conf/master.conf:/usr/local/etc/redis/redis.conf:ro
      - ./data/master:/data
    restart: unless-stopped
    healthcheck:
      test: ["CMD", "redis-cli", "-a", "你的强密码_至少32位随机串", "ping"]
      interval: 10s
      timeout: 3s

  # ---------- 2) 主从 + 哨兵（Day3 用）----------
  redis-s1:
    image: redis:8.6
    container_name: redis-s1
    command: ["redis-server", "--port", "6379", "--requirepass", "repl123456", "--masterauth", "repl123456"]
    ports: ["6380:6379"]

  redis-s2:
    image: redis:8.6
    container_name: redis-s2
    command: ["redis-server", "--port", "6379", "--replicaof", "redis-s1", "6379", "--requirepass", "repl123456", "--masterauth", "repl123456"]
    ports: ["6381:6379"]

  sentinel1:
    image: redis:8.6
    container_name: sentinel1
    command: ["redis-sentinel", "/etc/sentinel.conf", "--sentinel"]
    depends_on: [redis-s1, redis-s2]
    volumes: ["./conf/sentinel.conf:/etc/sentinel.conf"]
    ports: ["26379:26379"]

  redis-insight:
    image: redis/redisinsight:latest
    container_name: redis-insight
    ports: ["5540:5540"]

    image: oliver006/redis_exporter:latest
    container_name: redis-exporter
    environment:
      REDIS_ADDR: "redis://redis-master:6379"

# ===== conf/sentinel.conf =====
port 26379

sentinel failover-timeout mymaster 60000
sentinel parallel-syncs mymaster 1          # 每次只让1个从节点同步，避免全部不可读
sentinel resolve-hostnames yes

3. 无 Docker 时的安装方式

方式 A：Linux 源码编译（能拿到任意版本）

# 1) 装依赖
sudo apt update && sudo apt install -y build-essential tcl pkg-config libssl-dev

# 2) 下载指定版本（示例 8.6.0）
cd /opt && sudo wget https://download.redis.io/releases/redis-8.6.0.tar.gz
sudo tar -xzf redis-8.6.0.tar.gz && cd redis-8.6.0

# 3) 编译（多核加速；jemalloc 默认启用，比 glibc malloc 碎片更少）
sudo make -j$(nproc) BUILD_TLS=yes     # BUILD_TLS 开启 TLS 支持，生产跨机房建议开
sudo make install PREFIX=/opt/redis

# 4) 生产级目录规范（大厂一般这么分）
sudo mkdir -p /opt/redis/{conf,data,logs,run}
sudo cp redis.conf /opt/redis/conf/
sudo cp src/redis-server src/redis-cli src/redis-sentinel /opt/redis/bin/ 2>/dev/null || true

# 5) 修改关键项
#   daemonize yes
#   logfile /opt/redis/logs/redis.log
#   dir /opt/redis/data
#   pidfile /opt/redis/run/redis.pid

# 6) 启动与验证
/opt/redis/bin/redis-server /opt/redis/conf/redis.conf
/opt/redis/bin/redis-cli ping

4. 配置 ACL 多用户（生产必备，面试加分）

Redis 6.0 引入 ACL，让「一个密码全权限」成为历史。大厂内部通常按业务线分用户、按 key 前缀授权。这既是安全要求，也是面试常问的「你们 Redis 怎么做权限隔离」。

# ===== users.acl 文件示例 =====
# 语法：user <用户名> <on/off> >密码 ~key前缀 +命令 -命令 ...

# 默认超级用户（保留）
user default on >你的强密码_至少32位随机串 ~* &* +@all

# 订单业务：只能操作 order: 前缀，只允许读 + 常用写，禁止危险命令
user order-svc on >Order@2026#Secret ~order:* &order-events +@read +@write -@dangerous -flushall -keys -config

# 只读监控账号：只能读，且只看统计
user monitor on >Mon@2026#Secret ~* +@read +info +slowlog +client|list -keys -scan

# 复制专用账号（主从复制需要）
user repl on >Repl@2026#Secret ~* +psync +replconf +ping +sync
# 运行时动态管理 ACL（无需重启）
redis-cli -a '你的强密码' ACL SETUSER app1 on >App1Pwd ~app1:* +@read +@write -@dangerous
redis-cli -a '你的强密码' ACL LIST              # 查看所有用户规则
redis-cli -a '你的强密码' ACL WHOAMI            # 当前用户
redis-cli -a '你的强密码' ACL CAT               # 所有命令类别
redis-cli -a '你的强密码' ACL CAT dangerous     # 危险命令有哪些
redis-cli -a '你的强密码' ACL GETUSER order-svc  # 查看某用户详情
redis-cli -a '你的强密码' ACL SAVE              # 持久化到 aclfile（8.0 起支持）

# 影响面分析：某用户被改了权限，怎么知道错在哪？看 ACL LOG
redis-cli -a '你的强密码' ACL LOG 5
# 输出会告诉你：哪个用户、执行什么命令、被拒绝的原因、来自哪个 IP
💡 面试点：ACL 与 rename-command 怎么选

rename-command 是全局禁用命令，粒度粗且需要改配置重启；ACL 是按用户授权，可动态生效、可审计（ACL LOG）。
现代做法：用 ACL 按业务授权 + 保留少数高危命令的 rename 作为兜底。注意 Redis 8.0 起对模块命令的 ACL 归类有 breaking change——+@all -@write 这类规则不再自动放行模块命令（如 JSON.SET），升级时要复核权限。

5. 四种部署形态速览（Day3 会深入）

形态能力数据上限故障切换典型场景
单机缓存、简单业务单机内存无，挂了就挂开发、小流量、对可用性要求不高
主从读写分离 + 数据热备单机内存手动读多写少、报表类查询分流
哨兵
中小厂主流		主从 + 自动故障转移单机内存自动（秒级~十秒级）数据量 < 单机内存、需要高可用
Cluster
大厂主流		分片 + 高可用 + 水平扩展N × 单机内存自动 + 分片级隔离海量数据、高吞吐、需要线性扩容
⚠️ 选型的关键判断（面试高频）

只要数据量可能超过单机内存上限，就必须上 Cluster；否则哨兵更简单、运维成本更低、没有跨槽事务/多 key 操作的诸多限制。
反过来，如果业务有大量多 key 原子操作、Lua 脚本跨 key、需要 16 个 database，Cluster 会带来麻烦——这也是为什么很多公司核心交易仍用哨兵，只在大的、可分的业务上 Cluster。

面试深度问答

你们的 Redis 是怎么部署的？为什么这么选？高级

错误答法：「我们用 Cluster，因为 Cluster 好。」——面试官立刻会问「为什么不用哨兵」，答不出就崩。

正确答法（结构化 + trade-off）：

  1. 先讲判断依据：数据量是否需要超过单机内存、QPS 是否超过单实例承载（一般单实例 8-10 万 QPS）、是否需要水平扩容能力。
  2. 再讲选型：
    • 缓存型业务、数据量可控 → 哨兵（主从）。优势：无跨槽限制，多 key 操作/Lua/事务都能用，运维简单。缺点：容量和 QPS 受单机限制，扩容需停机或上代理（如 Codis 类方案）。
    • 海量数据、需要线性扩展 → Cluster。优势：分片扩容、故障域隔离（单分片挂了只影响 1/N 数据）。代价：多 key 操作受限（须同 slot，用 hash tag）、Lua 不能跨槽、只有 db0、客户端要支持重定向、运维复杂度高。
  3. 最后讲演进：「我们早期用哨兵，数据涨到 XX GB 后迁移到 Cluster，迁移过程用 DTS/双写灰度……」——有演进史的回答最能体现真实经验。

加分细节：提一句 Cluster 的故障切换不是全局的——只影响该分片，但如果某分片主从同时挂，这部分数据就不可用（比如 3 主 3 从，挂一主一从，1/3 数据丢失）。

Redis 线上安全生产要注意什么？（这道题在考你的运维意识）高级

按「网络 / 权限 / 内存 / 持久化 / 命令 / 监控」六层回答，每层给出具体动作：

层面动作为什么
网络绑内网 IP、安全组白名单、绝不放公网未授权访问是最常见入侵路径
权限ACL 按业务授权 + 强密码 + TLS（跨机房）最小权限、可审计
内存maxmemory 为物理内存 60%~75%；明确淘汰策略；监控 used_memory 与 evicted_keys防 OOM Killer；防写满后全部写失败
持久化开启 AOF everysec + RDB 冷备；stop-writes-on-bgsave-error yes限制数据丢失窗口；避免静默失败
命令rename/ACL 禁用 KEYS、FLUSHALL、CONFIG；用 SCAN 替代 KEYS；用 UNLINK 替代 DEL 删大 key防阻塞主线程、防误操作
监控慢日志 + 延迟监控 + 内存/连接数/命中率/主从延迟告警问题是「发现不了」而非「解决不了」

专家级补充：还要提容量规划（预留 fork 内存、考虑 COW 峰值）、变更管理（禁止业务高峰期 CONFIG SET 高风险参数、大 key 清理要低峰期）、演练（定期做故障转移演练、验证备份可恢复）。

Redis 的内存应该设多大？为什么要留 25%~40% 余量？高级

核心机制是 fork + COW（写时复制）：

  1. RDB 快照 / AOF 重写时，Redis fork() 出子进程。fork 本身在 Linux 上是写时复制，子进程与父进程共享同一份物理内存页，所以瞬间内存不会翻倍。
  2. 但只要父进程（主线程）修改了某个内存页，这个页就会被复制一份给子进程。写的 key 越多、越分散，被复制的页就越多。
  3. 最坏情况（全量写入）：额外占用接近一份完整数据集的内存。所以实际峰值可能是 1.x ~ 2 倍。
  4. 如果内存不够，Linux 的 OOM Killer 可能直接杀掉 Redis 进程——比 OOM 报错更糟（报错只影响写，被杀是服务全挂）。

实践建议：maxmemory 设为物理内存的 60%~75%；如果写入极频繁（大量随机写），可以更保守（50%~60%）。同时 vm.overcommit_memory=1 避免 fork 时因内存不足失败（这条内核参数是大厂标配）。

还能再说一层：这也是为什么「大 key 治理」很重要——大 key 在被修改和删除时，会产生大页复制和长时间阻塞。把 fork/COW、maxmemory、大 key 串起来讲，才是 10 年经验的样子。

升级方法论（这段很值钱）：

  1. 先评测：用从节点 + 生产流量回放（或影子流量）验证新版本性能与兼容性。
  2. 灰度顺序：从节点 → 主节点切换（Cluster 逐个分片）；先升从、后升主，利用主从切换把旧版本节点替换掉。
  3. 兼容性检查清单：ACL 规则、客户端版本（Jedis/Lettuce/Redisson）、Lua 脚本用到的 API、AOF/RDB 格式、集群协议、监控探针。
  4. 回滚预案：RDB/AOF 向下不兼容，所以回滚必须靠数据备份 + 重放，因此升级前要做一次全量备份并验证可恢复。
