Day1.2 · 八大数据结构：从「会用」到「能选型」

一句话结论

面试官问数据类型，从来不是让你背名字，而是考「给我一个业务场景，你能不能选出最合适的结构，并说清代价」。所以每学一种类型，必须同时记住三件事：底层编码、时间复杂度、它「不适合」什么。

1. 全景：8 大数据类型与选型决策树

2. String：不只是缓存

底层编码三态

编码触发条件内存布局
int值为整数且长度 ≤ 20 位直接存在 redisObject 的 ptr 里，不额外分配
embstr长度 ≤ 44 字节redisObject + SDS 一次性连续分配，缓存友好，只需一次内存分配/释放
raw长度 > 44 字节redisObject 与 SDS 分开分配（两次调 malloc）

为什么是 44 字节？jemalloc 以 64 字节为一个内存块，redisObject 占 16 字节（4bit type + 4bit encoding + 24bit lru + 4字节 refcount + 8字节 ptr），SDS 头 3 字节 + 末尾 \0 1 字节，16 + 3 + 44 + 1 = 64。这是「贴近底层优化」的经典案例，能讲出来很加分。

完整案例：缓存 + 计数器 + 分布式锁原语 + 限流

########## 案例 1：对象缓存（含防击穿的 SET 参数）##########

# 基础写入（带 TTL）
SET user:1001 '{"id":1001,"name":"张三","vip":true}' EX 3600

# NX：不存在才设置（分布式锁 / 防覆盖）；XX：存在才更新
SET lock:order:1001 "uuid-abc" NX PX 30000

# GET + EX + NX 组合：读缓存未命中时回填，避免覆盖别人写入的新值
SET user:1001 '{...}' EX 600 NX

# KEEPTTL：更新值但保留原有 TTL（7.0+ 常用）
SET user:1001 '{...updated...}' KEEPTTL

# 8.4+ compare-and-set / compare-and-delete：原生 CAS，不用 Lua
SET stock:1001 "99" IFEQ "100"      # 当前值等于 100 才设为 99
SET stock:1001 "new" IFGT "50"       # 当前值大于 50 才设置
DELEX stock:1001 IFEQ "0"         # 值等于 0 才删除（8.4+）

########## 案例 2：原子计数器 ##########
SET article:2001:views 0
INCR article:2001:views            # 原子 +1，返回新值
INCRBY article:2001:views 10       # 原子 +10
DECRBY stock 5                     # 原子 -5（库存扣减）
INCRBYFLOAT balance:u1 19.99       # 浮点累加（金额场景慎用，见下方警告）

# 一次操作多个 key（注意：非原子！中间可能穿插其他命令）
MSET k1 v1 k2 v2 k3 v3
MGET k1 k2 k3
MSETNX k4 v4 k5 v5                 # 全部不存在才设置（原子性，但批量场景少用）

# 7.0+ 批量设置 TTL（8.4 MSETEX）
MSETEX 2 k1 v1 k2 v2 EX 60

########## 案例 3：GETDEL / GETEX ##########
GETDEL captcha:13800000000         # 取出即删除 —— 验证码一次性消费的完美实现
GETEX session:token EX 7200        # 取值并续期（读时续 TTL，会话滑动过期）
GETEX session:token PERSIST        # 取值并去掉 TTL

########## 案例 4：应用层限流（固定窗口）##########
# 每用户每分钟最多 100 次：INCR + EXPIRE 组合
MULTI
INCR rate:uid:1001:202609301730
EXPIRE rate:uid:1001:202609301730 60
EXEC

########## 案例 5：位图签到（Bitmap）##########
SETBIT sign:1001:202609 30 1       # 9月30日签到（offset 从0开始，30号=offset 29）
GETBIT sign:1001:202609 30
BITCOUNT sign:1001:202609          # 本月签到天数
# 一个月只需 31 bit ≈ 4 字节；1000 万用户一个月仅约 37MB
BITOP AND dest sign:u1 sign:u2     # 位运算：求连续签到 / 共同活跃

########## 案例 6：Bitfield 紧凑计数 ##########
BITFIELD counter SET u8 0 200      # 从第0位起写入一个8位无符号整数
BITFIELD counter INCRBY u8 0 10    # 原子 +10，溢出回绕
BITFIELD counter GET u8 0
🚨 三个必须知道的坑
  1. INCRBYFLOAT 不要用于金额：浮点累加存在精度问题（虽然 Redis 内部用 long double 并做了截断，但跨系统传输仍会失真）。金额场景应用整数存「分」。
  2. MSET/MGET 不是原子的：MGET 返回的多个值可能来自不同时刻。MULTI 里的 MSET 是原子的，但 MULTI 本身不是「全成功或全失败」——它没有回滚，只会按顺序执行并返回每个命令的结果。
  3. KEEPTTL 与 EX 不可同时使用，且 6.0 之前 SET 会清除 TTL——这是历史 bug 的来源，升级时要注意行为变化。

3. Hash：对象存储的最佳实践（附一个真实事故）

Hash 是「存对象」的首选。但用错方式会引发严重事故——我们在 Day4 热 Key 里会复盘一个真实案例：把 800+ 个 SKU 的促销信息塞进一个 Hash，每次用 HGETALL 全量拉取，直接把单节点 CPU 打到 99.97%。

编码与阈值

编码切换条件（默认阈值）特点
listpack字段数 ≤ 128 且 每个值 ≤ 64 字节连续内存，省内存、缓存友好；查找 O(N) 但 N 很小
hashtable超过任一阈值查找 O(1)，但每个 entry 有额外开销

阈值参数：hash-max-listpack-entries 128、hash-max-listpack-value 64。

########## 案例：用户对象 ##########

# 写入单个字段（推荐：按需读写，不整体覆盖）
HSET user:1001 name "张三" age 30 city "广州" vip 1

# 读取
HGET user:1001 name
HMGET user:1001 name age city        # 批量取指定字段
HGETALL user:1001                    # ⚠️ 危险：字段多时会阻塞，生产慎用
HKEYS user:1001 / HVALS user:1001 / HLEN user:1001

# 原子自增（用户积分、库存字段）
HINCRBY user:1001 points 10
HINCRBYFLOAT user:1001 balance 1.5

# 存在性判断 + 不存在才写（原子）
HSETNX user:1001 nickname "小张"

# 安全遍历（替代 HGETALL）
HSCAN user:1001 0 COUNT 100          # 游标遍历，不阻塞
HSCAN user:1001 0 NOVALUES COUNT 100 # 8.0+ 只取字段名，更快

########## 案例：购物车（Hash 的经典用法）##########
HSET cart:1001 sku_2001 2 sku_2002 1     # field=商品ID, value=数量
HINCRBY cart:1001 sku_2001 1             # 加购（天然去重 + 数量累加）
HLEN cart:1001                           # 购物车商品种类数
HDEL cart:1001 sku_2002                  # 删除某商品

########## 案例：字段级 TTL（7.4+ / 8.0 增强）##########
HSET session:s1 token "abc" uid 1001
HEXPIRE session:s1 3600 FIELDS 2 token uid   # 只给这两个字段设 TTL
HTTL session:s1 FIELDS 2 token uid           # 查字段剩余 TTL（-1 永不过期，-2 不存在）
HPERSIST session:s1 FIELDS 1 token            # 移除字段 TTL

# 8.0 新增：读写同时设 TTL，省一次往返
HSETEX session:s1 EX 3600 FIELDS 1 token "abc"
HGETEX session:s1 EX 3600 FIELDS 1 token     # 取值 + 续期，一步完成
HGETDEL session:s1 FIELDS 1 token            # 取值 + 删除，一步完成
✅ 面试点：Hash vs String 存对象，怎么选？
维度String（JSON 序列化）Hash
写单个字段需读-改-写整个对象，有并发覆盖风险O(1) 直接改字段，无覆盖风险
读单个字段需反序列化整个 JSON（网络 + CPU 浪费）只取需要字段，省带宽
内存开销小对象更省（无额外 field 开销）字段多时 listpack 内存效率很高；字段少时反而比 String 多一点
TTL 粒度整个 key 一个 TTL7.4+ 支持字段级 TTL
适用整体读写为主、结构简单、需要严格版本控制字段多、需局部更新、需字段级过期

结论：字段多且需局部更新 → Hash；整体读写、需要压缩/加密整体处理 → String。这也是华为 OD 面试原题。

4. List：轻量消息队列与时间线

List 底层是 quicklist（7.0+ 由「双向链表 + 每个节点一个 listpack」组成）。这个设计是「链表 O(1) 头尾操作 + listpack 内存紧凑」的结合。

########## 案例 1：最新 N 条评论 ##########
LPUSH news:1001:comments "评论A" "评论B" "评论C"   # 左推，新评论在最前
LRANGE news:1001:comments 0 9                       # 取最新 10 条
LTRIM news:1001:comments 0 999                      # 只保留最新 1000 条（关键：防止无限增长）
LLEN news:1001:comments

########## 案例 2：简单消息队列（生产者-消费者）##########
# 生产者
LPUSH mq:order '{"orderId":1001}'

# 消费者（BRPOP 阻塞弹出，timeout=0 表示永久阻塞）
BRPOP mq:order 0

# ⚠️ 可靠性问题：BRPOP 弹出后消息就从 Redis 删除了，
#    如果消费者处理到一半崩溃，消息就永久丢失。
#    → 需要可靠投递，用 Stream（见第 8 节）或 RPOPLPUSH 做备份队列

########## 案例 3：可靠队列（RPOPLPUSH 备份方案）##########
# 消费者：从待处理队列取出，同时放入处理中队列（原子操作）
BRPOPLPUSH mq:order mq:order:processing 5

# 处理成功后，从 processing 队列删除
LREM mq:order:processing 1 '{"orderId":1001}'

# 另起一个监控任务，定期把 processing 里超时未确认的消息搬回主队列
LMOVE mq:order:processing mq:order RIGHT LEFT     # 6.2+ 统一命令 LMOVE

########## 案例 4：其他常用操作 ##########
RPUSH list a b c d        # 右推 → [a,b,c,d]
LPOP list 2               # 从左弹 2 个（6.2+ 支持 count）
LREM list 1 "b"            # 删除 1 个值为 b 的元素（count>0 从头删，<0 从尾删，=0 全删）
LSET list 0 "x"           # 按索引设置（⚠️ O(N)，大 List 慎用）
LINSERT list BEFORE "x" "y"
LPOS list "c"             # 6.0+ 查索引
⚠️ List 做消息队列的局限（面试必答）
  • 不支持多消费者组：一条消息只能被一个消费者拿到，无法广播给多个下游。
  • 无 ACK 机制：靠 RPOPLPUSH + 超时回补模拟，复杂度高且不精确。
  • 无消息回溯：消息消费即删，无法重放。
  • 无持久化的「消费位点」：消费者重启后无法从上次位置继续。
  • 结论：轻量、允许丢消息的场景用 List；要求可靠性用 Stream 或专业 MQ（Kafka/RocketMQ）。

5. Set：去重与集合运算

########## 案例 1：标签系统 ##########
SADD article:1001:tags Java Redis 高并发
SADD article:1002:tags Redis MySQL 高并发

# 共同标签（交集）—— 推荐系统中「找相似文章」
SINTER article:1001:tags article:1002:tags        # → Redis 高并发

# 合并标签（并集）
SUNION article:1001:tags article:1002:tags

# 差集：在 A 不在 B
SDIFF article:1001:tags article:1002:tags         # → Java

# 把结果存到新 key（避免大结果集在网络上传输）
SINTERSTORE common:tags article:1001:tags article:1002:tags

# 基数、判断、随机
SCARD article:1001:tags
SISMEMBER article:1001:tags Java
SRANDMEMBER article:1001:tags 2       # 随机取 2 个（可能重复，不删除）—— 抽奖候选
SPOP article:1001:tags 1              # 随机弹出 1 个（删除）—— 抽奖中奖

########## 案例 2：共同好友 ##########
SADD user:1:friends 2 3 4 5
SADD user:2:friends 3 4 6 7
SINTER user:1:friends user:2:friends           # 共同好友 → 3,4
SINTERCARD 2 user:1:friends user:2:friends LIMIT 10   # 7.0+ 只要数量，可加 LIMIT 提前返回

########## 案例 3：秒杀去重（防同一用户重复下单）##########
SADD seckill:1001:users 1001          # 返回 1=首次，0=已存在
# 配合 EXPIRE 控制去重窗口
EXPIRE seckill:1001:users 86400
💡 大 Set 运算的性能陷阱

SINTER 等运算的时间复杂度是 O(N)，N 是较小集合的元素个数（Redis 会先算基数小的集合）。但如果两个集合都很大（比如百万级），依然会阻塞主线程。
生产做法：SINTERSTORE 把结果落到新 key（计算在服务端做，不传输大量数据），或者改用 SINTERCARD ... LIMIT 只要数量，或把这类计算下沉到离线任务。
另外注意：Cluster 模式下，交并差要求所有 key 在同一个 slot（用 hash tag，如 {user:1}:friends 和 {user:1}:tags）。

6. ZSet：排行榜与延时队列（面试最高频）

ZSet 是唯一一个既能按分值排序、又能 O(log N) 范围查询和排名的结构，也是面试被问得最多的。底层是跳表 + 哈希表双结构：跳表负责按 score 排序和范围查询，哈希表负责 O(1) 定位 member→score。

########## 案例 1：游戏排行榜（最经典）##########
ZADD rank:202609 100 "player:1" 250 "player:2" 180 "player:3"

# 加分（没有则新增）
ZINCRBY rank:202609 50 "player:1"

# 取 Top 10（降序，带分数）
ZREVRANGE rank:202609 0 9 WITHSCORES

# 查某人排名（从 0 开始，降序）
ZREVRANK rank:202609 "player:2"       # → 0，表示第 1 名

# 查分数
ZSCORE rank:202609 "player:1"

# 按分数区间查（用于分页 / 条件筛选）
ZRANGEBYSCORE rank:202609 100 200 WITHSCORES
ZRANGEBYSCORE rank:202609 (100 +inf LIMIT 0 10   # ( 表示开区间

# 分页：按排名取
ZREVRANGE rank:202609 10 19           # 第 11-20 名

# ⚠️ 大 ZSet 分页的性能坑：ZREVRANGE 的 offset 是 O(log N + M)，
#    但深分页（offset 很大）依然会扫描，建议用「按分数游标」分页

# 统计分数区间内的人数
ZCOUNT rank:202609 100 200
ZLEXCOUNT rank:sameScore [a [z              # 同分时按字典序排（分数相同则按 member 字典序）

########## 案例 2：延时队列（订单超时未支付自动取消）##########
# score = 到期时间戳
ZADD delay:queue 1790000000 '{"orderId":1001,"type":"cancel"}'
ZADD delay:queue 1790000060 '{"orderId":1002,"type":"cancel"}'

# 消费者：只取「已到期」的任务（当前时间戳之前）
# ZRANGEBYSCORE delay:queue 0 <now> LIMIT 0 10
ZRANGEBYSCORE delay:queue 0 1769000000 LIMIT 0 10
ZREM delay:queue '{"orderId":1001,"type":"cancel"}'    # 取出后删除

# ⚠️ 并发安全：多消费者可能同时取到同一任务！
#    生产做法：用 ZPOPMIN with count（6.2+）原子弹出，或 Lua 脚本保证「取+删」原子
ZPOPMIN delay:queue 10

########## 案例 3：滑动窗口限流（比固定窗口更精确）##########
# 思路：score = 请求时间戳（毫秒），member = 唯一请求ID
ZADD limit:uid:1001 1769000061000 "req-abc"
# 1) 移除窗口外的请求（60秒前）
ZREMRANGEBYSCORE limit:uid:1001 0 1769000000000
# 2) 统计窗口内请求数
ZCARD limit:uid:1001
# 3) 超限则拒绝，否则继续
# 生产用 Lua 把这三步包成原子操作

########## 案例 4：按时间戳的「热搜榜」（带时效衰减）##########
# score 设计为「复合权重」，同时考虑热度和时间
# 例如：score = 热度分 * 10^10 + (10^10 - 时间戳)，保证同热度下新的排前面
ZADD hot:search 17690000610000000000000000 "话题A"
ZREVRANGE hot:search 0 9
✅ 面试深挖：ZSet 为什么用跳表而不是红黑树 / B+ 树？
  1. 范围查询更自然：跳表是链表 + 多层索引，找到起点后沿底层链表顺序遍历即可，对 CPU 缓存和内存局部性友好。红黑树做范围查询要中序遍历，指针跳转更多。
  2. 排名（ZRANK/ZREVRANGE）实现简单：跳表每个节点维护 span（跨度，表示跨越了多少个节点），累加 span 就能算出排名 O(log N)。红黑树要实现这个必须维护 size 域，调整时更复杂。
  3. 实现简单、并发友好：跳表没有旋转/再平衡，插入删除只需改指针，代码量远小于红黑树，也更易正确实现。
  4. 内存可控：跳表平均每个节点 1/(1-p) 个指针，Redis 取 p=0.25，平均 1.33 个指针，比红黑树（每个节点 3 指针 + 颜色）更省。
  5. 性能同数量级：查找/插入/删除都是 O(log N)，与平衡树相当，没有性能劣势。

一句话总结：「跳表用更简单的实现换到了同等性能，并且在范围查询和排名这两个 Redis 高频操作上更有优势。」——这个回答，够 10 年岗位的标准了。

7. HyperLogLog / Bitmap / GEO：三个「专精」结构

HyperLogLog：海量去重计数

# 统计 UV（独立访客），100 万用户只占约 12KB！
PFADD uv:20260930 user1 user2 user3 user4
PFCOUNT uv:20260930                     # 返回估算值，标准误差 0.81%

# 合并多个 HLL（比如「本月 UV = 各天 UV 合并」）
PFMERGE uv:202609 uv:20260901 uv:20260902

# 关键特性：只会高估或低估，但误差可控；不能取回具体元素
# 内部结构：16384 个 6bit 桶（共 12KB），稠密/稀疏两种编码自动切换
# 稀疏编码在元素少时更省内存，超过阈值（默认 3000）转稠密

# 参数调优（一般不用改）
CONFIG SET hll-sparse-max-bytes 3000

8. Stream：可靠消息队列（Redis 版 Kafka）

Redis 5.0 引入 Stream，解决了 List 做队列的可靠性问题。8.2/8.4/8.6 持续增强，8.6 还加入了幂等生产（at-most-once），是当前的版本热点。

########## 案例：订单事件流 ##########

# 1) 生产消息（* 表示自动生成递增ID：毫秒时间戳-序号）
XADD stream:orders * orderId 1001 status created amount 199.00
XADD stream:orders * orderId 1002 status paid amount 299.00

# 指定 ID（可用于幂等或时序对齐）
XADD stream:orders 1769000061000-0 orderId 1003 status created

# 8.6 幂等生产：同一 IDMP 值重复写入只会生效一次（崩溃重试场景的关键）
XADD stream:orders IDMPAUTO ord-1004 * orderId 1004 status created
#    ↑ 自动生成幂等ID                       ↑ 同一幂等ID重复发送不会产生重复消息

# 2) 控制流长度（防止无限增长）
XADD stream:orders MAXLEN ~ 100000 * orderId 1005 status created   # ~ 表示近似裁剪，更高效
XTRIM stream:orders MAXLEN 100000        # 手动裁剪

# 3) 读取
XLEN stream:orders
XRANGE stream:orders - +                 # 全部
XRANGE stream:orders - + COUNT 10
XREVRANGE stream:orders + - COUNT 5      # 倒序取最新 5 条
XREAD COUNT 10 STREAMS stream:orders 0   # 从头读（不阻塞）
XREAD BLOCK 5000 STREAMS stream:orders $  # 阻塞5秒，只读新消息（$ = 只关心新的）
XREAD LAST 10 STREAMS stream:orders       # 8.0+ 读最新 N 条（不用自己算 ID）

########## 消费组（核心能力，List 做不到）##########

# 创建消费组（$ 表示从最新消息开始；0 表示从头开始，可消费历史消息）
XGROUP CREATE stream:orders group:order-svc $
XGROUP CREATE stream:orders group:notify-svc 0
XINFO GROUPS stream:orders               # 查看所有消费组状态

# 消费者读取（> 表示「从未投递过的新消息」）
XREADGROUP GROUP group:order-svc consumer:c1 COUNT 10 STREAMS stream:orders >

# 消息处理完必须 ACK（否则会留在 PEL 待处理列表里）
XACK stream:orders group:order-svc 1769000061000-0

# 查看待处理消息（PEL）—— 故障恢复的关键
XPENDING stream:orders group:order-svc
XPENDING stream:orders group:order-svc - + 10 consumer:c1

# 认领超时未 ACK 的消息（消费者 c1 挂了，c2 接手）
XAUTOCLAIM stream:orders group:order-svc consumer:c2 60000 0-0 COUNT 10
#  ↑ 最小空闲时间 60秒      ↑ 起始ID
XCLAIM stream:orders group:order-svc consumer:c2 60000 1769000061000-0   # 精确认领

# 8.4+ 读取时直接认领空闲消息（简化故障恢复）
XREADGROUP GROUP group:order-svc consumer:c2 CLAIM 60000 STREAMS stream:orders >

########## 删除 ##########
XDEL stream:orders 1769000061000-0
XGROUP DELCONSUMER stream:orders group:order-svc consumer:c1
XGROUP DESTROY stream:orders group:order-svc
XDELEX stream:orders ACKED 1769000061000-0        # 8.2+ 只在已 ACK 时删除
🧠 专家视角：Stream vs Kafka，怎么选？
维度Redis StreamKafka / RocketMQ
吞吐十万级 QPS百万级 QPS
持久化内存为主（受 maxmemory 限制，需裁剪）磁盘持久化，可存海量历史

面试深度问答

Redis 有哪些数据类型？分别适合什么场景？基础

不要只报名字，按「结构 → 能力 → 场景 → 边界」四段式回答，展现选型思维：

  • String：二进制安全字节串（最大 512MB）。场景：对象缓存、原子计数器、分布式锁、Bitmap 位图、限流。边界：不适合存需要局部更新的复杂对象。
  • Hash：字段-值映射。场景：对象存储（用户信息、购物车）、字段级 TTL。边界：字段极多时 HGETALL 危险。
  • List：双端队列。场景：最新 N 条（LTRIM 控制长度）、轻量队列、时间线。边界：无 ACK、无消费组，不宜做可靠消息。
  • Set：去重集合，支持交并差。场景：标签、共同好友、抽奖、去重。边界：大集合运算阻塞。
  • ZSet：带分值的有序集合。场景：排行榜、延时队列、滑动窗口限流、权重队列。边界：大 ZSet 深分页有性能问题。
  • Bitmap / HyperLogLog / GEO / Stream：位图签到与活跃统计；HLL 海量 UV（12KB 估 1 亿）；GEO 附近的人（底层 ZSet）；Stream 可靠消息队列（消费组 + ACK）。

加分收尾：「选型的核心是看访问模式——是整体读写还是局部读写，需不需要排序/去重/范围查询，数据量级多大。比如同样是 UV 统计，只要数量就用 HLL，需要取回具体用户才用 Set。」

String 的底层 SDS 相比 C 字符串有什么优势？进阶

SDS（Simple Dynamic String）结构大致为：len | alloc | flags | buf[]。

  1. O(1) 获取长度：C 字符串用 strlen 要 O(N) 遍历；SDS 直接读 len 字段。这直接影响 STRLEN、APPEND 等命令性能。
  2. 二进制安全：C 字符串以 \0 结尾，无法存二进制数据（图片、序列化对象中间可能有 \0）。SDS 用 len 记录长度，\0 只是兼容 C 库调用的尾巴，可以存任意二进制。
  3. 杜绝缓冲区溢出：C 的 strcat 不检查空间；SDS 修改前会检查 alloc - len 是否足够，不够就自动扩容。
  4. 减少内存重分配次数：空间预分配（扩容时若新长度 < 1MB 则多分配一倍，≥1MB 则多分配 1MB）+ 惰性释放（缩容不立即回收，只改 len，留待复用）。这让 APPEND 这类操作从「每次都 realloc」变成「偶尔 realloc」。这就是 C 字符串需要 strcat 但 SDS 快的原因。
  5. 兼容 C 字符串函数：buf 末尾保留 \0，可以直接传给 printf 等 C 库函数。

能延伸：int 编码时数字直接存在 ptr 里，不分配 SDS；embstr 让 redisObject 和 SDS 一次分配（≤44字节），减少内存碎片和 malloc 次数。

ZSet 为什么用跳表不用红黑树/B+树？高级

四个维度回答（详见本节的深度框）：

  1. 范围查询（ZRANGEBYSCORE）：跳表找到起点后沿底层链表顺序遍历，内存局部性好、无回溯；红黑树要中序遍历，指针跳转多。
  2. 排名（ZRANK）：跳表节点有 span 字段，累加跨度即可 O(log N) 求排名；红黑树必须维护子树 size，旋转时更新更复杂。
  3. 实现复杂度：跳表无旋转/再平衡，插入删除只改指针，代码量和 bug 面远小于红黑树。Redis 追求「简单可靠」。
  4. 内存：Redis 取 p=0.25，平均指针数 1.33，比红黑树的固定 3 指针 + 颜色更省内存。

为什么不选 B+ 树：B+ 树是为磁盘 I/O 优化的（一个节点放一页，减少磁盘随机读），而 Redis 全内存操作，没有磁盘 I/O 问题，B+ 树的复杂节点分裂逻辑变成纯负担。

追问准备：「跳表的最坏时间复杂度是 O(N)（极端不平衡），为什么可接受？」→ 因为层数是随机决定的，概率上极不平衡的情况几乎不可能出现，期望复杂度是 O(log N)；Redis 的插入也做了一定随机化，不需要额外的再平衡机制。

一个业务要用 Redis 存「用户信息」，你会怎么设计 key 和结构？高级

这是开放设计题，考察的不是「知道 Hash」，而是完整的设计决策链。按以下顺序回答：

  1. 先问需求：字段有多少个？是否经常只更新个别字段？是否需要单独过期？数据量多大？QPS 多少？是否需要模糊查询？
  2. 选结构：
    • 字段少（<10）且整体读写为主 → String + JSON（实现简单、序列化开销可接受）。
    • 字段多、需局部更新、需字段级 TTL → Hash。
  3. Key 命名规范：业务:实体:标识[:维度]，例如 user:profile:1001、order:detail:2026093010001。要求：可读、可前缀隔离、便于 ACL 授权和批量清理。
  4. TTL 策略：热点数据 30 分钟 + 随机抖动（防雪崩）；不常变的配置类可长 TTL + 主动失效。
  5. 大 key 预防：预估单 key 大小，超过 10KB 就要重新设计（拆字段、拆维度）。
  6. Cluster 考虑：如果同一业务涉及多 key 原子操作，用 hash tag 让它们落到同一 slot；但要小心把热点都集中到一个 slot（这是我们 Day4 会讲的反面案例）。
  7. 一致性与写策略：缓存用 Cache Aside（先更新 DB 再删缓存），明确能接受的脏数据窗口。

收尾话术：「Redis 的 key 设计本质上是把数据库的索引设计前移到缓存层——设计得好，缓存命中率高、内存省、扩容平滑；设计得差，就会出现大 key、热 key、数据倾斜。」

HyperLogLog 为什么能用 12KB 统计上亿 UV？它的误差从哪来？专家

原理（伯努利实验 + 分桶平均 + 调和平均）：

  1. 核心洞察：把每个元素哈希成一个足够长的二进制串，「连续出现 0 的个数 k」在概率上能反映集合大小——如果一个集合有 N 个元素，那么观察到「首个 1 出现在第 k 位」的最大 k 大约等于 log₂(N)。就像抛硬币，抛得越多越容易出现连续很多次正面。
  2. 分桶降低方差：单个估算方差极大，所以 Redis 用 16384（2^14）个桶，用哈希值的前 14 位决定元素进哪个桶，后 50 位计算 k。每个桶记录自己见过的最大 k。
  3. 调和平均合并：最终估算用调和平均（而非算术平均）来抵抗极端值影响，并乘以常数 α ≈ 0.7213。
  4. 内存：16384 个桶 × 6 bit = 98304 bit ≈ 12KB（固定，与元素数量无关）。这就是它能统计上亿 UV 的原因。

误差来源与量化：

  • 随机性误差：标准误差 1.04/√m，m=16384 时约 0.81%。这是设计上的取舍——用「估计」换「恒定内存」。
  • 哈希碰撞：不同元素哈希值相同的概率极低（64 位哈希），影响很小。
  • 小基数偏差：元素很少时（比如几十个），线性计数法需修正——Redis 在基数小于阈值时使用【线性计数】修正。
  • 稀疏编码：元素少时用稀疏表示（只存非零桶）更省内存，超过 hll-sparse-max-bytes（默认 3000 字节）转稠密编码。

专家级补充：PFCOUNT 在多个 HLL 上是 O(N)，N 是 HLL 数量；PFCOUNT 单 key 会缓存上次结果（放在 key 的 metadata），但如果 key 被修改过，缓存失效，可能比 PFMERGE 加 PFCOUNT 更慢。这是很细的点，能说出来面试官会记住你。

Stream 的消费组是怎么保证消息不丢的？高级

关键在于 PEL（Pending Entries List，待处理条目列表）机制：

  1. 消息不会因为「被读」就删除。这是与 List 最本质的区别——XREADGROUP 只是把消息「投递并记录」到消费者的 PEL，消息本体还在 Stream 里。
  2. PEL 记录「谁拿了、什么时候拿的、投递了几次」。每条待处理消息有 consumer、delivery-time、delivery-count 三个关键属性。
  3. 只有 XACK 才从 PEL 移除。消费者处理成功必须显式 ACK。
  4. 故障恢复靠 XAUTOCLAIM：消费者挂了，它的待处理消息会一直留在 PEL。其他消费者用 XAUTOCLAIM（或 XCLAIM）按「最小空闲时间」把超时未确认的消息认领过来，delivery-count 会 +1，可用于识别「反复失败」的消息。
  5. 8.6 幂等生产（IDMP）：生产者崩溃重发时，用同一 IDMP 值写入只会生效一次，避免了「重复消息」这个经典难题——这解决了「at-least-once 必然带来重复」的问题，实现 at-most-once production。

面试加分：主动区分三个语义——at-most-once（最多一次，可能丢）、at-least-once（至少一次，可能重复）、exactly-once（精确一次，需要业务幂等或事务配合）。Redis Stream 的消费是 at-least-once，所以业务侧必须做幂等（用消息 ID 或业务唯一键去重）。「MQ 不保证不重复，业务必须幂等」是 10 年经验的必备认知。
