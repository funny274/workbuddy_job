Day 4 · 第 3 节 预计 90 分钟 大厂实战核心

Day4.3 · 大 Key / 热 Key 与线上治理

一句话结论

大 Key = 单个 key 的「体积/元素数」过大，危害是阻塞主线程（一次操作要几毫秒到几秒）、拖慢故障转移、引发内存不均。热 Key = 单个 key 的「访问频率」过高，危害是把单个分片的 CPU/带宽打满，且扩容（加机器）解决不了问题。

这是 10 年+ 岗位最容易拉开差距的章节：面试官问的不是「什么是大 key」，而是「线上 QPS 突然飙升、某个分片 CPU 打满，你怎么定位、怎么在不影响业务的前提下治理」。这一节会把京东、得物、B站的三套真实方案讲透。

1. 大 Key：定义、危害与量化标准

✅ 什么算「大 Key」（量化标准）

「大」有两个维度：元素数量和value 体积。行业通用经验值：

数据类型元素数量告警线体积告警线说明
String—> 10 KB（严格 > 1 MB 必须处理）单个 value 过大，网络传输 + 序列化开销大
Hash / List / Set / ZSet> 5,000（严格 > 10,000）> 1 MB元素数过多，整体操作（HGETALL/SMEMBERS）会阻塞
Stream> 10,000 条> 10 MB需配合 MAXLEN 裁剪

阿里云 / 腾讯云 Redis 的官方建议：单实例中大于 10KB 的 key 不超过 1000 个（不同厂商略有差异，但量级一致）。

🚨 大 Key 的五大危害（每条都要能说清机理）
  1. 阻塞主线程（最核心的危害）
    Redis 命令执行是单线程的。一次 HGETALL 一个 100 万元素的 Hash，需要序列化并返回几 MB 数据——执行时间可能几百毫秒甚至几秒。这期间所有其他请求全部排队等待。假设正常 QPS 是 10 万，一次 500ms 的阻塞就意味着 5 万个请求被延迟。
    关键：这不只是「这个请求慢」，而是「整个实例卡住」。
  2. 网络带宽打满
    读一个 10MB 的 key，单次就要传 10MB。如果 QPS 是 100，就是 1GB/s 的带宽需求——直接打满万兆网卡。而且大 key 的传输会挤压其他正常请求的带宽。
  3. 加剧删除时的阻塞
    删除大 key（DEL）时需要释放大量内存，这个释放过程是同步的，会阻塞主线程。一个 100 万元素的 Hash 删除可能耗时几十到几百毫秒。
    解法：用 UNLINK（异步删除，把 key 从 keyspace 摘掉后，把内存释放交给后台线程）。
  4. 拖慢持久化与故障转移
    RDB：大 key 会让 fork 出的子进程写盘量暴增，延长 RDB 时间。
    主从全量同步：一个 1GB 的大 key 通过网络传输到从节点，耗时长、易超时、可能反复重试。
    Cluster 槽迁移：MIGRATE 一个大 key 会阻塞两个节点。
  5. 内存分布不均（Cluster 场景）
    如果大 key 都集中在少数几个槽上，会导致某些节点内存远超其他节点，甚至触发 OOM 淘汰，而其他节点还很空闲。扩容（加节点）也没用，因为槽的分布是固定的。
⚠️ 大 Key 最常见的三种成因
  1. 设计错误：把「集合」当成「大集合」用。
    典型：用 SET order:all:users 存所有下单用户（几百万人）；用 HASH user:all 存所有用户信息。根因是没有按业务维度拆分。
  2. 无上限增长：忘了设置清理逻辑。
    典型：用 LIST 做消息队列但从不 LTRIM；用 ZSET 做排行榜但从不清理历史数据；用 Hash 记录用户行为日志，一直 HSET 不删。
  3. 业务自然增长：一开始很小，慢慢变大。
    典型：某商品详情页的「评论列表」缓存，一个大爆款商品积累了 500 万条评论。这种最难发现，因为上线时是正常的。

2. 怎么发现大 Key（四种手段）

手段一：redis-cli --bigkeys（最常用）

########## 扫描大 key ##########
redis-cli -h 10.0.0.5 -p 6379 --bigkeys

# 输出示例：
# ------- summary -------
# Sampled 1000000 keys in the keyspace!
# Total key length in bytes is 25000000 (avg len 25.00)
#
# Biggest string found 'user:profile:999999' has 1048576 bytes
# Biggest list   found 'feed:timeline:888888' has 500000 items
# Biggest hash   found 'order:detail:777777' has 200000 fields
# Biggest set    found 'activity:users:666666' has 1000000 members
# Biggest zset   found 'rank:global' has 3000000 members
#
# 0 lists with 0 items (00.00% of keys, avg size 0.00)
# 1 lists with 500000 items (00.00% of keys, avg size 500000.00)

# ⚠️ 工作原理与注意事项：
#  ① 它用 SCAN 遍历整个 keyspace，对每个 key 用 STRLEN/LLEN/HLEN/... 判断大小
#  ② 只报告「每种类型最大的那个 key」，不是所有大 key
#  ③ 会对每个 key 执行一次类型判断，对线上有一定压力（建议在从节点执行）
#  ④ 4.0+ 支持 --bigkeys 用 SCAN 实现，不会阻塞（不像 KEYS *）

########## 同族命令：--memkeys（7.0+）##########
redis-cli --memkeys
# 按"内存占用"排序，比 --bigkeys 更准确（--bigkeys 只看元素数/字符串长度）
redis-cli --memkeys --memkeys-samples 100
# --memkeys-samples 控制每种类型的采样元素数（默认 0 = 全部采样，慢；建议设 100）

手段二：MEMORY USAGE（精确查询单个 key）

# 精确计算某个 key 占用的内存（含数据结构开销，不只是 value 长度）
MEMORY USAGE user:profile:999999
# 返回：1048600（字节）

# 加上 SAMPLES 参数（默认 5）：采样计算，更快但可能有误差
MEMORY USAGE big:hash SAMPLES 0     # 0 = 精确计算全部元素（慢但准）
MEMORY USAGE big:hash SAMPLES 100   # 采样 100 个元素估算（快）

# 注意：MEMORY USAGE 对超大 key 本身也可能耗时（要遍历元素），
#      线上建议用 SAMPLES 采样，或直接在从节点执行

手段三：SCAN + 批量分析（自定义脚本，最实用）

#!/bin/bash
# ============================================
# 大 Key 扫描脚本（生产可用）
# 特点：分批 SCAN，统计所有大 key（不只是最大的），可导出报告
# 建议在【从节点】执行，避免影响主节点
# ============================================

HOST=${1:-127.0.0.1}
PORT=${2:-6379}
THRESHOLD=${3:-5000}          # 元素数阈值
cursor=0
total_keys=0
big_keys=0
report="/tmp/redis-bigkey-report-$(date +%Y%m%d%H%M%S).csv"

echo "type,key,size,detail" > "$report"

while : ; do
  # SCAN 每次取 500 个 key（COUNT 只是提示，不保证精确）
  reply=$(redis-cli -h $HOST -p $PORT SCAN $cursor COUNT 500)
  cursor=$(echo "$reply" | head -1)
  keys=$(echo "$reply" | tail -n +2)

  for key in $keys; do
    total_keys=$((total_keys+1))
    type=$(redis-cli -h $HOST -p $PORT TYPE "$key")

    size=0
    case "$type" in
      string) size=$(redis-cli -h $HOST -p $PORT STRLEN "$key") ;;
      list)   size=$(redis-cli -h $HOST -p $PORT LLEN "$key") ;;
      hash)   size=$(redis-cli -h $HOST -p $PORT HLEN "$key") ;;
      set)    size=$(redis-cli -h $HOST -p $PORT SCARD "$key") ;;
      zset)   size=$(redis-cli -h $HOST -p $PORT ZCARD "$key") ;;
      stream) size=$(redis-cli -h $HOST -p $PORT XLEN "$key") ;;
      *) continue ;;
    esac

    if [ "$size" -gt "$THRESHOLD" ]; then
      big_keys=$((big_keys+1))
      echo "$type,$key,$size," >> "$report"
      echo "[BIG] $type $key -> $size"
    fi
  done

  [ "$cursor" = "0" ] && break
done

echo "==============================="
echo "扫描完成：共 $total_keys 个 key，发现 $big_keys 个大 key"
echo "报告文件：$report"

💡 生产建议：怎么扫描才安全
  • 在从节点扫描：主从架构下，大 key 扫描会对实例产生压力，优先在从节点做（从节点数据一致）。
  • 低峰期执行：凌晨 2-5 点。
  • 控制频率：每天/每周一次，不要高频扫描。
  • 用云厂商的工具：阿里云 DAS、腾讯云 DBbrain 都有一键大 key 分析，比自研脚本更可靠。面试时提到这个会加分（说明你有云上生产经验）。
  • 日常也要有告警：不要等出故障才扫。可以对 MEMORY USAGE 做定期抽样监控，或者用 redis-cli --bigkeys 的输出做趋势对比。

3. 大 Key 的治理：从预防到存量清理

✅ 治理总原则：预防为主，存量分批平滑处理

核心原则：

  1. 预防优于治疗：设计阶段就把「大集合」拆开，比事后清理成本低得多。
  2. 存量清理必须「分批 + 限速 + 可中断」：绝对不能用一个 DEL bigkey 直接删——那本身就是一次几百毫秒的阻塞。
  3. 不要用 KEYS * 找 key：KEYS 会遍历整个 keyspace 并一次性返回所有 key，生产上绝对是事故。必须用 SCAN（游标式渐进遍历，不阻塞）。

3.1 预防：设计阶段就避开大 Key

反模式问题正确做法
SET all:users（一个 Set 存所有用户） 几百万元素，SMEMBERS 直接卡死 按业务分片：set:users:active、set:users:vip；或按 ID 区间 set:users:{0-9999}
HASH user:all（一个 Hash 存所有用户） 几百万人，HGETALL 卡死 一用户一 Hash：user:1001、user:1002；或按 ID 分片：user:shard:{1001%100}
LIST feed（无限追加，从不裁剪） 无上限增长，最终变成亿级 List 必须 LTRIM：LPUSH feed x; LTRIM feed 0 999（只保留最近 1000 条）
ZSET rank:all（全局排行榜，无清理） 数据无限增长 定期重建/按周期分 key：rank:daily:20260930；或只保留 Top N
String 存整个 JSON 列表 单个 value 几十 MB 拆成「列表 + 明细」：order:list:uid 存 ID 数组（小），order:detail:oid 存单条详情
用 Redis 存大文件 / 大对象 value 几百 MB Redis 只存元数据 + 指针，大文件放 OSS/S3 等对象存储
🚨 一个反例对比：商品评论缓存的设计演进

V1（原始设计，容易出事）：

# 一个 key 存所有评论
LPUSH comment:product:1001 "评论JSON1" "评论JSON2" ...   # 持续增长
LRANGE comment:product:1001 0 -1                        # 取出所有评论 → 卡死！

V2（分页 + 裁剪）：

# 只保留最近 500 条 + 分页读取
LPUSH comment:product:1001 "{...}"
LTRIM comment:product:1001 0 499        # 每次写完裁剪，保证不超过 500 条
LRANGE comment:product:1001 0 19        # 只取前 20 条（分页）

V3（大厂标准做法：热点与冷数据分离）：

# Redis 只缓存"热评前 100 条"，完整数据在 DB / ES
ZADD comment:hot:1001 score "评论ID"     # 按热度排序，只保留 Top 100
ZREMRANGEBYRANK comment:hot:1001 0 -101  # 裁剪，保持最多 100 条

# 用户要翻更多评论 → 走 DB 分页（或 ES 搜索）
# 这样：① Redis 里永远只有 100 条，不会变大；② 用户看到的是最有价值的评论

面试可说：「缓存大 key 治理的常见套路是『热数据进缓存，全量数据留 DB』——缓存的定位就是『加速热点访问』，不是『当数据库用』。这个认知一旦建立，很多大 key 问题在设计中就自然避免了。」

3.2 存量清理：安全的删除方案

✅ 删除大 Key 的四种方法（按安全性排序）

方法一：UNLINK（4.0+，最简单的正确解法）

# UNLINK 是异步删除：主线程只负责把 key 从 keyspace 摘除（O(1)），
# 实际的内存释放交给后台线程完成，不阻塞主线程
UNLINK big:hash:key

# ⚠️ 注意：
#  ① 需要 lazyfree-lazy-user-del 或显式用 UNLINK
#  ② 后台线程释放内存也要时间，但主线程已"看不见"这个 key 了
#  ③ lazyfree 相关配置：
lazyfree-lazy-eviction yes      # 淘汰时异步释放
lazyfree-lazy-expire yes        # 过期时异步释放
lazyfree-lazy-server-del yes    # 隐式删除（如 RENAME）时异步
lazyfree-lazy-user-del yes      # 用户 DEL 也异步（4.0+，启用后 DEL 等同 UNLINK）
lazyfree-lazy-user-flush yes     # FLUSHALL/FLUSHDB 异步（6.2+）

方法二：分批次删除元素（最精细的控制）

如果连 UNLINK 的「后台释放压力」都不放心（比如实例内存很紧张），可以自己分批删元素：

-- 每次删除 Hash 的 100 个 field（配合循环调用，每次间隔 10ms）
local fields = redis.call('HKEYS', KEYS[1])
local count = 0
for i = 1, math.min(#fields, tonumber(ARGV[1])) do
    redis.call('HDEL', KEYS[1], fields[i])
    count = count + 1
end
if redis.call('HLEN', KEYS[1]) == 0 then
    redis.call('DEL', KEYS[1])
end
return count

适用场景：超大 key（百万级元素）且内存非常紧张，需要「极平滑」地释放。

方法三：SCAN 系列命令遍历删除（针对 Collection）

# Hash：HSCAN 游标遍历 + HDEL
# Set： SSCAN + SREM
# ZSet：ZSCAN + ZREM
# List：没有 SCAN，用 LTRIM 逐段裁剪

# 示例：分批删除一个大 Hash
cursor=0
while : ; do
  result=$(redis-cli HSCAN big:hash $cursor COUNT 200)
  cursor=$(echo "$result" | head -1)
  fields=$(echo "$result" | tail -n +2 | awk 'NR%2==1')
  [ -n "$fields" ] && redis-cli HDEL big:hash $fields > /dev/null
  [ "$cursor" = "0" ] && break
  sleep 0.01        # 限速：每批间隔 10ms，避免 CPU 打满
done

方法四：重命名 + 异步清理（最稳妥的「平滑下线」）

# 思路：先让业务"看不见"这个 key，再慢慢清理
# ① 重命名到一个临时名字（业务代码不会再访问到）
RENAME big:key big:key:deleting:20260930

# ② 设置一个短的过期时间（让它自然过期，Redis 会异步释放）
EXPIRE big:key:deleting:20260930 60

# ③ 或者用 UNLINK 异步删除
UNLINK big:key:deleting:20260930

这个方案的好处：① RENAME 是 O(1) 的，瞬间完成；② 业务立刻不再访问到旧 key；③ 清理过程中如果发现问题，还能 RENAME 回来（可回滚）。

4. 热 Key：为什么扩容解决不了

✅ 热 Key 的本质问题

定义：某个 key 的访问频率极高（比如每秒几万到几十万次），导致承载它的那个 Redis 节点（或分片）CPU / 网络被打满。

为什么「加机器」没用（关键认知）：

Redis Cluster 用 CRC16(key) mod 16384 决定 key 落在哪个槽。这意味着同一个 key 永远落在同一个槽、同一个节点上——不管你有 3 个节点还是 300 个节点。

所以集群扩容只能分散「不同 key」的负载，对「同一个 key」的热度完全无效。这就是为什么大促时「加了 100 台 Redis，热 key 所在的那个分片还是 100% CPU」。

问题大 Key热 Key
矛盾焦点单个 key 太大 → 阻塞主线程、内存不均单个 key 太热 → 单分片 CPU/带宽打满
扩容能解决吗❌ 该 key 还是那么大❌ 该 key 还是落在同一个节点
根本解法拆分 key（按维度拆成多个小 key）拆分读压力（本地缓存 / 多副本 key / 读写分离）
典型场景评论列表、全局用户集合爆款商品详情、明星主页、大促配置
🚨 热 Key 的四大危害
  1. 单分片 CPU / 网络打满：该分片上的所有请求（不只是这个热 key）全部受影响，P99 延迟飙升，甚至触发集群误判节点下线。
  2. 引发缓存击穿：热 key 一旦失效，瞬时并发重建的流量会打爆 DB（Day4.1 讲过）。热 key 和击穿往往是同一个问题的两个面。
  3. 数据倾斜导致集群不均衡：热 key 所在的节点负载是其他节点的几十倍，集群整体资源利用率低下。
  4. 可能引发误故障转移：热 key 导致节点响应变慢 → Gossip 心跳超时 → 被标记为 PFAIL/FAIL → 触发不必要的故障转移，而故障转移本身又会加剧抖动（雪上加霜）。

5. 怎么发现热 Key（五种手段）

手段一：redis-cli --hotkeys（4.0+，最便捷）

########## --hotkeys 的原理与限制 ##########
redis-cli --hotkeys

# 输出示例：
# [00.00%] Hot key 'product:detail:1001' found so far with counter 98765
# [00.00%] Hot key 'rank:global' found so far with counter 54321

# ⚠️ 关键限制（面试常考）：
#  ① 它依赖 maxmemory-policy 是 LFU 系列（allkeys-lfu / volatile-lfu）！
#     因为 hotkeys 统计的是"每个对象的 LFU 访问计数器"
#  ② 如果是 LRU 策略，--hotkeys 会报错："Hot key detection requires LFU maxmemory policy"
#  ③ 它用 SCAN 遍历所有 key，会比较慢，对线上有压力
#  ④ 只能发现"当前缓存中"的热 key，已经过期的发现不了

########## 所以第一步是确认为 LFU 策略 ##########
CONFIG GET maxmemory-policy
# 如果不是 *_lfu，--hotkeys 用不了

########## 8.x 的 HOTKEYS 命令（原生热 key 检测，无需 LFU）##########
# Redis 8.0 引入了原生的 HOTKEYS 命令，不需要 LFU 策略
HOTKEYS START
# 等待一段时间（收集数据）
HOTKEYS GET
# 输出：1) "product:detail:1001"  2) (integer) 98765  3) ...
HOTKEYS STOP
HOTKEYS RESET   # 清空统计
⚠️ 重要提醒：--hotkeys 不是万能的

redis-cli --hotkeys 在生产上通常不可用，原因：

  1. 要求 LFU 策略，而很多生产环境用的是 LRU 或 noeviction。
  2. 即使改了 LFU，也会有「LFU 计数器初始值」的问题——新 key 需要被访问多次才会被统计到（这个"预热"过程可能很长）。
  3. 它是一次性的事后分析，没法实时监控。

所以真正的生产环境要用『客户端埋点 + 代理层统计 + 内核改造』这三类方案——这正是下面要讲的京东、得物、B站三大流派。

补充：Redis 8.x 的 HOTKEYS 命令是官方给出的答案——不依赖 LFU，通过采样在服务端统计热 key，可以随时 START/GET/STOP。这是 8.x 在热 key 治理上的重要进步。

手段二：客户端埋点统计（成本低，最常用）

/**
 * 客户端侧热 key 统计：用本地哈希 + 定时上报
 * 优点：零侵入 Redis，实时性好
 * 缺点：每个客户端只能看到自己发出的请求（分布式下要聚合）
 */
public class HotKeyCollector {

    // 每个客户端实例维护自己的计数（用 LongAdder 减少竞争）
    private final ConcurrentHashMap<String, LongAdder> counters = new ConcurrentHashMap<>();
    private static final int MAX_KEYS = 10000;   // 防止内存溢出

    /** 每次访问 key 时调用（异步、无锁路径） */
    public void record(String key) {
        if (counters.size() > MAX_KEYS) {
            // 简单降级：超过上限就不统计新 key（避免内存爆炸）
            return;
        }
        counters.computeIfAbsent(key, k -> new LongAdder()).increment();
    }

    /** 定时上报（每 10 秒）：把计数推给聚合服务 */
    @Scheduled(fixedRate = 10000)
    public void report() {
        Map<String, Long> snapshot = new HashMap<>();
        counters.forEach((k, v) -> {
            long count = v.sumThenReset();       // ⭐ sumThenReset：读取并清零，自然实现"滑动窗口"
            if (count > 100) {                  // 只上报有意义的数据，减少网络开销
                snapshot.put(k, count);
            }
        });
        if (!snapshot.isEmpty()) {
            // 发给聚合服务（Kafka / 专门的统计服务）
            kafkaTemplate.send("redis:hotkey:report",
                instanceId + ":" + JSON.toJSONString(snapshot));
        }
    }
}

手段三：代理层统计（监控所有流量，最准确）

在客户端和 Redis 之间加一层代理（如 Twemproxy、Codis、自研代理），代理能看到所有经过它的请求，可以在这里做统一的热 key 统计。

########## 代理层方案的优缺点 ##########
# 优点：
#   ① 能看到全量流量（不受单客户端视野限制）
#   ② 可以在代理层直接做"热 key 本地缓存"（下面会讲）
#   ③ 与业务代码解耦
# 缺点：
#   ① 多一跳网络，增加延迟（通常 0.1~0.5ms）
#   ② 代理本身成为需要高可用的组件
#   ③ 代理的统计本身有性能开销

手段四：MONITOR 命令（仅限临时排查，禁止生产长期使用）

# MONITOR 会实时打印所有执行的命令
redis-cli MONITOR

# 统计热 key（临时用）
redis-cli MONITOR | head -n 10000 | awk '{print $4}' | sort | uniq -c | sort -rn | head -20

# ⚠️⚠️⚠️ 严重警告：
#  ① MONITOR 会把每条命令都"回传"给客户端，自身消耗巨大
#  ② 会显著降低 Redis 吞吐（可能降低 50% 以上）
#  ③ 生产环境【只在紧急排查时短暂使用】，用完立刻 Ctrl+C
#  ④ 绝不能用 MONITOR 做长期监控！

手段五：Redis 8.x 原生 HOTKEYS（官方答案）

# Redis 8.0+ 内置热 key 检测：基于采样，对性能影响小
HOTKEYS START
# 让业务跑一段时间（如 60 秒）
HOTKEYS GET
# 返回 Top 热 key 及其访问计数
HOTKEYS STOP
HOTKEYS RESET

# 配置项（控制采样与内存开销）

# 更大的值 = 更低的内存开销，但统计精度下降

6. 热 Key 的治理：三大流派（大厂真实方案）

✅ 治理热 Key 的五种通用手段（先掌握通用层）
  1. 本地缓存（最有效的第一招）
    在应用进程内存里缓存热 key（Caffeine / Guava Cache / 自研），把大部分读请求拦在 Redis 之前。比如热 key 每秒 10 万次访问，本地缓存能拦掉 95%，Redis 只剩 5000 次。
    代价：① 本地缓存与 Redis 的一致性问题（需要过期时间 + 主动失效）；② 多实例之间的数据可能有差异；③ 需要预热。
    这是大厂处理热 key 最主流的第一道防线。
  2. 热 key 多副本（key 拆分）
    把一个热 key 复制成 N 份（如 hotkey:1001:0 ~ hotkey:1001:9），读的时候随机选一份。这样读压力就分散到 N 个槽（可能在不同节点）了。
    代价：① 写入时要写 N 份（写放大）；② 数据一致性维护成本上升；③ 只读场景才适用（写多的 key 不适合）。
    命令层面 CLUSTER KEYSLOT 可以用 hash tag 控制分布。
  3. 读写分离 / 从节点分流
    热 key 的读请求分散到多个从节点（READONLY + 客户端负载均衡）。
    代价：① 主从复制延迟导致可能读到旧数据；② 从节点数量有限，分压能力有限；③ Cluster 下从节点也可以服务读（配合 READONLY）。
  4. 代理层/服务端做二级缓存
    在代理层（如自研 Proxy）或 Redis 服务端做「热 key 自动识别 + 本地缓存」。对业务完全透明，是 B站/得物这类公司选择的方向（见下文）。
  5. 业务层规避：把热 key 打散到设计里
    最根本的一招：在设计阶段就避免「单一超级热点」。
    · 秒杀库存 → 拆成 100 个库存桶（stock:1001:0 ~ stock:1001:99），请求随机落到一个桶扣减，最后汇总。
    · 大促配置 → 用本地缓存 + 配置中心推送。
    · 明星微博 → 用「关注列表扇出 + 多级缓存」而不是「单 key 计数器」。

6.1 京东 JDHotKey：服务端「热 key 自动缓存」

✅ 京东的方案：在 Redis 前面加一层「热 key 本地缓存」

核心思路：改造客户端（或加 proxy），自动发现热 key 并把它们缓存到应用本地内存，后续对该 key 的请求直接本地返回，不再访问 Redis。

架构：

应用 → [JDHotKey 客户端] → Redis
              │
              ├─ ① 请求计数（本地 + 上报到"热 key 计算服务"）
              ├─ ② 从"热 key 计算服务"接收热 key 名单
              └─ ③ 命中热 key → 读本地缓存（Caffeine），不访问 Redis

关键设计：

  • 热 key 计算服务：集中收集所有客户端的访问计数，用滑动窗口（如最近 5 秒）计算，超过阈值的 key 进入「热 key 名单」。
  • 推送名单：把名单推送给所有客户端（一般用长连接 / 配置中心）。
  • 客户端本地缓存：客户端把热 key 的 value 缓存到本地，设置较短的过期时间（如 1-2 秒）或监听变更。
  • 退出机制：key 热度下降后从名单移除，客户端删掉本地缓存。

效果：热 key 的读请求绝大部分被本地缓存拦截，Redis 端压力大幅下降。

代价/注意点：

  • 本地缓存引入了一致性延迟（热 key 更新后，各实例本地缓存需要时间失效）。
  • 只适用于「读多写少」且「能容忍秒级延迟」的 key。库存这种不能这么干。
  • 「热 key 名单」的分发本身也要考虑可用性（名单服务挂了，客户端应该降级为「全部走 Redis」）。

6.2 得物：Redis 内核改造 + 热点探测

✅ 得物的方向：在 Redis 内核层做热点探测与自动缓存

核心思路：不满足于「在客户端拦截」，而是改造 Redis 源码，在服务端实现「热 key 自动识别 + 服务端本地缓存（或转发到其他节点）」。

为什么要在内核做：

  • 客户端方案有盲区：每个客户端只能看到自己的流量，如果热 key 的流量分散在 100 个客户端上，单看每个客户端都不"热"，聚合才有意义，但聚合又有延迟。
  • 内核能看到全量：Redis 本身就是处理所有请求的地方，在这里统计最准确、最实时。
  • 能在服务端直接分流：识别到热 key 后，可以在服务端做「本地缓存返回」，或者转发给其他有空闲的节点——不依赖客户端配合。

典型的技术点：

  • 在 lookupKey / 命令处理流程里插入统计逻辑（用近似算法控制开销，如 Count-Min Sketch）。
  • 热 key 的 value 在服务端内存里做一层缓存，命中则跳过磁盘/其他开销（对纯内存 Redis 而言主要是减少网络与序列化）。
  • 或者实现 「热 key 请求转发」：把热 key 的读请求转发到多个从节点，由服务端做负载均衡。

代价：

  • 维护成本极高：需要跟着 Redis 版本升级，自己维护分支，编译、测试、灰度。
  • 引入 bug 风险：改内核意味着可能引入内存安全、并发问题。
  • 一般只有体量很大、Redis 是核心基础设施的公司才这么做（得物、美团、快手等都有类似的内核改造）。

6.3 B站 HeavyKeeper：用算法解决「统计开销」

✅ HeavyKeeper 算法：在有限内存里找出高频元素

问题背景：要统计热 key，最朴素的方式是「每个 key 一个计数器」——但如果有 1 亿个 key，就需要 1 亿个计数器，内存不可接受。而且统计本身的开销会拖慢 Redis。

解决方案：用概率数据结构在「固定的小内存」里找出 Top-K 高频元素。主流算法有三个：

算法原理优点缺点
Count-Min Sketch二维计数器数组 + 多个哈希函数，取最小值作为估计实现简单、查询 O(k)只能「估计频次」，只高估不低估，找 Top-K 不够准
Space-Saving维护固定大小的「候选项表」，新元素替换最小计数的项天然输出 Top-K低频元素可能被误淘汰
HeavyKeeper
B站选择		基于「衰减的桶」+ 哈希指纹：新元素与桶内指纹比较，相同则计数+1，不同则按概率衰减桶内计数并可能替换比 Count-Min 更准、能用更小内存找出更精确的 Top-K、有效过滤「长尾噪声」实现相对复杂

HeavyKeeper 的核心机制（面试可以讲这个）：

  • 维护 d 个哈希表，每个表 w 个桶，每个桶存「指纹 + 计数」。
  • 新元素到达：用 d 个哈希函数定位到 d 个桶。
    · 如果某个桶的指纹相同 → 该桶计数 +1。
    · 如果不相同 → 以概率 b^(-count) 衰减该桶的计数（b 是衰减因子，如 1.08）。计数衰减到 0 时，用新元素替换。
  • 为什么这样设计有效：高频元素会不断命中自己所在的桶，计数持续增长；低频元素即使偶尔命中，也会被其他元素的「衰减」逐渐抹掉。这样一个桶就能代表「当前最高频的元素」，从而实现「用小内存找 Top-K」。

B站的落地：把 HeavyKeeper 集成到 Redis 客户端（或 proxy），实时上报热 key 到监控/调度系统，结合「本地缓存 + 副本」做多层治理。它的价值在于「把热 key 识别的资源开销降到可以常驻运行」——不再是「出故障了才临时排查」，而是常态监控。

💡 三大流派对比与选择
方案京东 JDHotKey得物（内核改造）B站（HeavyKeeper）
位置客户端Redis 内核客户端/Proxy + 算法
统计范围单客户端（需上报聚合）全量（最准）单节点（聚合后全局）

面试话术：「如果让我选，我会从成本从低到高做：

  1. 先用客户端埋点 + 定时上报（成本最低），配合本地缓存这一招——这一招就能解决 80% 的热 key 问题。
  2. 如果统计精度不够，引入 HeavyKeeper 类的概率算法做常态监控。
  3. 只有当 Redis 是公司级核心基础设施、体量足够大时，才考虑内核改造。

因为核心洞察是：热 key 问题的『发现』有各种成本不同的方案，但『治理』的答案高度一致——本地缓存 + 读写分离 + 业务层打散。把精力放在治理上比放在发现上收益更大。」

7. 一个大厂级热 Key 故障复盘

🚨 复盘：大促期间某爆款商品详情导致单分片打满

背景：某电商大促，Redis 3 主 3 从集群（每主 8GB，共 24GB）。大促开始后 10 分钟，监控告警。

现象：

  • 集群中 1 号主节点 CPU 从 30% 飙到 98%，另外两个主节点只有 40%。
  • 1 号节点上的请求 P99 从 1ms 飙到 450ms。
  • 同时 MySQL 的 QPS 从 8000 飙到 60000（说明有大量请求穿透了缓存）。
  • 10 分钟后，1 号节点的从节点被误判为 FAIL（因为心跳也超时了），触发了故障转移，抖动加剧。

排查过程（这是面试要讲的重点）：

  1. 看整体指标：确认是「单分片问题」而非「全集群问题」——其他两个主节点正常。这直接排除了「网络故障」「整体流量上涨」等假设。
  2. 看该分片的命令统计：redis-cli INFO commandstats，发现 cmdstat_hgetall 的调用次数异常高，占该节点总命令数的 65%。锁定问题命令是 HGETALL。
  3. 定位具体 key：临时用 redis-cli --hotkeys（提前把策略改成了 LFU）+ 客户端埋点数据交叉验证，发现是 product:detail:1001（某爆款商品）——它既是大 key（Hash 有 3 万 field），也是热 key（QPS 4 万）。
  4. 验证假设：用 MEMORY USAGE product:detail:1001 SAMPLES 0 确认占用 12MB；用 HLEN 确认 3 万 field。同时发现业务代码用 HGETALL 取全部字段。根因锁定。
  5. 为什么 MySQL QPS 也涨了：因为 HGETALL 太慢（12MB 序列化 + 传输），应用侧超时后自动降级去查了 MySQL，造成了雪崩效应。

应急处理（止血，5 分钟内）：

  1. 应用侧紧急降级：把商品详情的缓存读取开关关掉，直接读 DB（DB 加了限流保护，只放核心流量）。先止血，再治根。
  2. 调整该 key 的访问方式：把 HGETALL 改为按需取字段（HMGET field1 field2），或者拆成多个小 key。
  3. 本地缓存热 key：把爆款商品的数据加载到应用本地 Caffeine 缓存（TTL 2 秒）。

效果：1 号节点 CPU 从 98% 降到 35%，MySQL QPS 回落到 12000。

根治方案（1 周内）：

  1. 拆分数据模型：
    · product:base:1001 — 基础信息（详情页展示必需的字段，2KB）
    · product:sku:1001 — SKU 列表
    · product:desc:1001 — 富文本描述（单独 key，懒加载）
    详情页首屏只需要 base，一次 HGETALL 变成一次 GET（字符串）。
  2. 建立热 key 常态监控：接入 B站开源的 HeavyKeeper 方案，不再依赖出故障后手工排查。阈值设为「单 key QPS > 5000」，超阈值自动告警并通知业务方。
  3. 建立「大 key 上线卡点」：在 CI/CD 流水线中加一道检查——如果新增的 key 设计超过阈值（元素数 > 5000 或 value > 10KB），需要架构组评审。从流程上防止新的坑。
  4. 完善降级预案：明确哪些缓存可以降级、降级后 DB 能承受多少流量、限流阈值多少。不求「不出问题」，而求「出问题时能优雅降级」。

这个复盘的面试价值：它同时展示了 ① 分层排查的思路（整体 → 分片 → 命令 → key）；② 止血优先的原则；③ 从个案到机制的建设（监控、卡点、预案）。第三点是 10 年+ 岗位最想听的——你能把一个故障变成组织能力。

面试深度问答

什么是大 Key？有什么危害？基础

定义：单个 key 的元素数量或 value 体积过大。经验阈值：String > 10KB（严格 > 1MB）；Hash/List/Set/ZSet 元素数 > 5000（严格 > 10000）或体积 > 1MB。

五大危害：

  1. 阻塞主线程（最核心）：Redis 命令单线程执行，一次 HGETALL 大 Hash 可能耗时几百毫秒，期间所有请求排队。
  2. 网络带宽打满：单次传输几 MB 到几十 MB。
  3. 删除时阻塞：DEL 大 key 需要同步释放大量内存 → 用 UNLINK 异步删除。
  4. 拖慢持久化与主从同步：RDB 写盘量暴增；全量同步传输大 key 耗时长、易超时。
  5. Cluster 内存不均：大 key 集中导致节点间内存倾斜，扩容也解决不了。

发现：redis-cli --bigkeys、--memkeys、MEMORY USAGE key、MEMORY DOCTOR、SCAN 自定义脚本、云厂商工具。

治理：预防为主（设计时拆 key、给集合设上限/裁剪）；存量用 UNLINK 或分批删除，Never 用 DEL 直接删大 key，Never 用 KEYS *。

怎么发现大 Key？进阶
方式原理适用与注意
--bigkeysSCAN 遍历 + 对每个 key 执行 TYPE 和 STRLEN/LLEN/HLEN/...最常用；只报告每种类型最大的一个 key；建议在从节点、低峰期执行
--memkeys（7.0+）按内存占用排序，比 --bigkeys 更准配合 --memkeys-samples 控制采样
MEMORY USAGE key [SAMPLES n]精确/采样计算单个 key 的内存查已知怀疑对象；SAMPLES 0 精确但慢

发现大 Key 后怎么安全处理？高级

核心原则：分批、限速、可中断、可回滚。

方法一：UNLINK（首选）

UNLINK 把 key 从 keyspace 摘除是 O(1)，实际内存释放交给后台线程。不阻塞主线程。 建议同时开启 lazyfree-lazy-user-del yes，让 DEL 也等价于 UNLINK。

方法二：分批删元素（最平滑）

用 HSCAN/SSCAN/ZSCAN 游标遍历，每次删 100-500 个元素，每批 sleep 10ms 限速。适用于内存极度紧张、需要最平滑释放的场景。

方法三：RENAME + 异步清理（可回滚，最稳妥）

RENAME big:key big:key:deleting:20260930   # O(1)，业务立即不再访问
EXPIRE big:key:deleting:20260930 60        # 或配合 UNLINK
# 出问题还能 RENAME 回来 ✅

方法四：List 用 LTRIM 逐段裁剪（List 没有 SCAN）

关键点：

  • 不要在生产高峰做。
  • 配合监控：观察主线程延迟（INFO latencystats / LATENCY）、CPU、内存。
  • 同时改设计：删除只是止血，必须改造成「不会再变大」的模型（拆 key / 加裁剪 / 设上限），否则过段时间又会回来。
什么是热 Key？为什么扩容解决不了？进阶

定义：单个 key 的访问频率极高（如每秒几万到几十万次），导致承载它的节点 CPU / 网络被打满。

为什么扩容无效（核心洞察）：

Cluster 用 CRC16(key) mod 16384 决定 key 的槽位。同一个 key 永远落在同一个槽、同一个节点——所以扩到 3 个节点还是 300 个节点，这个热 key 都在同一个节点上。

扩容只能分散「不同 key」的负载，对「同一个 key」的热度完全无效。

对比大 key：

  • 大 key 的矛盾是「单个 key 太大」→ 阻塞主线程 → 解法是「拆 key」。
  • 热 key 的矛盾是「单个 key 太热」→ 单分片打满 → 解法是「拆读压力」（本地缓存 / 多副本 key / 读写分离）。

四大危害：① 单分片 CPU/带宽打满，影响该分片所有请求；② 一旦失效会引发缓存击穿打爆 DB；③ 集群资源倾斜；④ 节点变慢可能被误判下线，触发不必要的故障转移（雪上加霜）。

怎么发现热 Key？高级

热 Key 怎么治理？高级

五种手段（按性价比排序）：

  1. 本地缓存（最有效，第一招）：Caffeine/Guava Cache 缓存热 key，把读压力拦在 Redis 之前。代价是秒级不一致 + 多实例差异，所以只适用于「读多写少 + 能忍秒级延迟」的数据。
  2. 热 key 多副本：拆成 hotkey:1001:0 ~ hotkey:1001:9，读时随机选。读压力分散到 N 个槽。代价是写放大（要写 N 份），只适合读多写少。
  3. 读写分离 / 从节点分流：读请求分散到多个从节点（READONLY + 客户端 LB）。代价是可能读到旧数据。
  4. 代理层/服务端二级缓存：在 proxy 或 Redis 内核做热 key 自动缓存，对业务透明（B站/得物的方向）。
  5. 业务层打散（最根本）：设计阶段就避免单一超级热点。
    · 秒杀库存 → 拆成 100 个桶 stock:1001:0~99，随机扣减后汇总。
    · 大促配置 → 本地缓存 + 配置中心推送。
    · 明星主页 → 关注列表扇出 + 多级缓存，而不是单 key 计数器。

面试加分话术：「热 key 的『发现』方案成本差别很大，但『治理』的答案高度一致——本地缓存 + 读写分离 + 业务层打散。 所以我会优先把精力放在治理上。其中『业务层打散』是唯一能从根本上解决问题的——前三种都是『缓解』，只有设计上不产生超级热点才是『根治』。」

HeavyKeeper 是什么？为什么不用简单的计数器？专家

为什么不用简单计数器：如果有一亿个 key，一个 key 一个计数器需要一亿个计数器 → 内存不可接受。而且统计本身的读写开销会拖慢 Redis。

HeavyKeeper 的核心机制：

  • 维护 d 个哈希表，每个表 w 个桶，每桶存「指纹 + 计数」。
  • 新元素到达时，用 d 个哈希函数定位 d 个桶：
    • 桶指纹相同 → 计数 +1
    • 桶指纹不同 → 以概率 b^(-count) 衰减该桶计数（b 为衰减因子），计数降到 0 时用新元素替换
  • 效果：高频元素持续命中自己的桶、计数不断增长；低频元素被概率衰减逐渐抹掉。每个桶最终代表一个「高频候选」，从而用小内存找出 Top-K。

相比其他算法：

  • Count-Min Sketch：只能估计频次，只高估不低估，找 Top-K 不够准。
  • Space-Saving：天然输出 Top-K，但低频元素容易被误淘汰。
  • HeavyKeeper：结合指纹 + 概率衰减，在更小内存下得到更准确的 Top-K，且能有效过滤长尾噪声。

B站的工程价值：把热 key 识别的开销降到「可以常驻运行」——从此热 key 监控从「故障后临时排查」变成「常态化监控」。这是运维理念上的升级。

线上 Redis 突然变慢 / CPU 打满，你的排查思路？专家

这是最典型的「10 年+ 岗位」场景题。给一套完整的分层排查框架：

第 0 步：先止血（永恒的第一原则）

  • 确认影响面：是全集群还是单节点？是全部命令还是某类命令？
  • 如果影响业务，先降级（关闭非核心缓存、切到 DB 兜底、限流），再排查。

第 1 步：区分「全集群问题」还是「单节点问题」

  • 看各节点 CPU、QPS、延迟（INFO / 监控大盘）。这一步就能把问题范围砍掉一半。
  • 单节点 → 大概率是大 key / 热 key / 数据倾斜。
  • 全集群 → 大概率是业务流量突增 / 慢命令 / 网络问题 / 客户端问题。

第 2 步：看命令维度

INFO commandstats        # 各命令的调用次数和耗时 — 找出"耗时大户"
INFO latencystats        # 各命令的延迟分布（7.0+）
SLOWLOG GET 50           # 慢查询日志 — 找出具体慢命令
LATENCY LATEST           # 延迟事件（如 fork、expire-cycle）

常见嫌疑：KEYS、HGETALL、SMEMBERS、ZRANGE 0 -1、大范围的 SCAN、SORT、ZUNIONSTORE。看到这些命令出现在高频位置，基本就锁定了。

第 3 步：定位具体的 key

  • 大 key：--bigkeys / --memkeys / MEMORY USAGE。
  • 热 key：HOTKEYS（8.x）/ --hotkeys（需 LFU）/ 客户端埋点数据。
  • Cluster：CLUSTER SLOT-STATS ORDERBY CPU（8.2+）先找热槽，再找槽内热 key。

第 4 步：排除「非 Redis 自身」的原因

  • 客户端问题：连接数暴增（INFO clients）、连接池不足、Pipeline 使用不当、maxclients 打满。
  • 网络问题：带宽打满（大 key 传输）、网络抖动。
  • 持久化影响：INFO persistence 看是否有 fork 阻塞、AOF rewrite 在进行、rdb_last_fork_usec 是否异常。
  • 内存问题：used_memory_rss > maxmemory 触发频繁淘汰；mem_fragmentation_ratio > 1.5 碎片严重；内存被 swap 到磁盘（ratio < 1.0）会导致延迟飙升。
  • 主从/集群问题：主从全量同步、故障转移、槽迁移正在进行。

第 5 步：从个案到机制（架构师视角）

  • 建立常态监控（热 key/大 key 扫描 + 趋势告警），而不是出故障才查。
  • 建立上线卡点（设计阶段评审 key 模型，禁止无上限集合）。
  • 建立降级预案（哪些能降级、降级后 DB 能扛多少）。
  • 建立命令规范（禁止 KEYS、禁止对大的集合做全量操作，用 SDK 提供安全封装）。

面试收尾：「我的排查思路是『从大到小、层层收敛』——先定位是哪个节点，再定位是哪类命令，再定位是哪个 key，最后排除非 Redis 的原因。但更重要的是最后一步：把这次排查沉淀成监控、卡点和规范，让同类问题下次能自动预警而不是重新排查一遍。」

怎么预防大 Key 和热 Key？高级

一、设计阶段（最有效）

反模式正确做法
一个大 Set/Hash 存全局数据按业务维度或 ID 区间分片（user:shard:{id%100}）
List/ZSet 无限增长强制裁剪：LPUSH + LTRIM、ZADD + ZREMRANGEBYRANK，或按周期分 key（rank:daily:20260930）
Redis 存大对象/文件只存元数据，大文件放对象存储
String 存大 JSON 数组拆为「ID 列表 key + 单条明细 key」
用单个 key 做全局计数器/排行榜拆成多个桶/分片 key，读时聚合
秒杀库存放一个 key拆成 N 个库存桶，随机扣减后汇总

二、编码规范

  • 命令黑名单：禁止 KEYS；禁止对未知大小的集合用 HGETALL/SMEMBERS/LRANGE 0 -1；用 HMGET/分页/LTRIM 替代。
  • 统一 SDK：把 DEL 替换为 UNLINK 的逻辑封进 SDK，让业务方无法误用。
  • 强制 TTL：所有缓存 key 必须设过期时间（有明确永不过期需求的要评审）。
  • key 命名规范：业务:实体:ID，便于按前缀批量治理。

三、流程与监控

  • 上线卡点：在 CI/CD 里加检查（新增 key 模型超阈值需评审）。
  • 常态扫描：每天定时在从节点扫大 key，生成趋势报告，新增的大 key 自动告警。
  • 热 key 监控：客户端埋点 / HeavyKeeper / 8.x HOTKEYS，阈值告警。
  • 容量告警：单实例内存、碎片率、连接数、慢查询数量都要有阈值告警。
  • 降级预案：每个核心缓存都要明确「能不能降级、降级后影响是什么」。

一句话总结：「预防大 key/热 key 的答案是『设计 + 规范 + 监控 + 流程』四位一体。只靠事后排查治理，永远在救火；把检查点前移到设计和上线环节，才能从源头降低发生率。」
