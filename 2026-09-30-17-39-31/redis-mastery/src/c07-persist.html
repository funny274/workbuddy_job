Day2.4 · 持久化：Redis 会不会丢数据

一句话结论

「Redis 会不会丢数据」的正确答案不是「不会」，而是「取决于你选的持久化配置，每种配置都有明确的丢失窗口」。面试要能说出：RDB 丢多少、AOF 三种刷盘策略各丢多少、混合持久化怎么兼顾、以及 fork 为什么是最大的隐患。

1. 一张表看懂两种持久化

✅ fork + COW 的完整机制（面试深度核心）

fork 做了什么：

  1. 调用 Linux 的 fork() 系统调用创建子进程。
  2. 子进程不复制物理内存，而是复制父进程的页表（虚拟地址到物理地址的映射），父子进程指向同一份物理页，这些页被标记为只读。
  3. 页表大小与内存量成正比。Linux 每个页表项 8 字节，每页 4KB。所以 1GB 内存约需 2MB 页表；10GB 约 20MB。fork 时复制页表的耗时在这量级。

COW（Copy-On-Write）：

  1. 主进程收到写命令，要修改某个 key。发现该内存页是只读且被共享，触发缺页中断。
  2. 内核复制这一页（4KB），父子进程各持一份；主进程修改自己的副本，子进程继续读旧页（保证快照数据一致性）。
  3. 所以：写命令越多、越分散，复制的页越多，内存峰值越高。最坏情况（全量数据都被修改）额外占用接近一份完整数据集。

三个关键结论：

  • fork 耗时与内存量成正比：10GB 实例 fork 可能耗时 100-200ms，这段时间主线程完全阻塞（这就是 P99 毛刺的来源）。
  • COW 内存峰值与「写入的页数」成正比，不是与数据量。所以「大 key 在被 fork 期间被修改」会一次复制很多页——这也是大 key 危害的一个维度。
  • 必须留内存余量：maxmemory 设为物理内存的 60%-75%，因为 COW 峰值可能额外占 20%-40%。

关键内核参数：

# 1) 允许过量分配内存（否则 fork 可能失败）
sysctl vm.overcommit_memory = 1
# 0 = 启发式（默认，可能拒绝 fork）
# 1 = 总是允许分配（推荐）
# 2 = 不允许超过 swap + 一定比例的物理内存

# 2) 尽量不用 swap（或让内核不倾向换出 Redis）
sysctl vm.swappiness = 0

# 3) 关闭透明大页 THP（避免 COW 放大到 2MB 大页，导致延迟毛刺）
echo never > /sys/kernel/mm/transparent_hugepage/enabled
# ⭐ 这是最容易被忽略但影响最大的参数：
#   THP 开启时，COW 复制的是 2MB 大页而非 4KB 页，
#   复制开销放大 512 倍，会造成明显的延迟抖动

# 4) 观察 fork 实际耗时
INFO stats | grep latest_fork_usec
# 或看日志中的 "Background saving started by pid ..." 到最后完成的时间

3. AOF 深度：三种刷盘策略与重写

写回流程

# AOF 的完整写入链路（4 步）：
# 1) 命令执行完，追加到 redisServer.aof_buf（内存缓冲区）
# 2) 根据 appendfsync 策略，把 aof_buf 写（write）到 AOF 文件（内核页缓存）
# 3) 根据策略，调用 fsync 把页缓存刷到磁盘
# 4) 如果 AOF 文件增长超过阈值，触发 BGREWRITEAOF

########## 三种 appendfsync 策略对比 ##########
# always：每个写命令都 fsync
#   - 数据最安全（理论上不丢，但磁盘故障仍可能丢）
#   - 性能最差：QPS 从 10 万降到几千（受磁盘 IOPS 限制）
#   - 主线程每次都等 fsync，延迟高且抖动大

# everysec（默认，生产首选）：每秒 fsync 一次（后台 bio_aof_fsync 线程）
#   - 最多丢 1 秒数据
#   - 性能好（主线程不阻塞在 fsync 上）
#   - 如果上次 fsync 还没完成，主线程会短暂等待（最多 2 秒左右）

# no：不主动 fsync，交给操作系统（通常 30 秒）
#   - 性能最好
#   - 丢数据多（可达 30 秒）
#   - 实际上没人用

CONFIG SET appendfsync everysec
CONFIG GET appendfsync
⚠️ everysec 的两个隐藏细节（高频深挖点）
  1. everysec 并不是「完全不影响主线程」：如果上一次 fsync 还没完成（磁盘卡了），主线程在下次要写 AOF 时会等待（最多 aof-fsync-delay），这是「延迟毛刺」的来源之一。Redis 的日志里如果出现 "Asynchronous AOF fsync is taking too long"，说明磁盘有瓶颈。
  2. everysec 丢的 1 秒数据也可能超出预期：因为数据先进 aof_buf，再 write 到内核页缓存，再 fsync。如果 Redis 进程崩溃（而机器没崩），内核页缓存里的数据还能被 OS 刷盘保留；但如果机器断电，内核页缓存里没 fsync 的数据就丢了——这就是「最多丢 1 秒」的实际边界。

AOF 重写（BGREWRITEAOF）

✅ 为什么需要重写，以及 7.0 的 MP-AOF 改进

问题：AOF 记录的是「命令流」。如果一个 key 被改了 1000 次（INCR counter 1000 次），AOF 里就有 1000 条命令，但实际数据只需 SET counter 1000 一条。所以 AOF 会无限膨胀。

7.0 之前的 AOF 重写流程：

  1. fork 子进程，子进程扫描当前内存数据，生成一份最小命令集写入新的 AOF 临时文件（此时文件里可能只有 1/10 的命令）。
  2. 重写期间，主进程把新收到的写命令同时追加到「AOF 重写缓冲区」（aof_rewrite_buf）。
  3. 子进程写完后通知主进程。主进程把重写缓冲区的内容追加到新 AOF 文件末尾（补齐期间的增量）。
  4. 用新文件原子替换旧文件（rename）。

问题：第 3 步需要把「重写期间的所有写命令」缓存在内存里。如果重写期间写入量巨大（比如大促），重写缓冲区会吃掉大量内存，可能触发 OOM——这是 Redis 历史上的经典问题。

7.0 的 MP-AOF（Multi-Part AOF）：

  • 把 AOF 拆成一个 base 文件（RDB 格式或 AOF 格式的快照）+ 多个 incr 增量文件，用一个 manifest 文件记录它们的关系。
  • 重写时，子进程生成一个新的 base 文件（新的「代」）；重写期间的写命令直接写入新的 incr 文件，不再需要内存中的重写缓冲区。
  • 重写完成后更新 manifest，指向新的 base + 新的 incr。重写缓冲区被彻底消除，内存峰值问题解决。
# 7.0+ 的 AOF 目录结构
/var/lib/redis/appendonlydir/
├── appendonly.aof.1.base.rdb      # base 文件（混合持久化时是 RDB 格式）
├── appendonly.aof.1.incr.aof      # 增量文件
├── appendonly.aof.2.incr.aof
└── appendonly.aof.manifest        # 清单，记录 base + 所有 incr 文件

# ⚠️ 重要运维影响：7.0 升级后 AOF 变成一个目录，备份脚本和监控脚本要改！
CONFIG GET appenddirname
########## AOF 重写触发与监控 ##########
auto-aof-rewrite-percentage 100     # AOF 文件比上次重写后增长 100%（即翻倍）时触发
auto-aof-rewrite-min-size 64mb      # 且文件至少 64MB 才触发

BGREWRITEAOF                        # 手动触发（异步）

INFO persistence | grep -E 'aof_enabled|aof_rewrite_in_progress|aof_last_bgrewrite_status|aof_last_write_status|aof_current_size|aof_base_size|aof_pending_rewrite|aof_last_cow_size|aof_rewrites'
# aof_last_bgrewrite_status → err 时必须告警！
# aof_last_write_status     → err 说明磁盘写 AOF 失败（磁盘满 / 权限问题）
# aof_current_size 与 aof_base_size 的比值可判断是否需要重写

########## AOF 损坏修复 ##########
# 场景：Redis 意外宕机，AOF 尾部有半条命令（写了一半）

#        AOF is not valid. Use the --fix option to try fixing it.
# --fix 会把不完整命令截断，数据可能丢失最后几条

# 8.4+ 支持自动修复 AOF（aof-load-truncated 相关）

4. 混合持久化（4.0+）：生产推荐配置

✅ 混合持久化的原理与收益

配置：aof-use-rdb-preamble yes（4.0+ 默认开启）

原理：AOF 重写时，base 文件用 RDB 二进制格式（恢复快），之后的增量用 AOF 命令格式（安全）。重放时先加载 RDB 部分（快），再重放 AOF 增量。

收益对比（10GB 数据的恢复时间）：

方案文件大小恢复时间丢失窗口
纯 RDB约 3GB约 30 秒最多 5-15 分钟（取决于 save 规则）
纯 AOF（everysec）约 6-8GB约 3-5 分钟最多 1 秒
混合持久化约 4-5GB约 40-60 秒最多 1 秒

生产推荐配置：

appendonly yes
appendfsync everysec
aof-use-rdb-preamble yes          # 混合持久化
auto-aof-rewrite-percentage 100
auto-aof-rewrite-min-size 1gb      # 小文件重写收益低，阈值调大减少 fork 次数

# RDB 作为冷备（不要用于恢复，主要用于备份/迁移/复制）
save 3600 1                     # 或直接关掉，靠 AOF + 定期外部备份
stop-writes-on-bgsave-error yes

# 关键：备份策略（生产必备）
# - AOF 文件定期归档到对象存储（按小时/天）
# - RDB 每天全量备份到异地
# - 定期做「恢复演练」：把备份加载到测试实例验证可用
🚨 五个真实的生产事故模式
  1. fork 风暴：save 规则配了 3 条 + AOF 重写 + 主从全量同步同时触发，短时间内多次 fork，每次阻塞几百毫秒。现象是「周期性 P99 毛刺」。解法：减少 save 规则、调大 auto-aof-rewrite-min-size、错开主从同步时间、控制单实例内存。
  2. AOF 写到磁盘满：aof_last_write_status: err，此时如果 appendfsync always，写命令直接失败。生产要监控磁盘空间 + 配置告警。
  3. THP 导致延迟抖动：COW 复制 2MB 大页而非 4KB，放大 512 倍。现象是 fork 期间出现几十毫秒的延迟。解法：关闭透明大页。
  4. 升级 7.0 后备份脚本失效：AOF 从单文件变成 appendonlydir/ 目录，老脚本备份不到数据。解法：升级前审查所有自动化脚本。
  5. 恢复时间过长导致故障扩大：10GB 纯 AOF 恢复要 5 分钟，主库故障后 5 分钟不可用。解法：用混合持久化；或者用「哨兵/集群快速切换 + 从库承载读」而非等主库恢复。

面试深度问答

RDB 和 AOF 的区别？生产怎么选？基础

先对比，再给结论。见本节第 1 节的表。

生产标准答案：「我们用的是 AOF（everysec）+ 混合持久化 + RDB 冷备」的组合：

  • AOF everysec 保证最多丢 1 秒数据，满足绝大多数业务的数据安全要求；同时性能影响很小（fsync 在后台线程）。
  • 混合持久化（aof-use-rdb-preamble yes）让 AOF 重写后的 base 文件是 RDB 格式，把恢复时间从几分钟压到几十秒——这是「故障恢复速度」这个 SLA 的关键。
  • RDB 只作为冷备：每天全量备份到异地对象存储，用于「误删数据恢复」「跨集群迁移」「盘古式重建」。不指望 RDB 做主恢复，因为它的丢失窗口太大。

为什么不选纯 RDB：丢数据太多（5-15 分钟），缓存场景可以接受，但一旦 Redis 承载了队列/计数器/分布式锁这类不能丢的数据就不行了。

为什么不选纯 AOF（不带混合）：恢复太慢，故障恢复时间（MTTR）会拖长，这对 SLA 是硬伤。「恢复速度也是可用性的一部分」——这个观点很能加分。

fork 的时候会阻塞主线程吗？阻塞多久？高级

会阻塞，且阻塞时间与内存量成正比。

  1. fork 本身是阻塞主线程的：Linux 的 fork() 要复制父进程的页表。页表大小约 内存量/512（4KB 页，每页表项 8 字节 → 每 GB 约 2MB 页表）。所以 10GB 实例约复制 20MB 页表，耗时约 50-200ms（取决于 CPU 和内存带宽）。
  2. 数据量越大，fork 越慢：这就是为什么单实例内存不建议超过 10-16GB——不只是 COW 内存，还有 fork 时间。
  3. COW 之后不阻塞主线程：fork 完成后子进程独立跑，主线程继续处理请求。但——每次主线程写一个被共享的页，都要触发缺页中断 + 复制页，这有 CPU 和内存带宽开销，会间接导致延迟上升。
  4. 真正的「抖动」往往来自 THP：如果透明大页开启，COW 复制的是 2MB 大页，开销放大 512 倍。关闭 THP 是必须的。

怎么量化观察：

INFO stats | grep latest_fork_usec            # 最近一次 fork 耗时（微秒）⭐
INFO persistence | grep rdb_last_cow_size     # COW 复制的字节数
redis-cli --latency-history -i 5              # 看是否有周期性毛刺

优化手段：① 控制单实例内存（<10-16GB）；② 关闭 THP；③ vm.overcommit_memory=1；④ 减少 save 规则、调大 AOF 重写阈值，避免频繁 fork；⑤ 如果非常敏感，考虑用「主从 + 只读从库 + 在从库上做持久化」的架构。

AOF 重写的流程？重写缓冲区的作用？7.0 有什么变化？高级

7.0 之前的流程（四步）：

  1. fork 子进程，子进程扫描当前内存数据，生成最小命令集写入临时 AOF 文件。注意：子进程看到的是 fork 那一刻的数据快照。
  2. 主进程把重写期间新收到的写命令，同时追加到 AOF 缓冲区（正常写）和 AOF 重写缓冲区（aof_rewrite_buf）。
  3. 子进程完成后通知主进程，主进程把重写缓冲区的内容追加到新 AOF 文件——这一步补齐了「fork 之后到重写完成之前」的增量，保证不丢数据。
  4. rename 原子替换旧 AOF 文件。

重写缓冲区的作用：解决「子进程用旧快照生成新文件 + 期间有新增写命令」的数据一致性问题。必须有它，否则重写期间的数据会丢。

它的问题：重写期间的所有写命令都要缓存在内存。如果写入量巨大（大促），缓冲区可能膨胀到几百 MB 甚至 GB，导致内存暴涨/OOM。重写时间越长、写入越密集，问题越严重。

7.0 的 MP-AOF 改进：

  • 把 AOF 拆成 base（快照，RDB 格式）+ 多个 incr（增量）+ manifest（清单）。
  • 重写时子进程生成新的 base（新一代），期间的写命令直接追加到新的 incr 文件——不需要内存中的重写缓冲区。
  • 完成后更新 manifest。内存峰值问题从根上解决。

运维影响（这是加分点）：AOF 从「单个文件」变成「目录 + 多文件」，所以：① 备份脚本要改成备份整个 appendonlydir；② 用 redis-check-aof --fix 时要指定具体的文件；③ 从 7.0 降级到 6.x 需要先做 AOF 格式转换（基本等于不支持降级）。「升级前审查脚本」是真实的踩坑经验。

Redis 会丢数据吗？能保证不丢吗？高级

结论：单机 Redis 无法保证完全不丢数据，只能缩小丢失窗口。分场景回答：

配置丢失窗口适用
不持久化重启即全丢纯缓存，可接受（但生产不推荐）
RDB save 60 10000最多 60 秒（实际可能更久）缓存、可容忍较多丢失
AOF everysec最多 1 秒生产主流
AOF always理论不丢（除磁盘故障）性能下降 10 倍以上，几乎无人用
主从 + AOF everysec（+ 哨兵/集群）主节点宕机可能丢 1 秒内数据（异步复制）高可用主流

为什么「主从 + AOF」也可能丢 1 秒：Redis 的复制是异步的。主节点执行完写命令后立即返回给客户端，同时异步发送给从节点。如果主节点在这 1 秒内宕机，从节点的数据可能落后主节点，切换后就会丢这部分数据。这就是「异步复制的固有风险」。

那怎么做到接近不丢：

  1. WAIT 命令：WAIT numreplicas timeout 可以阻塞等待直到 N 个从节点确认收到。用它把「异步复制」变成「同步确认」，代价是延迟增加。
  2. min-replicas-to-write + min-replicas-max-lag：至少要有 N 个从节点且延迟小于 M 秒，主节点才接受写入。这是防止「脑裂时写丢数据」的关键配置。
  3. 业务层面：对于绝对不能丢的数据（如订单、支付），不要只依赖 Redis——用 Redis 做前置（预扣减、幂等），最终一致性由 DB 兜底（异步落库 + 对账）。这是大厂的标准姿势。

一句话收尾：「Redis 的定位是高性能数据层，不是强一致的账本。我们的原则是——能被重建的数据放 Redis 且允许丢；不能重建的数据（订单、金额）必须落库，Redis 只做加速和前置校验。」

为什么生产不建议用 SAVE？BGSAVE 期间能处理请求吗？进阶

SAVE vs BGSAVE：

  • SAVE：在主线程上执行，整个快照过程阻塞所有客户端请求。10GB 数据可能阻塞几秒到几十秒。生产严禁使用（通常通过 rename-command 或 ACL 禁用）。
  • BGSAVE：fork 子进程执行，fork 的那一瞬间阻塞主线程（几十到几百毫秒），之后主线程继续服务。

BGSAVE 期间能处理请求吗？能，但有三个注意点：

  1. fork 的瞬间是阻塞的：这段时间所有请求都要排队。所以 fork 耗时是 P99 毛刺的来源。
  2. COW 有性能开销：主线程写共享页时触发缺页中断和页复制，消耗 CPU 和内存带宽，间接导致延迟上升。
  3. BGSAVE 期间不会触发另一个 BGSAVE：如果再触发，Redis 会直接返回「Background save already in progress」。但 save 规则和 AOF 重写、主从全量同步之间也要注意避免叠加。

生产规范：① 用 BGSAVE，禁用 SAVE；② 控制单实例内存；③ 关闭 THP；④ 减少 save 规则条数；⑤ 监控 latest_fork_usec，超过 500ms 就要考虑拆分实例。

Redis 重启后数据是怎么加载的？进阶

加载优先级：如果开启了 AOF，只加载 AOF，忽略 RDB。

  1. 进程启动时检查 appendonly。为 yes → 读 appendonlydir/appendonly.aof.manifest，按清单加载 base 文件 + 所有 incr 文件。appendonly no → 加载 dump.rdb。
  2. 加载 base 文件：如果是 RDB 格式（混合持久化），直接二进制加载（快）；如果是 AOF 格式，逐条重放。
  3. 重放 incr 文件：逐条执行命令。这里有个细节——重放时会用假的客户端执行（fakeClient），且不写回 AOF、不传播给从节点。
  4. 如果 AOF 尾部损坏（aof-load-truncated yes），Redis 会截断不完整的命令并继续启动，同时在日志里警告。如果设为 no，Redis 会拒绝启动（更安全但需人工介入）。

为什么 AOF 优先于 RDB：因为 AOF 的数据通常更新（everysec 最多丢 1 秒，而 RDB 可能丢几分钟）。如果两个都加载会导致数据重复或混乱，所以必须二选一。

重要提示：加载 AOF 时如果数据量大，会长时间阻塞（因为重放是单线程的）。这也是为什么推荐混合持久化——base 用 RDB 格式，加载时是二进制解析，比逐条重放快得多。

监控：INFO persistence 里的 loading:0/1 和 loading_start_time，以及重启后 used_memory 与重启前的对比（如果明显变小，说明数据丢了）。
